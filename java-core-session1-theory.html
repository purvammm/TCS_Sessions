Ask the batch "Who has seen a NullPointerException?" — every hand goes up. "Who can tell me, precisely, what Java did to your program at that moment?" — far fewer. That gap is what today closes.

The problem

Your program will meet the real world

Everything you write assumes things. Every one of those assumptions is a place the real world can hurt you.

🗂️

The file isn't there

Someone renamed it, or the path is wrong on Linux but fine on Windows.

⌨️

The user typed nonsense

You asked for an age. They typed "twenty". Or nothing at all.

🔌

The network blinked

The database was there a second ago. Now the socket is closed.

➗

The maths broke

The divisor was 0 because the list was empty.

🫙

Something was null

A lookup returned nothing and you called a method on it anyway.

📏

The index was wrong

Classic off-by-one: i <= length instead of i < length.

The real question The question is never "how do I stop errors happening?" — you can't. The question is "when it happens, does my program lose data, or does it recover gracefully and tell someone useful?"

Why the language has this feature

Life before exceptions — return codes

Older languages like C signal failure by returning a special value: -1, NULL, false. It works, but it rots your code.

✗ Return-code style

  • Every single call must be checked
  • Nothing forces you to check — silence on failure
  • Error handling is tangled into the happy path
  • A valid result and an error may share a value
  • No room to explain why it failed
→

✓ Exception style

  • Happy path reads top to bottom, uninterrupted
  • Failure can't be silently ignored
  • Handling lives in its own block
  • Carries a message, a type and a stack trace
  • Can travel up to whoever can actually fix it
// Return-code style — the check drowns the logic
int code = openFile("data.txt");
if (code == -1) { /* now what? */ }
int read = readLine(code);
if (read == -1) { /* and here too */ }

// Exception style — logic first, failure handled once
try {
    String line = readFirstLine("data.txt");
    System.out.println(line);
} catch (IOException e) {
    System.out.println("Could not read the file: " + e.getMessage());
}

The core idea

An exception is an object

This is the sentence to remember: an exception is just a Java object that describes something going wrong. It is not magic. It is a normal instance of a normal class, created with new like anything else.

// Completely ordinary object creation:
ArithmeticException e = new ArithmeticException("/ by zero");

System.out.println(e.getMessage());   // / by zero
System.out.println(e.getClass());     // class java.lang.ArithmeticException

What makes it special is the keyword throw. Throwing an object means: stop normal execution and start looking for someone to handle this.

Every exception carries four useful things 1. Its type — FileNotFoundException tells you the category at a glance. 2. A message — getMessage(), human-readable detail. 3. A stack trace — the exact path of method calls that led here. 4. Optionally a cause — the lower-level exception that triggered it.

How it travels

The call stack & stack unwinding

Java tracks which method is running using a call stack. Calling a method pushes a frame on top; returning pops it. When an exception is thrown, Java pops frames looking for a matching catch. That popping is called unwinding.

divide(int, int)← thrown here
calculate(int, int)no catch — popped
processOrder()no catch — popped
main(String[])catch found ✓

If nobody catches it, the exception reaches the top of the stack. The JVM then prints the stack trace to System.err and terminates that thread. In a single-threaded console program, that means your program is over.

Why this design is powerful The method that detects a problem is rarely the method that knows what to do about it. A low-level file reader can't decide whether to show a dialog, retry, or fall back to defaults. Unwinding lets the error travel up to a layer with enough context to decide.

A skill, not a nuisance

How to read a stack trace

Most beginners see a wall of red text and panic. Stack traces are extremely precise — they usually hand you the answer.

Exception in thread "main" java.lang.ArithmeticException: / by zero at com.tcs.Calculator.divide(Calculator.java:12) at com.tcs.Calculator.calculate(Calculator.java:7) at com.tcs.Main.main(Main.java:4)
PartWhat it tells you
thread "main"Which thread died. In our labs this is always main.
java.lang.ArithmeticExceptionThe type — the category of problem.
/ by zeroThe message — the specific detail.
Calculator.java:12Where it was thrown. Read this line first — always.
Lines belowWho called whom. Read top to bottom = innermost to outermost.

Two habits that will save you hours 1. Find the topmost line that mentions your own package — that's usually your bug, not the framework's. 2. When you see Caused by:, scroll to the last one. That's the root cause; everything above it is wrapping.

Error is not your business OutOfMemoryError, StackOverflowError, NoClassDefFoundError — these mean the JVM itself is in trouble. Catching them almost never helps and usually hides a serious problem. Rule: never catch Error, and never catch Throwable.

The mental test Ask: "Could a careful programmer have prevented this by writing better code?" — Yes → it should be unchecked. No, the outside world simply failed → checked.

The basic tool

try / catch

try marks code that might fail. catch says what to do if a matching exception appears.

try {
    int result = 10 / divisor;        // risky
    System.out.println(result);       // SKIPPED if the line above throws
} catch (ArithmeticException e) {
    System.out.println("Cannot divide by zero.");
}
System.out.println("Program continues.");   // this still runs

The bit everyone gets wrong first When line 2 of a try throws, lines 3, 4 and 5 never execute. Control jumps straight to catch. Students constantly assume the try block "finishes anyway" — it does not.
Ask the batch "If divisor is 2, how many lines print?" (two) "If it's 0?" (two again — but different ones). Trace it out loud before moving on.

More than one thing can go wrong

Multiple catch blocks — order matters

One try can have many catch blocks. Java checks them top to bottom and runs the first one that matches — where "matches" means the exception is that type or a subclass of it.

try {
    int[] nums = {1, 2, 3};
    int index = Integer.parseInt(userInput);
    System.out.println(100 / nums[index]);
} catch (NumberFormatException e) {          // most specific first
    System.out.println("That wasn't a number.");
} catch (ArrayIndexOutOfBoundsException e) {
    System.out.println("Index must be 0-2.");
} catch (ArithmeticException e) {
    System.out.println("That element is zero.");
} catch (Exception e) {                      // broadest LAST — safety net
    System.out.println("Unexpected: " + e.getMessage());
}

✗ Won't even compile

catch (Exception e) { }
catch (ArithmeticException e) { }
// error: alreadyCaught —
// ArithmeticException has
// already been caught

✓ Specific → general

catch (ArithmeticException e) { }
catch (Exception e) { }
// compiles: narrow first,
// wide net afterwards
Rule Subclasses before superclasses. Java catches this mistake at compile time, which is a small mercy — the error is exception X has already been caught.

Java 7+

Multi-catch — one block, several types

When two different failures deserve the same response, don't duplicate the block. Separate the types with a pipe |.

✗ Duplicated

catch (NumberFormatException e) {
    log(e);
    showError("Bad input");
} catch (DateTimeParseException e) {
    log(e);
    showError("Bad input");
}

✓ Multi-catch

catch (NumberFormatException
     | DateTimeParseException e) {
    log(e);
    showError("Bad input");
}
Two rules for multi-catch 1. The types must not be in a parent–child relationship. catch (IOException | FileNotFoundException e) is a compile error — FileNotFoundException is already an IOException, so listing both is redundant. 2. The variable e is implicitly final — you can't reassign it inside the block.
Ask the batch "What type does the compiler give e in a multi-catch?" — the nearest common ancestor of the listed types. So you can only call methods that both types support (usually getMessage()).

The cleanup block

finally — runs no matter what

finally executes whether the try succeeded, threw a caught exception, threw an uncaught exception, or even hit a return. It exists for cleanup you cannot afford to skip.

Connection conn = null;
try {
    conn = openConnection();
    conn.save(record);
    return true;                  // finally STILL runs before returning
} catch (SQLException e) {
    logger.error("Save failed", e);
    return false;                 // finally runs here too
} finally {
    if (conn != null) conn.close();   // guaranteed — no leak
}
ScenarioDoes finally run?
try completes normallyYes
Exception thrown and caughtYes
Exception thrown and not caughtYes — then the exception continues up
return / break / continue inside tryYes — before control actually leaves
System.exit(0) is calledNo — the JVM stops immediately
The JVM crashes or power is lostNo
Never return from a finally block A return in finally silently discards any in-flight exception and overrides the real return value. It's one of the nastiest bugs to track down. Same goes for throwing from finally.

Java 7+ — the modern way

try-with-resources

The finally-to-close pattern was so common, and so easy to get wrong, that Java built it into the language. Declare the resource in parentheses after try and Java closes it for you — automatically, in reverse order, even if an exception is thrown.

✗ Old — 9 lines of ceremony

BufferedReader br = null;
try {
    br = new BufferedReader(
        new FileReader("d.txt"));
    System.out.println(br.readLine());
} catch (IOException e) {
    e.printStackTrace();
} finally {
    if (br != null) {
        try { br.close(); }
        catch (IOException ignored) { }
    }
}
→

✓ New — closes itself

try (BufferedReader br =
        new BufferedReader(
            new FileReader("d.txt"))) {
    System.out.println(br.readLine());
} catch (IOException e) {
    e.printStackTrace();
}
// br.close() is called for you,
// guaranteed, before catch runs
// Several resources at once — closed in REVERSE order (out, then in)
try (FileReader in  = new FileReader("in.txt");
     FileWriter out = new FileWriter("out.txt")) {
    // ... copy ...
}
The contract: AutoCloseable Any class implementing AutoCloseable (one method: void close()) can go in the parentheses — including your own classes. You'll write one in the lab. Files, streams, sockets, JDBC connections and Scanner all already implement it.

Going on the offensive

throw — raising an exception yourself

So far we've been catching. Just as important is throwing. When a method is handed input it cannot honour, the worst thing it can do is quietly carry on with bad data.

✗ Silent corruption

void setAge(int age) {
    this.age = age;   // -5? sure!
}
// Bug surfaces days later,
// somewhere completely
// unrelated. Good luck.

✓ Fail fast, at the source

void setAge(int age) {
    if (age < 0 || age > 130) {
        throw new IllegalArgumentException(
            "Age must be 0-130, got: "
            + age);
    }
    this.age = age;
}
Fail fast Detect the problem as close as possible to where it was caused, and say clearly what was wrong. Notice the message includes the offending value — "got: -5". A message without the actual value wastes everyone's time.
Handy built-in guards Objects.requireNonNull(name, "name must not be null") throws a well-described NPE in one line. IllegalArgumentException for bad arguments, IllegalStateException for "you called this at the wrong time". Prefer these standard types over inventing your own where they fit.

Declaring, not doing

throws — passing the buck upward

Sometimes a method genuinely cannot decide how to handle a failure. Rather than a pointless catch, it declares that it may fail and lets the caller deal with it.

// This method does NOT handle the problem — it announces it
public String readConfig(String path) throws IOException {
    BufferedReader br = new BufferedReader(new FileReader(path));
    return br.readLine();
}

// Now every caller must either catch it...
try {
    String cfg = readConfig("app.properties");
} catch (IOException e) {
    System.out.println("Using defaults instead.");
}

// ...or declare it too, and push the decision further up
public void startup() throws IOException {
    String cfg = readConfig("app.properties");
}
readConfig() throws IOExceptiondeclares
startup() throws IOExceptionpropagates
main() try/catchdecides ✓
Don't put throws Exception on everything It compiles, and it's the laziest thing you can do. It tells callers nothing, forces them to catch everything, and destroys the type information that makes checked exceptions useful in the first place. Declare the narrowest type you actually throw.

One-liner to memorise throws is a warning label on the box. throw is actually setting off the alarm.

Speaking your domain's language

Writing your own exception

Built-in types describe technical failures. Your application has business failures: insufficient funds, seat already booked, invalid IFSC code. A custom exception names the problem in the language of the business.

InsufficientFundsException.java
public class InsufficientFundsException extends Exception {   // CHECKED

    private final double shortfall;      // extra data the caller can use

    public InsufficientFundsException(String message, double shortfall) {
        super(message);                  // ALWAYS pass the message up
        this.shortfall = shortfall;
    }

    public double getShortfall() { return shortfall; }
}
// Throwing it
if (amount > balance) {
    throw new InsufficientFundsException(
        "Withdrawal of " + amount + " denied", amount - balance);
}

// Catching it — and using the extra data
catch (InsufficientFundsException e) {
    System.out.printf("Denied. Add %.2f more.%n", e.getShortfall());
}
The four standard constructors Good practice is to offer all four, each delegating to super: (), (String message), (String message, Throwable cause), and (Throwable cause). The ones taking a cause are what make exception chaining possible — next slide but one.

The design decision

Extend Exception or RuntimeException?

extends Exception → checked

Use when the caller can realistically recover and you want the compiler to force them to think about it.

Good fits: InsufficientFundsException, SeatUnavailableException — the caller can offer an alternative.

extends RuntimeException → unchecked

Use when it signals a bug or a broken precondition, where there's no sensible local recovery.

Good fits: InvalidConfigurationException, ResourceNotFoundException in a web API.

public class ResourceNotFoundException extends RuntimeException {  // UNCHECKED
    public ResourceNotFoundException(String resource, Object id) {
        super(resource + " not found with id: " + id);
    }
}
// No throws clause needed anywhere. In Spring Boot a @ControllerAdvice
// turns this into a clean 404 response — see Spring Boot Session 3.
Ask the batch — this one divides professionals Modern frameworks (Spring, Hibernate) lean heavily towards unchecked, arguing checked exceptions pollute signatures throughout a codebase. The classic Java position favours checked for recoverable errors. Both are defensible. What matters is being consistent inside one project.

Don't lose the evidence

Exception chaining — keep the cause

When you catch a low-level exception and throw a higher-level one, you must attach the original as the cause. Otherwise you throw away the stack trace that says what actually broke.

✗ Evidence destroyed

catch (SQLException e) {
    throw new DataAccessException(
        "Could not load user");
}
// Trace stops here. WHY did
// SQL fail? Nobody will
// ever know.

✓ Cause preserved

catch (SQLException e) {
    throw new DataAccessException(
        "Could not load user", e);
}                        //  ^^^
// Full chain survives all
// the way to the log.
com.tcs.DataAccessException: Could not load user id=42 at com.tcs.UserRepository.findById(UserRepository.java:31) at com.tcs.UserService.getUser(UserService.java:18) Caused by: java.sql.SQLException: Connection refused: connect at com.tcs.Db.connect(Db.java:12) ... 4 more ← the actual root cause
Rule Whenever you re-throw, pass the original exception in — as a constructor argument or via initCause(). Retrieve it later with getCause(). A stack trace without its cause is a bug report with the crucial page torn out.

Architecture

Translating exceptions across layers

Each layer of an application should throw exceptions that make sense at its own level of abstraction. A web controller shouldn't be handling SQLException — that's a leak of database detail into the presentation layer.

Repository / DAO Catches SQLException → throws DataAccessException (with cause)
Service Catches DataAccessException → throws UserNotFoundException (business language)
Controller / UI Catches UserNotFoundException → shows "User not found" / HTTP 404 
// Repository — technical
catch (SQLException e) {
    throw new DataAccessException("Query failed for id " + id, e);
}

// Service — business
catch (DataAccessException e) {
    throw new UserNotFoundException("No user with id " + id, e);
}

// Controller — human
catch (UserNotFoundException e) {
    return "error/not-found";        // and log e at this boundary
}
Log once, at the boundary A classic mistake is logging the same exception at every layer, producing four copies of one problem. Log where you finally handle it — and let it propagate silently (but with its cause attached) until then.

Do this

Best practices

  • Catch the narrowest type you can. catch (FileNotFoundException e) beats catch (Exception e).
  • Never swallow an exception. An empty catch block is where bugs go to hide.
  • Always chain the cause when re-throwing.
  • Put context in the message — ids, filenames, the offending value.
  • Clean up in finally, or better, use try-with-resources.
  • Throw early, catch late. Validate at the boundary; handle where you have enough context.
  • Prefer standard exceptions where they fit; go custom for business rules.
  • Keep try blocks small — wrap the risky line, not fifty lines.
  • Log with the exception object, not just its message: log.error("msg", e).
The single best habit Before you write catch, answer this out loud: "What will this block actually DO about it?" If the honest answer is "nothing", you shouldn't be catching there — let it propagate to somewhere that can.

Never do this

try {

✓ Handle or propagate

try {

Not everything deserves an exception

When not to throw

Exceptions are for the exceptional. "Not found" during a search isn't exceptional — it's a perfectly ordinary outcome. Reaching for exceptions to express normal results makes code slower and harder to read.

✗ Exception as a return value

try {
    User u = findUser(name);
    greet(u);
} catch (NotFoundException e) {
    showSignupPrompt();
}
// "not found" is normal here,
// not an emergency

✓ Optional says "maybe"

Optional<User> u = findUser(name);
if (u.isPresent()) {
    greet(u.get());
} else {
    showSignupPrompt();
}
// or: u.ifPresentOrElse(
//        this::greet,
//        this::showSignupPrompt);
Three cheaper alternatives 1. Validate first. if (scanner.hasNextInt()) is better than parsing and catching. 2. Return Optional<T> for "there may be no answer". 3. Return empty collections, never null — this alone eliminates a large share of all NullPointerExceptions.
The performance angle Constructing an exception captures the whole stack trace, which is genuinely expensive. In a tight loop, exception-driven control flow can be orders of magnitude slower than an if. This matters in real systems.

// Spring Boot Session 3 preview — your custom exception, one clean handler
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleNotFound(ResourceNotFoundException e) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
                             .body(new ErrorResponse(404, e.getMessage()));
    }
}
// No try/catch in any controller. Every 404 formatted identically.
