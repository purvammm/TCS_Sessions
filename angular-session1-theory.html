Concept 1

What is Angular?

Angular is an open-source front-end framework, written in TypeScript and maintained by Google. Its purpose is to build single-page applications — rich, app-like websites that run in the browser.

🅰️

Written in TypeScript

You also write your Angular code in TypeScript. The framework and your app speak the same language.

🏢

Backed by Google

Used in Google's own products. Predictable release cadence, long-term support, huge ecosystem.

🧩

Component-based

From Angular 2 onwards, everything is a component. Your app is a tree of them — a parent with children, each child with its own children.

🔋

Batteries included

Routing, forms, HTTP, testing and a CLI all ship as part of the framework. You don't assemble them from ten libraries.

That last point is the one to hold on to. In Angular you never build "a page" — you build small, self-contained components and then nest them inside each other until they form a page.

Concept 2 — the idea Angular is built around

What is a single-page application?

In a traditional multi-page application (JSP, Servlets, PHP, ASP.NET Web Forms), every click asks the server for a brand-new HTML page. The browser throws away everything it had and re-paints from scratch — you see the flash, the spinner, the scroll position jumping back to the top.

In a single-page application, the browser loads one HTML page — literally one file, index.html — exactly once. After that, JavaScript swaps pieces of the screen in and out. When new data is needed, only the data travels over the network (as JSON), not a whole new page.

Multi-page (the old way)

  • Every click = a full page reload
  • Server re-renders the entire HTML each time
  • Visible flicker; state is lost between pages
  • Server is responsible for the UI
→

Single-page (Angular)

  • One page load, then only sections change
  • Browser renders; server just returns JSON
  • Smooth, app-like, state survives navigation
  • Server is a pure API — reusable by mobile too
Why this matters to you as a Java developer This is a split of responsibility. Your Spring Boot REST API stops producing HTML and starts producing JSON. Angular consumes that JSON and owns the entire user interface. The same API can then serve a web app, an Android app and an iOS app without change — that's the real payoff.

Concept 3

Angular versions — a short history

  • 2010AngularJS 1.x — the original. JavaScript-based, MVC architecture, used $scope and controllers. Still alive in legacy projects, but end-of-life.
  • 2016Angular 2 — a complete rewrite, not an upgrade. TypeScript, component-based, mobile-friendly, dramatically faster. This is where "modern Angular" begins.
  • 2016–17Angular 4 & 5 — smaller bundles, the new HttpClient, faster compilation. (There is no Angular 3 — the router package had already reached v3, so they skipped the number to keep versions aligned.)
  • 2018–19Angular 6, 7, 8 — ng update, the CLI matures, differential loading, lazy loading improvements.
  • 2020Angular 9 & 10 — the Ivy renderer becomes the default: smaller, faster, better error messages.
  • 2021–22Angular 11 → 14 — strict typing by default, standalone components introduced, typed reactive forms.
  • 2023+Angular 15 → 17+ — standalone APIs become the recommended default, signals, new control-flow syntax. Everything you learn here still applies.
Beginner note — the naming trap "AngularJS" means version 1.x only. "Angular" with no "JS" means version 2 and everything after it. They are different frameworks with different architectures — code does not port between them. When you search online, a StackOverflow answer using $scope is AngularJS and will not help you. Add the version number to your searches.

Angular ships a major version roughly every six months. Don't be alarmed by high version numbers — the core concepts in these four sessions (components, binding, directives, services, routing) have been stable since Angular 2.

Why the rewrite was worth it AngularJS's two-way-binding-everywhere model was magical for small apps and painful for large ones — it became almost impossible to reason about what changed what. Angular 2's component tree with explicit, directional data flow is the fix: data flows down into children, events flow up to parents. You always know where a change came from.

Concept 4 — the case for Angular

Why Angular? A concrete comparison

Imagine an employee management screen. Here's how the same feature set looks built two ways.

❌ The JSP / Servlet version

  • list.jsp — show all employees
  • search.jsp — a search form + its results
  • insert.jsp — add a new employee
  • update.jsp — edit an existing one
  • delete.jsp — confirm and delete

Five separate pages. Each click is a full round-trip and a full page reload. The HTML for the table is duplicated across files. Styling is hand-rolled. To add a column, you edit several JSPs.

✅ The Angular version

  • One employee-list component — the table
  • One employee-form component — reused for insert and update
  • Search is a filter on data already in memory — no server hit
  • Delete removes a row in place, no reload
  • Bootstrap/Material gives a polished UI for free

A handful of reusable components. To add a column you change one template. No page ever reloads.

Ask the batch So what's the real advantage of Angular over a JSP/Servlet app? (Look for: no reloads, reusable components, clean separation of UI and API, one backend serving many clients, and far less duplicated markup.)

The bigger picture

Where Angular sits in your stack

Angular is a front-end framework — it runs in the user's browser, not on your server. Your Spring Boot application becomes a pure JSON API sitting behind it.

The handshake Angular sends an HTTP request; Spring Boot answers with JSON; Angular turns that JSON into what the user sees. Everything you built in the Spring Boot sessions is the right-hand side of this diagram. Today we start building the left-hand side.

Note that Angular never talks to the database directly. It has no credentials, no SQL — all of that stays safely on the server. This is a security feature, not a limitation.

Concept 5 — the language

What is TypeScript?

JavaScript is loosely typed (also called dynamically typed): a variable has no fixed type, and can silently change from a number to a string to a boolean. The language allows it and says nothing.

// Plain JavaScript — all three lines are legal
let age = 42;        // a number
age = "Anoop";       // now a string  (?!)
age = true;          // now a boolean (?!)

That flexibility is convenient in a five-line script and disastrous in a fifty-thousand-line application. A variable named age holding true will not crash where the mistake was made — it will crash somewhere far away, at runtime, in front of a user.

TypeScript, released by Microsoft in 2012, is a superset of JavaScript: all valid JavaScript is valid TypeScript, plus TypeScript adds static typing on top. The same code above now fails immediately, in your editor, before you even save:

// TypeScript
let age = 42;
age = "Anoop";
// ✖ Error: Type 'string' is not assignable to type 'number'.
"Superset" — what that means in practice You are not learning a new language from scratch. TypeScript is JavaScript plus type annotations. If you know Java, the type-checking part will feel immediately familiar; if you know JavaScript, everything you know still works.

Concept 5 continued

The one-sentence summary TypeScript's types exist only at development time — they are stripped away during compilation, and the browser runs ordinary JavaScript. Types cost you nothing at runtime and save you enormous amounts of debugging. That is why Angular is written in TypeScript and why your Angular code will be too.

TypeScript basics · 1 of 7

Type inference vs declared types

There are two ways a TypeScript variable gets its type. Both give you full type safety — the difference is only whether you write the type or the compiler works it out.

Inference — the compiler guesses from the initial value

let str = "Hello World";   // TS infers: string
str = "Goodbye";           // ✔ fine — still a string
str = 100;                 // ✖ Error: Type 'number' is not assignable to type 'string'

Declaration — you state the type explicitly with : type

let name: string = "Anoop";
let age: number = 40;
let isActive: boolean = true;
let anything: any = "could be anything";   // opts OUT of type checking
TypeHoldsExample
stringText"Trivandrum"
numberIntegers and decimals (no separate int/float)25000.50
booleantrue / falsetrue
anyAnything — disables checking for that variablelet x: any;
voidUsed for functions that return nothingfunction log(): void
Use any sparingly any switches off the very feature you came for. It's an escape hatch for awkward third-party data, not a default. If your file is full of any, you're writing JavaScript with extra steps.

TypeScript basics · 2 of 7

Interfaces — giving an object a shape

Types like string describe single values. An interface describes the shape of an object: which properties it must have, and of what type.

interface Person {
  name: string;
  city: string;
  age: number;
}

let myData: Person = {
  name: "Anoop",
  city: "Trivandrum",
  age: 40
};

console.log(myData.name);   // Anoop  — and the editor autocompletes '.name'

Now the compiler protects you in three ways:

let bad1: Person = { name: "Anoop", city: "Trivandrum" };
// ✖ Property 'age' is missing

let bad2: Person = { name: "Anoop", city: "Trivandrum", age: "forty" };
// ✖ Type 'string' is not assignable to type 'number'

let bad3: Person = { name: "Anoop", city: "Trivandrum", age: 40, pin: 695001 };
// ✖ Object literal may only specify known properties — 'pin' does not exist on 'Person'
Why this matters for Angular When your API returns a list of employees, you'll declare interface Employee { ... } and type the response as Employee[]. From that moment on, the editor autocompletes every field, and a typo like emp.nmae is caught instantly instead of rendering as undefined in the browser. You'll do exactly this in Session 2.

TypeScript basics · 3 of 7

Optional properties — the ? marker

Real data is often incomplete: a user hasn't filled in their age, a middle name doesn't exist. Adding ? after a property name makes it optional — present or absent, both valid.

interface Person {
  name: string;
  city: string;
  age?: number;      // ← optional
}

let p1: Person = { name: "Anoop", city: "Trivandrum", age: 40 };  // ✔ with age
let p2: Person = { name: "Ajay",  city: "Chennai" };              // ✔ without age

console.log(p2.age);   // undefined — not an error, just absent
Required vs optional — the mental rule Ask: "could a valid object of this type genuinely be missing this field?" If yes, mark it ?. If no, leave it required so the compiler forces you to supply it. Don't mark things optional just to silence an error — that only moves the bug to runtime.
The catch An optional property may be undefined, so guard before using it: if (p2.age) { ... }. This is exactly the discipline that prevents "cannot read property of undefined" — the single most common error in front-end development.

TypeScript basics · 4 of 7

Union types — "one of these"

Sometimes a value legitimately has more than one possible type. A union type, written with the pipe |, says "any one of these types is acceptable — and nothing else."

interface Person {
  name: string;
  city: string;
  age: number | string;      // ← a number OR a string
}

let p1: Person = { name: "Anoop", city: "Trivandrum", age: 40 };        // ✔
let p2: Person = { name: "Ajay",  city: "Chennai",    age: "Forty" };   // ✔
let p3: Person = { name: "Rekha", city: "Kochi",      age: true };      // ✖ boolean not allowed

The genuinely useful form: literal unions

let status: "Active" | "Inactive";
status = "Active";     // ✔
status = "active";     // ✖ wrong case — caught at compile time!
status = "Pending";    // ✖ not one of the allowed values
This is better than an enum for simple cases A literal union gives you a fixed set of allowed strings with full autocomplete and zero runtime code. You'll use exactly this in Session 2 for the employee status field that drives the green/red row colouring.

TypeScript basics · 5 of 7

Three ways to loop

let arr = [10, 20, 30, 40];

1 · Classic for — you control the index

for (let i = 0; i < arr.length; i++) {
  console.log(i + " → " + arr[i]);
}
// 0 → 10 · 1 → 20 · 2 → 30 · 3 → 40

2 · for...of — gives you the VALUES

for (let value of arr) {
  console.log(value);
}
// 10 · 20 · 30 · 40

3 · for...in — gives you the KEYS / INDICES

for (let index in arr) {
  console.log(index);        // "0" · "1" · "2" · "3"  ← strings, not numbers!
  console.log(arr[index]);   // 10 · 20 · 30 · 40
}
The mistake almost everyone makes once for...of = values. for...in = keys. Writing for (let x in arr) console.log(x) when you wanted the values prints 0 1 2 3 and leaves people staring at the screen. Memorise it as: "index" for for...in. For arrays, prefer for...of.
Where you'll see this again Angular's *ngFor="let emp of employees" is deliberately of, not in — it iterates the values. Knowing the difference here means that syntax will make immediate sense in Session 2.

TypeScript basics · 6 of 7

Typed arrays & tuples

Arrays — many values, all the same type

let numbersArray: number[] = [1, 2, 3];
numbersArray.push(4);         // ✔
numbersArray.push("five");    // ✖ Argument of type 'string' is not assignable

let names: string[] = ["Anoop", "Ajay", "Rekha"];
let mixed: (number | string)[] = [1, "two", 3, "four"];   // union array
let people: Person[] = [];    // an array of objects — the Angular workhorse

Tuples — a fixed length, with a fixed type per position

let employee: [number, string, string, number];
employee = [1001, 'Anoop', 'Software Engineer', 25000.00];   // ✔ exact match

employee = ['Anoop', 1001, 'Software Engineer', 25000.00];   // ✖ wrong order
employee = [1001, 'Anoop', 'Software Engineer'];             // ✖ wrong length

console.log(employee[1]);   // 'Anoop' — TS knows position 1 is a string
 ArrayTuple
LengthGrows and shrinks freelyFixed at declaration
TypesOne type (or a union) throughoutA specific type per position
Use it forLists — employees, products, resultsA fixed record — a coordinate pair, a CSV row

In practice you'll use arrays constantly and tuples rarely. Know tuples exist so you recognise them; reach for an interface whenever the data has meaningful field names.

TypeScript basics · 7 of 7

Classes — because every Angular component is one

This is the piece that connects TypeScript to Angular. Every component, every service you write is a TypeScript class. The syntax will look very familiar coming from Java.

class Employee {
  // properties, with types
  id: number;
  name: string;
  private salary: number;         // private — only usable inside this class

  constructor(id: number, name: string, salary: number) {
    this.id = id;
    this.name = name;
    this.salary = salary;
  }

  // a method — note the return type after the parentheses
  getDetails(): string {
    return this.id + " - " + this.name;
  }
}

let e1 = new Employee(1001, "Anoop", 25000);
console.log(e1.getDetails());    // 1001 - Anoop
console.log(e1.salary);          // ✖ Property 'salary' is private

The constructor shorthand you'll see everywhere in Angular

// These two classes are IDENTICAL. TypeScript declares AND assigns
// the property for you when you put an access modifier on the parameter.
class Employee {
  constructor(public id: number, public name: string) { }
}
Remember this shorthand In Session 3 you will write constructor(private employeeService: EmployeeService) { } and it will look like nothing is happening. It is: that one line declares a private field and assigns Angular's injected service to it. This shorthand is the single most common line of code in a real Angular app.
ModifierVisible where
public (the default)Everywhere — including the component's HTML template
privateOnly inside the same class
protectedThe class and its subclasses
readonlyAssignable once, in the constructor; never again
Angular-specific gotcha A component's HTML template can only see public members. If you mark a property private and then use it in your template with {{ }}, the build fails. Keep template-bound properties public.

TypeScript bonus — you'll need this in Session 3

Functions & arrow functions

Typed parameters and a typed return value turn a function into a contract the compiler enforces at every call site.

// Normal function: typed parameters, typed return
function add(a: number, b: number): number {
  return a + b;
}

// Optional parameter (?) and a default value
function greet(name: string, title?: string): string {
  return title ? title + " " + name : name;
}

// void = returns nothing
function logIt(msg: string): void {
  console.log(msg);
}

Arrow functions — the compact form Angular uses constantly

// long form
let double = function (n: number): number { return n * 2; };

// arrow form — identical behaviour
let double2 = (n: number): number => n * 2;

// This shape is what you'll write when subscribing to HTTP calls:
this.http.get('/api/users').subscribe(
  data => { this.users = data; },        // success handler
  error => { console.log(error); }       // error handler
);
Why arrow functions matter in Angular specifically An arrow function keeps this pointing at your component. A traditional function () { } callback does not — inside it, this becomes something else entirely and this.users = data silently fails. Always use arrow functions for callbacks in Angular. This one habit prevents a genuinely baffling class of bug.

How it actually runs

From TypeScript to a running page

Browsers do not understand TypeScript. Something has to translate it — and the Angular CLI does this for you, automatically, every time you save a file.

You write .ts files
→
TS compiler checks types, strips them
→
Angular compiler templates → render code
→
Bundled JS served to the browser

Two things are worth internalising here:

  • Types vanish. The JavaScript that reaches the browser has no type annotations at all. Types are a development-time safety net with zero runtime cost.
  • Type errors stop the build. If your types don't line up, ng serve prints the error and the browser shows the previous working version. That red text in the terminal is your friend — read it, it names the file and line.
You will never run the compiler by hand ng serve starts a watcher: save a file → recompile → the browser refreshes itself in under a second. That loop is what makes front-end development feel fast, and it's the first thing you'll verify in the lab.

Understanding what you just generated

Anatomy of a generated project

Beginner note — "why are there so many files?!" Your Hello World has a dozen-plus files, whereas a Java Hello World is one class with a main(). That's normal and it's a trade: Angular front-loads structure so that a large app stays organised. Every project you ever open will have this same layout — which means you'll always know where to look. You'll only touch src/app/ today.

The five files that matter today

Inside src/app/

app.component.tsThe class. Properties (data) and methods (behaviour), plus the @Component decorator that links it to its template and styles.
app.component.htmlThe template. The HTML the user actually sees, with Angular syntax like {{ title }} woven in.
app.component.cssStyles scoped to this component only. A rule here cannot leak out and break another component — a genuinely valuable guarantee.
app.component.spec.tsUnit tests for this component. Generated for you; safe to ignore for these four sessions.
app.module.tsThe manifest. Declares which components belong to the app, which Angular modules it imports (e.g. FormsModule), and which component to boot first.

Notice the naming pattern — it is rigidly consistent and worth learning now:

The naming convention <name>.component.<type> — so login.component.ts, login.component.html, login.component.css, login.component.spec.ts. Services follow the same idea: employee.service.ts. Every Angular developer in the world uses this, and the CLI enforces it.

Deep dive — the question everyone asks

How does the browser find your component?

You open index.html and there's almost nothing in it. So how does your app appear? Follow the chain:

1 · index.html loads its <body> contains just: <app-root></app-root>
▼
2 · main.ts runs bootstrapModule(AppModule) — hands control to Angular
▼
3 · app.module.ts is read bootstrap: [AppComponent] — "start with this component"
▼
4 · AppComponent renders its selector is 'app-root', so its template replaces that tag

That's the whole mechanism. The selector in the @Component decorator is a custom HTML tag name. Wherever that tag appears, Angular renders that component's template.

@Component({
  selector: 'app-root',                 // ← matches <app-root> in index.html
  templateUrl: './app.component.html',
  styleUrls: ['./app.component.css']
})
export class AppComponent {
  title = 'hello-world';
}
The unlock for Session 2 Once you see that a component is just "a tag plus a template", nesting becomes obvious. Generate a header component, drop <app-header></app-header> into another template, and it appears there. That's how the component tree is built — and it's the first thing you'll do in Session 2's lab.

Recap

What you now know

  • Angular is a Google-built, TypeScript-based framework for single-page applications, structured as a tree of components.
  • "AngularJS" = 1.x (legacy, JavaScript, MVC). "Angular" = 2+ (modern, TypeScript, components). Different frameworks.
  • Angular replaces five reloading JSPs with a few reusable components, and turns your Spring Boot app into a clean JSON API.
  • TypeScript = JavaScript + static types, so mistakes surface in your editor instead of in production.
  • You can declare types, define interfaces, mark properties optional with ?, allow several types with unions, loop three ways, and type arrays and tuples.
  • Every Angular component is a TypeScript class — including the constructor shorthand you'll rely on in Session 3.
  • Two installs (Node, then the CLI) and three commands (ng new, cd, ng serve) give you a running app on port 4200.
  • You can name every file in src/app/ and explain the boot chain: index.html → main.ts → AppModule → AppComponent.
