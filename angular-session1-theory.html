Vocabulary first — so nothing is a mystery later

Jargon buster: words you'll hear all day

Front-end development has a lot of terminology. Here is every term we will use today, in one place, in plain words. You do not need to memorise this — just know the slide is here.

JavaScript
The one programming language that every web browser can run. If you want code to execute inside a browser, it ends up as JavaScript.
TypeScript
JavaScript with types added. You write TypeScript; a tool converts it into JavaScript for the browser.
Compile / transpile
Converting code from one language into another. TypeScript → JavaScript. "Transpile" just means compiling between two similar-level languages.
Framework
A large, opinionated toolkit that gives your application its structure. Angular is a framework. (More on this in two slides.)
Node.js
A program that runs JavaScript outside the browser, on your machine. Angular's tools are written in JavaScript, so you need Node to run them.
npm
Node Package Manager — downloads and manages third-party code libraries. It is the JavaScript world's Maven.
Package / library
A reusable chunk of code published by someone else. Same idea as a JAR file.
CLI
Command Line Interface — a tool you type commands at. The Angular CLI creates projects and files for you.
Component
One reusable piece of screen, with its own logic, markup and styling. Angular apps are built entirely out of these.
Template
The HTML belonging to a component — what the user actually sees.
SPA
Single-Page Application — the browser loads one page once, then JavaScript swaps pieces of it in and out. (Next slide but one.)
JSON
A plain-text format for data — the format your Spring Boot API already returns. Angular's job is to turn JSON into what the user sees.
Bundle
All your many source files squashed into a few big JavaScript files, so the browser downloads fewer things. The CLI does this for you.
localhost:4200
The address of the little web server the Angular CLI runs on your own machine while you develop. Nobody else can see it.

Concept 1

What is Angular?

Angular is an open-source front-end framework, written in TypeScript and maintained by Google, used to build single-page applications — rich, app-like websites that run inside the browser.

🅰️

Written in TypeScript

And you write your app in TypeScript too. The framework and your code speak the same language, so error messages and autocomplete are genuinely helpful.

🏢

Backed by Google

Used inside Google's own products. A predictable release every six months, long-term support, and a very large ecosystem of tutorials and libraries.

🧩

Component-based

From Angular 2 onwards, everything is a component. Your app is a tree of them: a parent holding children, each child holding its own children.

🔋

Batteries included

Routing, forms, HTTP, testing and a command-line tool all ship as part of Angular. You don't have to research and glue together ten separate libraries.

The one sentence to remember In Angular you never build "a page". You build small, self-contained components, and then nest them inside one another until they add up to a page.
Ask the batch Have you used a website that felt more like an app than a website — Gmail, a banking dashboard, a flight booking site? What felt different about it compared to an older website?

Concept 1 continued — a distinction worth 30 seconds

"Framework", not "library" — why the word matters

People use these two words loosely, but the difference explains why Angular feels the way it does.

A library

  • You call it, when you choose to
  • You design the structure of your app
  • Small, focused, does one job
  • Examples: a date-formatting library, a charting library
vs

A framework

  • It calls your code, at moments it decides
  • It provides the structure; you fill in the blanks
  • Large, covers the whole application
  • Examples: Angular, and — on the Java side — Spring Boot
Analogy A library is a power drill: you pick it up when you need a hole. A framework is a house being built around you: the walls, wiring and plumbing are already decided, and you decide what goes in each room. Angular decides the shape of your app; you decide what it does.
Why this is good news Because Angular is opinionated, every Angular project looks the same. Join a new team, open their repository, and you already know where things are. That is exactly the benefit you already get from Spring Boot's conventions.

Concept 2 — the idea Angular is built around

What is a single-page application?

In a traditional multi-page application — JSP, Servlets, PHP, ASP.NET Web Forms — every click asks the server for a brand-new HTML page. The browser throws away everything it had and repaints from scratch. That is the flash you see, the spinner, the scroll position jumping back to the top.

In a single-page application, the browser loads one HTML file — literally one, called index.html — exactly once. After that, JavaScript swaps pieces of the screen in and out. When new data is needed, only the data travels over the network (as JSON), never a whole new page.

Multi-page (the old way)

  • Every click = a full page reload
  • The server re-renders the entire HTML each time
  • Visible flicker; anything the user had typed is lost
  • The server is responsible for how things look
→

Single-page (Angular)

  • One page load, then only sections change
  • The browser renders; the server just returns JSON
  • Smooth and app-like; state survives navigation
  • The server is a pure API — a mobile app can reuse it
Analogy Multi-page is replacing the whole newspaper every time one headline changes. Single-page is a whiteboard — you wipe one corner and rewrite just that bit.

Concept 2 continued

What changes for you, the Java developer

This is not just a cosmetic improvement. It is a redistribution of responsibility between server and browser, and it changes what your Spring Boot code does.

QuestionMulti-page (JSP)Single-page (Angular)
Who builds the HTML?The server, on every requestThe browser, once, then it edits it in place
What travels over the network?Whole HTML pages, repeatedlySmall JSON payloads — just the data
What does your controller return?ModelAndView / a JSP nameA Java object, serialised to JSON
Can a mobile app reuse the backend?No — it returns HTMLYes — JSON suits any client
Who owns the user interface?The backend team, mostlyThe front-end team, entirely
The real payoff Your Spring Boot application stops producing HTML and starts producing JSON. Angular consumes that JSON and owns the whole user interface. The same API then serves a web app, an Android app and an iOS app without a single change. That is why the industry moved this way.

Concept 3

Angular versions — a short history

  • 2010AngularJS 1.x — the original. Written in JavaScript, MVC architecture, used $scope and controllers. Still alive in legacy projects, but officially end-of-life.
  • 2016Angular 2 — a complete rewrite, not an upgrade. TypeScript, component-based, mobile-friendly, dramatically faster. This is where "modern Angular" begins.
  • 2016–17Angular 4 & 5 — smaller downloads, the new HttpClient, faster compilation. (There is no Angular 3: the router package had already reached v3, so they skipped the number to keep every package aligned.)
  • 2018–19Angular 6, 7, 8 — ng update arrives, the CLI matures, lazy loading improves.
  • 2020Angular 9 & 10 — the Ivy renderer becomes the default: smaller bundles, faster rendering, far better error messages.
  • 2021–22Angular 11 → 14 — strict typing on by default, standalone components introduced, typed reactive forms.
  • 2023+Angular 15 → 17 and beyond — standalone APIs become the recommended default, signals, new template control-flow syntax. Everything you learn here still applies.
Beginner trap — the naming "AngularJS" means version 1.x only. "Angular" with no "JS" means version 2 and everything after. They are different frameworks with different architectures, and code does not port between them. When you search online, an answer using $scope is AngularJS and will not help you. Always put a version number in your search.

Concept 3 continued

Why a full rewrite was worth it AngularJS bound everything to everything, in both directions, automatically. That felt magical in a small app and became almost impossible to reason about in a large one — you genuinely could not tell what had changed what. Angular 2's component tree fixed it with explicit, directional data flow: data flows down into children, events flow up to parents. You can always trace where a change came from.

Concept 4 — the case for Angular

Why Angular? A concrete comparison

Forget theory for a moment. Imagine an employee management screen: list them, search them, add one, edit one, delete one. Here is that same feature set, built two ways.

❌ The JSP / Servlet version

  • list.jsp — show all employees
  • search.jsp — a search form and its results
  • insert.jsp — add a new employee
  • update.jsp — edit an existing one
  • delete.jsp — confirm, then delete

Five separate pages. Every click is a full round-trip and a full reload. The table markup is copy-pasted across files. To add one column you edit several JSPs and hope you found them all.

✅ The Angular version

  • One employee-list component — the table
  • One employee-form component — reused for insert and update
  • Search filters data already in memory — no server hit at all
  • Delete removes the row in place, no reload
  • Bootstrap or Angular Material gives a polished look for free

A handful of reusable components. To add a column you change one template. No page ever reloads.

Ask the batch So what is the real advantage here? (Looking for: no reloads, reusable components, a clean split between UI and API, one backend serving many clients, and far less duplicated markup to keep in sync.)

The bigger picture

Angular is a front-end framework: it runs in the user's browser, not on your server. Your Spring Boot application becomes a pure JSON API sitting behind it.

Part 2 — the language · Concept 5

What is TypeScript?

Before we can write Angular, we need the language Angular is written in. Start with the problem it solves.

JavaScript is loosely typed (also called dynamically typed): a variable has no fixed type and can silently change from a number, to a string, to a boolean. The language permits it and says nothing.

// Plain JavaScript — all three of these lines are legal
let age = 42;        // a number
age = "Anoop";       // now a string  (?!)
age = true;          // now a boolean (?!)

That flexibility is convenient in a five-line script and disastrous in a fifty-thousand-line application. A variable named age holding true will not crash where the mistake was made — it will crash somewhere far away, much later, at runtime, in front of a user.

TypeScript, released by Microsoft in 2012, is a superset of JavaScript: every valid JavaScript program is also a valid TypeScript program, and TypeScript adds static typing on top. The same code now fails immediately, in your editor, before you have even saved the file:

// TypeScript
let age = 42;
age = "Anoop";
// ✖ Error: Type 'string' is not assignable to type 'number'.
"Superset" — what that actually means You are not learning a brand-new language. TypeScript is JavaScript plus type annotations. If you know Java, the type-checking part will feel instantly familiar. If you know a little JavaScript, everything you already know still works exactly as before.

Concept 5 continued

TypeScript vs JavaScript

AspectJavaScriptTypeScript
TypingDynamic — types are decided while runningStatic — types are checked before the code runs
Runs in the browser?DirectlyMust be compiled to JavaScript first
When do errors surface?At runtime, in front of the userAt compile time, in your editor

The detail that surprises everyone TypeScript's types exist only at development time. They are stripped away completely during compilation, and the browser runs ordinary JavaScript with no types in it at all. So types cost you nothing at runtime — no performance penalty, no extra download — and save you enormous amounts of debugging. That is why Angular is written in TypeScript, and why your Angular code will be too.

Concept 5 continued — the step people forget

How TypeScript actually becomes JavaScript

A browser has never heard of TypeScript. Something has to translate your .ts files into .js files first. That something is the TypeScript compiler, and in an Angular project the CLI runs it for you, automatically, every time you save.

Here is the same code before and after. Notice the types simply vanish — they were only ever instructions to the compiler:

What you write — greet.ts

function greet(name: string): string {
  return "Hello, " + name;
}

What the browser gets — greet.js

function greet(name) {
  return "Hello, " + name;
}
Analogy Types are like the scaffolding on a building. Essential while you are constructing it, checked carefully by an inspector, and then taken away completely before anyone moves in.

TypeScript step 1 of 12

Variables: let, const, and inference

There are two ways to give a variable a type, and you will use both constantly.

Option A — declare the type yourself

let empName: string = "Anoop";
let empAge: number = 40;
let isActive: boolean = true;

The pattern is name: type = value. Note the order is the opposite of Java — the name comes first, then a colon, then the type.

Option B — let TypeScript work it out (this is called inference)

let empName = "Anoop";     // TypeScript infers: string
let empAge = 40;           // infers: number
let isActive = true;       // infers: boolean

empAge = 41;               // ✔ fine, still a number
empAge = "forty-one";      // ✖ Error: Type 'string' is not assignable to type 'number'
You get type safety even when you don't ask for it Because you gave it an initial value, TypeScript already knows the type. Inference means safety for free — and it is why real Angular code often looks untyped when it is fully type-checked. Hover over any variable in VS Code and it will tell you the type it inferred.

let vs const

TypeScript step 3 of 12

The any escape hatch — and why to resist it

any means "this can be anything; stop checking". It makes every error disappear, which is exactly why it is dangerous.

❌ With any

let emp: any = { name: "Anoop" };

emp.nmae;          // no error — typo!
emp.salary * 2;    // no error — NaN at runtime
emp.doAnything();  // no error — crash at runtime

TypeScript has been told to look away. You are writing plain JavaScript again, but with extra steps.

✅ With a real type

let emp: { name: string } = { name: "Anoop" };

emp.nmae;          // ✖ 'nmae' does not exist
emp.salary * 2;    // ✖ 'salary' does not exist
emp.doAnything();  // ✖ not a function

Three bugs caught in your editor, in the second you typed them, for free.

The rule for this series You are allowed to use any when you are genuinely stuck and want to move on — but treat it as a note to come back, never as a solution. Every any is a place where TypeScript has stopped protecting you. Angular projects created by the CLI even switch on a "strict" setting that discourages it.

TypeScript step 4 of 12 — this one matters a lot

Interfaces — giving an object a shape

So far we have typed single values. Real applications move objects around — an employee, a customer, an order. An interface describes what such an object must look like.

src/app/models/employee.ts
export interface Employee {
  id: number;
  name: string;
  designation: string;
  salary: number;
}

Now TypeScript can check every employee object you create anywhere in the app:

const e1: Employee = {
  id: 1001,
  name: "Anoop",
  designation: "Software Engineer",
  salary: 25000
};                          // ✔ all four properties, correct types

const e2: Employee = {
  id: 1002,
  name: "Ajay"
};                          // ✖ Error: missing 'designation' and 'salary'

const e3: Employee = {
  id: "1003",               // ✖ Error: 'string' is not assignable to 'number'
  name: "Rekha",
  designation: "Tester",
  salary: 22000
};
Analogy An interface is a form with required fields. It doesn't fill anything in itself — it just refuses to accept your submission if a field is missing or the wrong kind of thing.
Why you will use these constantly When JSON arrives from your Spring Boot API, you will tell Angular "the response is an Employee[]". From that moment your editor autocompletes emp.designation and flags emp.designtaion as a typo. An interface is how you make server data trustworthy on the client. The word export just means "other files may import this".

TypeScript step 5 of 12

Optional properties — the ? marker

Sometimes a field genuinely might not be there. A single ? after the property name means "this one is allowed to be missing".

export interface Employee {
  id: number;
  name: string;
  designation: string;
  salary: number;
  email?: string;        // ← optional
  phone?: string;        // ← optional
}

const e1: Employee = {
  id: 1001, name: "Anoop", designation: "Engineer", salary: 25000
};                                     // ✔ valid — no email, no phone

const e2: Employee = {
  id: 1002, name: "Ajay", designation: "Team Lead", salary: 45000,
  email: "ajay@example.com"
};                                     // ✔ also valid
The consequence you must handle Because email might be missing, TypeScript will not let you use it carelessly. This is a good thing — it is forcing you to think about the empty case, which is exactly the bug you would otherwise ship. 
console.log(e1.email.toUpperCase());
// ✖ Error: 'e1.email' is possibly 'undefined'

// Fix 1 — check first
if (e1.email) { console.log(e1.email.toUpperCase()); }

// Fix 2 — optional chaining: "if it exists, then call it"
console.log(e1.email?.toUpperCase());     // prints: undefined

// Fix 3 — supply a fallback with ??  ("nullish coalescing")
console.log(e1.email ?? "no email on file");
Remember these two operators ?. means "only carry on if the thing on the left exists". ?? means "use the right-hand value if the left is null or undefined". You will use ?. in Angular templates all the time, while you are waiting for server data to arrive.

TypeScript step 6 of 12

Union types — "one of these"

A union type uses the | symbol to say a value may be one of several types. Read | as the word "or".

let empId: number | string;

empId = 1001;        // ✔ a number
empId = "EMP-1001";  // ✔ a string
empId = true;        // ✖ Error: 'boolean' is not assignable to 'number | string'

The genuinely useful version restricts a value to specific allowed words. This is called a literal union, and it is TypeScript's answer to a Java enum:

type Status = "Active" | "Inactive" | "OnLeave";

let s: Status = "Active";      // ✔
let t: Status = "active";      // ✖ Error — wrong case, caught immediately
let u: Status = "Retired";     // ✖ Error — not one of the three
Using it inside an interface
export interface Employee {
  id: number;
  name: string;
  status: "Active" | "Inactive";     // only these two strings are legal
}
Why this is better than a plain string If status were just a string, then "Actve" would compile happily and your colour-coded table would silently show the wrong colour. As a union, that typo is a red squiggle before you save. Your editor also autocompletes the three valid values — you cannot get them wrong.

TypeScript step 7 of 12

Typed arrays

An array holds many values of the same type. Write the element type, then [].

let names: string[] = ["Anoop", "Ajay", "Rekha"];
let salaries: number[] = [25000, 45000, 22000];
let flags: boolean[] = [true, false, true];

names.push("Suresh");     // ✔ fine
names.push(42);           // ✖ Error: 'number' is not assignable to 'string'

Arrays of your own interfaces are the shape almost all real data takes — this is what a list of employees from your API looks like:

let employees: Employee[] = [
  { id: 1001, name: "Anoop", designation: "Software Engineer", salary: 25000 },
  { id: 1002, name: "Ajay",  designation: "Team Lead",         salary: 45000 },
  { id: 1003, name: "Rekha", designation: "Tester",            salary: 22000 }
];

console.log(employees.length);        // 3
console.log(employees[0].name);       // Anoop  — and autocomplete works here

TypeScript step 8 of 12

Tuples — a fixed-length, mixed-type array

An ordinary array holds many of one type. A tuple holds a fixed number of values, each with its own type, in a fixed order.

// A tuple: exactly two items — a number, then a string, in that order
let emp: [number, string] = [1001, "Anoop"];

console.log(emp[0] + 1);              // 1002 — TypeScript knows [0] is a number
console.log(emp[1].toUpperCase());    // ANOOP — and [1] is a string

let wrong: [number, string] = ["Anoop", 1001];   // ✖ Error — order matters
let tooMany: [number, string] = [1001, "Anoop", true];  // ✖ Error — length is fixed
Analogy An array is a shopping bag — put in as many apples as you like. A tuple is an egg carton — a fixed number of slots, and each slot expects a specific thing.
Honest guidance: you will not use these much Tuples appear in exam questions far more often than in real Angular code, because an interface is almost always clearer. Compare: [1001, "Anoop"] tells you nothing about what the two values mean, whereas { id: 1001, name: "Anoop" } is self-documenting. Recognise tuples when you see them; reach for interfaces when you write.

TypeScript step 9 of 12

Three ways to loop

All three appear in real code, and the difference between the middle two catches everyone out once.

1 · The classic for — when you need the index

let names: string[] = ["Anoop", "Ajay", "Rekha"];

for (let i = 0; i < names.length; i++) {
  console.log(i + " → " + names[i]);
}
// 0 → Anoop
// 1 → Ajay
// 2 → Rekha

2 · for...of — gives you each value (use this one)

for (const n of names) {
  console.log(n);           // Anoop, Ajay, Rekha
}

3 · for...in — gives you each index, as a string

for (const i in names) {
  console.log(i);           // "0", "1", "2"  ← strings, not numbers!
  console.log(names[i]);    // Anoop, Ajay, Rekha
}
The classic mix-up — memorise this line for...of gives you the object / value. for...in gives you the index / key. Nearly every time you want of. Using in on an array by mistake gives you the strings "0", "1", "2", so i + 1 produces "01" instead of 1 — a memorably confusing bug.
And in Angular? You will rarely write any of these in a template. Angular gives you *ngFor, which loops in the HTML itself. But you will write for...of and the array methods from two slides ago inside your component classes constantly.

TypeScript step 10 of 12

Functions — parameters, return types, defaults

A function in TypeScript types its parameters and its return value. The return type goes after the parameter list, following a colon.

function add(a: number, b: number): number {
  return a + b;
}

console.log(add(5, 3));         // 8
console.log(add("5", 3));       // ✖ Error: 'string' is not assignable to 'number'
console.log(add(5));            // ✖ Error: Expected 2 arguments, but got 1

Returning nothing — void

function logEmployee(e: Employee): void {
  console.log(e.name + " earns " + e.salary);
  // no return statement — so the return type is void
}

Optional and default parameters

// greeting is optional — the ? again
function greet(name: string, greeting?: string): string {
  return (greeting ?? "Hello") + ", " + name;
}
greet("Anoop");            // "Hello, Anoop"
greet("Anoop", "Welcome"); // "Welcome, Anoop"

// Or give it a default value directly
function raise(salary: number, percent: number = 10): number {
  return salary + (salary * percent / 100);
}
raise(20000);        // 22000  — used the default 10
raise(20000, 25);    // 25000
One rule about optional parameters Every optional parameter must come after all the required ones. function f(a?: string, b: number) is an error — TypeScript would have no way to know which argument you meant.

TypeScript step 11 of 12

Arrow functions — shorter, and everywhere in Angular

An arrow function is a compact way to write a function. You will meet these constantly in Angular — inside .filter(), inside .subscribe(), inside every event handler.

function (a, b) { return a + b; }
The traditional form. Works fine, just wordy.
(a, b) => { return a + b; }
Arrow form. function is gone; => sits between the parameters and the body.
(a, b) => a + b
One-expression form. With no braces, the value is returned automatically — no return keyword.
n => n * 2
A single parameter needs no brackets either. This is the form you will see most often.

Why they matter — this is the real use case

let employees: Employee[] = [ /* ...four employees... */ ];

// "give me employees earning over 30000"
const rich = employees.filter(e => e.salary > 30000);

// "give me just their names"
const names = employees.map(e => e.name);

// "find the one with id 1002"
const one = employees.find(e => e.id === 1002);

Read e => e.salary > 30000 as the sentence: "given an employee e, is its salary greater than 30000?" If you have used Java streams, this is exactly a lambda: e -> e.getSalary() > 30000. Same idea, different arrow.

Also: always compare with ===, never == === compares value and type — which is what you want, always. == tries to convert types first, giving nonsense like 0 == "" being true. Use three equals signs every single time.

TypeScript step 12 of 12 — the most important one

Classes — because every Angular component is one

If you know Java classes, you already know this. Three differences to spot: public is the default, a field's type comes after a colon, and the constructor is always called constructor.

export class Employee {
  // fields — declared with their types
  id: number;
  name: string;
  salary: number;

  // the constructor — always literally named 'constructor'
  constructor(id: number, name: string, salary: number) {
    this.id = id;
    this.name = name;
    this.salary = salary;
  }

  // a method — no 'public' needed, it's the default
  getDetails(): string {
    return this.id + " — " + this.name;
  }

  applyRaise(percent: number): void {
    this.salary = this.salary + (this.salary * percent / 100);
  }
}

// Creating one — 'new', exactly like Java
const e = new Employee(1001, "Anoop", 25000);
console.log(e.getDetails());     // 1001 — Anoop
e.applyRaise(10);
console.log(e.salary);           // 27500
Interface or class — which do I use? An interface is a shape check only; it disappears at compile time and cannot hold logic. A class is real code that exists at runtime and can have methods. Rule of thumb: use an interface for data coming from your API, and a class when you need behaviour. Every Angular component you write will be a class.

Access modifiers and the constructor shorthand

Access modifiers work as you would expect

ModifierVisible whereNote
publicEverywhereThe default — you rarely type it
privateOnly inside this classUse it to protect internal data
protectedThis class and its subclassesUncommon in Angular code
readonlyEverywhere, but cannot be reassignedLike Java's final

Now the shorthand — and it is the one you must recognise

Writing the same field name three times (declare, parameter, assign) is tedious, so TypeScript has a shortcut: put an access modifier on a constructor parameter, and it becomes a field automatically.

The long way

class Employee {
  private id: number;
  private name: string;

  constructor(id: number,
              name: string) {
    this.id = id;
    this.name = name;
  }
}

Identical, using the shorthand

class Employee {
  constructor(
    private id: number,
    private name: string
  ) { }
}
Why this slide exists In Session 3 you will write constructor(private http: HttpClient) { } and wonder where the http field came from. This is where. The word private on that parameter silently declared and assigned the field for you. If you have used Spring's constructor injection, this is the same pattern with less typing.

Part 3 — getting Angular running · Concept 6

Environment setup, step 1: Node.js and npm

Angular's tooling — the compiler, the development server, the bundler — is itself written in JavaScript. To run JavaScript on your own machine rather than in a browser, you need Node.js.

🟩

Node.js

A JavaScript runtime for your computer. Think of it as the JVM of the JavaScript world: the thing that executes the code.

📦

npm

Node Package Manager. Downloads libraries and records them in a file. It is Maven, for JavaScript — and it is installed automatically with Node.

Install and verify

  1. Go to nodejs.org and download the LTS build. LTS means "Long Term Support" — the stable one. Do not take "Current".
  2. Run the installer and accept every default. On Windows, leave "Add to PATH" ticked.
  3. Close your terminal and open a new one. This step is skipped constantly and it is why the next command appears to fail.
  4. Check both tools respond:
node -v
npm -v
What good looks like node -v prints something like v20.11.1 and npm -v prints something like 10.2.4. You want Node 18 or higher. If either command says "not found", Node is either not installed or not on your PATH — reopen the terminal first, then reinstall if it persists.
The Java parallel, line for line node -v is your java -version. npm is your mvn. package.json is your pom.xml. node_modules/ is your ~/.m2 folder of downloaded dependencies. Nothing here is a new idea — only new names.

Concept 6 continued

Environment setup, step 2: the Angular CLI

The Angular CLI is the command-line tool that creates projects, generates files, runs a development server and builds for production. You install it once, globally, and then use it in every project.

npm install -g @angular/cli
npm install
Download a package.
-g
Globally — available from any folder, not just this one. Without -g it installs into the current project only.
@angular/cli
The package name. The @angular/ prefix is a "scope" — it marks the package as officially published by the Angular team.

Then confirm it worked:

ng version

You should see an ASCII Angular logo and a table of versions. From now on, every Angular command starts with ng.

If ng is "not recognised" The install probably succeeded but the terminal was already open when it finished. Close it and open a new one. On Windows PowerShell you may also hit a script-execution block — the fix is Set-ExecutionPolicy -Scope CurrentUser RemoteSigned. Behind a corporate proxy, set npm config set proxy http://your-proxy:port and the matching https-proxy first.

Concept 7 continued — don't skip this

What those three commands actually did

A lot happened invisibly. Understanding it now prevents a great deal of confusion later.

1 · ng new creates ~20 config and source filesthe project skeleton, ready to run
▼
2 · It runs npm install for youdownloading a few hundred MB into node_modules/
▼
3 · ng serve compiles your TypeScript to JavaScriptand bundles it into a handful of .js files
▼
4 · It starts a development web server on port 4200serving those bundles, only on your machine
▼
5 · It watches your files and recompiles on every savethe browser then refreshes itself — "live reload"
Step 5 is the one that changes how you work Leave ng serve running in its own terminal all day. Edit a file, press save, and glance at the browser — it has already updated. You never manually rebuild and you never manually refresh. Open a second terminal for other ng commands.
Two things beginners do here 1. Pressing Ctrl+C in that terminal stops the server, and then localhost:4200 goes blank. That is not a bug — restart it with ng serve.
2. Running ng serve twice gives "port 4200 is already in use". You already have one running; use the tab you already had, or start the second on another port with ng serve --port 4300.

Concept 8 — the guided tour

Anatomy of a generated project

Twenty files appeared. That is intimidating for about ten minutes, and then you realise you only ever touch three of them. Here is the whole tree:

hello-world/ ├── node_modules/ every downloaded library — never edit, never commit ├── src/ ★ YOUR CODE LIVES HERE — this is the only folder you open │ ├── app/ ★ your components, services and models │ ├── assets/ images, fonts, static JSON files │ ├── index.html the ONE page of your single-page application │ ├── main.ts the entry point — the first code that runs │ └── styles.css global styles, applied to the whole app ├── angular.json CLI configuration — build options, file paths ├── package.json dependency list + the npm scripts (your pom.xml) ├── package-lock.json exact resolved versions, so every machine matches ├── tsconfig.json TypeScript compiler settings, including strict mode └── .gitignore tells git to skip node_modules/ and dist/
The 90% rule Ninety percent of your work happens inside src/app/. Everything above that line is configuration you will not touch for months. If a slide mentions a file outside src/, it is for context — not something you need to memorise.
About node_modules/ It is huge — often hundreds of megabytes and tens of thousands of files — and it is never committed to git. It can always be recreated by running npm install, because package.json lists everything needed. If a teammate's project won't start after they clone it, "did you run npm install?" is the first question.

Concept 8 continued

Inside src/app/ — the four files that matter

src/app/ ├── app.component.ts ★ the CLASS — your logic and data (TypeScript) ├── app.component.html ★ the TEMPLATE — what the user sees (HTML) ├── app.component.css ★ the STYLES — scoped to this component only ├── app.component.spec.ts unit tests — ignore for this series └── app.module.ts the app's registry of components and features

Those first three files are one component split three ways: behaviour, markup, appearance. Every component you ever generate follows this identical pattern, which is why Angular projects are so easy to navigate.

src/app/app.component.ts
import { Component } from '@angular/core';

@Component({
  selector: 'app-root',                   // the HTML tag that renders this
  templateUrl: './app.component.html',    // where its markup lives
  styleUrls: ['./app.component.css']      // where its styles live
})
export class AppComponent {
  title = 'hello-world';                  // data the template can display
}
@Component({ ... })
A decorator — extra information attached to the class. It tells Angular "this class is a component, and here is how to render it". It is Angular's @RestController.
selector: 'app-root'
The custom HTML tag name. Wherever <app-root></app-root> appears, Angular puts this component.
title = 'hello-world'
An ordinary class field. The template can display it with {{ title }} — that is Session 2's first topic.

Concept 8 continued — the question everyone asks

How does the browser find your component?

You never wrote a line linking index.html to AppComponent, yet it works. There is a four-step chain, and it is worth being able to recite it.

1 · src/index.htmlcontains just <app-root></app-root> in its body
▼
2 · src/main.tsthe entry point — it bootstraps AppModule
▼
3 · app.module.tsits bootstrap: [AppComponent] names the starting component
▼
4 · app.component.tsselector 'app-root' matches the tag — Angular renders it there

src/index.html — the whole body

<body>
  <app-root></app-root>
</body>

That is genuinely all of it. Your entire application is injected into that one empty tag.

src/main.ts

platformBrowserDynamic()
  .bootstrapModule(AppModule)
  .catch(err => console.error(err));

"Start Angular in a browser, beginning from AppModule." You will almost never edit this file.

Learn this sentence index.html → main.ts → AppModule → AppComponent → the tag <app-root>. It is a standard interview question, and more usefully it is how you debug a blank white page: check each link in the chain in order.

Concept 8 continued

app.module.ts — the app's registry

An NgModule is a list: "here is everything my application is made of". Angular will not use a component it has not been told about, and that single fact explains most beginner errors.

src/app/app.module.ts
import { NgModule } from '@angular/core';
import { BrowserModule } from '@angular/platform-browser';
import { AppComponent } from './app.component';

@NgModule({
  declarations: [
    AppComponent          // ← every component of MINE goes in this list
  ],
  imports: [
    BrowserModule         // ← features from Angular or other libraries
  ],
  providers: [],          // ← services (Session 3)
  bootstrap: [AppComponent]  // ← the component to start the app with
})
export class AppModule { }
SectionWhat goes in it
declarationsYour own components, directives and pipes. Miss one out and you get "is not a known element".
importsWhole feature modules from elsewhere — FormsModule for forms, HttpClientModule for HTTP, RouterModule for routing. Sessions 2, 3 and 4 each add one.
providersServices, when registered the older way. Session 3 explains why you usually don't need this list any more.
bootstrapThe single root component. Only AppModule has this, and it never changes.
Good news, twice over 1. When you create a component with ng generate, the CLI adds it to declarations for you. That is the single biggest reason to always use the CLI rather than creating files by hand.
2. Angular 15+ offers "standalone components", which skip modules entirely. This series uses modules because they are what you will find in existing corporate projects — and because declarations makes the "Angular must be told about everything" rule visible rather than magical.

The errors you will probably hit today

These are not signs that you are doing badly. Every one of them is normal, and each has a one-line fix.

What you seeWhat it means, and the fix
'ng' is not recognizedThe CLI isn't on your PATH. Close the terminal and open a new one — that fixes it nine times out of ten. Otherwise re-run npm install -g @angular/cli.
Port 4200 is already in useng serve is already running somewhere. Use the tab you already have, or run ng serve --port 4300.
The serve command requires to be run in an Angular projectYou are in the wrong folder. Run cd hello-world first — the project folder, not its parent.

The instinct to immediately re-run the command, or to start deleting things, is what turns a thirty-second fix into a lost afternoon.

Recap

What you now know

  • Angular is a Google-built, TypeScript-based framework for single-page applications, structured as a tree of components.
  • "AngularJS" means 1.x — legacy, JavaScript, MVC. "Angular" means 2+ — modern, TypeScript, components. They are different frameworks.
  • An SPA loads one page once and then swaps sections; only JSON travels afterwards. Your Spring Boot app becomes a pure API.
  • TypeScript is JavaScript plus static types, and those types vanish at compile time — so they cost nothing at runtime.
  • You can declare types, define interfaces, mark properties optional with ?, restrict values with unions, type arrays and tuples, loop three ways, and write arrow functions.
  • Every Angular component is a TypeScript class — including the constructor(private x: X) shorthand you will rely on in Session 3.
  • Two installs (Node, then the CLI) and three commands (ng new, cd, ng serve) give you a live app on port 4200 that reloads as you type.
  • You can name every file in src/app/ and recite the boot chain: index.html → main.ts → AppModule → AppComponent.
