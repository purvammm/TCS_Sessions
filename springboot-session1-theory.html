Groundwork · 1 of 4

A 60-second Java refresher

Everything today is built from four Java ideas you already know. We are only re-stating them because Spring's documentation uses these words constantly, and being fuzzy on them is what makes Spring feel confusing.

Class

A blueprint. It describes what something looks like and what it can do — but it isn't a thing yet. class Car { }

Object (instance)

An actual thing built from the blueprint, living in memory. new Car() creates one.

Interface

A contract — a list of method names with no bodies. It says "whoever implements me must be able to do these things," without saying how.

Annotation

A label you stick on a class, method or field, written with an @. It doesn't do anything by itself — something else reads the label and reacts to it.

The one that matters most today: annotations An annotation is a note to a tool, not an instruction to Java. Writing @RestController above a class doesn't change what the class does when you run it by hand. It means: "Spring, when you scan my code, notice this class and treat it as a web request handler." Almost all of Spring Boot works this way — you leave labels, and the framework reads them at startup.

Groundwork · 2 of 4

What exactly is a "framework"?

People use library and framework loosely, but the difference explains almost everything about how it feels to write Spring code.

A library — you are in charge

You write the main flow of the program and you call the library when you need something done.

Example: you call Math.sqrt(16) when you want a square root. Nothing happens unless you ask.

A framework — it is in charge

The framework writes the main flow and it calls your code at the right moments.

Example: Spring receives a web request, decides your method is the right one, and calls it for you. You never write the code that listens for requests.

Analogy A library is a toolbox — you pick up the tool you need, when you need it. A framework is a building already under construction with slots left for you to fill. You don't decide where the walls go; you fill in the rooms. That trade — giving up control of the overall flow — is what buys you all the free functionality.
The formal name for this "The framework calls your code instead of your code calling the framework" is known as Inversion of Control (IoC) — the control of the program flow has been inverted, handed from you to the framework. Keep that phrase in mind; it comes back as one of the central ideas of the session.

Groundwork · 3 of 4

How the web actually talks

Everything we build today is a server: a program that sits waiting, and answers when someone asks it something. The asker is called the client — a browser, a mobile app, Postman, or another server.

Client browser / Postman / app
→
Request "GET me /hello"
→
Your Server Spring Boot app
→
Response "200 OK · Hello!"

The rules for that conversation are called HTTP. It is strictly one question, one answer — the client asks, the server replies, and the connection is done. A request always carries at least two things:

  • A method (also called a verb) — the kind of thing you want: GET to read, POST to create, PUT to update, DELETE to remove.
  • A path — what you want it done to: /hello, /students, /students/5.

A response always carries a status code (a three-digit number saying how it went — 200 means fine, 404 means not found) and usually a body (the actual content).

Reading a URL In http://localhost:8080/hello: localhost means "this same computer", 8080 is the port — a numbered door on that computer that your program is listening at — and /hello is the path. Two programs cannot listen at the same port, which is the cause of the very common "Port 8080 was already in use" error.

Groundwork · 4 of 4

Who actually listens for requests?

Plain Java has no idea how to receive an HTTP request. Something has to hold the port open, read the raw bytes off the network, work out that they form a GET /hello, and hand that to your code as a tidy Java object. That something is a web server — and in the Java world the usual one is Apache Tomcat.

The networkRaw bytes arrive at port 8080 from somewhere on the internet.
TomcatHolds the port open, parses the bytes into a request object, and passes it on.
SpringLooks at the method and path, decides which of your methods should handle it.
Your codeRuns your one method and returns a value. Spring and Tomcat turn it back into a response.
Why this slide matters Historically, Tomcat was a separate program you installed on the machine, and you had to package your app up and hand it over to Tomcat to run. One of Spring Boot's headline features is that Tomcat now comes inside your application, so you just run your app like any other Java program. We'll come back to this in a few slides — but now you know what it's actually replacing.

The "before" picture

Life before Spring Boot

The Spring Framework arrived in 2003 and genuinely improved Java backend development — it introduced dependency injection and a clean way to structure applications. But while Spring made well-organised code possible, starting and assembling a Spring project stayed slow and error-prone. Before you could write a single line of business logic, you had to do a great deal of manual plumbing:

  • Write reams of XML to declare every object your app used and describe how they connect to one another.
  • Manually wire dependencies — explicitly state which object should be handed to which other object.
  • Install and configure an external Tomcat, then build a WAR file and deploy it into that server.
  • Hand-pick compatible library versions — Spring MVC, Jackson, the logging library, the servlet API — and hope they all agreed with each other.
  • Copy the same boilerplate setup into every new project, every single time.
The real cost Teams routinely spent a day or more just getting an empty project to start up correctly. The framework was powerful, but the setup ceremony stood between developers and the actual work of building features. Spring Boot was released in 2014 to delete exactly this friction.

Pain point #1 — configuration

XML configuration hell

In classic Spring, the framework had no way to discover your objects on its own — you described every single one of them in an XML file by hand. Even a tiny application's configuration looked like this:

<beans xmlns="http://www.springframework.org/schema/beans">
    <bean id="greetingService" class="com.example.GreetingServiceImpl" />

    <bean id="helloController" class="com.example.HelloController">
        <property name="greetingService" ref="greetingService" />
    </bean>

    <bean class="org.springframework.web.servlet.view.InternalResourceViewResolver">
        <property name="prefix" value="/WEB-INF/views/" />
        <property name="suffix" value=".jsp" />
    </bean>
</beans>
  • Every new class meant another <bean> entry, added and maintained by hand.
  • A typo in a class name or a ref was not caught by the compiler — it failed only at runtime, often deep into startup, with an unhelpful message.
  • On real projects this XML grew into hundreds of lines — frequently larger and harder to maintain than the Java it was wiring together.
Why this matters to you today Spring Boot replaces nearly all of this with annotations and auto-configuration. The XML above becomes two short annotations — @Service and @RestController — that the framework finds by itself. You will write exactly those two annotations in the lab. You will never write Spring XML in this course; we show it only so you appreciate what was removed.

Pain points #2, #3 & #4

Wiring, servers & version juggling

🔌

Manual wiring

You connected every dependency yourself in XML. Forget one and you discovered it only when the app crashed at runtime — not at compile time.

🖥️

No embedded server

Build a WAR file → install Tomcat → configure it → deploy the WAR into it. Four slow manual steps before the app would answer a single request.

🧩

Version conflicts

You aligned versions of Spring, Jackson, logging and the servlet API by hand. Mismatches produced cryptic crashes — the infamous "dependency hell."

📝

Repeated boilerplate

The same scaffolding was copied into every project before any feature work could begin — wasted, repetitive, easy-to-get-wrong effort.

The pattern behind all four Every one of these is configuration work that is the same for almost every project. Spring Boot's insight was simple but powerful: if 95% of projects configure these things identically, the framework should just do it by default, and let you override only the 5% that is genuinely different. That idea is called convention over configuration, and it is the heart of Spring Boot.

The solution

What is Spring Boot?

Spring Boot is a layer built on top of the Spring Framework that lets you create stand-alone, production-grade applications you can simply run. The crucial point, and the thing most beginners get wrong: it does not replace Spring. You still write Spring beans, controllers and services exactly as before — Boot removes the manual setup that used to surround them.

Your Application controllers, services, business logic — the part you write
▼ runs on
Spring Boot auto-configuration · embedded server · starters · Actuator
▼ built on
Spring Framework IoC container · MVC · data access · AOP
Mental model Spring is the engine; Spring Boot is the ignition key and the auto-tuning that gets the engine running instantly. Everything you learn about core Spring — beans, dependency injection, MVC — still applies, unchanged. Boot just means you spend your time on features instead of setup.

What Spring Boot gives you

The four things Boot provides

Everything Spring Boot does can be grouped under four headings. Understanding these four is understanding Spring Boot — we'll take each one apart over the next several slides.

⚙️

1 · Auto-configuration

Inspects which libraries you've added and configures sensible objects automatically — this is what replaced all the XML.

🚀

2 · Embedded server

Tomcat lives inside your application. Run it as an ordinary Java program; there is no separate server to install.

📦

3 · Starter dependencies

One curated entry brings in everything needed for a capability, with versions guaranteed to fit together.

📊

4 · Production-ready

Health checks, metrics and monitoring are one dependency away, through a module called Actuator.

Together, these turn "a day of setup" into "run the main method."

The guiding principle

Convention over configuration

This is the philosophy that makes the four pillars possible. Rather than forcing you to describe every detail, Spring Boot assumes the most common, sensible setup (the "convention") and lets you override only the parts that are genuinely different for your project (the "configuration"). The framework makes informed guesses from what it can see:

  • Sees spring-boot-starter-web on the classpath → assumes you're building a web app, and starts an embedded Tomcat listening on port 8080.
  • Sees an H2 database driver → assumes an in-memory database, and configures a connection to it for you.
  • Finds a class annotated @RestController → registers it automatically to handle incoming web requests.
What this means for you day to day You write configuration only where your needs differ from the convention — for example, adding server.port=9090 to change the port. If you're happy with the defaults (and usually you are), you write nothing at all. Less code to write means less code to get wrong.
A word you'll see constantly: classpath The classpath is simply the list of all code available to your program when it runs — your own classes plus every library JAR file that was downloaded for you. When we say "Boot scans the classpath", it means "Boot looks at which libraries are present." Adding a dependency to pom.xml is how a library gets onto the classpath.

Pillar 1 · how it works

Auto-configuration, step by step

Auto-configuration is the mechanism that replaced XML. At startup, Spring Boot runs a decision process across hundreds of pre-written configuration classes that ship inside the framework. Each one asks itself a question: "given this particular project, should I activate?"

1 · Scan classpath which libraries are present?
→
2 · Check conditions is this needed, and not already done?
→
3 · Create objects only what's actually required
  • Each auto-configuration is conditional: it activates only if the relevant library is genuinely on the classpath (@ConditionalOnClass) and you haven't already created that object yourself (@ConditionalOnMissingBean).
  • This is exactly why adding a starter is enough to get working features — the matching auto-configuration notices the new library and wires everything up behind the scenes.
  • If you do define your own object of the same type, Boot detects it and backs off, using yours instead. You are never locked out of taking control.
The sentence to remember Auto-configuration is "sensible defaults, applied only when they're needed, and always overridable." It is not magic and it is not hidden — it is a large pile of ordinary Spring configuration classes that the framework authors wrote so that you don't have to.

Pillar 1 · proving it to yourself

Auto-configuration isn't a black box

A healthy instinct when a framework does things for you is to ask "how do I see what it did?" Spring Boot has a built-in answer. Add one line to application.properties:

debug=true

Restart the app, and Boot prints a conditions evaluation report to the console — a full list of every auto-configuration it considered, split into those that matched and those that didn't, with the reason:

============================
CONDITIONS EVALUATION REPORT
============================

Positive matches:
-----------------
   DispatcherServletAutoConfiguration matched:
      - @ConditionalOnClass found required class
        'org.springframework.web.servlet.DispatcherServlet'

   EmbeddedWebServerFactoryCustomizerAutoConfiguration matched:
      - @ConditionalOnWebApplication (required) found 'session' scope

Negative matches:
-----------------
   DataSourceAutoConfiguration:
      Did not match:

Read that last one carefully DataSourceAutoConfiguration is the piece that would set up a database connection. It says "did not match — couldn't find the DataSource class", which is correct: we haven't added a database library yet. In Session 3 you'll add one, and this exact entry will move up into the positive matches. That is auto-configuration, in the open, explaining itself.

Pillar 2

The embedded server

Remember the four-step deployment from the "before" picture? Spring Boot deletes it by packaging Tomcat inside your application as just another library.

Before — external server

  • Download and install Tomcat on the machine
  • Configure it (ports, paths, contexts)
  • Build your app into a .war file
  • Copy the WAR into Tomcat's folder
  • Restart Tomcat and hope
  • Every machine needs the same setup
→

After — embedded server

  • Run the main method
  • Tomcat starts itself, in-process
  • Build produces one runnable .jar
  • java -jar myapp.jar and it's live
  • Nothing to install anywhere
  • Identical on every machine
Why this changed the industry Because the app now carries its own server, the artifact you test is the artifact you ship — one self-contained JAR with no assumptions about the machine it lands on. That property is precisely what makes Spring Boot apps easy to put inside Docker containers and run on cloud platforms, which is where Session 4 heads.

Tomcat is the default; Boot also supports Jetty and Undertow if you swap one dependency. You will almost never need to.

Pillar 3

Starter dependencies

A starter is a single dependency that exists purely to pull in a whole coherent set of other dependencies, at versions already tested together. It contains almost no code of its own — it is a curated shopping list.

Without starters

  • spring-web — pick a version
  • spring-webmvc — must match
  • jackson-databind — for JSON
  • tomcat-embed-core — the server
  • validation-api + an implementation
  • slf4j + logback — logging
  • …then debug the version clashes
→

With one starter

  • spring-boot-starter-web
  • That's the whole list. Every item on the left arrives automatically, at versions the Spring team has verified work together.
  • No <version> tag needed — the parent POM decides it.
Where the versions come from Your pom.xml inherits from spring-boot-starter-parent. That parent holds a giant list of "if you use library X, use version Y" decisions. It's why your dependency entries have a groupId and artifactId but usually no version at all — and why you should resist the urge to add one manually.

Supporting cast

Maven, in plain English

Spring Boot leans on a build tool. Ours is Maven, and beginners often treat it as mysterious. It only does three jobs:

1

Fetches libraries

Reads the list in pom.xml, downloads those JARs from the internet, and caches them in a folder called .m2 on your machine.

2

Compiles & tests

Turns your .java files into .class files, then runs your tests.

3

Packages

Bundles the compiled classes plus all those libraries into one runnable .jar file.

CommandWhat it does
mvn spring-boot:runCompile and start the application (the usual way to run from a terminal)
mvn clean packageDelete old output, build a runnable JAR into the target/ folder
mvn clean installSame as package, plus copy the JAR into your local .m2 cache
mvn dependency:treePrint every library actually in use — invaluable when versions clash
You may not even need Maven installed Every Initializr project ships a Maven wrapper — the files mvnw (Mac/Linux) and mvnw.cmd (Windows). Run ./mvnw spring-boot:run and the wrapper downloads the exact right Maven version for you. This is why a project builds identically on every teammate's machine.

Supporting cast

pom.xml, section by section

This is the file that defines your project. Every generated project has the same four meaningful parts:

<project>
  <!-- 1. PARENT: inherits Spring Boot's tested library versions -->
  <parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>3.5.0</version>
  </parent>

  <!-- 2. COORDINATES: your project's unique identity -->
  <groupId>com.tcs.training</groupId>      <!-- your organisation -->
  <artifactId>demo</artifactId>            <!-- this project's name -->
  <version>0.0.1-SNAPSHOT</version>        <!-- SNAPSHOT = in development -->

  <!-- 3. DEPENDENCIES: the libraries you want. Note: no versions! -->
  <dependencies>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-web</artifactId>
    </dependency>
  </dependencies>

  <!-- 4. BUILD: the plugin that makes the runnable JAR -->
  <build>
    <plugins>
      <plugin>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-maven-plugin</artifactId>
      </plugin>
    </plugins>
  </build>
</project>
Remember this pair — it comes back on the very next topic groupId + artifactId are what Spring Initializr uses to guess your Java package name. That guess is the single most common cause of a broken first project, so we are about to give it a slide of its own.

Pillar 4

Production-ready features

Real applications need to answer operational questions: are you alive? how much memory are you using? what version is deployed? Writing that yourself is tedious. Add spring-boot-starter-actuator and you get it for free, as ordinary HTTP endpoints.

The architecture

How a request flows through your app

This is the most important diagram of the session. When a request arrives at GET /students/5, it travels along a fixed path. Knowing this path is how you know where to put code and where to look when something breaks.

Client

→
Tomcat

→
Dispatcher

Spring's traffic cop
→

Client → Tomcat → DispatcherServlet → Controller → Service → Repository → Database, and the response returns along the same path in reverse.

The DispatcherServlet deserves a name-check because it appears in error messages. It is a single object Spring creates for you that receives every request, then asks: "which method in this application has a mapping matching GET /students/5?" It calls that method, takes the returned value, converts it to JSON, and sends it back. You never write it and never call it — but it is the thing that makes @GetMapping work.

The response travels back the same way Repository → Service → Controller → DispatcherServlet → Tomcat → Client. Each layer hands its result up to the one that called it. Nothing skips a layer.

The architecture

Responsibilities by layer

Those middle three boxes are your code, and splitting them this way is the single most valuable habit in backend development. Each layer has one job and talks only to its neighbour.

ControllerHandles the web. Reads the URL and request body, calls the service, returns a result and a status code. Contains no business rules.
ServiceHolds the thinking. Business rules, validation, calculations, coordinating multiple repositories. Knows nothing about HTTP.
RepositoryTalks to the database. Saving, finding, deleting rows. Knows nothing about business rules.
Model / EntityCarries the data. A plain Java class representing a Student, a Post, an Order. Passed between all the layers.
Analogy — a restaurant The waiter (controller) takes your order and brings your food, but doesn't cook. The chef (service) cooks and decides the recipe, but never talks to customers. The storeroom keeper (repository) fetches ingredients, and neither cooks nor serves. If the waiter started cooking at the table, the restaurant would descend into chaos — and so does a codebase where controllers contain business logic.
Why bother, honestly? Because requirements change. If the business rule "students must be over 16" lives in the service, you change it in one place and every entry point gets the new rule. If it's copy-pasted into three controllers, you will fix two of them and ship the bug in the third.

The entry point

@SpringBootApplication

Every Spring Boot app has exactly one main class, and it is generated for you. It is remarkably short:

package com.tcs.training.demo;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class DemoApplication {

    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }
}

Two lines are doing the work. SpringApplication.run(...) is what actually boots everything: it creates the container, runs auto-configuration, scans for your classes, and starts Tomcat. And @SpringBootApplication is the label that tells it how.

Leave this class where it is Do not move the main class into a sub-package, and do not create a second one. Its package location determines which of your classes Spring can find — which is the topic of the next two slides, and the single most common thing beginners get wrong.

The entry point

@SpringBootApplication, unpacked

That one annotation is shorthand for three separate annotations. You will occasionally see all three written out in older code — they mean exactly the same thing.

@SpringBootConfiguration
Marks this class as a source of configuration — a place where beans may be declared. It's a specialised form of @Configuration.
@EnableAutoConfiguration
Switches on auto-configuration — the classpath-scanning, condition-checking process from earlier. Without this, Boot behaves like plain Spring.
@ComponentScan
Tells Spring to search for your annotated classes — starting in this class's own package and going down through every sub-package.
Focus on the third one @ComponentScan has no arguments here. So where does it search? It defaults to "the package this class lives in, and everything below it." That default is entirely reasonable — and it is the reason the next slide exists.

⚠️ The single most important slide in this deck

Component scanning: the golden rule

Spring only manages classes it can find. It finds them by scanning downward from the main class's package. That gives us one rule that prevents the most frequent beginner failure:

The golden rule Every class you create must live in the same package as the main class, or in a sub-package of it.

Suppose your main class sits in com.tcs.training.demo. Then:

com.tcs.training └── demo ← main class DemoApplication lives here ├── controller ✅ FOUND — inside demo │ └── HelloController.java ├── service ✅ FOUND — inside demo │ └── GreetingService.java └── model ✅ FOUND — inside demo └── Student.java com.tcs.training └── controller ❌ NOT FOUND — sibling of demo, not inside it └── HelloController.java Spring never sees this class.
What "not found" looks like when you run it The app starts perfectly — no error at all — but every request to your endpoint returns the Whitelabel Error Page, 404 Not Found. That is what makes it so confusing: nothing appears broken, the URL simply isn't registered, because Spring never noticed the class. If a service is involved instead, you get a startup failure reading "required a bean of type … that could not be found."

⚠️ Applying the golden rule

How to know your base package — always

The rule is easy. The mistake people make is assuming what the base package is instead of checking. Here is the check, and it takes five seconds:

1

Open the main class

The file ending in ...Application.java — the one with @SpringBootApplication on it.

2

Read line 1

The package ...; declaration at the very top. That is your base package. Not what you assumed — what it says.

3

Prefix everything with it

Every new class goes in <that>.controller, <that>.service, and so on.

Why the assumption goes wrong: Spring Initializr builds the package name by joining your Group and Artifact, stripping out hyphens. So the two fields you typed produce a third value you didn't type:

Group you typeArtifact you typePackage Initializr actually generates
com.tcs.trainingdemocom.tcs.training.demo
com.tcs.trainingstudent-apicom.tcs.training.studentapi  ← not com.tcs.training!
com.tcs.trainingspringboot-democom.tcs.training.springbootdemo
The lab handles this for you In the lab sheet, every project's exact base package is printed at the top of the setup step, and each file's full path is shown on a banner above its code. Follow those and you cannot hit this problem. But learn the five-second check anyway — you'll need it on the job.

The container · 1 of 5

What is a "bean", really?

"Bean" sounds mysterious. It isn't. Read this definition slowly:

Definition A bean is just an ordinary Java object that Spring created and is keeping hold of for you.

That's all. There is no special Bean class to extend and no interface to implement. The only difference between a bean and any other object is who called new:

An ordinary object — you own it

GreetingService s = new GreetingService();

// You created it.
// You must decide when to make it,
// how many to make, and pass it
// to everyone who needs it.

A bean — Spring owns it

@Service
public class GreetingService { }

// Spring found this at startup,
// created ONE instance, and holds it.
// Anyone who needs it gets that one,
// handed over automatically.
Two immediate consequences One: by default there is exactly one instance of each bean for the whole application (called singleton scope). Two: because Spring created it, Spring can do extra work around it — wrap it in a transaction, add security checks, publish metrics — without you writing that code. Handing over the new is what buys you those features.

The container · 2 of 5

Dependency Injection: the problem it solves

First, the word. A dependency is simply an object that another object needs in order to do its job. A controller that must produce greetings depends on a greeting service. That's it.

So we have one question: who gives the controller its service? There are only two answers, and they lead to very different codebases.

❌ The object fetches its own

public class HelloController {

    private GreetingService service
        = new GreetingService();
    // ↑ hard-wired, permanently
}

The controller is now welded to that exact class. To use a different implementation, you must edit and recompile the controller.

✅ The object is given one

@RestController
public class HelloController {

    private final GreetingService service;

    public HelloController(
            GreetingService service) {
        this.service = service;   // handed in
    }
}

The controller states what it needs and receives it. It never names a concrete class, so what it receives can change freely.

That's the whole idea Dependency Injection means an object does not create the things it needs — they are handed to it from outside. Spring is the "outside": it builds every bean, works out who needs whom, and passes them in. That's why you'll write very few new keywords from here on.

The container · 3 of 5

Why we care: tight vs loose coupling

"Because it's cleaner" is not a good enough reason. Here is the concrete pay-off, using a realistic change: your app sends notifications by email, and now it must send SMS instead.

Tightly coupled (new inside)Loosely coupled (injected)
Swap the implementationEdit the controller's source code and recompile it.Point Spring at a different bean. The controller isn't touched.
Test it in isolationNearly impossible — every test really sends an email.Pass in a fake in the test's constructor. Fast, and no email leaves the building.
Reuse elsewhereThe class drags its dependency along wherever it goes.Reusable anywhere, because it only asks for an interface.
Who controls the lifecycleScattered across your code, invisibly.One place: the container.
Testability is the one that wins arguments Notice row two. Injection is what makes unit testing practical: you can hand a class a harmless stand-in instead of the real database or the real email server. Teams that adopt DI usually do it for testability first, and enjoy the flexibility as a bonus.
Depend on interfaces to get the full benefit The pay-off is largest when the type you inject is an interface (NotificationService) rather than a concrete class (EmailService). Then the injected object can be swapped for any implementation without the receiving class knowing. You'll do exactly this in Session 3 with a service interface and its implementation.

The container · 4 of 5

Telling Spring "manage this class"

Spring won't manage a class unless you label it. The labels are called stereotype annotations. Technically @Component is the only one that matters — the others are @Component, renamed to communicate the class's role.

@Component
The generic one. "This is a Spring-managed bean." Use it when no other label fits.
@Service
A bean containing business logic. Same behaviour as @Component, but it documents your intent for the next reader.
@Repository
A bean that talks to the database. This one adds real behaviour: Spring translates vendor-specific database exceptions into its own consistent exception types.
@Controller
A bean that handles web requests and returns view names (for HTML pages).
@RestController
@Controller + @ResponseBody. Returns data (JSON) rather than a page. This is what we use for APIs — all four sessions.
Then how does Spring know what to inject? By type. When Spring builds HelloController and sees its constructor asks for a GreetingService, it looks through its beans for one of that type and passes it in. You never write the connection anywhere — it is matched automatically. (If two beans share a type, Spring can't choose, and asks you to disambiguate with @Qualifier.)

The IoC container

All those beans live somewhere. That somewhere is the IoC container (also called the application context) — one big object Spring creates at startup that holds every bean and knows how they connect.

HelloController
@RestController
GreetingService
@Service
StudentRepository
@Repository
DispatcherServlet
auto-configured
↑ Spring created every one of these, and injects them into each other on demand.

Its startup sequence, in order:

  1. Scan — walk the base package and all sub-packages looking for stereotype annotations. (The golden rule lives here.)
  2. Instantiate — create one instance of each class it found.
  3. Inject — work out the dependency graph and hand each bean what it asked for.
  4. Serve — start Tomcat and begin accepting requests.
Steps 1 and 3 are where startup failures happen "A component required a bean of type 'X' that could not be found" means step 3 failed: something asked for X, and step 1 never found an X to give it. Nine times out of ten the cause is a missing stereotype annotation, or a class sitting outside the scanned packages.

Doing the injection

Three ways to inject — and which to use

Spring supports three mechanisms. You should recognise all three, because you'll meet them in existing code, but you should write only one.

StyleHow it looksVerdict
Constructor public Ctrl(Service s) { this.s = s; } ✅ Recommended. The field can be final, the object can never exist half-built, and it's trivially testable with plain new.
Field @Autowired private Service s; ⚠️ Works, very common in older code and tutorials. But the field can't be final, and you cannot construct the class in a test without Spring.
Setter @Autowired public void setS(Service s) Only for genuinely optional dependencies — rare.
The convenience that surprises people Since Spring 4.3, if a class has exactly one constructor, you can omit @Autowired entirely — Spring uses that constructor automatically. So the recommended style is also the shortest: 
@RestController
public class HelloController {

    private final GreetingService service;

    // No @Autowired needed — one constructor, so Spring just uses it.
    public HelloController(GreetingService service) {
        this.service = service;
    }
}

Putting it together

Dependency injection, end to end

Two small files. This is the complete pattern you'll write in Lab 5, and the pattern every remaining session builds on.

1 · The service — the bean being injected

package com.tcs.training.demo.service;

import org.springframework.stereotype.Service;

@Service   // ← "Spring, manage me"
public class GreetingService {

    public String greet(String name) {
        return "Hello, " + name + "!";
    }
}

2 · The controller — the bean receiving it

package com.tcs.training.demo.controller;

import com.tcs.training.demo.service.GreetingService;
// ...web annotations imported too

@RestController
public class GreetController {

    private final GreetingService service;

    public GreetController(GreetingService service) {
        this.service = service;   // injected
    }

    @GetMapping("/greet/{name}")
    public String greet(@PathVariable String name) {
        return service.greet(name);
    }
}

What Spring does at startup, precisely: finds both classes (they're under the base package ✅), creates one GreetingService, sees GreetController's constructor needs a GreetingService, passes the one it made, and registers /greet/{name} with the DispatcherServlet. You wrote no wiring code at all.

Delete one annotation and watch it break Remove @Service from GreetingService and the app refuses to start, reporting that GreetController required a bean of type GreetingService which could not be found. Try it in the lab — deliberately breaking things is the fastest way to understand what an annotation was doing.

Building endpoints

What is REST?

REST (Representational State Transfer) is not a technology or a library — it is a style of designing web APIs. Its central idea is that your application exposes resources (the nouns: students, posts, orders) at URLs, and you act on them using HTTP's existing verbs.

URLs name things, not actions

/students is the collection; /students/5 is one student. The URL says what, never what to do.

The verb says the action

Same URL, different meaning: GET /students/5 reads, DELETE /students/5 removes.

Stateless

Every request carries everything needed to understand it. The server remembers nothing between requests — which is what lets you run many copies of it (Session 4).

JSON as the format

Data goes back and forth as JSON text. Spring converts your Java objects to JSON automatically.

The most common design mistake Putting verbs in URLs: /getStudent?id=5 or /deleteStudent/5. HTTP already has verbs — using them twice is redundant. The REST way is GET /students/5 and DELETE /students/5. Session 2 covers URI design properly; for now, just use nouns in paths.

Building endpoints

HTTP methods and their Spring annotations

Each HTTP verb has a matching Spring annotation. Put it on a method, and that method answers that kind of request at that path.

VerbMeaningSpring annotationExample
GETRead data. Changes nothing.@GetMappingGET /students
POSTCreate something new.@PostMappingPOST /students
PUTReplace/update an existing thing.@PutMappingPUT /students/5
DELETERemove a thing.@DeleteMappingDELETE /students/5
PATCHUpdate part of a thing.@PatchMappingPATCH /students/5

And two annotations for pulling values out of the request — the difference between them trips up almost everyone, so look carefully at where each value sits in the URL:

@PathVariable — part of the path

// GET /hello/Purvam
@GetMapping("/hello/{name}")
public String hi(@PathVariable String name) {
    return "Hello, " + name;
}
// name = "Purvam"
// Used to identify WHICH resource.

@RequestParam — after the ?

// GET /hello?name=Purvam
@GetMapping("/hello")
public String hi(@RequestParam String name) {
    return "Hello, " + name;
}
// name = "Purvam"
// Used to filter, sort or paginate.

The project · 3 of 4

application.properties

One file, src/main/resources/application.properties, holds all your settings as simple key=value lines. It arrives empty, and an empty file is a perfectly valid one — it means "every default is fine."

# --- The server ---
server.port=8080                    # which port to listen on (default 8080)
spring.application.name=demo        # app's name, shown in logs

# --- Logging ---
logging.level.root=INFO             # global log level
logging.level.org.springframework.web=DEBUG   # chattier, just for web code

# --- Diagnostics ---
debug=true                          # print the auto-config report at startup
You may see YAML instead The same settings can live in application.yml, written as an indented tree rather than dotted keys. Both are equally valid and widely used; we stay with .properties because there is no indentation to get wrong. Never keep both files for the same setting — that gets confusing fast.
Two things worth knowing early Profiles: a file named application-dev.properties is loaded only when the dev profile is active — that's how one codebase carries different settings for development and production. Precedence: command-line arguments and environment variables beat this file, which is how deployment platforms inject real passwords without editing your code.

How to read a Spring Boot error

You will see errors today. That's normal and expected. What separates a confident developer from a stuck one is knowing that Spring Boot errors are unusually well written — the answer is nearly always in the first few lines.

Boot prints startup failures in a fixed, friendly format. Read the Action line first:

***************************
APPLICATION FAILED TO START
***************************

Description:

Field service in com.tcs.training.demo.controller.GreetController
required a bean of type 'com.tcs.training.demo.service.GreetingService'
that could not be found.

Action:

Consider defining a bean of type
'com.tcs.training.demo.service.GreetingService' in your configuration.
What you seeWhat it meansWhere to look first
required a bean … could not be foundSomething asked for a bean that doesn't exist.Missing @Service/@Component, or the class is outside the base package.
Whitelabel Error Page, 404App is running fine; that URL simply isn't registered.Typo in the path, missing @RestController, or the golden rule was broken.
Port 8080 was already in useAnother program holds that port.Stop the old run, or set server.port=8081.
Caused by: … (at the bottom)The real cause of a long stack trace.Always scroll to the last "Caused by" — that's the origin.
The habit to build today Don't panic and don't scroll past it. Read the Description, read the Action, then look for the class name it mentions. Spring Boot is genuinely trying to tell you the answer.

Common beginner mistakes

MistakeWhat happensFix
Class created outside the main class's packageSilent 404 / bean not found. The #1 cause of lost time.Apply the golden rule — read the main class's package line and go underneath it.

Q · What are the four things Spring Boot gives you? tap to reveal ▾

An ordinary Java object that Spring created and holds on to — rather than one you created with new. By default there is one instance per application.

In the main class's package or a sub-package of it, because @ComponentScan only searches downward from there. Break this and you get a silent 404 Whitelabel page.

Fields can be final, the object can never exist in a half-built state, and the class can be created with plain new in a test — no Spring required.

@PathVariable reads a value from inside the path — /hello/Purvam. @RequestParam reads one from after the ? — /hello?name=Purvam.
