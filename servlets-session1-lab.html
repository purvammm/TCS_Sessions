LAB 0▶ Create the Dynamic Web Project
Goal Create the right kind of project and connect it to Tomcat. This is the step where more people go wrong than anywhere else today — a plain Java Project cannot run a servlet, and the symptoms are confusing. Five minutes of care here saves an hour later.
  1. New project: File → New → Dynamic Web Project. Don't see it? File → New → Other → type "dynamic" in the filter. Still nothing? You're on the wrong Eclipse edition — see prerequisites.
  2. Project name: ServletBasics — exactly this, because it becomes part of every URL you type across both sessions.
  3. Target runtime: click New Runtime… → Apache Tomcat v9.0 → Next → browse to your unzipped Tomcat folder → Finish. This is what puts the Servlet API on your build path — without it HttpServlet won't resolve.
  4. Dynamic web module version: leave the default (3.1 or 4.0).
  5. Click Next twice to reach the final "Web Module" page. Tick "Generate web.xml deployment descriptor" — this is easy to miss and we need that file immediately.
  6. Finish. Then verify what you got, below.
Verify the project type — the 5-second check Look at the project's icon in Project Explorer. A Dynamic Web Project shows a small globe 🌐 badge on the folder; a plain Java Project doesn't. Then expand it — you must see a WebContent folder (some Eclipse versions name it src/main/webapp) containing WEB-INF with web.xml inside.

Second check: right-click the project. Is there a "Run As → Run on Server" option? If not, you created the wrong project type — delete it and start again.

Concept — the name attribute is the contract A form is how the browser collects data and packages it into a request. The single most important thing on this page is the name attribute of each input: that's the exact string your servlet will pass to getParameter(). Get a name wrong and the servlet silently reads null — no error, just a confusing failure later.

The four attributes that matter, and why
AttributeWhat it controls
action="login"Where the request goes. It's relative, so it resolves to /ServletBasics/login — the servlet's url-pattern.
method="get"Which servlet method is called — doGet. Change it to post and Tomcat looks for doPost instead.
name="id", name="pwd"The parameter names. These become getParameter("id") and getParameter("pwd"). Case-sensitive.
type="password"Masks the characters on screen only. The value still travels in plain text — especially obvious with GET, as you're about to see.

LAB 3GETPOST▶ Your First Servlet — LoginServlet
Goal — the centrepiece of Part 1 Write a real servlet: read the form data, convert it, check it, and write HTML back. Every mechanic from the theory appears in this one file — setContentType, PrintWriter, getParameter, String-to-int conversion, null-safe comparison, and a doPost delegate.
Step 1 — create the package and the class

Right-click src → New → Package → name it com.tcs.web → Finish.
Then right-click com.tcs.web → New → Class → name it LoginServlet → Finish. Replace the file's entire contents with the code below.

📄LoginServlet.javasrc/com/tcs/web/paste the WHOLE file
package com.tcs.web;

import java.io.IOException;
import java.io.PrintWriter;

// On Tomcat 10+ change these four to jakarta.servlet.*
import javax.servlet.ServletException;
import javax.servlet.http.HttpServlet;
import javax.servlet.http.HttpServletRequest;
import javax.servlet.http.HttpServletResponse;

public class LoginServlet extends HttpServlet {

    private static final long serialVersionUID = 1L;

    // Constants, not per-request data — so fields are safe here.
    // Hardcoded on purpose: this is a teaching exercise, not real auth.
    // Real apps check a database and store only hashed passwords.
    private static final int    VALID_ID  = 123;
    private static final String VALID_PWD = "Christi";

    protected void doGet(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {

        // 1. Tell the browser we're sending HTML. MUST come before getWriter().
        response.setContentType("text/html");

        // 2. This writer is the pipe to the browser (NOT System.out).
        PrintWriter out = response.getWriter();

        // 3. Which button was pressed? Our submit had name="action" value="login".
        String action = request.getParameter("action");

        out.println("<html><body>");
        out.println("<h2>Login result</h2>");

        // Constant FIRST: safe even when action is null.
        // action.equals("login") would throw NullPointerException -> 500 page.
        if ("login".equals(action)) {

            // 4. Form data always arrives as String — even the numeric field.
            // These are LOCAL variables: one per thread, therefore thread-safe.
            String idText = request.getParameter("id");
            String pwd    = request.getParameter("pwd");

            try {
                // 5. Convert it yourself. This throws if the user typed letters.
                int id = Integer.parseInt(idText);

                if (id == VALID_ID && VALID_PWD.equals(pwd)) {
                    out.println("<h3><font color='green'>Login successful. Welcome!</font></h3>");
                } else {
                    // Deliberately vague: never reveal WHICH one was wrong.
                    out.println("<h3><font color='red'>Invalid id or password.</font></h3>");
                }

            } catch (NumberFormatException e) {
                // User typed letters, or left the box empty. Without this catch
                // the user would see a raw 500 error page with a stack trace.
                out.println("<h3><font color='red'>User ID must be a number.</font></h3>");
            }

        } else {
            out.println("<h3><font color='red'>Unknown action: " + action + "</font></h3>");
        }

        out.println("<p><a href='index.html'>&laquo; Back to login</a></p>");
        out.println("</body></html>");
    }

    // Without this, a form using method="post" gets 405 Method Not Allowed.
    // Delegating keeps all the logic in one place.
    protected void doPost(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {
        doGet(request, response);
    }
}
Step 2 — map the servlet to a URL

Tomcat still doesn't know this class exists. Open web.xml and paste these two blocks immediately before the closing </web-app> tag.

📄web.xmlWebContent/WEB-INF/ADD before </web-app>
    <servlet>
        <servlet-name>LoginServlet</servlet-name>
        <servlet-class>com.tcs.web.LoginServlet</servlet-class>
    </servlet>

    <servlet-mapping>
        <servlet-name>LoginServlet</servlet-name>
        <url-pattern>/login</url-pattern>
    </servlet-mapping>
Understand what those two blocks do They're joined by the identical <servlet-name> — that string is just a nickname used to link them. The first block says "the nickname LoginServlet means the class com.tcs.web.LoginServlet." The second says "the URL /login should be handled by the nickname LoginServlet." Together they connect /ServletBasics/login → your Java class.

Two rules: the <servlet-class> must be the fully-qualified name (package included), and the <url-pattern> must start with /.

LAB 4▶ Break It On Purpose — three failures, deliberately
Why this is the most valuable lab of the session These three bugs will happen to you — in an assignment, in an interview task, or at work. If you've seen each symptom once, on purpose, in a file you understand, you'll recognise it in five seconds instead of losing an afternoon. Do all three. Undo each one before moving to the next.

Experiment 1 · Remove setContentType

Break it

In LoginServlet.doGet, comment out the content-type line, save, and log in successfully again:

// response.setContentType("text/html");     <- comment this out
PrintWriter out = response.getWriter();
Symptom — tags render as literal text
.../login?action=login&id=123&pwd=Christi
<html><body> <h2>Login result</h2> <h3><font color='green'>Login successful. Welcome!</font></h3>
Your Java is perfect. The browser simply wasn't told the body was HTML, so it displayed the characters literally. No exception, no console error — just a wrong-looking page.
Now the sneakier version — put it back, but in the wrong place Uncomment the line and move it to after getWriter(): 
PrintWriter out = response.getWriter();
response.setContentType("text/html");        <- TOO LATE. Silently ignored.
Still broken, and still no error. Response headers are committed the moment you obtain the writer, so the call does nothing. This is the version that wastes people's time, because the line is right there in the file and looks correct. Move it back above getWriter().

Experiment 2 · Print to the wrong stream

Break it

Change the success line to use System.out instead of out, save, and log in:

System.out.println("<h3><font color='green'>Login successful. Welcome!</font></h3>");
Symptom — the message vanishes from the page and appears in Eclipse The browser shows the heading and the back-link, but no success message. Meanwhile in Eclipse's Console view:
<h3><font color='green'>Login successful. Welcome!</font></h3>
System.out is for you; out is for the user. Change it back to out.println.
Keep this one as a habit, though Add this as the first line of doGet and leave it there for the rest of the lab: 
System.out.println("doGet called — action=" + request.getParameter("action")
                 + ", id=" + request.getParameter("id"));
Now every request prints a trace line. This is how you check what actually arrived when a value is mysteriously null or a comparison unexpectedly fails.

Experiment 3 · Cause a 405

Break it — two edits

1. In index.html, change method="get" to method="post".
2. In LoginServlet, comment out the whole doPost method. Save both, restart, and submit the form.

Symptom — 405 Method Not Allowed
http://localhost:8080/ServletBasics/login

HTTP Status 405 — Method Not Allowed

The specified HTTP method is not allowed for the requested resource.

Tomcat found your servlet — this is not a 404 — but the request was a POST and your servlet only implements doGet. HttpServlet's default doPost replies 405.

Two things to notice: the URL now has no query string (POST puts the data in the body — the password is no longer in the address bar), and there's nothing in the console, because your code never ran.
Fix it — and see why the delegate pattern is worth knowing Uncomment doPost and reload. It works immediately, over POST, with the password no longer visible in the URL. Then decide what to leave: keeping method="post" is the more realistic choice for a login form; reverting to method="get" keeps the parameters visible, which is handy while you're still learning. Either is fine — the doPost delegate handles both.

LAB 5▶ Checkpoint Exercise — Add a Third Field
Your turn — write this one yourself No full solution given up front. You have everything you need, and this is where it moves from "I pasted it" to "I can do it." Budget about 10 minutes.
The task Add an email field to the login form and extend the validation:
  1. Add a new table row in index.html with an input named email.
  2. In the servlet, read it with request.getParameter("email").
  3. Require that it isn't null, isn't blank, and contains an @. Hint: email.contains("@").
  4. Login succeeds only if all three checks pass — id, password, and email.
  5. Show a specific red message for a bad email, different from the wrong-password message. Good error messages tell the user what to fix.
Test these four cases before you call it done 1. Everything valid → green success.  2. Valid id/password but email ravi.example.com (no @) → the email-specific red message.  3. Email left completely blank → still a clean message, not a 500 page.  4. Valid email but wrong password → the password message.
Stuck? Here's the shape of the check — fill in the rest 
String email = request.getParameter("email");

// Order matters: the null check must come FIRST, so the later
// calls can never throw NullPointerException (short-circuit &&).
boolean emailOk = email != null && !email.trim().isEmpty() && email.contains("@");

if (!emailOk) {
    out.println("<h3><font color='red'>Please enter a valid email address.</font></h3>");
} else if (id == VALID_ID && VALID_PWD.equals(pwd)) {
    // ... success ...
} else {
    // ... invalid id or password ...
}
Going further, if you finish early Real email validation uses a regular expression, not contains("@"). Try email.matches("^[\\w.-]+@[\\w.-]+\\.[a-zA-Z]{2,}$") and test it against a@b (should fail — no top-level domain) and ravi.sharma@tcs.com (should pass).

Then try type="email" on the input instead of type="text". The browser now validates before submitting — but keep your server-side check anyway: anyone can bypass browser validation by editing the URL. Never trust the client.
LAB 6▶ Mapping Without XML — @WebServlet
Goal — two things at once Map a servlet using an annotation instead of web.xml, and build a small tool that makes the theory's "HTTP request structure" slide tangible: a servlet that echoes back what the browser actually sent you. You'll use this to inspect requests for the rest of the course.
Do this

Right-click com.tcs.web → New → Class → name it EchoServlet → Finish. Paste the whole file. Note: you add nothing to web.xml this time.

📄EchoServlet.javasrc/com/tcs/web/paste the WHOLE file
package com.tcs.web;

import java.io.IOException;
import java.io.PrintWriter;
import java.util.Enumeration;

import javax.servlet.ServletException;
import javax.servlet.annotation.WebServlet;      // <- the new import
import javax.servlet.http.HttpServlet;
import javax.servlet.http.HttpServletRequest;
import javax.servlet.http.HttpServletResponse;

/**
 * Shows what the browser actually sent. Mapped by annotation —
 * there is NO entry for this servlet in web.xml.
 */
@WebServlet("/echo")
public class EchoServlet extends HttpServlet {

    private static final long serialVersionUID = 1L;

    protected void doGet(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {

        response.setContentType("text/html");
        PrintWriter out = response.getWriter();

        out.println("<html><body>");
        out.println("<h2>Echo — what the browser actually sent</h2>");

        // ===== The request line (theory slide 10, part 1) =====
        out.println("<h3>Request line</h3>");
        out.println("<p>Method: <b>"       + request.getMethod()      + "</b><br />");
        out.println("URI: <b>"              + request.getRequestURI()  + "</b><br />");
        out.println("Query string: <b>"     + request.getQueryString() + "</b></p>");

        // ===== Every parameter, whatever its name =====
        out.println("<h3>Parameters</h3>");
        Enumeration<String> names = request.getParameterNames();

        if (!names.hasMoreElements()) {
            out.println("<p>None sent. Try adding <code>?name=Ravi&amp;city=Ahmedabad</code>"
                      + " to the URL.</p>");
        } else {
            out.println("<table border='1' cellpadding='6'>");
            out.println("<tr><th>Name</th><th>Value</th></tr>");
            while (names.hasMoreElements()) {
                String n = names.nextElement();
                out.println("<tr><td>" + n + "</td><td>"
                          + request.getParameter(n) + "</td></tr>");
            }
            out.println("</table>");
        }

        // ===== A few real headers (theory slide 10, part 2) =====
        out.println("<h3>Some headers</h3>");
        out.println("<p>Host: "       + request.getHeader("Host")            + "<br />");
        out.println("Accept: "         + request.getHeader("Accept")          + "<br />");
        out.println("Accept-Language: "+ request.getHeader("Accept-Language") + "<br />");
        out.println("User-Agent: "     + request.getHeader("User-Agent")      + "</p>");

        out.println("<p><a href='index.html'>&laquo; Back to login</a></p>");
        out.println("</body></html>");
    }

    protected void doPost(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {
        doGet(request, response);
    }
}

⚠ Never map the same servlet both ways If you add @WebServlet("/echo") and a web.xml entry for the same class or the same URL, Tomcat may refuse to start with a duplicate mapping error — and the message is not obvious. Pick one per servlet.

Also note: <welcome-file-list> has no annotation equivalent, so web.xml never disappears entirely.
Try it yourself 1. Change the annotation to @WebServlet("/inspect"), restart, and confirm /echo now 404s while /inspect works. 2. Point the login form's action at echo and submit it — you'll see your login parameters listed in the table, which is a genuinely useful debugging trick when a form isn't sending what you expect. 3. Change the form to method="post" and submit again: the Method row now reads POST and Query string becomes null — the data moved into the body. That's the GET/POST difference, visible in one screen.

The five-minute triage list 404? URL wrong — check the project name, then <url-pattern>, then restart Tomcat.  500? Read the first line of the stack trace in the Eclipse console.  405? Form method doesn't match your servlet methods — add doPost.  Tags shown as text? setContentType missing or after getWriter().  Blank page? You printed with System.out.  Value always null? The name="" attribute doesn't match your getParameter("...") string.

Lifecycle

  1. init() — once, on the first request ever
  2. service() → doGet() / doPost() — every request
  3. destroy() — once, at shutdown
  4. One instance, many threads → per-request data in locals, never fields

Habits to keep

  1. setContentType before getWriter() — always
  2. "literal".equals(variable), never variable.equals("literal")
  3. Wrap every parseInt / parseDouble in try/catch
  4. Per-request data in local variables, never instance fields
  5. Changed web.xml? Restart Tomcat
