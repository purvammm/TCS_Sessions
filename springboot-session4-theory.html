Motivation

Where one big application starts hurting

Everything you've built is a monolith: one application, one deployable JAR, one database. For most projects that is genuinely the right choice. But picture a shopping site three years in, with 40 developers and one codebase:

SituationWhat actually happens
A one-line typo fix in InvoicingRebuild, retest and redeploy the entire application — including Search, Payments and Login.
A memory leak in the PDF-report moduleThe whole process runs out of memory. Customers can't even browse products.
Search takes 1000 requests/sec, Invoicing takes 10/dayTo scale Search you must run more copies of everything — paying for idle Invoicing modules.
The team wants Python for a recommendation engineImpossible. It's one Java codebase, on one framework version.
40 developers, one repositoryConstant merge conflicts, and a release train everyone must wait for.
Notice the common thread None of these are problems with the code. They're problems with everything being welded together: one deployment unit, one process, one language, one release schedule. Microservices attack the welding — not the code.

⚠️ Read this before you fall in love with microservices

What splitting up actually costs you

Look at that table again. Microservices win the top four rows and lose the bottom four. That is not an accident — it's the fundamental trade:

The trade-off, in one sentence Microservices don't remove complexity. They move it out of your code and into the spaces between your services.

Here is what appears in those spaces — every one of them a problem you simply did not have last week:

New problemIn a monolith it was…Now it is…
Finding another componentA method call. Guaranteed to work.A network call to an address that may have changed.
FailureAn exception you catch.A timeout, a retry storm, or a cascading outage.
Debugging one requestOne stack trace.Five services, five log files, no shared thread.
A multi-step operationOne @Transactional method.A distributed saga with compensating actions.
ConfigurationOne properties file.Twelve services × three environments.
Running it locallyClick Run.Start eight applications in the right order.
The advice every experienced engineer gives Start with a monolith. Split it when the pain is real — when deployments genuinely block each other, or one component genuinely needs different scaling. Teams that begin with microservices because they sound modern usually end up with a "distributed monolith": all the operational cost, none of the independence. Everything in today's session exists to manage costs you should only take on deliberately.

The pay-off · 1 of 2

Horizontal vs vertical scaling

The main reason to accept those costs is scaling. There are two ways to handle more load:

⬆️ Vertical — a bigger machine

More CPU and RAM in the one server. 4 cores → 32 cores.

  • ✅ No code changes at all
  • ❌ There's always a physical ceiling
  • ❌ Cost rises steeply, not linearly
  • ❌ Usually needs downtime to resize
  • ❌ Still a single point of failure

➡️ Horizontal — more machines

More copies of the app behind a load balancer. 1 → 10 instances.

  • ✅ Effectively unlimited
  • ✅ Cost scales linearly
  • ✅ Add or remove copies with no downtime
  • ✅ No single point of failure
  • ⚠️ Requires the app to be stateless
Why that warning is the thread running through this whole course Horizontal scaling only works if any copy can serve any request — the REST stateless constraint from Session 2. And the copies must all see the same data, which is why Session 3 moved storage into a shared database. In today's lab you'll run three instances of one service and watch requests distributed between them. That's only possible because of those two earlier decisions.

The pay-off · 2 of 2

Load balancing & high availability

Ten copies of a service raise an obvious question: which copy gets each request? A load balancer decides.

Clients
→
Load Balancer
→
Instance 1 :8080
Instance 2 :8082
Instance 3 :8083

It does two jobs simultaneously:

JobHow
Distribute loadSpread requests so no instance is overwhelmed. The simplest strategy is round robin: take each in turn, then start again.
Provide high availabilityHealth checks. It asks each instance "are you alive?" — this is exactly what /actuator/health from Session 1 is for. An instance that stops answering is removed from rotation, and users never notice.
High availability, defined High availability means no single failure takes the system down. One instance = one crash is a total outage. Three instances plus health checks = one crash means reduced capacity, but the service stays up. In the lab you'll kill an instance mid-test and watch traffic carry on.

Pattern 1 · the problem

Why hardcoded addresses fail

Order Service needs data from Product Service. The obvious approach:

@Service
public class OrderService {

    private final RestTemplate restTemplate;

    public Product getProduct(Long id) {
        // Hardcoded address. Looks fine on your laptop...
        return restTemplate.getForObject(
                "http://localhost:8081/api/products/" + id, Product.class);
    }
}

It works perfectly — until it doesn't:

What happens in realityResult
Deployed to a server, so it isn't localhost any moreBroken. Edit and redeploy.
You scale Product Service to three instancesTwo are ignored entirely. No balancing.
An instance crashes and restarts on a different portBroken until someone notices.
A cloud platform assigns IPs dynamicallyYou can't know the address in advance.
Twelve services all reference each other this wayChange one address, redeploy several services.
The insight The caller shouldn't ask "what is Product Service's address?" — that answer keeps changing. It should ask "where is PRODUCT-SERVICE right now?" and let something else keep track. That something is a service registry.

Pattern 1 · the solution

Service Registry — Eureka

Eureka is a service registry: a small Spring Boot application whose entire job is to keep a live list of which services exist and where they currently are.

1

Register

On startup each service tells Eureka: "I'm STUDENT-MS, at host X port 8080."

2

Heartbeat

Every 30 seconds it says "still alive". Silence for ~90 seconds and Eureka removes it.

3

Discover

A caller asks Eureka "where is STUDENT-MS?" and gets back all live addresses.

4

Balance

With several addresses returned, the client round-robins between them.

The Eureka dashboard is a web page showing exactly this — and you'll have it open all lab:

🖥️ Eureka  ·  http://localhost:8761
ApplicationAvailability ZonesStatus
STUDENT-MS3UP (3) — :8080, :8082, :8083
CUSTOMER-MS1UP (1) — :8081
API-GATEWAY1UP (1) — :9393
The name in that first column STUDENT-MS comes from spring.application.name=student-ms, upper-cased by Eureka. That name is what callers use instead of an address — lb://STUDENT-MS rather than http://localhost:8080. Nobody ever writes a port again.

Pattern 1 · the code

Eureka setup — server and client

The server — the registry itself

@SpringBootApplication
@EnableEurekaServer     // ← that's it
public class EurekaServerApplication {
    public static void main(String[] a) {
        SpringApplication.run(
            EurekaServerApplication.class, a);
    }
}
server.port=8761
spring.application.name=eureka-server

# A registry doesn't register with itself
eureka.client.register-with-eureka=false
eureka.client.fetch-registry=false

A client — any normal service

@SpringBootApplication
// No annotation needed at all!
// The dependency is enough — Boot
// auto-configures registration.
public class StudentMsApplication {
    public static void main(String[] a) {
        SpringApplication.run(
            StudentMsApplication.class, a);
    }
}
server.port=8080
spring.application.name=student-ms   # ← the registry name

eureka.client.service-url.defaultZone=\
  http://localhost:8761/eureka/
Two things people get wrong One: register-with-eureka=false on the server is essential — without it the registry tries to register with itself and floods the log with connection errors. Two: spring.application.name is not cosmetic here. It is the identity other services use to find you. Leave it out and your service appears as UNKNOWN.
Startup order matters Start Eureka first, then the services. A client that starts first will log connection failures — harmless, since it retries, but confusing. Give the registry 20–30 seconds before starting anything else.

Pattern 2

API Gateway — one front door

With ten services on ten ports, should a mobile app know all ten addresses? Obviously not. An API Gateway is a single entry point that routes each request to the right service behind it.

❌ Without a gateway

  • Client must know 10 addresses
  • Authentication implemented 10 times
  • Rate limiting implemented 10 times
  • CORS configured 10 times
  • Every internal port exposed publicly
  • Move a service → update every client
→

✅ With a gateway

  • Client knows one address
  • Authentication in one place
  • Rate limiting in one place
  • CORS in one place
  • Services stay private
  • Move a service → change one route

One public port, several private services:

Pattern 2 · the code

Two ways to configure routes

You'll do both in the lab, because the contrast makes the value of the registry obvious.

A · Manual routes — explicit

spring.cloud.gateway.server.webflux
  .routes[0].id=student-service
spring.cloud.gateway.server.webflux
  .routes[0].uri=lb://STUDENT-MS
spring.cloud.gateway.server.webflux
  .routes[0].predicates[0]=Path=/api/students/**

✅ Full control — you can rewrite paths, add filters, set order.
❌ A new service means a new block of config.

B · Discovery locator — automatic

spring.cloud.gateway.server.webflux
  .discovery.locator.enabled=true
spring.cloud.gateway.server.webflux
  .discovery.locator.lower-case-service-id=true

✅ Every registered service is routable instantly at /{service-name}/**. Zero config per service.
❌ Less control, and it exposes everything by default.

The crucial part in option A is lb://STUDENT-MS. The lb:// scheme means "ask the registry for this name, then load balance across whatever instances come back." No host. No port. That one line is where discovery and load balancing meet.

⚠️ These property names changed recently — check your version In Spring Cloud 2025.0 and later the prefix is spring.cloud.gateway.server.webflux.* (shown above). In 2024.0 and earlier it was simply spring.cloud.gateway.*. Both are given side by side in the lab sheet — if your routes are silently ignored, this is almost certainly why.

Services talking to each other

Calling another service by name

The gateway handles traffic coming in. But services often need to call each other directly — and thanks to the registry, they can do it by name instead of address.

Option 1 · @LoadBalanced RestTemplate

@Configuration
public class AppConfig {
    @Bean
    @LoadBalanced          // ← the magic
    public RestTemplate restTemplate() {
        return new RestTemplate();
    }
}
// "STUDENT-MS" is a REGISTRY NAME,
// not a hostname. Spring resolves it
// and balances across instances.
Student s = restTemplate.getForObject(
    "http://STUDENT-MS/api/students/" + id,
    Student.class);

Option 2 · OpenFeign — declarative

@FeignClient(name = "STUDENT-MS")
public interface StudentClient {

    @GetMapping("/api/students/{id}")
    Student getStudent(@PathVariable Long id);
}
// No implementation — Spring generates
// it, exactly like a JpaRepository.
// Then just inject and call it.
Notice the pattern you've now seen three times JpaRepository in Session 3, and @FeignClient here: you declare an interface and Spring generates the implementation. Feign turns a remote HTTP call into what looks like an ordinary method call — which is elegant, but also a little dangerous, because it hides the fact that a network is involved. That's precisely why circuit breakers exist.

Pattern 4

Circuit Breaker — failing fast on purpose

Payment Service becomes slow — every call takes 30 seconds before timing out. Order Service calls it on every request, so Order's threads all sit waiting. Order Service becomes unresponsive too. Then everything calling Order stalls. One slow service has taken down the whole system. That's a cascading failure.

A circuit breaker — named after the electrical kind — watches the failure rate and, past a threshold, stops even trying:

CLOSED

Normal. Calls pass through and the breaker counts failures.

OPEN

Tripped. Too many failures, so calls fail instantly without touching the network. Returns a fallback.

HALF_OPEN

Testing. After a wait, a few trial calls go through. Succeed → CLOSED. Fail → OPEN again.

@CircuitBreaker(name = "paymentService", fallbackMethod = "paymentFallback")
public String processPayment(Order order) {
    return paymentClient.charge(order);     // the risky remote call
}

// Called instead, when the breaker is OPEN. Same signature + the exception.
public String paymentFallback(Order order, Throwable t) {
    return "Payment queued — we'll process it shortly";
}
Why "fail fast" beats "wait and hope" Failing in 1 millisecond with a sensible fallback is far better than blocking a thread for 30 seconds. Your service stays responsive, the struggling service gets breathing room to recover instead of being hammered, and users see graceful degradation rather than a dead site. The library is Resilience4j.

Pattern 5

Distributed Tracing — following one request

A user reports "checkout was slow." That request went Gateway → Order → Product → Payment → Notification. Five services, five separate log files, and no way to tell which lines belong to that one request. This is the single most-underestimated cost of microservices.

Distributed tracing fixes it by attaching a trace id at the entry point and passing it along every hop:

# Gateway         [traceId=a1b2c3d4, spanId=001]
2026-09-05 10:32:14 [a1b2c3d4,001] INFO  Gateway     : routing POST /api/orders
2026-09-05 10:32:14 [a1b2c3d4,002] INFO  OrderMS     : creating order 5512
2026-09-05 10:32:14 [a1b2c3d4,003] INFO  ProductMS   : reserving stock for SKU-88
2026-09-05 10:32:16 [a1b2c3d4,004] WARN  PaymentMS   : gateway slow — 2100ms  ← 🚨
2026-09-05 10:32:16 [a1b2c3d4,005] INFO  NotifyMS    : queued confirmation email

Search your aggregated logs for a1b2c3d4 and you get the complete story across all five services — in order, with timings. The WARN line answers the question immediately.

TermMeaning
TraceThe whole journey of one request. One trace id, shared by every hop.
SpanOne unit of work within the trace — usually one service's part.
Trace idThe shared identifier propagated in HTTP headers between services.
The modern tooling Micrometer Tracing generates and propagates the ids (it replaced Spring Cloud Sleuth), and Zipkin or Jaeger collects them and draws a waterfall diagram of where the time went. Add the dependency and the ids appear in your logs automatically — you write nothing.

Putting it together

The full picture

Every piece from this session, and where a request goes:

Client
→
API Gateway :9393
⇄
Eureka :8761

Student MS :8080 · :8082 · :8083
Customer MS :8081

Trace GET /api/students/1 through it, step by step:

  1. The client sends the request to the gateway — the only address it knows.
  2. The gateway matches the path /api/students/** to the route lb://STUDENT-MS.
  3. It asks Eureka: "where is STUDENT-MS?"
  4. Eureka returns all three live instances.
  5. The load balancer picks one by round robin.
  6. The request is forwarded; the service reads its database and replies.
  7. The response travels back through the gateway to the client.
What's remarkable about that list No component ever needed a hardcoded address. The client knows only the gateway; the gateway knows only a service name; the addresses come from the registry, live. Add a fourth instance and it starts receiving traffic within seconds — nothing to reconfigure, nothing to redeploy.

Check yourself

Quick recap — tap each card to reveal

Q · What's the real trade-off with microservices? tap to reveal ▾
They don't remove complexity — they move it out of your code and into the spaces between services. You gain independent deployment and targeted scaling; you inherit network failures, service discovery, distributed transactions and much harder debugging.
Q · Why can't you just hardcode another service's URL? tap to reveal ▾
Because addresses change — deployments, crashes, restarts on new ports, dynamic cloud IPs — and a single hardcoded address ignores every other instance, so there's no load balancing. A registry answers "where is it now?" instead.
Q · What are Eureka's four steps? tap to reveal ▾
Register (services announce themselves at startup) → Heartbeat (every 30s, or they're evicted) → Discover (callers ask by name and get all live addresses) → Balance (the caller round-robins between them).
Q · What does lb://STUDENT-MS mean? tap to reveal ▾
"Ask the registry for the service named STUDENT-MS, then load balance across whatever instances it returns." No host, no port — that one line is where discovery and load balancing meet.
Q · Name three things a gateway does that you'd otherwise repeat per service. tap to reveal ▾
Authentication, rate limiting and CORS — plus request logging and header manipulation. Written once at the front door instead of ten times behind it.
Q · What are the three circuit breaker states? tap to reveal ▾
CLOSED — normal, calls pass and failures are counted. OPEN — tripped, calls fail instantly with a fallback. HALF_OPEN — after a wait, a few trial calls: success returns to CLOSED, failure back to OPEN.
Q · Why is failing fast better than waiting? tap to reveal ▾
Because blocking threads on a slow dependency makes your service unresponsive too — a cascading failure. Failing in 1ms with a fallback keeps you responsive and gives the struggling service room to recover instead of being hammered.
Q · What does a trace id solve? tap to reveal ▾
It tags one request with a shared id passed to every service it touches, so you can search five separate log files and reconstruct the complete, ordered journey — with timings — for that one request.
Q · Why must a service be stateless to scale horizontally? tap to reveal ▾
Because the load balancer sends each request to any instance. If one instance held your data in its own memory, a request routed elsewhere would find it missing. Shared state must live in a database — which is what Session 3 set up.
