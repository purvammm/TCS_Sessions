The problem

What's wrong with arrays

✗ Arrays

  • Fixed size — decided at creation, forever
  • No add, no remove, no insert
  • You track "how many are actually filled" yourself
  • Removing means shifting everything manually
  • Searching means writing your own loop
  • Only length and [i] — that's the entire API
→

✓ Collections

  • Grow and shrink automatically
  • add, remove, contains, indexOf, clear
  • size() is always accurate
  • Shifting handled internally
  • Sorting, searching, reversing built in
  • Interchangeable implementations behind one interface
// Removing element 2 from an array — the honest version
int[] nums = {10, 20, 30, 40, 50};
int[] smaller = new int[nums.length - 1];
for (int i = 0, j = 0; i < nums.length; i++) {
    if (i != 2) smaller[j++] = nums[i];
}
nums = smaller;                       // 6 lines, and easy to get wrong

// The same thing with a List
List<Integer> list = new ArrayList<>(List.of(10, 20, 30, 40, 50));
list.remove(2);                       // done.
Arrays are not useless They're faster, use less memory, and are the right choice for fixed-size numeric data (image pixels, matrices) and for primitives where boxing would hurt. But for business objects whose count varies at runtime, always reach for a collection.

The angle brackets

Generics — type safety at compile time

Before Java 5, collections held Object. Everything came out as Object and had to be cast — and mistakes were only discovered at runtime.

✗ Raw type — pre-generics

List names = new ArrayList();
names.add("Priya");
names.add(42);        // allowed!

String s = (String) names.get(1);
// ClassCastException at RUNTIME
// Compiler was perfectly happy.
→

✓ Generic — type-safe

List<String> names =
        new ArrayList<>();
names.add("Priya");
// names.add(42);   COMPILE ERROR

String s = names.get(0);
// No cast needed. Impossible
// to get this wrong.

List<String>A list that holds only Strings
new ArrayList<>()The diamond — type inferred from the left. Java 7+

Why List<int> won't compile Generics work only with reference types, never primitives. Use the wrapper: List<Integer>. Java then autoboxes silently — list.add(5) becomes list.add(Integer.valueOf(5)). Convenient, but each boxed value is a heap object, so for millions of numbers a plain int[] is dramatically more efficient.

It's also a Deque LinkedList implements Deque, so it doubles as a stack or a queue: addFirst, addLast, peekFirst, pollLast, push, pop. This is where it genuinely earns its place.
The classic performance disaster for (int i = 0; i < linkedList.size(); i++) linkedList.get(i); — each get(i) walks the chain, so the loop is O(n²). On 100,000 elements that's billions of steps. Always for-each a LinkedList — that uses the iterator and stays O(n).

Honest professional advice Use ArrayList. It is the right answer well over 90% of the time. Its cache locality means it often beats LinkedList even for operations where the theory says it shouldn't. Reach for LinkedList only when you genuinely need Deque behaviour — and even then ArrayDeque is usually faster.
Ask the batch "LinkedList inserts in O(1), so it's better for insert-heavy code, right?" — Only if you're already at the position. Getting there costs O(n), which usually cancels the benefit entirely. Big-O on paper and wall-clock time on real hardware are not the same thing.

Walking a list

Four ways to iterate

List<String> names = new ArrayList<>(List.of("Priya", "Rahul", "Anita"));

// 1. Classic for — when you need the index
for (int i = 0; i < names.size(); i++) {
    System.out.println(i + ": " + names.get(i));
}

// 2. Enhanced for (for-each) — the default choice. Read-only.
for (String name : names) {
    System.out.println(name);
}

// 3. Iterator — the only safe way to REMOVE while iterating
Iterator<String> it = names.iterator();
while (it.hasNext()) {
    String name = it.next();
    if (name.startsWith("R")) {
        it.remove();                       // safe
    }
}

// 4. forEach + lambda — Java 8+, concise
names.forEach(name -> System.out.println(name));
names.forEach(System.out::println);        // method reference
UseWhen
Classic forYou need the index, or you're iterating backwards
for-eachDefault. Reading every element. Works on any Iterable
IteratorRemoving during iteration, or you need ListIterator's add/set
forEachA one-line action per element; reads well in a stream chain
for-each is syntactic sugar The compiler rewrites for (String s : names) into an Iterator loop. That's why a class must implement Iterable to be for-each-able — and why the same syntax works for arrays, lists, sets and your own classes.

The exception everyone hits once

ConcurrentModificationException

Modify a collection structurally while a for-each loop is walking it, and the iterator notices — and refuses to continue with possibly-corrupt state.

✗ Throws immediately

List<String> names =
    new ArrayList<>(
        List.of("Priya","Rahul","Anita"));

for (String n : names) {
    if (n.startsWith("R")) {
        names.remove(n);   // BOOM
    }
}
// ConcurrentModificationException

✓ Three safe options

// A. removeIf — cleanest
names.removeIf(n -> n.startsWith("R"));

// B. Iterator.remove()
Iterator<String> it = names.iterator();
while (it.hasNext()) {
    if (it.next().startsWith("R"))
        it.remove();
}

// C. Collect, then removeAll
List<String> doomed = new ArrayList<>();
for (String n : names)
    if (n.startsWith("R")) doomed.add(n);
names.removeAll(doomed);
How it detects this — modCount The list keeps a counter of structural changes. The iterator records that value when created and re-checks it on every next(). Mismatch → exception. This is fail-fast behaviour: an immediate, obvious error instead of silently skipped elements. Note: it's about structural change, so set(i, v) is fine — that replaces, it doesn't resize.
Remember this one Never add or remove inside a for-each. Use removeIf. It's one line and it's correct.

Sorting, part 1

Comparable — the natural order

To sort your own objects, Java must be told how to compare two of them. Comparable defines one ordering, built into the class itself — its natural order.

public class Account implements Comparable<Account> {

    private final String accountNumber;
    protected double balance;

    @Override
    public int compareTo(Account other) {
        return Double.compare(this.balance, other.balance);   // ascending by balance
    }
}

List<Account> accounts = new ArrayList<>(...);
Collections.sort(accounts);      // uses compareTo()
accounts.sort(null);             // same thing, modern style
compareTo returnsMeaning
A negative numberthis comes before other
ZeroThey are equal for ordering purposes
A positive numberthis comes after other
Use Double.compare, not subtraction return (int)(this.balance - other.balance); looks fine and is subtly broken: the cast to int turns a difference of 0.5 into 0 ("equal"), and with large int values subtraction can overflow and flip the sign. Always use Integer.compare, Double.compare or String.compareTo.
Keep it consistent with equals Ideally a.compareTo(b) == 0 exactly when a.equals(b). If they disagree, sorted collections like TreeSet (Session 4) behave in ways that will genuinely surprise you.

Sorting, part 2

Comparator — any order you like

One natural order is rarely enough. Comparator is an external comparison strategy: as many orderings as you need, and you don't have to own the class.

// Verbose form
accounts.sort(new Comparator<Account>() {
    @Override
    public int compare(Account a, Account b) {
        return a.getHolder().compareTo(b.getHolder());
    }
});

// Lambda
accounts.sort((a, b) -> a.getHolder().compareTo(b.getHolder()));

// Best — the factory methods read like English
accounts.sort(Comparator.comparing(Account::getHolder));

// Descending
accounts.sort(Comparator.comparingDouble(Account::getBalance).reversed());

// Multi-level: by type, then by balance descending, then by name
accounts.sort(Comparator.comparing(Account::accountType)
                        .thenComparing(Comparator.comparingDouble(Account::getBalance).reversed())
                        .thenComparing(Account::getHolder));

// Nulls last, without a single null check
accounts.sort(Comparator.comparing(Account::getHolder,
                                   Comparator.nullsLast(Comparator.naturalOrder())));
ComparableComparator
LivesInside the classOutside — a separate object
MethodcompareTo(T other)compare(T a, T b)

Needs source accessYes — you must edit the classNo — works on any type

Session 2 connection Both are interfaces. When you pass a Comparator to sort, the library calls your compare method through a Comparator reference — dynamic dispatch into code you wrote. That's the whole "program to an interface" idea, in the most-used method in the JDK.

The most quoted rule in OOP

Favour composition over inheritance

We met this warning in Session 2. Now let's see the concrete failure, because it explains why the rule exists.

✗ Inheritance for reuse

class AuditedList<E>
        extends ArrayList<E> {
    private int addCount = 0;

    @Override
    public boolean add(E e) {
        addCount++;
        return super.add(e);
    }
    @Override
    public boolean addAll(
            Collection<? extends E> c) {
        addCount += c.size();
        return super.addAll(c);
    }
    public int getAddCount() {
        return addCount;
    }
}

var list = new AuditedList<String>();
list.addAll(List.of("a","b","c"));
list.getAddCount();   // 6, not 3!

✓ Composition — a wrapper

class AuditedList<E> {
    private final List<E> inner =
        new ArrayList<>();
    private int addCount = 0;

    public boolean add(E e) {
        addCount++;
        return inner.add(e);
    }
    public boolean addAll(
            Collection<? extends E> c) {
        addCount += c.size();
        return inner.addAll(c);
    }
    public int getAddCount() {
        return addCount;
    }
    public int size() {
        return inner.size();
    }
}

// getAddCount() == 3. Correct.
Why the left column double-counts ArrayList.addAll() internally calls add() for each element. Your override counted 3 in addAll, then super.addAll called your overridden add three more times. You depended on an implementation detail the ArrayList authors never promised — and a future JDK could change it. Composition has no such exposure: you control the entire surface.

The weakest link, and the most useful

Dependency & dependency injection

A dependency is a class you merely use — no field, just a parameter or local variable. And when you do need it long-term, accept it rather than create it.

✗ Creates its own collaborator

class ReportService {
    private final CsvFormatter fmt
        = new CsvFormatter();
    // Hard-wired. Want JSON output?
    // Edit this class. Want to test
    // without real formatting?
    // You can't.
}

✓ Injected through the constructor

interface Formatter {
    String format(List<Account> a);
}

class ReportService {
    private final Formatter fmt;

    ReportService(Formatter fmt) {
        this.fmt = fmt;      // given
    }
}
new ReportService(new CsvFormatter());
new ReportService(new JsonFormatter());
new ReportService(new FakeFormatter());
//                     ^ for tests
You've just met the core idea of Spring That right-hand pattern is constructor injection, and it is the single most important idea in Spring Boot. When you write @Service and @Autowired, the framework is doing exactly this: creating the collaborator and handing it to you, so your class depends on an interface and never on a concrete implementation. Composition + programming to interfaces = testable, flexible code.

All of it together

One model, every relationship

// ===== INHERITANCE (IS-A) - from Session 2 =====
abstract class Account { ... }
class SavingsAccount extends Account { ... }

// ===== COMPOSITION (owns) - history is created inside and dies with the account =====
class TransactionHistory {
    private final List<String> entries = new ArrayList<>();   // and a List inside!
    void record(String e) { entries.add(e); }
    List<String> getEntries() { return List.copyOf(entries); }   // defensive copy
}

abstract class Account {
    private final TransactionHistory history = new TransactionHistory();  // COMPOSITION
    public void deposit(double amt) {
        balance += amt;
        history.record("DEPOSIT " + amt);
    }
}

// ===== AGGREGATION (holds, doesn't own) - customers outlive branches =====
class Customer {
    private final String name;
    private final List<Account> accounts = new ArrayList<>();   // AGGREGATION
    public void addAccount(Account a) { accounts.add(a); }
    public double totalWealth() {
        double total = 0;
        for (Account a : accounts) total += a.getBalance();      // polymorphic!
        return total;
    }
}

class Branch {
    private final String name;
    private final List<Customer> customers;                     // AGGREGATION
    Branch(String name, List<Customer> customers) {             // passed IN
        this.name = name;
        this.customers = customers;
    }
}

// ===== DEPENDENCY (uses) - Formatter is only a parameter =====
class ReportService {
    public String generate(Branch branch, Formatter formatter) {  // DEPENDENCY
        return formatter.format(branch);
    }
}
Read the relationships out loud A SavingsAccount IS-A Account · an Account OWNS its TransactionHistory · a Customer HAS Accounts · a Branch HAS Customers · ReportService USES a Formatter. Five relationships, four kinds, one small model.

A leak you should know about

Don't hand out your internal list

Composition means you own the part. If you return a direct reference to your internal collection, callers can modify your object's state behind your back — and your encapsulation is gone.

✗ Encapsulation broken

class Customer {
    private final List<Account>
        accounts = new ArrayList<>();

    public List<Account> getAccounts() {
        return accounts;    // LEAK
    }
}

Customer c = new Customer("Priya");
c.getAccounts().clear();
// All of Priya's accounts, gone.
// No validation, no logging,
// nothing you could prevent.

✓ Three safe options

// A. Immutable copy (best)
public List<Account> getAccounts() {
    return List.copyOf(accounts);
}

// B. Unmodifiable view (cheaper)
public List<Account> getAccounts() {
    return Collections
        .unmodifiableList(accounts);
}

// C. Don't expose it at all -
//    expose behaviour instead
public int accountCount() {
    return accounts.size();
}
public void addAccount(Account a) {
    // validate, log, THEN add
    accounts.add(a);
}
Best practice Return List.copyOf(...) from getters, and take copies of collections passed into constructors too. Better still: follow option C — expose behaviour, not data. If callers only ever need the count and the ability to add, don't give them the list at all.

Decision aid

Which relationship? Which List?

Modelling two classes

Is B genuinely a kind of A, usable anywhere A is expected?Yes → class B extends A (inheritance)
Does A own B exclusively, and B is meaningless without A?Yes → composition: create B inside A, keep it private final
Does A hold B, but B has its own life and may be shared?Yes → aggregation: accept B in the constructor or a setter
Does A only need B for the duration of one method?Yes → dependency: take it as a parameter, no field

Choosing a List implementation

Default, no strong opinion?ArrayList — right more than 90% of the time
Lots of get(i) by index?ArrayList — O(1) vs O(n)
Need a stack or a queue?ArrayDeque — not Stack, not Vector
Heavy add/remove at both ends?LinkedList or ArrayDeque
Must never change after creation?List.of(...) — immutable and clear about it
Shared across threads?CopyOnWriteArrayList or Collections.synchronizedList — never Vector

Do this

Best practices

  • Declare the interface, instantiate the class: List<X> l = new ArrayList<>()
  • Always parameterise — never use a raw List
  • Default to ArrayList unless you have a measured reason not to
  • Never modify a collection inside a for-each — use removeIf
  • Use Double.compare/Integer.compare in comparators, never subtraction
  • Prefer Comparator.comparing(...) over hand-written compare methods
  • Return empty collections, never null — kills a whole class of NPEs
  • Return defensive copies from getters, or expose behaviour instead of data
  • Pre-size big lists: new ArrayList<>(expectedSize)
  • Apply the IS-A test before extends — and prefer composition when reusing
  • Inject collaborators rather than constructing them inside
