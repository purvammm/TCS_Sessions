Goal Take two of the crashes from Task 1 and make the program survive them. Prove to yourself that lines after the failing line inside a try are skipped.
Try it yourself first Wrap a division in try/catch (ArithmeticException e). Print a friendly message in the catch. Then add a System.out.println("after the try") outside the whole thing and predict whether it runs. Attempt it before opening the solution.
▶ Show solution
📄SafeOps.javacreate this file
public class SafeOps {

    public static void main(String[] args) {
        System.out.println("--- safe division ---");
        safeDivide(100, 5);
        safeDivide(100, 0);

        System.out.println("\n--- safe parsing ---");
        System.out.println("Parsed: " + safeParse("42"));
        System.out.println("Parsed: " + safeParse("forty-two"));

        System.out.println("\n--- skip proof ---");
        skipProof();

        System.out.println("\nProgram finished normally. No crash.");
    }

    static void safeDivide(int a, int b) {
        try {
            int result = a / b;
            System.out.println(a + " / " + b + " = " + result);
        } catch (ArithmeticException e) {
            System.out.println("Cannot divide " + a + " by zero. (" + e.getMessage() + ")");
        }
    }

    // Returning a fallback value instead of crashing
    static int safeParse(String text) {
        try {
            return Integer.parseInt(text);
        } catch (NumberFormatException e) {
            System.out.println("  '" + text + "' is not a number - using 0");
            return 0;
        }
    }

    // Proves that the rest of the try block is SKIPPED
    static void skipProof() {
        try {
            System.out.println("line 1 - runs");
            int boom = 10 / 0;
            System.out.println("line 3 - NEVER runs");
        } catch (ArithmeticException e) {
            System.out.println("caught it - jumped straight here");
        }
        System.out.println("after the try - always runs");
    }
}
Expected output
--- safe division --- 100 / 5 = 20 Cannot divide 100 by zero. (/ by zero) --- safe parsing --- Parsed: 42 'forty-two' is not a number - using 0 Parsed: 0 --- skip proof --- line 1 - runs caught it - jumped straight here after the try - always runs Program finished normally. No crash.
The words "line 3 - NEVER runs" never appear. That's the whole lesson.
TASK 3▶ Multiple Catch, Ordering & Multi-catchTheory slides 13–14
Goal Handle three different failures from one try, then deliberately break the ordering rule to see the compiler stop you. Finally, collapse two branches into a multi-catch.
📄MultiCatchLab.javacreate this file
public class MultiCatchLab {

    public static void main(String[] args) {
        // Each input triggers a DIFFERENT catch block
        process("1");      // fine
        process("9");      // index out of bounds
        process("abc");    // not a number
        process("2");      // divide by zero (nums[2] is 0)
    }

    static void process(String input) {
        System.out.println("\nInput: " + input);
        int[] nums = {10, 5, 0};
        try {
            int index = Integer.parseInt(input);       // may throw NumberFormatException
            int value = nums[index];                   // may throw ArrayIndexOutOfBounds
            System.out.println("  100 / " + value + " = " + (100 / value));  // may throw Arithmetic
        } catch (NumberFormatException e) {
            System.out.println("  Not a number: " + input);
        } catch (ArrayIndexOutOfBoundsException e) {
            System.out.println("  Index must be 0-2, you gave: " + input);
        } catch (ArithmeticException e) {
            System.out.println("  That slot holds zero - cannot divide.");
        } catch (Exception e) {
            System.out.println("  Unexpected: " + e.getClass().getSimpleName());
        }
    }
}
Expected output
Input: 1 100 / 5 = 20 Input: 9 Index must be 0-2, you gave: 9 Input: abc Not a number: abc Input: 2 That slot holds zero - cannot divide.
One try block, four completely different outcomes — and the program never crashed.
Break it on purpose — the ordering rule Move the catch (Exception e) block so it is first, then recompile. Do not fix it yet — read the compiler error.
What the compiler says
MultiCatchLab.java:20: error: exception java.lang.NumberFormatException has already been caught } catch (NumberFormatException e) { ^ 1 error
This is a compile-time error, not a runtime one — Java refuses to let you write an unreachable catch block. Now move it back to last.

Now collapse two into a multi-catch

The "not a number" and "bad index" cases both mean "your input was unusable". Combine them:

        } catch (NumberFormatException | ArrayIndexOutOfBoundsException e) {
            System.out.println("  Unusable input '" + input + "' ("
                               + e.getClass().getSimpleName() + ")");
        } catch (ArithmeticException e) {
            System.out.println("  That slot holds zero - cannot divide.");
        }
Now try an illegal multi-catch Change it to catch (Exception | ArithmeticException e) and compile. You'll get "Alternatives in a multi-catch statement cannot be related by subclassing" — the two types must be unrelated. Revert afterwards.
TASK 4▶ finally & try-with-resourcesTheory slides 15–16
Goal Prove finally runs in all four scenarios, then write your own AutoCloseable class and watch Java close it for you. This is the single most practically useful task in the sheet — it's exactly what you'll do with files in Session 4 and with JDBC connections at work.
📄FinallyLab.javacreate this file
public class FinallyLab {

    public static void main(String[] args) {
        System.out.println("1. no exception   -> " + noException());
        System.out.println("2. caught         -> " + caught());
        System.out.println("3. returns early  -> " + returnsEarly());
        System.out.println("\n4. uncaught - finally still runs, then it propagates:");
        try {
            uncaught();
        } catch (ArithmeticException e) {
            System.out.println("   main caught it after finally ran");
        }
    }

    static String noException() {
        try {
            return "try";
        } finally {
            System.out.println("   finally ran (1)");
        }
    }

    static String caught() {
        try {
            int x = 1 / 0;
            return "unreachable";
        } catch (ArithmeticException e) {
            return "catch";
        } finally {
            System.out.println("   finally ran (2)");
        }
    }

    static String returnsEarly() {
        try {
            return "returned";      // finally runs BEFORE this value is handed back
        } finally {
            System.out.println("   finally ran (3)");
        }
    }

    static void uncaught() {
        try {
            int x = 1 / 0;
        } finally {
            System.out.println("   finally ran (4) - before unwinding continues");
        }
    }
}
Expected output
finally ran (1) 1. no exception -> try finally ran (2) 2. caught -> catch finally ran (3) 3. returns early -> returned 4. uncaught - finally still runs, then it propagates: finally ran (4) - before unwinding continues main caught it after finally ran
Look closely at 1–3: "finally ran" prints before the return value. That's the proof that finally executes before control actually leaves the method.

Your own AutoCloseable

Two files. Resource pretends to be a database connection; the demo shows it being closed for you.

📄Resource.javacreate this file
public class Resource implements AutoCloseable {

    private final String name;

    public Resource(String name) {
        this.name = name;
        System.out.println("  OPEN  " + name);
    }

    public void use() {
        System.out.println("  USE   " + name);
    }

    public void fail() {
        throw new IllegalStateException(name + " blew up mid-operation");
    }

    @Override
    public void close() {                 // called automatically
        System.out.println("  CLOSE " + name);
    }
}
📄TwrLab.javacreate this file
public class TwrLab {

    public static void main(String[] args) {
        System.out.println("A. happy path, two resources:");
        try (Resource first = new Resource("first");
             Resource second = new Resource("second")) {
            first.use();
            second.use();
        }

        System.out.println("\nB. exception thrown - is it still closed?");
        try (Resource r = new Resource("risky")) {
            r.use();
            r.fail();
        } catch (IllegalStateException e) {
            System.out.println("  CAUGHT " + e.getMessage());
        }

        System.out.println("\nDone - nothing leaked.");
    }
}
Now run it
  1. javac Resource.java TwrLab.java
  2. java TwrLab
  3. Watch the order of OPEN and CLOSE lines in part A.
Expected output
A. happy path, two resources: OPEN first OPEN second USE first USE second CLOSE second CLOSE first B. exception thrown - is it still closed? OPEN risky USE risky CLOSE risky CAUGHT risky blew up mid-operation Done - nothing leaked.
Two critical observations. (1) In part A resources close in reverse order — second then first. (2) In part B CLOSE appears before CAUGHT: the resource is closed before the catch block even starts. You wrote no finally at all.
TASK 5▶ throw, throws & Failing FastTheory slides 17–19
Goal Stop being the person who catches and become the person who throws. Build a validator that refuses bad data at the door, and see the difference between throw and throws in one file.
Try it yourself first Write static void setAge(int age) that throws IllegalArgumentException if the age is negative or above 130. Include the offending value in the message.
📄ValidationLab.javacreate this file
import java.util.Objects;

public class ValidationLab {

    public static void main(String[] args) {
        // --- unchecked: no throws clause needed, no catch forced ---
        tryRegister("Priya", 28);
        tryRegister("Rahul", -5);
        tryRegister("", 40);
        tryRegister(null, 30);

        // --- checked: the compiler FORCES us to deal with it ---
        System.out.println("\n--- checked exception ---");
        try {
            loadProfile("missing-user");
        } catch (ProfileException e) {
            System.out.println("Handled: " + e.getMessage());
        }
    }

    static void tryRegister(String name, int age) {
        try {
            register(name, age);
            System.out.println("Registered " + name + ", age " + age);
        } catch (IllegalArgumentException | NullPointerException e) {
            System.out.println("Rejected: " + e.getMessage());
        }
    }

    // Validates at the boundary and FAILS FAST. No throws clause: unchecked.
    static void register(String name, int age) {
        Objects.requireNonNull(name, "name must not be null");
        if (name.isBlank()) {
            throw new IllegalArgumentException("name must not be blank");
        }
        if (age < 0 || age > 130) {
            throw new IllegalArgumentException("age must be 0-130, got: " + age);
        }
        // ... only reached with valid data ...
    }

    // CHECKED: declared with throws, so callers must handle it
    static void loadProfile(String userId) throws ProfileException {
        throw new ProfileException("No profile for user: " + userId);
    }
}
📄ProfileException.javacreate this file
public class ProfileException extends Exception {   // extends Exception = CHECKED
    public ProfileException(String message) {
        super(message);
    }
}
Expected output
Registered Priya, age 28 Rejected: age must be 0-130, got: -5 Rejected: name must not be blank Rejected: name must not be null --- checked exception --- Handled: No profile for user: missing-user
Every rejection message names what was wrong and the actual value. That's the standard to hold yourself to.
Prove the compiler enforces checked exceptions Delete throws ProfileException from loadProfile's signature and compile. Then put it back, but remove the try/catch in main and compile again.
Both errors you should see
# removing the throws clause: error: unreported exception ProfileException; must be caught or declared to be thrown # removing the try/catch in main: error: unreported exception ProfileException; must be caught or declared to be thrown
This is exactly what "checked" means: the compiler will not let you ignore it. Now change ProfileException to extends RuntimeException and watch both errors disappear.

public class InsufficientFundsException extends Exception {   // CHECKED - recoverable

    private final double shortfall;

    public InsufficientFundsException(String message, double shortfall) {
        super(message);
        this.shortfall = shortfall;
    }

    public double getShortfall() {
        return shortfall;
    }
}

📄BankAccount.javacreate this file
public class BankAccount {

    private final String accountNumber;
    private final String holder;
    private double balance;

    public BankAccount(String accountNumber, String holder, double openingBalance) {
        if (openingBalance < 0) {
            throw new InvalidAmountException(openingBalance);
        }
        this.accountNumber = accountNumber;
        this.holder = holder;
        this.balance = openingBalance;
    }

    public void deposit(double amount) {
        if (amount <= 0) {
            throw new InvalidAmountException(amount);       // caller's mistake
        }
        balance += amount;
        System.out.printf("  Deposited %.2f  | balance %.2f%n", amount, balance);
    }

    public void withdraw(double amount) throws InsufficientFundsException {
        if (amount <= 0) {
            throw new InvalidAmountException(amount);
        }
        if (amount > balance) {
            double shortfall = amount - balance;
            throw new InsufficientFundsException(
                String.format("Cannot withdraw %.2f - balance is only %.2f", amount, balance),
                shortfall);
        }
        balance -= amount;
        System.out.printf("  Withdrew  %.2f  | balance %.2f%n", amount, balance);
    }

    public double getBalance()      { return balance; }
    public String getAccountNumber() { return accountNumber; }
    public String getHolder()        { return holder; }

    @Override
    public String toString() {
        return String.format("%s (%s): %.2f", accountNumber, holder, balance);
    }
}
📄BankDemo.javacreate this file
public class BankDemo {

    public static void main(String[] args) {
        BankAccount acc = new BankAccount("AC1001", "Priya Sharma", 5000);
        System.out.println("Opened: " + acc);

        System.out.println("\n1. Valid operations:");
        acc.deposit(2000);
        attemptWithdraw(acc, 3000);

        System.out.println("\n2. Withdraw more than the balance (checked):");
        attemptWithdraw(acc, 99999);

        System.out.println("\n3. Negative deposit (unchecked):");
        try {
            acc.deposit(-100);
        } catch (InvalidAmountException e) {
            System.out.println("  Rejected: " + e.getMessage());
        }

        System.out.println("\n4. Balance is still intact:");
        System.out.println("  " + acc);
        System.out.println("  Never negative: " + (acc.getBalance() >= 0));
    }

    static void attemptWithdraw(BankAccount acc, double amount) {
        try {
            acc.withdraw(amount);
        } catch (InsufficientFundsException e) {
            System.out.println("  Denied: " + e.getMessage());
            System.out.printf("  You need %.2f more.%n", e.getShortfall());
        }
    }
}

TASK 7▶ Chaining & Translating Across LayersTheory slides 22–23
Goal See with your own eyes what Caused by: looks like — and what you destroy when you forget to pass the cause. This is the task that most changes how you write production code.
📄ChainLab.javacreate this file
public class ChainLab {

    public static void main(String[] args) {
        System.out.println("=== WITH the cause attached ===");
        try {
            service(42);
        } catch (ServiceException e) {
            e.printStackTrace(System.out);
        }

        System.out.println("\n=== WITHOUT the cause (evidence destroyed) ===");
        try {
            badService(42);
        } catch (ServiceException e) {
            e.printStackTrace(System.out);
        }

        System.out.println("\n=== Walking the chain programmatically ===");
        try {
            service(42);
        } catch (ServiceException e) {
            Throwable t = e;
            int depth = 0;
            while (t != null) {
                System.out.println("  ".repeat(depth) + "-> "
                        + t.getClass().getSimpleName() + ": " + t.getMessage());
                t = t.getCause();
                depth++;
            }
        }
    }

    // --- Service layer: business language, cause preserved ---
    static void service(int id) throws ServiceException {
        try {
            repository(id);
        } catch (RepositoryException e) {
            throw new ServiceException("Could not load user " + id, e);   // cause!
        }
    }

    // --- The WRONG version: cause dropped ---
    static void badService(int id) throws ServiceException {
        try {
            repository(id);
        } catch (RepositoryException e) {
            throw new ServiceException("Could not load user " + id);      // no cause
        }
    }

    // --- Repository layer: technical language, wraps the raw failure ---
    static void repository(int id) throws RepositoryException {
        try {
            rawDatabaseCall();
        } catch (IllegalStateException e) {
            throw new RepositoryException("Query failed for id " + id, e);
        }
    }

    // --- Pretend JDBC driver failure ---
    static void rawDatabaseCall() {
        throw new IllegalStateException("Connection refused: localhost:5432");
    }
}

Expected output — compare the two traces
=== WITH the cause attached === ServiceException: Could not load user 42 at ChainLab.service(ChainLab.java:38) at ChainLab.main(ChainLab.java:6) Caused by: RepositoryException: Query failed for id 42 at ChainLab.repository(ChainLab.java:52) ... 2 more Caused by: java.lang.IllegalStateException: Connection refused: localhost:5432 at ChainLab.rawDatabaseCall(ChainLab.java:59) ... 3 more === WITHOUT the cause (evidence destroyed) === ServiceException: Could not load user 42 at ChainLab.badService(ChainLab.java:46) at ChainLab.main(ChainLab.java:13) (no Caused by - the connection failure is gone forever) === Walking the chain programmatically === -> ServiceException: Could not load user 42 -> RepositoryException: Query failed for id 42 -> IllegalStateException: Connection refused: localhost:5432
This is the whole lesson of the task In the first trace you learn the database was refusing connections on port 5432 — you can act on that. In the second you learn only that "something went wrong loading user 42". Same bug, same code path; one is fixable in two minutes and the other costs you an afternoon. Always pass the cause.
TASK 8▶ Put It Together — the Interactive BankTheory slides 24–26
Goal A menu-driven console app that cannot be crashed by the user, no matter what they type. Reuse BankAccount and both exception classes from Task 6. This is the file you bring to Session 2.
Before you start — the challenge Your target: however hard your neighbour tries, they cannot make this program print a stack trace. Letters where numbers go, empty input, negative amounts, pressing Enter on its own — all handled.
📄BankApp.javacreate this file
import java.util.InputMismatchException;
import java.util.Scanner;

public class BankApp {

    public static void main(String[] args) {
        BankAccount account = new BankAccount("AC1001", "Priya Sharma", 5000);

        // Scanner is AutoCloseable - let try-with-resources close it
        try (Scanner scanner = new Scanner(System.in)) {
            boolean running = true;

            while (running) {
                printMenu(account);
                String choice = scanner.nextLine().trim();

                switch (choice) {
                    case "1" -> showBalance(account);
                    case "2" -> doDeposit(account, scanner);
                    case "3" -> doWithdraw(account, scanner);
                    case "4" -> {
                        System.out.println("Goodbye. Final balance: " + account);
                        running = false;
                    }
                    default  -> System.out.println("!! Please choose 1, 2, 3 or 4.");
                }
            }
        }
    }

    static void printMenu(BankAccount account) {
        System.out.println("\n===== " + account.getAccountNumber()
                           + " | " + account.getHolder() + " =====");
        System.out.println("1. Check balance");
        System.out.println("2. Deposit");
        System.out.println("3. Withdraw");
        System.out.println("4. Exit");
        System.out.print("Choice: ");
    }

    static void showBalance(BankAccount account) {
        System.out.printf("Balance: %.2f%n", account.getBalance());
    }

    static void doDeposit(BankAccount account, Scanner scanner) {
        try {
            double amount = readAmount(scanner, "Amount to deposit: ");
            account.deposit(amount);
        } catch (InvalidAmountException e) {
            System.out.println("!! " + e.getMessage());
        } catch (NumberFormatException e) {
            System.out.println("!! That is not a valid number.");
        }
    }

    static void doWithdraw(BankAccount account, Scanner scanner) {
        try {
            double amount = readAmount(scanner, "Amount to withdraw: ");
            account.withdraw(amount);
        } catch (InsufficientFundsException e) {
            System.out.println("!! " + e.getMessage());
            System.out.printf("!! You need %.2f more.%n", e.getShortfall());
        } catch (InvalidAmountException e) {
            System.out.println("!! " + e.getMessage());
        } catch (NumberFormatException e) {
            System.out.println("!! That is not a valid number.");
        }
    }

    // Reading with nextLine + parse is far safer than nextDouble()
    static double readAmount(Scanner scanner, String prompt) {
        System.out.print(prompt);
        String raw = scanner.nextLine().trim();
        if (raw.isEmpty()) {
            throw new NumberFormatException("empty input");
        }
        return Double.parseDouble(raw);      // throws NumberFormatException on junk
    }
}
Now run it

▶ Common Issues & Fixes
SymptomCause & fix
error: class X is public, should be declared in a file named X.javaFilename must match the public class name exactly, including capitals.
error: unreported exception … must be caught or declaredYou're calling something that throws a checked exception. Either wrap it in try/catch or add throws to your method.
error: exception X has already been caughtA broader catch appears before a narrower one. Reorder: subclasses first.
error: Alternatives in a multi-catch … cannot be related by subclassingTwo types in the same multi-catch are parent/child. Keep only the parent.
Infinite loop of "invalid input"You used scanner.nextInt(), which leaves bad tokens in the buffer. Use nextLine() + parseInt.
Input is skipped after reading a numberClassic nextInt()-then-nextLine() problem — the newline is left behind. Use nextLine() throughout.
NoClassDefFoundError when runningYou typed java BankApp.class. Drop the extension: java BankApp.
Custom exception "doesn't need catching"It extends RuntimeException. Extend Exception for checked behaviour.
No Caused by: in the traceYou didn't pass the cause: use the (String, Throwable) constructor.
switch with -> won't compileArrow switch needs Java 14+. Check javac -version, or use classic case "1": … break;.
▶ Glossary — terms you'll hear today
TermPlain-English meaning
ExceptionAn object describing something that went wrong at runtime
ThrowableThe root class of everything you can throw
ErrorA JVM-level failure (out of memory, stack overflow) — don't catch it
Checked exceptionThe compiler forces you to catch it or declare it
Unchecked exceptionExtends RuntimeException; the compiler ignores it. Usually your bug
Call stackThe list of methods currently running, innermost first
Stack unwindingPopping frames off the stack while hunting for a matching catch
Stack traceThe printed snapshot of that stack at the moment of the throw
throwA statement that raises an exception right now
throwsA signature clause warning callers this method may fail
finallyA block that runs whatever happens — for cleanup
try-with-resourcestry (…) syntax that closes resources automatically
AutoCloseableThe interface (one method, close()) that makes that possible
Chaining / causeAttaching the original exception to a new one so the trace survives
Suppressed exceptionAn exception from close() that was set aside so the primary one could propagate
Fail fastDetecting and reporting bad data immediately, at the boundary
SwallowingCatching an exception and doing nothing — the worst anti-pattern here
