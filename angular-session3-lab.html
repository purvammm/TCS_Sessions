📄src/app/reactive-registration/reactive-registration.component.tsREPLACE the whole file
import { Component } from '@angular/core';
import { FormGroup, FormControl, Validators } from '@angular/forms';

@Component({
  selector: 'app-reactive-registration',
  templateUrl: './reactive-registration.component.html',
  styleUrls: ['./reactive-registration.component.css']
})
export class ReactiveRegistrationComponent {

  userForm = new FormGroup({
    name: new FormControl('', [
      Validators.required,
      Validators.minLength(3)
    ]),
    age: new FormControl('', [
      Validators.required,
      Validators.min(18),
      Validators.max(60)
    ]),
    city: new FormControl('', [
      Validators.required
    ]),
    postalCode: new FormControl('', [
      Validators.required,
      Validators.pattern('^[0-9]{6}$')       // exactly six digits
    ])
  });

  submitted: any = null;

  // shorthand so the template stays readable
  get f() { return this.userForm.controls; }

  onSubmit(): void {
    if (this.userForm.invalid) { return; }    // belt and braces
    console.log('Reactive form value:', this.userForm.value);
    this.submitted = this.userForm.value;
  }

  prefill(): void {
    this.userForm.setValue({
      name: 'Anoop', age: '40', city: 'Trivandrum', postalCode: '695001'
    });
  }

  clear(): void {
    this.userForm.reset();
  }
}
That get f() line is worth stealing It lets the template write f['name'].hasError('required') instead of userForm.controls['name'].hasError('required'). Purely for readability — but in a ten-field form it's the difference between a template you can read and one you can't.

import { Injectable } from '@angular/core';
import { Employee } from './models/employee';

@Injectable({
  providedIn: 'root'        // one shared instance for the whole app
})
export class EmployeeService {

  // the data now lives HERE, not in a component
  private employees: Employee[] = [
    { id: 1001, name: 'Anoop',  designation: 'Software Engineer', salary: 25000, status: 'Active',   joinDate: new Date('2022-08-15') },
    { id: 1002, name: 'Ajay',   designation: 'Team Lead',         salary: 45000, status: 'Inactive', joinDate: new Date('2019-03-01') },
    { id: 1003, name: 'Rekha',  designation: 'Tester',            salary: 22000, status: 'Active',   joinDate: new Date('2023-01-10') },
    { id: 1004, name: 'Suresh', designation: 'Architect',         salary: 65000, status: 'Inactive', joinDate: new Date('2015-11-23') }
  ];

  /** every employee */
  getEmployees(): Employee[] {
    return this.employees;
  }

  /** case-insensitive search by name; empty term returns everyone */
  searchByName(term: string): Employee[] {
    if (!term || term.trim() === '') {
      return this.employees;
    }
    const lower = term.toLowerCase();
    return this.employees.filter(e => e.name.toLowerCase().includes(lower));
  }

  /** a single employee, or undefined if the id doesn't exist */
  getById(id: number): Employee | undefined {
    return this.employees.find(e => e.id === id);
  }

  /** how many are currently Active */
  countActive(): number {
    return this.employees.filter(e => e.status === 'Active').length;
  }
}
Expected right now Nothing changes in the browser, and that's correct. You've created the service but no component uses it yet. Confirm the app still compiles cleanly ("✔ Compiled successfully.") before moving on.
Why is the array private? So nobody outside the service can reach in and mutate it. Callers must go through your methods, which means the service stays in control of how data is read and changed. It's the same reasoning behind private fields in a Java class — and it's what will let Task 6 and Session 4 swap the array for HTTP calls without breaking a single caller.

import { Component, OnInit } from '@angular/core';
import { Employee } from '../models/employee';
import { EmployeeService } from '../employee.service';

@Component({
  selector: 'app-employee-list',
  templateUrl: './employee-list.component.html',
  styleUrls: ['./employee-list.component.css']
})
export class EmployeeListComponent implements OnInit {

  employees: Employee[] = [];
  searchTerm: string = '';
  activeCount: number = 0;

  // ① INJECT — Angular hands us the shared instance. No 'new' anywhere.
  constructor(private employeeService: EmployeeService) { }

  // ② INITIALISE — ngOnInit, not the constructor
  ngOnInit(): void {
    this.loadAll();
  }

  loadAll(): void {
    this.employees   = this.employeeService.getEmployees();
    this.activeCount = this.employeeService.countActive();
    this.searchTerm  = '';
  }

  onSearch(): void {
    this.employees = this.employeeService.searchByName(this.searchTerm);
  }

  clearAll(): void {
    this.employees = [];
  }

  toggleStatus(emp: Employee): void {
    emp.status = emp.status === 'Active' ? 'Inactive' : 'Active';
    this.activeCount = this.employeeService.countActive();
  }
}
Read that constructor line again constructor(private employeeService: EmployeeService) { } — the body is empty, yet this.employeeService works everywhere in the class. That's the TypeScript shorthand from Session 1 slide 18: the access modifier on the parameter declares the field and assigns the injected value. This is the single most common line in real Angular code.

import { Injectable } from '@angular/core';
import { HttpClient } from '@angular/common/http';
import { Observable } from 'rxjs';

// the shape of what the API returns (only the fields we care about)
export interface ApiUser {
  id: number;
  name: string;
  username: string;
  email: string;
  phone: string;
}

@Injectable({ providedIn: 'root' })
export class UserService {

  private baseUrl = 'https://jsonplaceholder.typicode.com/users';

  constructor(private http: HttpClient) { }

  getUsers(): Observable<ApiUser[]> {
    return this.http.get<ApiUser[]>(this.baseUrl);
  }

  getUser(id: number): Observable<ApiUser> {
    return this.http.get<ApiUser>(`${this.baseUrl}/${id}`);
  }

  addUser(user: any): Observable<any> {
    return this.http.post<any>(this.baseUrl, user);
  }
}
Why type the response as ApiUser[]? Because then user.name autocompletes and user.nmae is a compile error — the Session 1 interface lesson paying off on live data. Using any[] works but throws away the safety you came to TypeScript for.

  users: ApiUser[] = [];
  loading: boolean = false;
  errorMsg: string = '';

  constructor(private userService: UserService) { }

  ngOnInit(): void {
    this.loadUsers();
  }

  loadUsers(): void {
    this.loading  = true;
    this.errorMsg = '';

    this.userService.getUsers().subscribe({
      next: (data) => {
        this.users   = data;
        this.loading = false;
        console.log('Received ' + data.length + ' users from the API');
      },
      error: (err) => {
        this.errorMsg = 'Could not load users. Check your connection.';
        this.loading  = false;
        console.error('HTTP error:', err);
      }
    });

    // this line runs BEFORE the data arrives — proof that it's asynchronous
    console.log('Request sent. users.length is still ' + this.users.length);
  }
}

Read that order carefully. The line written after subscribe() ran first. That's asynchronous code: subscribe() registers a callback and returns immediately. This is why you can never read this.users on the line after the call.
Test the error path — every real app needs this Change the URL in the service to something invalid, e.g. .../userzzz, and save. The error handler fires: the red message appears and the console shows a 404. Now delete the whole error: block and try again — the app fails silently, and a user would just see an empty list forever. That's why you always handle both next and error. Restore the correct URL and the error block when you're done.
Prove the "lazy Observable" rule Comment out the entire .subscribe({...}) call so only this.userService.getUsers(); remains. Save, reload, and check the Network tab: no request is made at all. No error either. An Observable is a recipe — nothing happens until someone subscribes. Remember this the next time an API call "doesn't fire".
