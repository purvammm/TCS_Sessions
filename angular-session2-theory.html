Concept 1 — the core building block

What is a component?

A component is one self-contained piece of user interface: a navigation bar, a search box, a table, a login form. An Angular application is nothing but components nested inside components. Every single one is made of exactly three parts:

🧠

1 · Class

An ordinary TypeScript class holding properties (the data) and methods (the behaviour). This is the component's brain — it knows nothing about HTML.

🏷️

2 · Metadata

The @Component({...}) decorator above the class. It tells Angular "this class is a component", what tag renders it, and where its template and styles live.

🖼️

3 · Template

The HTML the user sees. It can read the class's properties and call its methods — that link is what data binding provides.

Remove any one of the three and it stops being a component. The class alone is just a class; the HTML alone is just a file; the decorator is the glue that introduces them to Angular.

Ask the batch If a component is a class plus a template, what do you think the decorator's job is? (Look for: it's how the class declares itself to Angular — without it Angular has no idea the class exists, which template belongs to it, or what tag should render it.)

Concept 1 continued

Your app is a tree of components

There is always exactly one root component — AppComponent, rendered by the <app-root> tag in index.html. Everything else lives inside it, or inside one of its children.

Nesting is done purely by placing a component's selector tag inside another component's template.
Why break a page into components at all? Reuse (one status-badge used in five places), isolation (a bug in the table can't break the header), testability (test a small class, not a whole page) and teamwork (two people edit two components without merge conflicts). This is the same reasoning that made you split a Java class into methods — one level up.

Concept 2 — creating one

Generating a component

ng generate component login

# the short form everyone actually types:
ng g c login
CREATE src/app/login/login.component.css (0 bytes) CREATE src/app/login/login.component.html (20 bytes) CREATE src/app/login/login.component.spec.ts (612 bytes) CREATE src/app/login/login.component.ts (296 bytes) UPDATE src/app/app.module.ts (412 bytes)

Read that output carefully — it does two jobs:

  • CREATE — a new folder src/app/login/ containing four files, all correctly named and pre-populated with valid boilerplate.
  • UPDATE — it adds LoginComponent to the declarations array in app.module.ts. This registration step is what makes the component usable anywhere in the app.
Beginner note — always use the CLI If you hand-create the files, you will forget the declarations entry, and Angular will tell you "'app-login' is not a known element" — an error that has cost every Angular beginner at least twenty minutes. The CLI never forgets. Use it every single time.

Concept 2 continued

The four files, and the naming rule

src/app/login/ ├── login.component.css styles — scoped to this component only ├── login.component.html the template ├── login.component.spec.ts unit tests └── login.component.ts the class + @Component decorator
The naming convention — non-negotiable <component-name>.component.<file-type>
Multi-word names use kebab-case in the file name and PascalCase in the class name: ng g c employee-list → files employee-list.component.ts → class EmployeeListComponent → selector app-employee-list.
You typeYou get
ng g c loginFolder login/, class LoginComponent, selector app-login
ng g c employee-listFolder employee-list/, class EmployeeListComponent, selector app-employee-list
ng g c shared/headerSame, nested inside a shared/ folder — how you organise a larger app

The app- prefix on selectors is there so your components can never collide with a real HTML tag or a third-party library's tags. It's configurable, but leave it alone.

Concept 2 · walkthrough 1 of 2

Inside the component class

src/app/login/login.component.ts
import { Component } from '@angular/core';

@Component({
  selector: 'app-login',
  templateUrl: './login.component.html',
  styleUrls: ['./login.component.css']
})
export class LoginComponent {

  uname: string = '';          // bound to the username input
  pass: string = '';           // bound to the password input
  message: string = '';        // shown back to the user

  performLogin(): void {
    if (this.uname === 'admin' && this.pass === 'admin123') {
      this.message = 'Login successful. Welcome, ' + this.uname + '!';
    } else {
      this.message = 'Invalid username or password.';
    }
  }
}
import { Component }
Pulls the Component decorator in from Angular's core package. TypeScript requires you to import anything you use.
selector
The custom tag that renders this component: <app-login></app-login>.
templateUrl
The path to this component's HTML file. Relative to this .ts file.
styleUrls
An array of CSS files — a component may have more than one.
export class
export makes the class visible outside its own file, so app.module.ts can import and declare it. Miss it, and nothing else can see your component.
this.uname
Inside a class method you must write this. to reach a property. Forgetting it is the #1 beginner compile error.

Nine lines, and three different bindings are already at work. Notice how the template never stores anything — it only points at the class:

SyntaxWhat it doesDirection
[(ngModel)]="uname"Keeps the input box and the uname property in syncBoth ways
(click)="performLogin()"Runs the class method when the button is clickedView → class

The separation to appreciate The class contains zero HTML. The template contains zero logic — it doesn't compare passwords, it just calls a method. That clean split is exactly why components are easy to test and easy to change.

Two things worth pausing on

Decorators, and the one-root rule

What a decorator actually is

A decorator is a TypeScript feature: a function, written as @Name({...}), that attaches metadata to the thing below it. It doesn't change your class's behaviour — it describes your class to the framework. If you've used Java annotations like @RestController or @Service, this is the same idea with the same purpose.

Angular decoratorIts Spring Boot cousinSays
@Component@Controller"This class renders a piece of UI"
@Injectable@Service"This class can be injected into others"
@NgModule@Configuration"This class groups and configures a set of things"

The one-root rule

Every Angular app has exactly one root component, and everything else lives inside it. To display a new component you put its selector into a template that is already being rendered:

src/app/app.component.html
<app-header></app-header>

<app-login></app-login>

<app-employee-list></app-employee-list>
Generated a component and nothing appeared? That's expected — and it catches everyone once. ng g c creates and registers a component, but it can't guess where you want it. Nothing renders until you add its selector tag to a template that's already on screen. Start with app.component.html.

Concept 3 — where the HTML lives

Templates, option 1: inline

You can write the HTML directly inside the decorator using the template property instead of templateUrl. Backticks (`) let the string span multiple lines.

import { Component } from '@angular/core';

@Component({
  selector: 'app-root',
  template: `
    <h1>{{ appTitle }}</h1>
    <p>This HTML lives inside the TypeScript file.</p>
  `,
  styles: [`
    h1 { color: #dd0031; }
  `]
})
export class AppComponent {
  appTitle: string = 'My Angular App';
}

Note the plurals: template + styles for inline, versus templateUrl + styleUrls for external files. Mixing them up produces a confusing error, so read carefully.

When inline is genuinely the right choice Only for very small templates — a badge, an icon, a two-line label. Everything sits in one file, which is convenient when there's barely any HTML to hold.

Concept 4 — the heart of Angular

Data binding: the whole picture on one slide

Data binding is the automatic connection between your component class and its template. Change a property and the screen updates. Type in a box and the property updates. You never write code to copy values back and forth — that is Angular's central promise.

🧠 Component class

Properties and methods — the source of truth. Plain TypeScript.

⇄four kinds of binding

🖼️ Template (view)

What the user sees and interacts with. Plain HTML plus Angular syntax.

BindingSyntaxDirectionUse it to…
Interpolation{{ property }}Class → ViewDisplay a value as text
Property[attr]="property"Class → ViewSet an element's property/attribute
Event(event)="method()"View → ClassReact to clicks, typing, submits
Two-way[(ngModel)]="property"Both waysKeep a form field and a property in sync
A memory aid that actually works Square brackets [ ] = data flowing in to the element. Round brackets ( ) = events flowing out of the element. Both together [( )] = data flowing both ways. Angular developers call it "banana in a box" — the banana ( ) goes inside the box [ ]. That silly image will stop you writing ([ngModel]) by mistake.

Binding 1 of 4

Interpolation — {{ }}

One-way binding, class → view. Angular evaluates whatever is inside the double curly braces, converts the result to a string, and drops it into the HTML.

The class

export class HelloComponent {
  name: string = 'Ajay Kishan';
  age: number = 28;
  city: string = 'Chennai';
}

The template

<p>Hello user: <b>{{ name }}</b></p>
<p>Age next year: {{ age + 1 }}</p>
<p>{{ name }} — {{ city }}</p>
<p>{{ name.toUpperCase() }}</p>
http://localhost:4200

Hello user: Ajay Kishan

Age next year: 29

Ajay Kishan — Chennai

AJAY KISHAN

What you may put inside {{ }} Simple expressions only: properties, arithmetic, string concatenation, method calls that just return a value. Not allowed: assignments ({{ x = 5 }}), new, ;, or if/for. And keep it lightweight — Angular re-evaluates every expression on every change-detection pass, so heavy computation belongs in the class, not the template.

Binding 2 of 4

Property binding — [ ]

Also one-way, class → view — but instead of writing text into the page, it sets a property of an HTML element. Square brackets around the property name mean "the right-hand side is an expression, not a literal string."

The class

export class DemoComponent {
  name: string = 'Ajay Kishan';
  imgPath: string = 'assets/logo.png';
  isDisabled: boolean = true;
  rowCount: number = 5;
}

The template

<input type="text" [value]="name">

<img [src]="imgPath" [alt]="name">

<button [disabled]="isDisabled">Save</button>

<textarea [rows]="rowCount"></textarea>
The brackets change everything <button disabled="isDisabled"> — no brackets: the button is disabled by the literal string "isDisabled", which is truthy. Always disabled, whatever your class says.
<button [disabled]="isDisabled"> — brackets: Angular evaluates the property and disables the button only when it's true. This is a real bug people ship.

Property binding also passes data from a parent component into a child component — an important pattern you'll meet as soon as you build nested components.

Bindings 1 vs 2

Interpolation or property binding?

Both are one-way, class → view. Under the hood Angular actually converts interpolation into property binding — so for strings they are genuinely interchangeable:

<!-- these two lines do exactly the same thing -->
<img src="{{ imgPath }}">
<img [src]="imgPath">
SituationUseBecause
Text content inside an element{{ }}It reads naturally: <p>Hello {{ name }}</p>
Mixing text and values together{{ }}Concatenation is effortless: title="Emp {{ id }} - {{ name }}"
A non-string value — boolean, number, object, array[ ]Interpolation stringifies everything. [disabled]="false" works; disabled="{{false}}" passes the string "false", which is truthy.
Passing data to a child component[ ]The child expects a real typed object, not text
The one-line rule Showing text? Use {{ }}. Setting anything that isn't text? Use [ ].

Binding 3 of 4 — part 1

Event binding — the class side

So far data has only flowed class → view. Event binding is the return path: the user does something, and a method on your class runs. Direction: view → class.

status.component.ts
import { Component } from '@angular/core';

@Component({
  selector: 'app-status',
  templateUrl: './status.component.html'
})
export class StatusComponent {

  Status: boolean = true;
  clickCount: number = 0;

  clicked(): void {
    this.Status = !this.Status;      // flip true ⇄ false
    this.clickCount++;
  }

  onKey(event: any): void {
    console.log('You typed: ' + event.target.value);
  }
}

These are ordinary TypeScript methods — nothing Angular-specific about them. The wiring happens entirely in the template, which is why the class stays testable in isolation.

The $event object If a method needs details about what happened — which key, what the input contains, the mouse position — declare a parameter and pass $event from the template. For an input box, event.target.value holds the current text.

Binding 3 of 4 — part 2

Event binding — the template side

status.component.html
<button (click)="clicked()">Click</button>

<p>Status: {{ Status }}</p>
<p>Clicked {{ clickCount }} times</p>

<input (keyup)="onKey($event)" placeholder="type here...">

<div (mouseenter)="clicked()">Hover me</div>
http://localhost:4200

Clicked 3 times

Watch what happens on one click: the method changes Status and clickCount → Angular notices the properties changed → the two interpolations re-render. Event binding in, interpolation out — that round trip is a complete interactive feature, and you wrote no DOM code at all.

EventFires when
(click)The element is clicked — by far the most common
(keyup) / (keydown)A key is released / pressed
(change)An input loses focus after its value changed
(input)Every keystroke in a text field
(submit)A form is submitted (Session 3)
(mouseenter) / (mouseleave)The pointer enters / leaves the element

Binding 4 of 4 — part 1

Two-way binding with ngModel

Two-way binding is not a new mechanism — it is property binding and event binding combined into one piece of syntax. These two blocks behave identically:

The long way — two bindings

<input
  [value]="userName"
  (input)="userName = $event.target.value">

Data in via [value], data out via (input). Verbose and easy to get wrong.

The Angular way — one binding

<input [(ngModel)]="userName">

Same behaviour: typing updates the property, and changing the property updates the box. Banana in a box.

⚠️ Beginner note — the single most common Angular failure ngModel lives in FormsModule, which is not imported by default. Forget it and the input simply does nothing — often with no visible error at all. If two-way binding isn't working, check this first, before anything else.
src/app/app.module.ts
import { FormsModule } from '@angular/forms';     // ① import it

@NgModule({
  declarations: [ AppComponent, LoginComponent ],
  imports: [
    BrowserModule,
    FormsModule                                    // ② list it here
  ],
  bootstrap: [ AppComponent ]
})
export class AppModule { }

Both steps are required. Adding the import line at the top without adding FormsModule to the imports array changes nothing.

Binding 4 of 4 — part 2

Two-way binding in full

hello.component.ts

export class HelloComponent {

  private _userName: string = '';

  get userName(): string {
    return this._userName;
  }

  set userName(value: string) {
    console.log('changed to: ' + value);
    this._userName = value;
  }
}

hello.component.html

<label>Your name:</label>
<input [(ngModel)]="userName">

<p>Hello, {{ userName }}!</p>

<p>Characters: {{ userName.length }}</p>
http://localhost:4200

Your name: Purvam

Hello, Purvam!

Characters: 6

Type a single letter and three things update at once — the property, the greeting and the character count — with no event handler written by you.

Why a getter/setter pair here? A plain property (userName: string = '') works perfectly and is what you'd normally write. The getter/setter version is shown because it proves the two-way part: open the browser console and you'll see "changed to: …" logged on every keystroke — the view genuinely writing back into the class.

Concept 5 — directives

What is a directive?

A directive is an instruction you place in your HTML that tells Angular to change that element — add it, remove it, restyle it. Components are technically directives that come with their own template; the ones on this slide are the two "plain" kinds.

🏗️

Structural directives

Change the structure of the DOM — they add and remove elements entirely. Always prefixed with an asterisk *.

*ngIf · *ngFor · *ngSwitch

🎨

Attribute directives

Change the appearance or behaviour of an element that already exists. No asterisk; they use property-binding brackets.

ngClass · ngStyle

Why the asterisk? The * is shorthand for something bigger: Angular wraps that element in an invisible <ng-template> and stamps it out (or doesn't) as needed. You don't need the details — but you do need to remember the asterisk. Writing ngIf without it is a silent no-op: no error, and your element simply always shows.

Structural directive 1 of 3

*ngIf — show it or don't

<!-- renders only when the expression is truthy -->
<div *ngIf="employee">
  <p>Name: {{ employee.name }}</p>
</div>

<p *ngIf="employees.length === 0">No employees found.</p>

<p *ngIf="isLoggedIn">Welcome back!</p>

With an else branch

<div *ngIf="employees.length > 0; else emptyState">
  <p>Showing {{ employees.length }} employees.</p>
</div>

<ng-template #emptyState>
  <p>No employees to display. Add one to get started.</p>
</ng-template>
Removed, not hidden — and that matters When *ngIf is false the element is not in the DOM at all. Inspect the page and it's genuinely absent. That's different from CSS display: none, which keeps the element (and its cost) around. *ngIf is the right tool when the content is expensive or shouldn't exist yet.
Why *ngIf saves you from crashes <p>{{ employee.name }}</p> throws when employee is still undefined — which is exactly the case while an API call is in flight. Wrapping it in *ngIf="employee" means Angular doesn't even evaluate the inside until there's data. You will rely on this constantly in Session 3.

Structural directive 2 of 3

*ngFor — repeat for each item

The workhorse of every real application. Put it on the element you want repeated — for a table, that's the <tr>, not the <table>.

<li *ngFor="let emp of employees">
  {{ emp.name }} — {{ emp.designation }}
</li>

With the index, and other useful locals

<tr *ngFor="let emp of employees; let i = index">
  <td>{{ i + 1 }}</td>
  <td>{{ emp.name }}</td>
</tr>

<!-- also available: first, last, even, odd -->
<tr *ngFor="let emp of employees; let isEven = even"
    [ngClass]="{'striped': isEven}">
  <td>{{ emp.name }}</td>
</tr>
let emp
A local variable naming the current item. Only exists inside this element. Call it whatever reads best.
of employees
of — the array to iterate, exactly like TypeScript's for...of from Session 1.
let i = index
The zero-based position. Use i + 1 for a human-friendly serial number.
Two mistakes to avoid 1. Writing *ngFor="let emp in employees" — in is wrong here and gives you nothing useful. It's always of.
2. Putting *ngFor on the <table> instead of the <tr> — you'll get four whole tables instead of four rows.

Structural directive 3 of 3

*ngSwitch — pick one of many

When you'd otherwise chain four *ngIfs over the same variable, use ngSwitch. It reads better and evaluates the expression once.

<div [ngSwitch]="employee.department">

  <p *ngSwitchCase="'IT'">💻 Information Technology</p>
  <p *ngSwitchCase="'HR'">👥 Human Resources</p>
  <p *ngSwitchCase="'FIN'">💰 Finance</p>
  <p *ngSwitchDefault>🏢 General</p>

</div>
PartNotes
[ngSwitch]On the container. Square brackets, no asterisk — it's a property binding.
*ngSwitchCaseOn each option. Asterisk required. String values need inner quotes: "'IT'".
*ngSwitchDefaultThe fallback when nothing matched. Optional but almost always worth adding.
The quote trap *ngSwitchCase="IT" looks right and never matches — Angular reads IT as a property of your component, finds nothing, and compares against undefined. String literals need the inner single quotes: *ngSwitchCase="'IT'".

Concept 6 — attribute directives

ngClass & ngStyle

ngClass — apply CSS classes conditionally

<tr *ngFor="let emp of employees"
    [ngClass]="{
      'text-success': emp.status === 'Active',
      'text-danger':  emp.status === 'Inactive'
    }">
  <td>{{ emp.name }}</td>
  <td>{{ emp.status }}</td>
</tr>

You pass an object: each key is a class name, each value is a condition. When the condition is true the class is applied; when it flips to false Angular removes it. Multiple classes can be active at once.

ngStyle — apply inline styles conditionally

<tr *ngFor="let emp of employees"
    [ngStyle]="{
      'background-color': emp.status === 'Active' ? '#eefcf1' : '#fff0ef',
      'font-weight': emp.salary > 40000 ? 'bold' : 'normal'
    }">
  <td>{{ emp.name }}</td>
</tr>

Choosing between them

ngClass vs ngStyle

✅ Prefer ngClass

/* employee-list.component.css */
.text-success {
  background: #eefcf1;
  color: #1a9e34;
  font-weight: 600;
}
[ngClass]="{'text-success': emp.status === 'Active'}"

⚙️ ngStyle when it's truly dynamic

<!-- a width you can't know in advance -->
<div [ngStyle]="{'width': percent + '%'}"></div>

<!-- a colour that came from the API -->
<span [ngStyle]="{'color': item.hexColour}"></span>
The rule of thumb Reach for ngClass by default — it keeps styling in your stylesheet where it belongs. Use ngStyle only when the value genuinely can't be expressed as a fixed class, because it's calculated at runtime.

Concept 7 — pipes

Pipes — transform what's displayed

A pipe transforms a value on its way to the screen, without changing the underlying property. Syntax is the pipe character |, which will look familiar if you've used a Unix shell.

<p>{{ name | uppercase }}</p>          <!-- ANOOP -->
<p>{{ name | lowercase }}</p>          <!-- anoop -->
<p>{{ salary | currency:'INR' }}</p>   <!-- ₹25,000.00 -->
<p>{{ joinDate | date:'dd/MM/yyyy' }}</p>  <!-- 15/08/2024 -->
<p>{{ ratio | percent }}</p>           <!-- 75% -->
<p>{{ emp | json }}</p>                <!-- the whole object, formatted -->

<!-- pipes chain, left to right -->
<p>{{ name | uppercase | slice:0:3 }}</p>  <!-- ANO -->
PipeDoesParameters (after a colon)
uppercase / lowercaseChanges casenone
dateFormats a date'short', 'dd/MM/yyyy', 'fullDate'
currencyAdds a currency symbol & grouping'INR', 'USD'
numberControls decimal places'1.2-2'
percentShows a fraction as a percentageoptional digits
sliceCuts a string or array0:3
jsonDumps an object — brilliant for debuggingnone
The key property of a pipe It changes the display only. {{ name | uppercase }} shows "ANOOP" while name in your class is still "Anoop". Your data stays clean; the presentation adapts. And {{ someObject | json }} is the fastest debugging tool in Angular — remember it.

  • ngModel needs FormsModule in app.module.ts. Check this first when two-way binding "does nothing".
  • *ngIf adds/removes elements, *ngFor repeats them, *ngSwitch picks one — all with an asterisk.
  • ngClass and ngStyle restyle existing elements conditionally — no asterisk, square brackets.
  • Pipes transform the display without touching the data, and | json is your debugging friend.
Now go and build it The lab has you generate real components, build a working login form with two-way binding, render the employee table with *ngFor, colour its rows with ngClass, and finish with a pipe. Open angular-session2-lab.html and work down it.
