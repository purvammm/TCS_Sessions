Concept 1 — the single most important idea in Angular

What is a component?

A component is one self-contained piece of user interface: its own logic, its own markup, its own styling — bundled together and reusable.

Think about any application you use. A dashboard is not one big thing; it is a header, a sidebar, a set of summary cards, a chart and a table. Each of those is independent. Each could appear on another page unchanged. Each of those is a component.

📦

Self-contained

Everything the piece needs lives together in one folder. You can understand it without reading the rest of the app.

♻️

Reusable

Write a employee-card once, then use it on the list page, the search page and the dashboard.

🔒

Isolated

Its CSS cannot leak out and break another component. Its data is its own.

🧩

Composable

Components nest inside components. That nesting is how a whole page gets built.

Analogy A component is a LEGO brick. Each brick is complete in itself, and you build anything by connecting bricks — you never carve a castle from one solid block. The old way of building web pages was carving from one block; components are the bricks.
The Java parallel You already do this on the backend. You don't write one enormous Main class — you write a Controller, a Service, a Repository, each with one job. A component is that same discipline, applied to the screen.

Concept 1 continued

The three parts of every component

Every component in every Angular project is the same three things. Once you have seen it once, you have seen every component you will ever meet.

1 · The class employee-list.component.ts — the brain. Your data and your logic: fields to hold values, methods to respond to clicks.
2 · The template employee-list.component.html — the face. The HTML the user actually sees, which can read from the class.
3 · The styles employee-list.component.css — the clothes. CSS that applies to this component only and cannot leak elsewhere.
4 · The metadata The @Component({ ... }) decorator sitting on top of the class — it is the label that ties the other three together and tells Angular the HTML tag name.
Read it as a sentence "This class holds the data. That HTML file displays it. That CSS file styles it. And this decorator tells Angular that all three belong together, and that they appear wherever the tag <app-employee-list> is written."
There is a fourth file, and you can ignore it The CLI also creates employee-list.component.spec.ts — a starter file for unit tests. Testing is a genuinely valuable topic and it is out of scope for these four sessions. Leave the file alone; it does not affect your app.

Concept 1 continued

Your app is a tree of components

There is always exactly one component at the top — AppComponent, the one Session 1 traced from index.html. Every other component hangs beneath it.

app-root

│
app-header

app-employee-list

app-footer

│

app-search-box

Parents hold children. Children can hold their own children. There is no depth limit.
Two rules that follow from the tree, and they matter 1. Data flows down — a parent hands values to a child. That is @Input.
2. Events flow up — a child tells its parent something happened. That is @Output.
Because the flow is always one direction per mechanism, you can always trace where a change came from. This is the exact problem AngularJS 1.x had, and it is why Angular 2 was rewritten.

Concept 1 continued — the part that clicks

How a component actually gets on screen

This is the mechanism, and it is simpler than people expect. A component declares a selector — a made-up HTML tag name. Write that tag anywhere, and Angular puts the component there.

1 · The component declares its tag

@Component({
  selector: 'app-employee-list',
  ...
})
export class EmployeeListComponent { }

2 · Any template can then use that tag

<h1>My Directory</h1>

<app-employee-list></app-employee-list>

<p>Footer text</p>

Angular finds <app-employee-list>, looks up the component whose selector matches, renders that component's template, and drops the result in at exactly that spot.

Analogy The selector is a picture frame hook on the wall. You put the hook where you want the picture. Angular hangs the picture on it.
Why app- at the front of every selector? It is a prefix, added by the CLI, to guarantee your tag names never collide with real HTML tags or with a third-party library's components. Imagine naming a component button — chaos. Keep the prefix. And note that these tags are never self-closing: write <app-x></app-x>, not <app-x />, which silently fails.

Concept 2 — let the tool do the work

Generating a component

You could create the files by hand. You should not. One command does it correctly, every time:

ng generate component employee-list

# the short form everyone actually types
ng g c employee-list
what the CLI prints
CREATE src/app/employee-list/employee-list.component.css (0 bytes)
CREATE src/app/employee-list/employee-list.component.html (28 bytes)
CREATE src/app/employee-list/employee-list.component.spec.ts (595 bytes)
CREATE src/app/employee-list/employee-list.component.ts (222 bytes)
UPDATE src/app/app.module.ts (412 bytes)
Read that last line again — it is the whole reason to use the CLI UPDATE src/app/app.module.ts. The CLI did not just make files; it registered your component in the module's declarations list. Angular refuses to render a component it has not been told about, and hand-created components are where beginners lose an hour to "'app-employee-list' is not a known element".
Two things to get right 1. Run it from the project folder (the one containing angular.json), in a second terminal — leave ng serve running in the first.
2. Name it in lowercase-with-hyphens: employee-list, not EmployeeList or employeeList. The CLI converts it to the right form everywhere.

Concept 2 continued

The four files, and the naming rule

src/app/employee-list/ ├── employee-list.component.ts ★ the class — your logic ├── employee-list.component.html ★ the template — what's on screen ├── employee-list.component.css ★ the styles — this component only └── employee-list.component.spec.ts tests — ignore for this series

Notice the pattern: one folder per component, and every file named <name>.component.<ext>. This is not a suggestion — it is the convention every Angular project on earth follows, which is why you can open a stranger's repository and navigate it immediately.

The naming rule you must be able to translate

Learn to read this both ways If you see <app-customer-form> in a template, you know instantly that the class is CustomerFormComponent and it lives in src/app/customer-form/customer-form.component.ts. That translation, done automatically in your head, is most of what "knowing your way around an Angular project" means.

The error this prevents — and you will still meet it 'app-employee-list' is not a known element means one of exactly three things: (a) the component isn't in declarations, (b) you spelled the tag differently from the selector, or (c) you created the files by hand. Check them in that order and you will find it in seconds.

Concept 2 continued

Inside the component class

src/app/employee-list/employee-list.component.ts
import { Component } from '@angular/core';
import { Employee } from '../models/employee';

@Component({
  selector: 'app-employee-list',
  templateUrl: './employee-list.component.html',
  styleUrls: ['./employee-list.component.css']
})
export class EmployeeListComponent {

  // ── FIELDS: data the template can display ──────────────
  heading = 'Employee Directory';
  showTable = true;

  employees: Employee[] = [
    { id: 1001, name: 'Anoop', designation: 'Software Engineer', salary: 25000, status: 'Active' },
    { id: 1002, name: 'Ajay',  designation: 'Team Lead',         salary: 45000, status: 'Inactive' }
  ];

  // ── METHODS: things the template can call ──────────────
  toggleTable(): void {
    this.showTable = !this.showTable;
  }

  getActiveCount(): number {
    return this.employees.filter(e => e.status === 'Active').length;
  }
}
The mental model for the rest of this series A component class is a box of values and behaviours that its own template is allowed to read. Put a field on the class, and the template can display it. Put a method on the class, and the template can call it on a click. That is the entire relationship — and every one of today's four bindings is just a different way of crossing that line.

Concept 2 continued

The @Component decorator, line by line

A decorator is extra information attached to a class. It does not change what the class does — it tells the framework how to treat it. If you have written @RestController or @Service in Java, this is precisely the same idea.

@Component({
  selector:    'app-employee-list',
  templateUrl: './employee-list.component.html',
  styleUrls:   ['./employee-list.component.css']
})
export class EmployeeListComponent { }
PropertyMeaning
selectorThe HTML tag name that renders this component. Write <app-employee-list></app-employee-list> and this component appears there.
templateUrlThe path to the HTML file. The ./ means "in the same folder as this .ts file".
styleUrlsAn array of CSS file paths — a component may have several. Newer CLI versions generate styleUrl (singular, no array) instead; both work.
Three rules about decorators 1. It sits immediately above the class — no blank line, no other code between.
2. The comma-separated properties go inside ({ ... }) — note it is braces inside brackets, which is the single most common syntax error here.
3. One class gets one @Component. If you need a second component, make a second file.
A clarification, since people coming from React ask An Angular template may have several root-level elements — you do not need to wrap everything in a single outer <div>. Angular is happy with a template that starts with three sibling <p> tags.

Concept 2 continued

Two ways to write a template

Option 1 — template (inline)

@Component({
  selector: 'app-hello',
  template: `
    <h2>Hello!</h2>
    <p>{{ message }}</p>
  `
})
export class HelloComponent {
  message = 'Inline template';
}

Everything in one file. Fine for a two-line component.

Option 2 — templateUrl (separate file)

@Component({
  selector: 'app-hello',
  templateUrl: './hello.component.html'
})
export class HelloComponent {
  message = 'External template';
}

HTML in its own file. This is what the CLI generates and what you should use.

If you write an inline template, you must use backticks Not 'single' and not "double" quotes — backticks (`, the key above Tab on most keyboards). Backticks are the only string form in JavaScript that may span multiple lines. Using ordinary quotes for a multi-line template is a classic beginner error with a confusing error message.
Which should you use? Almost always templateUrl Separate files give you HTML syntax highlighting, autocomplete, easier diffs in code review, and they stop your .ts file becoming a wall of markup. Use template only for something genuinely tiny. The same choice exists for styles: styles: ['...'] inline versus styleUrls: ['...'] in a file.

Concept 2 continued — a genuinely great feature

Component styles cannot leak out

This is worth a slide of its own because it solves a problem that has plagued web development for twenty years. Put this in one component's CSS file:

employee-list.component.css
h2    { color: red; }
table { width: 100%; border-collapse: collapse; }

That h2 rule affects only the h2 tags inside this component's template. An h2 in the header component, or in the footer, or anywhere else in the app, is completely untouched.

Traditional CSS

  • Every rule is global
  • Two developers both style .card and break each other
  • You defend yourself with long names like .employee-list-table-header
  • Nobody dares delete an old rule
→

Angular component CSS

  • Rules are scoped automatically
  • h2 here cannot affect h2 there
  • Short, obvious selectors are safe again
  • Delete a component, its CSS goes with it
How it works, briefly Angular adds a unique attribute to this component's elements (something like _ngcontent-abc-1) and quietly rewrites your CSS selectors to require it. Inspect an element in your browser's dev tools and you can see it. The feature is called view encapsulation, and it is on by default.
So where do global styles go? src/styles.css — that file is global, and it is where a CSS framework like Bootstrap would be imported, or where you would set the app's font.

Concept 2 continued — building the tree for real

Nesting: putting a child inside a parent

You have components. Now assemble them. This is three lines of work, and it is how every Angular page is composed.

src/app/app.component.html — the parent
<app-header></app-header>

<app-employee-list></app-employee-list>

<app-footer></app-footer>

That is the whole root template. AppComponent now contains almost no markup of its own — it is a layout, arranging three children. This is very common and very healthy: top-level components arrange, leaf components display.

http://localhost:4200

app-employee-list → the table of employees

Nothing appeared? Check these three, in order 1. Is the tag spelled exactly like the selector? 2. Is the component in declarations in app.module.ts? 3. Did you write a closing tag — <app-header></app-header> and not <app-header />? That third one fails silently, which makes it the nastiest.
Ask the batch If the employee table also needs to appear on a "reports" page later, how much work is that now? (One line. That is the payoff for having built it as a component rather than as markup inside a page.)

Concept 3 — today's centrepiece

Data binding: the whole picture on one slide

Data binding is the connection between your component class and your template. There are four kinds, and the only thing that really distinguishes them is which direction the information travels. Get the direction right and the syntax follows.

KindSyntaxDirectionUse it when
Interpolation {{ value }} Class → Template You want to display text on the page.
Property binding [property]="value" Class → Template You want to set an HTML attribute from your data.
Event binding (event)="method()" Template → Class You want to react to a click or other user action.
Two-way binding [(ngModel)]="value" Class ⇄ Template You have a form input that must stay in sync both ways.
A memory trick for the punctuation Square brackets [ ] look like a box being filled → data flowing in, from class to template. Round brackets ( ) look like a mouth shouting → an event flowing out, from template to class. And [( )] is both at once — hence its nickname, "banana in a box": the banana ( ) inside the box [ ].
Why this beats what you did before In a JSP you print a value into HTML once, and it is frozen. In Angular the binding is live: change the field in your class, and the screen updates by itself. You never write code to "refresh the display" — that is Angular's entire job.

Binding 1 continued — the rules, and the traps

What you can and cannot put inside {{ }}

✅ Allowed

{{ title }}
{{ user.name }}
{{ employees.length }}
{{ salary * 12 }}
{{ firstName + ' ' + lastName }}
{{ getTotal() }}
{{ isActive ? 'Yes' : 'No' }}
{{ employees[0].name }}
{{ user?.address?.city }}

❌ Not allowed

{{ let x = 5 }}
{{ if (a) { } }}
{{ for (...) { } }}
{{ count++ }}
{{ salary = 30000 }}
{{ new Date() }}
{{ window.alert('hi') }}
{{ myVar ?? doSomething() }}
{{ console.log(x) }}
The one rule that covers all of it A template expression must produce a value and must have no side effects. You may read; you may not change. So a + b is fine, but a = b and count++ are not. Declarations, loops and if statements are out too — Angular gives you *ngIf and *ngFor for those, which is exactly why they exist.
Two traps worth knowing now 1. A misspelled field shows nothing at all. {{ titel }} renders an empty string — no error, no warning. When text mysteriously fails to appear, check your spelling and capitalisation first.
2. Don't put heavy work in a method call. {{ getTotal() }} is re-run every time Angular checks the screen, which is often. Fine for adding four numbers; bad for looping ten thousand rows.

Binding 2 of 4 · Class → Template

Property binding — [ ]

Interpolation puts text between tags. Property binding sets a value on a tag — its src, its disabled, its value. Wrap the property name in square brackets and the right-hand side becomes an expression rather than a literal string.

The class

export class AppComponent {
  imageUrl = 'assets/logo.png';
  isSaveDisabled = true;
  inputValue = 'Anoop';
  rowCount = 4;
  linkTarget = 'https://angular.dev';
}

The template

<img [src]="imageUrl">

<button [disabled]="isSaveDisabled">
  Save
</button>

<input [value]="inputValue">

<a [href]="linkTarget">Docs</a>

<button [disabled]="rowCount === 0">
  Export
</button>
The critical detail — brackets change the meaning entirely <img src="imageUrl"> looks for a file literally called "imageUrl" and gives you a broken image.
<img [src]="imageUrl"> reads the field named imageUrl from your class and uses its value.
Without brackets it is a plain string. With brackets it is an expression. That single distinction accounts for a large share of "why is my image broken" questions.
And a common variant of the same mistake [disabled]="true" — brackets, so true is the boolean. Correct.
disabled="false" — no brackets, so "false" is a non-empty string, which HTML treats as "yes, disabled". The button stays disabled and you are baffled. With booleans, always use brackets.

Interpolation or property binding?

They both send data the same direction, so how do you choose? Ask what you are filling in.

Binding 3 of 4 · Template → Class

Event binding — ( )

The first binding that goes the other way. Round brackets around an event name say: "when this happens in the template, run that method on the class."

The class — the methods

export class LoginComponent {
  message = '';
  clickCount = 0;

  onLogin(): void {
    this.message = 'Login clicked!';
  }

  increment(): void {
    this.clickCount++;
  }

  greet(who: string): void {
    this.message = 'Hello, ' + who;
  }
}

The template — the wiring

<button (click)="onLogin()">
  Login
</button>

<button (click)="increment()">
  Clicked {{ clickCount }} times
</button>

<button (click)="greet('Anoop')">
  Greet Anoop
</button>

<p>{{ message }}</p>
Watch what happens after a click — this is the payoff onLogin() changes a field. It does not touch the page. Yet the <p>{{ message }}</p> updates immediately, because interpolation is a live binding. You change data; Angular updates the screen. You will never write document.getElementById(...) again.

Events you will actually use

EventFires when
(click)The element is clicked. By far the most common.
(input)The user types in a text box — on every keystroke.
(change)A field's value is committed — on leaving the field, or on selecting from a dropdown.
(submit)A form is submitted. Used in Session 3.
(keyup)A key is released. (keyup.enter) narrows it to just the Enter key.
(mouseenter)The pointer moves over the element.
Don't forget the parentheses on the method (click)="onLogin()" calls the method. (click)="onLogin" merely names it and does nothing at all — silently. If a button appears dead, check for the missing ().

Binding 3 continued

$event — getting data out of the event

Often you don't just want to know that something happened — you want to know what the user typed. Angular hands you the event object under the special name $event.

the template
<input (input)="onType($event)" placeholder="Type something">
<p>You typed: {{ typed }}</p>
the class
typed = '';

onType(event: Event): void {
  // event.target is the input element; .value is what's in it
  this.typed = (event.target as HTMLInputElement).value;
}
$event
Angular's name for the event object. Only meaningful inside an event binding.
event.target
The element the event came from — here, the <input>.
as HTMLInputElement
A type assertion: "trust me, this is an input element, so it has a .value." Needed because TypeScript only knows it is some element.
There is a much nicer way, and it's on the next slide That as HTMLInputElement cast is clumsy — and for form inputs you will almost never need it, because two-way binding does this job in one clean line. Learn $event because you will meet it (and you need it for non-form events), but reach for [(ngModel)] first.
A useful shortcut worth remembering <input (keyup.enter)="search($event)"> — the .enter part means "only when the Enter key is released". Angular supports this for any key, e.g. (keyup.escape). It saves you writing an if to check which key it was.

Binding 4 of 4 · Class ⇄ Template

Two-way binding with [(ngModel)]

A text box has a genuine two-directional need: the class should be able to set its contents, and the class should learn when the user types. Doing that with the bindings you already know takes two attributes:

<!-- the manual way — property binding IN, event binding OUT -->
<input [value]="empName" (input)="empName = getValue($event)">

That works, and it is verbose. [(ngModel)] collapses both directions into one:

<!-- the same thing, in one attribute -->
<input [(ngModel)]="empName">

Component class

empName = 'Anoop';

The single source of truth.

⇄[(ngModel)]
both ways, always

The input on screen

Shows Anoop, and reports every keystroke back.

Never out of step.

Why it's called "banana in a box" [( )] — the round banana ( ) sits inside the square box [ ]. It is a silly name that works: box on the outside, banana on the inside. Get the order wrong and you get ([ngModel]), which is an error people stare at for a long time.

Binding 4 continued — the error everyone hits exactly once

ngModel needs FormsModule

Write [(ngModel)] in a fresh project and you get this, and it stops the build:

the error in your terminal
Error: Can't bind to 'ngModel' since it isn't a known property of 'input'.

The message is genuinely confusing, because nothing looks wrong with your line. The real cause: ngModel is not part of Angular's core — it lives in a separate feature module, and you have to ask for it.

src/app/app.module.ts — the two lines to add
import { NgModule } from '@angular/core';
import { BrowserModule } from '@angular/platform-browser';
import { FormsModule } from '@angular/forms';        // ← 1. import it
import { AppComponent } from './app.component';

@NgModule({
  declarations: [ AppComponent ],
  imports: [
    BrowserModule,
    FormsModule                                       // ← 2. list it here
  ],
  providers: [],
  bootstrap: [ AppComponent ]
})
export class AppModule { }
Remember the pattern, not just this instance "Can't bind to X since it isn't a known property" almost always means a module is missing from imports. You will meet the same shape of error twice more: HttpClientModule for HTTP in Session 3, and RouterModule for routing in Session 4. Recognise the pattern once and you will fix all three in seconds.
Also: imports, not declarations FormsModule is somebody else's module, so it goes in imports. declarations is only ever for your own components, directives and pipes. Putting a module in declarations produces a long, unhelpful error.

Binding 4 continued — a complete working example

Two-way binding in full: a login form

login.component.ts

export class LoginComponent {
  username = '';
  password = '';
  message  = '';

  onLogin(): void {
    if (this.username === 'admin' &&
        this.password === 'admin123') {
      this.message = '✅ Login successful!';
    } else {
      this.message = '❌ Invalid credentials';
    }
  }

  onClear(): void {
    this.username = '';
    this.password = '';
    this.message  = '';
  }
}

login.component.html

<h2>Login</h2>

<label>Username:</label>
<input [(ngModel)]="username"
       name="username">

<label>Password:</label>
<input type="password"
       [(ngModel)]="password"
       name="password">

<button (click)="onLogin()"
        [disabled]="!username || !password">
  Login
</button>

<button (click)="onClear()">Clear</button>

<p>{{ message }}</p>

<p class="hint">
  Live preview: {{ username }}
</p>
Count the bindings in that template — all four are there [(ngModel)] two-way on both inputs · (click) events on both buttons · [disabled] property binding that greys out Login until both fields have content · {{ message }} and {{ username }} interpolation. That is the whole of today's Concept 3, in one screen of markup.
Note the name attribute on each input When an ngModel input sits inside a <form> tag, Angular requires a name. Adding it always is a harmless habit that avoids a puzzling error later, and Session 3 explains what Angular does with it.

Concept 4 — making the page change shape

What is a directive?

A directive is an instruction you attach to an HTML element to change its behaviour or appearance.

Bindings let you push data into a fixed page. Directives let you change the page itself — hide a section, repeat a row four times, swap a colour. There are three kinds:

1 · Structural Add or remove elements from the page. Always written with a leading asterisk: *ngIf, *ngFor, *ngSwitchCase.
2 · Attribute Change the look or behaviour of an element that is already there. No asterisk: ngClass, ngStyle, ngModel.
3 · Components Technically a component is a directive — one that comes with its own template. Interesting trivia; changes nothing about how you use them.
The asterisk is the whole distinction — memorise this Asterisk = the element may not exist at all. *ngIf and *ngFor add and remove elements from the page.
No asterisk = the element definitely exists, we're just changing it. ngClass and ngStyle restyle something already on screen.
Forgetting the asterisk on *ngIf is the most common directive mistake there is — and it fails silently, showing the element always.

Structural directive 1 of 3

*ngIf — show it, or don't

Put *ngIf on an element and it appears only when the condition is true.

The class

export class AppComponent {
  isLoggedIn = false;
  employees = [];
  errorMessage = '';

  toggle(): void {
    this.isLoggedIn = !this.isLoggedIn;
  }
}

The template

<button (click)="toggle()">
  Toggle
</button>

<p *ngIf="isLoggedIn">
  Welcome back!
</p>

<p *ngIf="employees.length === 0">
  No employees found.
</p>

<div *ngIf="errorMessage">
  {{ errorMessage }}
</div>
It removes the element — it does not merely hide it When isLoggedIn is false, that <p> is not in the page at all. Inspect it in your browser's dev tools and there is nothing there — not an invisible element, nothing. That matters: a removed element costs no memory, runs no code, and cannot be read by someone poking at the page. It is genuinely different from CSS's display: none.
The mistake to expect <p ngIf="isLoggedIn"> — no asterisk. Angular treats it as a meaningless attribute, ignores it, and the paragraph shows always. No error is reported. If a section refuses to hide, look for the missing * first.

Structural directive 1 continued

*ngIf with an else

Often you want one thing or the other. Angular does this with a template reference — a named block of markup, marked with #.

<div *ngIf="isLoggedIn; else loginPrompt">
  <h3>Welcome back, {{ username }}!</h3>
  <button (click)="logout()">Log out</button>
</div>

<ng-template #loginPrompt>
  <h3>Please log in</h3>
  <button (click)="showLogin()">Log in</button>
</ng-template>
; else loginPrompt
Note the semicolon, then the word else, then a name. The name has no # here.
<ng-template>
A container that renders nothing by itself. It only exists to hold markup for something else to use.
#loginPrompt
Gives the template a name. The # is required here, at the definition.
Where you'll really need this — Session 3 The classic use is a loading state: "show the table if the data has arrived, otherwise show 'Loading…'". That is exactly what you will write in Session 3 when the data comes from a server and takes a moment to appear.
Two easy syntax errors here A comma instead of a semicolon (*ngIf="x, else y") fails. And writing else #loginPrompt with a hash fails too — the # belongs only on the <ng-template>.

Structural directive 2 of 3 — the one you'll use most

*ngFor — repeat for each item

This is the directive that fixes Session 1's annoyance. Instead of writing out employees[0], employees[1], employees[2]… you write the markup once and Angular repeats it for every item.

Session 1's approach

<p>{{ employees[0].name }}</p>
<p>{{ employees[1].name }}</p>
<p>{{ employees[2].name }}</p>
<p>{{ employees[3].name }}</p>

Breaks the moment there are five employees.

→

With *ngFor

<p *ngFor="let emp of employees">
  {{ emp.name }}
</p>

Works for four, for four hundred, for none.

Reading the syntax

*ngFor="let emp of employees"
"For each item in employees, call it emp, and repeat this element once per item."
let emp
A name you invent. It exists only inside this element. emp, e, employee — all fine.
of employees
The array on your class. It is of, exactly like for...of in TypeScript — never in.
Put the *ngFor on the element you want repeated On a table row, it goes on the <tr> — not on the <table> (which would give you four separate tables) and not on the <td> (which would repeat one cell). Ask yourself: which single tag do I want four copies of? That is where the asterisk goes.

Structural directive 2 continued

*ngFor extras: the index, and trackBy

Getting the row number with index

<tr *ngFor="let emp of employees; let i = index">
  <td>{{ i + 1 }}</td>          <!-- 1, 2, 3, 4 — humans count from 1 -->
  <td>{{ emp.name }}</td>
</tr>

Note the semicolon before let i = index. Angular also gives you first, last, even and odd the same way — useful for striping rows:

<tr *ngFor="let emp of employees; let isEven = even"
    [class.striped]="isEven">
  <td>{{ emp.name }}</td>
</tr>

trackBy — a performance habit worth forming early

<!-- the template -->
<tr *ngFor="let emp of employees; trackBy: trackById">
  <td>{{ emp.name }}</td>
</tr>
// the class
trackById(index: number, emp: Employee): number {
  return emp.id;             // "identify each row by its id"
}
What trackBy actually saves you Without it, when the array changes Angular cannot tell which items are the same ones, so it destroys and rebuilds every row. With it, Angular matches rows by id and touches only what genuinely changed. On four rows you will not notice. On a five-hundred-row table it is the difference between instant and sluggish — and it also stops odd bugs where a half-typed input loses its contents when the list refreshes.

Structural directive 3 of 3

*ngSwitch — pick one of many

When you have three or more mutually exclusive options, a chain of *ngIfs gets ugly. *ngSwitch is the tidy version — and if you know Java's switch, you already know it.

<div [ngSwitch]="employee.designation">

  <span *ngSwitchCase="'Architect'">🏛️ Senior technical leadership</span>
  <span *ngSwitchCase="'Team Lead'">👥 Manages a team</span>
  <span *ngSwitchCase="'Tester'">🔍 Quality assurance</span>
  <span *ngSwitchDefault>💻 Individual contributor</span>

</div>
PartNote
[ngSwitch]On the container. Square brackets, no asterisk — the container always exists.
*ngSwitchCaseOn each option. With an asterisk — these come and go.
*ngSwitchDefaultThe fallback when nothing matched. Optional, but include it.
The quotes-inside-quotes detail that catches everyone *ngSwitchCase="'Architect'" — double quotes outside, single quotes inside. The value is a template expression, so a literal string needs its own quotes. Writing *ngSwitchCase="Architect" makes Angular look for a field named Architect, find nothing, and match nothing. This is the number one ngSwitch bug.
When to use which One or two conditions → *ngIf, possibly with else. Three or more on the same value → *ngSwitch. There is no correctness difference; it is purely about which reads better in six months' time.

Attribute directive 1 of 2

ngClass — apply CSS classes conditionally

This is how you make a table colour its own rows: green for active employees, red for inactive. You write CSS classes as normal, then let ngClass decide which apply.

the CSS — ordinary classes, nothing special
.active-row   { background-color: #eefcf1; color: #1a9e34; }
.inactive-row { background-color: #fff0ef; color: #b00027; }
.high-earner  { font-weight: bold; }

Three ways to write it, from simplest to most useful

<!-- 1. Object form — "apply each class when its condition is true" (use this) -->
<tr [ngClass]="{
      'active-row':   emp.status === 'Active',
      'inactive-row': emp.status === 'Inactive',
      'high-earner':  emp.salary > 40000
    }">

<!-- 2. Single-class shorthand — neat when there's only one -->
<tr [class.active-row]="emp.status === 'Active'">

<!-- 3. Expression form — returns a class name -->
<tr [ngClass]="emp.status === 'Active' ? 'active-row' : 'inactive-row'">
http://localhost:4200
IDNameSalaryStatus
1001Anoop25,000Active
1002Ajay45,000Inactive
1003Rekha22,000Active
1004Suresh65,000Inactive
Note that several classes can apply at once In the object form, every condition is evaluated independently. Suresh's row gets both inactive-row (red) and high-earner (bold), because both are true. That composability is why the object form is the one to reach for.

Attribute directive 2 of 2

ngStyle — set inline styles conditionally

Same idea as ngClass, but it sets CSS properties directly instead of naming a class. Reach for it when the value is calculated rather than chosen from a fixed set.

<!-- Object form -->
<td [ngStyle]="{
      'color':       emp.salary > 40000 ? 'green' : 'red',
      'font-weight': emp.status === 'Active' ? 'bold' : 'normal',
      'font-size':   '16px'
    }">
  {{ emp.salary }}
</td>

<!-- Single-property shorthand -->
<td [style.color]="emp.salary > 40000 ? 'green' : 'red'">

<!-- With units baked into the property name — genuinely handy -->
<div [style.width.px]="percentComplete * 3"></div>
<div [style.height.%]="50"></div>
The case where ngStyle is clearly right A progress bar. Its width is 72% because a calculation said so — you cannot write a CSS class for every possible percentage. Anything computed on a continuous scale belongs in ngStyle.
Two syntax notes 1. Property names with a hyphen need quoting: 'font-weight'. Or use the camelCase form fontWeight with no quotes.
2. Don't forget units. 'width': 300 does nothing; you need 'width': '300px' — or the [style.width.px] form, which adds them for you.

Attribute directives — choosing between them

ngClass vs ngStyle

QuestionngClassngStyle
What it setsCSS class namesCSS properties, inline
Where the styling livesIn your .css file, where it belongsScattered through your HTML
Reusable elsewhere?Yes — the class can be applied anywhereNo — it's tied to this one element

The rule of thumb Default to ngClass. Reach for ngStyle only when the value is genuinely computed and could not be expressed as a named class. In real projects you will use ngClass ten times for every ngStyle.
Ask the batch A dashboard shows each project's completion as a coloured bar: green above 75%, amber 40–75%, red below 40%, and the bar's width is the exact percentage. Which directive handles the colour, and which the width? (Colour → ngClass, three named states. Width → ngStyle, a continuous value. Often you use both on the same element.)

Concept 5 — formatting for humans

Pipes — transform what's displayed

Your data says 25000. A user should see ₹25,000.00. Your data says 2026-09-05T18:30:00Z. A user should see 5 Sep 2026.

A pipe formats a value for display only, using the | character. Crucially, your underlying data is never changed — only what appears on screen.

Pipes with parameters, and chaining

Parameters follow a colon

<!-- currency: which currency, and how to show the symbol -->
{{ 25000 | currency:'INR' }}                    <!-- ₹25,000.00 -->
{{ 25000 | currency:'INR':'symbol':'1.0-0' }}   <!-- ₹25,000    -->
{{ 25000 | currency:'USD' }}                    <!-- $25,000.00 -->

<!-- date: a format string -->
{{ today | date:'shortDate' }}          <!-- 9/5/26            -->
{{ today | date:'fullDate' }}           <!-- Saturday, September 5, 2026 -->
{{ today | date:'dd/MM/yyyy' }}         <!-- 05/09/2026        -->

<!-- number: minimum integer digits . min-max decimal places -->

<!-- slice: from index, to index -->
{{ longText | slice:0:50 }}

Chaining — pipes feed into each other, left to right

{{ emp.name | titlecase | slice:0:10 }}
{{ today | date:'fullDate' | uppercase }}
<!-- SATURDAY, SEPTEMBER 5, 2026 -->
Analogy — and it's where the name comes from Think of a production line. The value enters at the left, passes through each station, and comes out formatted at the right. Each pipe does one small job and hands the result on. It is exactly the | of a Unix shell, and the same idea as chaining Java stream operations.
The important thing pipes do NOT do {{ emp.name | uppercase }} does not change emp.name. The stored value is still 'Anoop'; only the pixels say ANOOP. So if you later save that employee, you save the original. That is the correct behaviour — format for display, store the truth.

Concept 6 — components talking to each other · downwards

Parent → child with @Input

You have a tree of components. Now the obvious question: how does a parent give a child some data? Answer: the child declares an input, and the parent fills it in with property binding.

The CHILD declares what it accepts

import { Component, Input }
  from '@angular/core';
import { Employee }
  from '../models/employee';

@Component({
  selector: 'app-employee-card',
  templateUrl:
    './employee-card.component.html'
})
export class EmployeeCardComponent {

  // "a parent may pass me an employee"
  @Input() employee!: Employee;

  @Input() showSalary = false;
}

The PARENT fills it in

<!-- employee-list.component.html -->

<app-employee-card
  *ngFor="let emp of employees"
  [employee]="emp"
  [showSalary]="true">
</app-employee-card>

The child's @Input() name becomes an attribute the parent can property-bind to. Note it is the same square brackets you already know.

employee-card.component.html — the child's own template
<div class="card">
  <h3>{{ employee.name }}</h3>
  <p>{{ employee.designation }}</p>
  <p *ngIf="showSalary">{{ employee.salary | currency:'INR' }}</p>
</div>
Why bother? Because now the card is reusable EmployeeCardComponent knows nothing about where its employee came from — an array, a search result, an API. It just renders whichever one it is handed. That is what makes it reusable on the list page, the search page and the dashboard. A component that fetches its own data can only ever be used one way.
Two details in that code 1. The ! in employee!: Employee tells strict mode "I promise a parent will set this". Without it you get "has no initializer and is not definitely assigned".
2. [showSalary]="true" needs the brackets to pass the boolean true. Writing showSalary="true" passes the string "true", which is a different thing and a classic source of confusion.

Concept 6 continued · upwards

Child → parent with @Output

The reverse problem: a Delete button lives on the child card, but the array lives on the parent. The child cannot — and should not — reach up and modify the parent. Instead it raises an event, and the parent decides what to do.

The CHILD announces

import { Component, Input, Output,
         EventEmitter }
  from '@angular/core';

export class EmployeeCardComponent {
  @Input() employee!: Employee;

  // "I will emit a number when
  //  someone clicks delete"
  @Output() deleteRequested =
    new EventEmitter<number>();

  onDeleteClick(): void {
    this.deleteRequested
        .emit(this.employee.id);
  }
}
<!-- the child's template -->
<button (click)="onDeleteClick()">
  Delete
</button>

The PARENT listens

<!-- the parent's template -->
<app-employee-card
  *ngFor="let emp of employees"
  [employee]="emp"
  (deleteRequested)="removeEmployee($event)">
</app-employee-card>
// the parent's class
removeEmployee(id: number): void {
  this.employees =
    this.employees.filter(
      e => e.id !== id);
}

Same round brackets as (click) — because it is an event binding. And $event carries whatever the child emitted.

The principle behind this — worth understanding, not just copying The child reports; the parent decides. The card does not know whether "delete" means removing from an array, calling an API, or showing a confirmation dialog — and it should not. That separation is why you can drop the same card into a different screen with different delete behaviour. The pattern has a name: data down, events up.

Concept 7 — the hook you'll use in every component from now on

ngOnInit — where setup code belongs

Angular creates and destroys your components, and it lets you run code at specific moments in that process. Those moments are called lifecycle hooks. There are several; you need exactly one today.

import { Component, OnInit } from '@angular/core';

@Component({ /* ... */ })
export class EmployeeListComponent implements OnInit {

  employees: Employee[] = [];

  constructor() {
    // Only for receiving dependencies (Session 3). Keep it empty for now.
  }

  ngOnInit(): void {
    // Angular calls this ONCE, after the component is built
    // and its @Input values have been set. Do setup here.
    this.employees = this.loadEmployees();
  }
}
implements OnInit
Declares that this class has an ngOnInit. Optional in practice, but include it — TypeScript then catches a misspelled method name.
ngOnInit()
Runs once, after construction and after @Input values arrive. The right place for fetching data and initialising forms.
constructor()
Runs first, before Angular has finished wiring the component. Use it only to receive injected dependencies.
"Why not just do it in the constructor?" Because at constructor time your @Input values have not arrived yet — they are still undefined. A child that reads this.employee.name in its constructor crashes; the same line in ngOnInit works. The rule is simple and worth adopting permanently: constructor for dependencies, ngOnInit for work.
The other hooks, for awareness only ngOnChanges (an @Input changed), ngAfterViewInit (the template has rendered), ngOnDestroy (the component is being removed — used for cleanup). You will not need them in this series. ngOnInit covers the overwhelming majority of real cases.

Recap

What you now know

  • A component is a class + a template + scoped styles + a @Component decorator, and an app is a tree of them.
  • A component appears wherever its selector tag is written, and ng g c creates all four files and registers it in the module.
  • Component CSS cannot leak out — Angular scopes it for you, which makes short class names safe again.
  • The four bindings and their directions: {{ }} and [ ] go in, ( ) goes out, [( )] goes both.
  • [(ngModel)] needs FormsModule in imports — and that error shape means "a module is missing" every time you see it.
  • Structural directives (with an asterisk) add and remove elements: *ngIf, *ngFor, *ngSwitch.
  • Attribute directives (no asterisk) restyle what's there: ngClass for named states, ngStyle for computed values.
  • Pipes format for display without changing your data — and | json is the fastest debugging tool you have.
  • @Input passes data down, @Output + EventEmitter sends events up: data down, events up.
  • ngOnInit is where setup code goes — the constructor is only for dependencies.
