The motivating problem — why we're about to create five packages

What happens if you don't organise

Imagine writing the product manager the way we wrote the login servlet: everything in doGet. It works — for about a week. Here's the class you'd end up with:

protected void doGet(HttpServletRequest request, HttpServletResponse response) {

    response.setContentType("text/html");
    PrintWriter out = response.getWriter();

    // reading input...
    int id = Integer.parseInt(request.getParameter("id"));
    double price = Double.parseDouble(request.getParameter("price"));

    // ...validation rules...
    if (price < 0) { out.println("<h3>Bad price</h3>"); return; }

    // ...connection details...
    Connection con = DriverManager.getConnection("jdbc:derby:...", "sa", "");

    // ...SQL...
    PreparedStatement ps = con.prepareStatement("UPDATE product SET price=? WHERE id=?");

    // ...and HTML generation, all in one method.
    out.println("<table border='1'>...");

    // Repeat all of the above for insert, delete and view.
    // 400 lines. Four copies of the connection code.
}
🔍

Nothing is findable

Where's the SQL? Somewhere in a 400-line method, between HTML strings. Changing a query means reading all of it.

📋

Everything is duplicated

The connection URL appears four times. Change database and you must find every copy — and you will miss one.

🧪

Nothing is testable

To test "reject negative prices" you'd need a running Tomcat and a live database. So nobody tests it.

The one question that drives all of today's design "When one thing changes, how many places must I edit?" In the code above, the answer is always "several, and I'm not sure which." The goal of MVC is to make the answer "one."

The standard answer

Model–View–Controller

MVC splits code by responsibility, so each class has exactly one reason to change. It's the most widely used architectural pattern in application development, and it long predates the web:

🗃️

Model — the data

What the application is about: a Product, an Employee. Plus the code that stores and fetches it. Knows nothing about the web.

🖥️

View — what the user sees

The presentation. Today it's HTML built by PrintWriter; later it'll be JSP or a template engine. Contains no business rules.

🎛️

Controller — the traffic cop

Receives the request, decides what should happen, calls the model, picks the view. Coordinates; doesn't do the work itself.

Why bother, in one concrete sentence When the boss says "show prices with two decimals," you want to touch one place — not hunt through SQL, validation, and HTML tangled in a single method. Separation of concerns isn't neatness; it's the ability to change one thing safely.

The five packages

MVC in the abstract becomes five concrete packages. Every file you create today belongs to exactly one of these, and each layer talks only to the next one down:

PackageRoleWhat goes in it — and what must never
webView / Web layer The servlets — where client requests land. Reads parameters, calls the service, writes HTML. No SQL here, ever.
serviceController / Service layer Business logic and validation. "Is the price negative? Then refuse." Calls the DAO. Knows nothing about HTTP or SQL.
daoData Access Object All SQL lives here — and only here. INSERT, SELECT, UPDATE, DELETE via PreparedStatement. No HTML, no validation.
beanThe Model objects POJOs — private fields, getters/setters, constructors. Our Product. Pure data carriers; no logic at all.
helperInfrastructure Database connection management — one place that opens and closes connections. The only class that knows the JDBC URL.

→

→

Where does bean sit in that chain? Everywhere — it's the currency, not a step. A Product object is what the layers hand to each other: the servlet builds one from form data, the service validates it, the DAO writes it to the database, and a DAO SELECT returns a List<Product> back up the chain. That's why it's in its own package that everyone imports.

Layer by layer · 1 of 5 — bean

The Model object — Product

A POJO (Plain Old Java Object), also called a bean: a class that does nothing but hold data. Its plainness is the point — it's the neutral currency the layers pass around, so no layer needs to know about any other.

package com.tcs.bean;

public class Product {

    private int    id;         // one field per table column,
    private String name;       // with matching types
    private double price;
    private int    quantity;

    public Product() { }                                // no-arg: create empty, fill via setters

    public Product(int id, String name,                  // all-args: build complete in one line
                   double price, int quantity) {
        this.id = id;  this.name = name;
        this.price = price;  this.quantity = quantity;
    }

    public int getId() { return id; }                    // ... plus getters and setters
    public void setId(int id) { this.id = id; }          //     for all four fields
    // ...
}
🔒

Why private fields?

Encapsulation. Today the getter just returns the value. But when a rule appears — "price is never negative" — a setter gives you one place to enforce it and no caller has to change.

🔨

Why both constructors?

The all-args one is what the DAO and servlet use. The no-arg one is needed when something creates the object then fills it — and frameworks require it.

⚡

Don't type it by hand

Declare the four fields, then Source → Generate Getters and Setters (Alt+Shift+S). Same menu generates constructors and toString().

The naming convention isn't cosmetic getPrice() / setPrice() is the JavaBeans convention, and tooling relies on it: it means "there is a property called price." That's how JSP tags, Spring form binding, and JSON libraries find your data automatically. Name them wrong and the frameworks stop seeing your fields.

Layer by layer · 2 of 5 — helper

Connection management — DBHelper

One class whose only job is opening and closing database connections. The JDBC URL lives here and nowhere else — which is what makes "switch from Derby to MySQL" a one-file change instead of a treasure hunt.

package com.tcs.helper;

public class DBHelper {

    // The ONLY place in the whole application that knows this.
    private static final String URL  = "jdbc:derby:C:/derbydb/productdb;create=true";
    private static final String USER = "sa";
    private static final String PASS = "";

    public static Connection connect() {
        try {
            // No Class.forName() needed — JDBC 4.0+ auto-discovers the driver
            // from the JAR, which is why the JAR's location matters (slide 15).
            return DriverManager.getConnection(URL, USER, PASS);
        } catch (SQLException e) {
            System.out.println("DB connect failed [" + e.getSQLState() + "]: " + e.getMessage());
            return null;                     // callers MUST check for null
        }
    }

    public static void close(Connection con) {
        try {
            if (con != null) { con.close(); }    // null-tolerant on purpose
        } catch (SQLException e) {
            System.out.println("DB close failed: " + e.getMessage());
        }
    }
}
Three design decisions worth understanding 1 · Why static? There's no state to keep, so there's nothing to instantiate — DBHelper.connect() reads cleanly from anywhere.
2 · Why return null on failure instead of throwing? It keeps the DAO simple for a first build. It is a compromise — null-returning methods are easy to misuse — which is exactly why every DAO method starts with an if (con == null) guard. Production code would throw a custom DataAccessException.
3 · Why is close() null-tolerant? So a finally block can call it unconditionally. Fewer branches, fewer bugs.
Recognise this class? It's the JDBC session's DBConnector, unchanged. And in Spring Boot, this entire class disappears — replaced by four lines in application.properties. Same job, less typing, every time you move up a layer of abstraction.

Layer by layer · 3 of 5 — dao

All the SQL — ProductDao

The Data Access Object is the only place in the entire application where SQL appears. Four methods, one per CRUD operation. Here's the shape they all share:

public boolean updateProduct(int id, double price) {

    String sql = "UPDATE product SET price = ? WHERE id = ?";      // 1. parameterised SQL

    Connection con = DBHelper.connect();
    if (con == null) { return false; }                             // 2. guard the null

    try (PreparedStatement ps = con.prepareStatement(sql)) {        // 3. auto-closed

        ps.setDouble(1, price);       // bind in the ? order — 1-based, not 0
        ps.setInt(2, id);

        return ps.executeUpdate() > 0;                             // 4. rows changed -> boolean

    } catch (SQLException e) {
        System.out.println("Update failed [" + e.getSQLState() + "]: " + e.getMessage());
        return false;
    } finally {
        DBHelper.close(con);                                       // 5. always release
    }
}
#The rule, and why it matters
1PreparedStatement with ?, always. Parameters are bound as data and can never become SQL, so SQL injection is impossible. It's also faster — the database compiles the template once.
2Guard the null connection. DBHelper.connect() can fail. Skip this and you get a NullPointerException and a 500 page instead of a clean "failed" message.
3try-with-resources closes the statement on success and on exception.
4Match the method to the SQL verb. executeUpdate() for INSERT/UPDATE/DELETE (returns a row count); executeQuery() for SELECT (returns a ResultSet). Swap them and you get 0 rows or an exception.
5Close the connection in finally so it's released even when something throws. Leaked connections eventually exhaust the database.
And the SELECT returns data, not HTML getAllProducts() returns a List<Product> — it would be shorter to print the table right there, and completely wrong. The DAO must not know its caller is a web page. Returning data keeps it reusable by a servlet, a REST endpoint, a report, or a test. Data layers return data; presentation layers decide how it looks. It also returns an empty list, never null, so callers can always safely loop.

Layer by layer · 4 of 5 — service

Business logic — ProductService

Here's the fair objection: "if the service just forwards calls to the DAO, why does it exist?" Correct — and that's why ours does real work. Validation.

package com.tcs.service;

public class ProductService {

    private ProductDao dao = new ProductDao();

    public boolean addProduct(Product p) {

        // ===== business rules live HERE — one place, every caller covered =====
        if (p == null)                                        { return false; }
        if (p.getId() <= 0)                                   { return false; }   // ids are positive
        if (p.getName() == null || p.getName().trim().isEmpty()) { return false; } // name required
        if (p.getPrice() < 0 || p.getQuantity() < 0)          { return false; }   // no negatives

        // Only now do we touch the database.
        return dao.insertProduct(p);
    }

    public List<Product> getAllProducts() {
        return dao.getAllProducts();      // nothing to validate on a read
    }
}
📍

Why not in the servlet?

Because a second UI — a REST API, an admin page — would have to duplicate every rule. And one of the copies would drift.

📍

Why not in the DAO?

The DAO's job is data access, not company policy. Mixing them means you can't change a rule without touching SQL.

🧪

The real payoff

No request, no PrintWriter, no SQL — so this is testable as a plain Java class, with no server running.

The honest limitation of returning boolean false tells the servlet that something failed, never why. "Blank name", "duplicate id" and "database unreachable" all look identical from above. That's an acceptable simplification while learning — and it's why the DAO logs the real SQLException to the console, so the detail isn't lost, just not surfaced. The proper fix is custom exceptions carrying a reason, which is exactly what @ControllerAdvice does in the Spring Boot sessions.

Layer by layer · 5 of 5 — web

The servlet — ProductServlet

The servlet's job shrinks dramatically once the other layers exist. It does exactly three things: read parameters, call the service, write HTML. No SQL, no connections, no business rules.

public class ProductServlet extends HttpServlet {

    // Safe as a FIELD: the service holds no per-request state, so all
    // threads can share this one object. Contrast with an id or a name,
    // which must NEVER be a field (Part 1, slide 19).
    private ProductService service = new ProductService();

    protected void doGet(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {

        response.setContentType("text/html");
        PrintWriter out = response.getWriter();

        String action = request.getParameter("action");
        if (action == null) { action = "view"; }        // default, don't crash

        // ... route on action, then print ...
    }

    private void handleUpdate(HttpServletRequest request, PrintWriter out) {
        try {
            int    id    = Integer.parseInt(request.getParameter("id"));       // parse
            double price = Double.parseDouble(request.getParameter("price"));

            if (service.updateProduct(id, price)) {                            // delegate
                out.println("<h3><font color='green'>Product updated.</font></h3>");
            } else {                                                           // report
                out.println("<h3><font color='red'>Updation failed — no id " + id + ".</font></h3>");
            }
        } catch (NumberFormatException e) {
            out.println("<h3><font color='red'>ID and price must be numbers.</font></h3>");
        }
    }
}
Notice how thin this got Parse, delegate, report. That's the whole controller. All the interesting decisions moved down into the service, and all the SQL into the DAO — so this file changes only when the user interface changes. That's the definition of a well-placed responsibility.
Two things in this file to look at twice 1 · service is an instance field, and that's fine — it's stateless and shared. An int id field would be a serious bug. The rule is about per-request data, not about fields in general.
2 · out is passed as a parameter to the handler methods, not stored as a field — for exactly that reason.

All five layers, one request

The call chain, both directions

Here's what actually happens when someone submits the "add product" form. Notice the Product object travelling down, and the result travelling back up:

 LayerWhat it does with what it received
⬇ 1web · ProductServletReceives 4 Strings from the form. Parses them, builds a Product, calls service.addProduct(p).
⬇ 2service · ProductServiceReceives a Product. Checks id > 0, name not blank, price/quantity not negative. If OK, calls dao.insertProduct(p).
⬇ 3dao · ProductDaoReceives a Product. Asks DBHelper for a connection, binds the fields to a PreparedStatement, executes.
⬇ 4helper · DBHelperReceives nothing. Hands back an open Connection (or null).
⬇ 5DerbyRuns the INSERT, reports 1 row affected.
⬆ 6daoConverts the row count to true, closes the connection.
⬆ 7servicePasses the boolean straight up.
⬆ 8webSees true, prints a green success message, then the refreshed table.
The two things flowing through that chain Going down: a Product — the bean, the shared currency. Coming up: a boolean (for writes) or a List<Product> (for reads). No layer ever passes an HttpServletRequest or a ResultSet across a boundary — that's the discipline that keeps the layers independent.

The payoff, made concrete

Why the layers are worth the extra files

Five packages for a four-column table feels like overkill — a fair objection. Here's what you actually buy, in situations you will genuinely face:

The change requestAll-in-one servletLayered (MVC)
"Switch from Derby to MySQL"Hunt through every servlet for connection codeEdit DBHelper. One file.
"Reject negative prices"Add the same if everywhere a price is written — and miss oneAdd it once in ProductService; every path is covered
"Also expose this as a JSON API"Copy-paste the logic and edit the copy — now two versions to maintainNew servlet, same service. Zero logic duplicated
"Write unit tests"Nearly impossible — logic needs a running server to executeTest ProductService as a plain Java class
"Redesign the page"Risk breaking SQL while editing HTML — same methodTouch only the web layer. Data code untouched
The honest caveat For a genuinely tiny app, layering is extra ceremony — and you should know that rather than treat it as gospel. But applications don't stay tiny, and retrofitting structure into tangled code is far more expensive than starting with it. The habit is what you're learning today, not the file count.
You've seen this shape before — and you'll see it again JDBC's DAO pattern (Tester → DAO → DBConnector) was the same idea with three layers. Spring Boot's @Controller → @Service → @Repository is the same idea with annotations. Learn the shape once and every Java framework afterwards looks familiar.

Creating the product table

Open a SQL Scrapbook (right-click the connection → Open SQL Scrapbook), pick your connection in the toolbar dropdowns, and run these one statement at a time with Ctrl + Alt + X:

CREATE TABLE product (

INSERT INTO product VALUES (1, 'Laptop',   55000.00, 10);
INSERT INTO product VALUES (2, 'Mouse',      750.50, 100);
INSERT INTO product VALUES (3, 'Keyboard',  1200.00, 45);

🔑

Why id is the primary key

It guarantees uniqueness, so WHERE id = 3 can only ever match one row. That's what makes update and delete precise instead of accidentally hitting many rows.

💾

Why we seed sample rows

So view has something to show and update/delete have something to work on. Otherwise your first test tells you nothing.

📄

Two Derby quirks worth knowing now 1. Derby folds unquoted identifiers to UPPERCASE, so the table appears as PRODUCT in the explorer. Your SQL can still say product — it's the same table. 2. Strings use single quotes ('Laptop'). Double quotes mean identifier in SQL, so "Laptop" would be read as a column name and error out.

Database setup · 3 of 3 — read this before the lab

Two traps that cost people an hour

These are not exotic edge cases — they hit almost everyone, and both produce symptoms that point in completely the wrong direction:

Trap 1 · The Derby JAR must go in TWO places You added derby.jar to the driver definition and the connection worked. That copy is used by Eclipse's own tools — the explorer and the scrapbook. Your web application cannot see it, because Tomcat runs your code in a separate JVM with its own classpath. So the JAR also goes in: 
WebContent/WEB-INF/lib/derby.jar     <- the SAME file, copied here too
The symptom: the explorer shows your rows perfectly, but the page returns 500 and the console says No suitable driver found for jdbc:derby:.... Whenever you see "No suitable driver," this is the answer.
Trap 2 · Use an ABSOLUTE database path A relative URL like jdbc:derby:productdb creates the database in the JVM's current working directory — and Eclipse's working directory is not Tomcat's. The result is baffling: the explorer shows your 4 rows, but the servlet reports "No products found", because it silently created a second, empty database somewhere else. 
// ✗ relative — two different databases      jdbc:derby:productdb;create=true
// ✓ absolute — one shared database        jdbc:derby:C:/derbydb/productdb;create=true
Use forward slashes even on Windows, and use the same absolute URL in the Data Source Explorer and in DBHelper.
Bonus trap · embedded Derby allows only ONE program at a time Embedded Derby loads inside whichever JVM opens it and takes an exclusive lock. If the Data Source Explorer is connected when Tomcat starts, you get ERROR XSDB6: Another instance of Derby may have already booted the database. Fix: right-click the connection → Disconnect before running the app. Or avoid the dance entirely with H2 and AUTO_SERVER=TRUE, which permits simultaneous access.

The mechanism behind trap 1

Why WEB-INF/lib specifically?

It's worth understanding why that folder is magic, because it explains several other things about web apps at the same time.

1 · The JAR in the driver definition

  • Used by Eclipse itself — Data Source Explorer, SQL Scrapbook
  • Lets you browse tables and run queries by hand
  • An IDE tool convenience, nothing more
  • Your application cannot see it

2 · The JAR in WEB-INF/lib/

  • Used by your web app running on Tomcat
  • What makes DriverManager.getConnection() work at runtime
  • Packaged into the .war and deployed with your code
  • Mandatory for actual JDBC calls
The rule from the servlet specification A web application's classloader automatically picks up every JAR in WEB-INF/lib/. Drop the file in that folder and it's on your classpath — no build-path configuration needed. That's the whole mechanism.
And this is also why WEB-INF is browser-inaccessible The same specification forbids serving anything under WEB-INF to a client. Think about what's in there: your web.xml, your compiled classes, and every JAR your app depends on. Nobody outside should be able to download your configuration or your dependencies. The folder is protected by design, not by accident — which is also why a JSP you want to protect goes inside it, and a CSS file you want served does not.

The CRUD design pattern · 1 of 4

One servlet, four actions

CRUD is four operations. You could write four servlets with four mappings — or one servlet that reads an action parameter and branches. We do the latter, because it keeps all product handling in one readable place:

String action = request.getParameter("action");
// treat "no action given" as a sensible default instead of crashing
if (action == null) {
    action = "view";
}

if (action.equals("view")) {
    // nothing to do — the table is printed below for every action

} else if (action.equals("insert")) {
    handleInsert(request, out);                // CREATE

} else if (action.equals("update")) {
    handleUpdate(request, out);                // UPDATE

} else if (action.equals("delete")) {
    handleDelete(request, out);                // DELETE

} else {
    out.println("<h3><font color='red'>Unknown action: " + action + "</font></h3>");
}

displayAllProducts(out);                       // READ — runs for ALL of them
ApproachTrade-off
One servlet + action+ One mapping, one file, shared helper methods, all behaviour visible at once.  − Grows long; the if-ladder can sprawl as features are added.
Four servlets+ Each class is tiny and single-purpose.  − Four mappings to maintain, and shared code needs a common parent or utility class.
Where this pattern leads That if-ladder is a hand-written front controller — and it's exactly what Spring MVC's DispatcherServlet does industrially. When you later write @GetMapping("/products"), Spring is running a far more sophisticated version of the ladder you're about to write. Write it by hand once and annotations stop being mysterious.

The CRUD design pattern · 2 of 4

Passing parameters: links vs forms

Both put parameters in a request. Which one you reach for depends on whether the user needs to type anything:

🔗 A link — no input needed

<a href="product?action=view">
    View all products
</a>

<!-- delete row 3: two params -->
<a href="product?action=delete&amp;p=3">
    Delete
</a>

Always a GET; parameters sit in the query string. Perfect when the values are already known — the row's own id. This is how we build the per-row Delete link.

📝 A form — the user types

<form action="product" method="post">
  <input type="hidden"
         name="action" value="insert" />

  <input type="text" name="id" />
  <input type="text" name="name" />
  <input type="text" name="price" />
  <input type="text" name="quantity" />

  <input type="submit" value="Add" />
</form>

GET or POST, your choice. Necessary when values come from the user. The hidden field carries the action invisibly — clearer than Part 1's submit-button trick, because the server's value no longer depends on the button's visible label.

Two details on that delete link 1 · In HTML the correct parameter separator is the entity &amp;, not a bare &. Browsers forgive the bare version, so it usually works — but &amp; is valid HTML and won't surprise you.
2 · A delete link is a GET that changes data, which technically breaks GET's idempotency rule from Part 1. It's the pragmatic classic approach and fine for learning, but be aware: a crawler or browser pre-fetcher following that link would silently delete rows. Real applications use a POST form with a confirmation for destructive actions.
The choice, summarised Nothing to type → link (GET). Something to type → form (POST for writes). Which lines up exactly with Part 1's GET-to-read / POST-to-write rule — the design isn't arbitrary, it follows from HTTP's own semantics.

The CRUD design pattern · 3 of 4

The boolean-return pattern

Your DAO ran an UPDATE. Did it change anything? Maybe the id didn't exist. The servlet needs to know so it can show the right message — so every write method returns a boolean:

// ===== DAO: turn "rows affected" into a plain yes/no =====
public boolean updateProduct(int id, double price) {
    // ... prepare and bind ...
    int rows = ps.executeUpdate();
    return rows > 0;        // 0 rows matched -> false. 1+ -> true.
}

// ===== SERVLET: branch on it and tell the user the truth =====
if (service.updateProduct(id, price)) {
    out.println("<h3><font color='green'>Product updated successfully.</font></h3>");
} else {
    out.println("<h3><font color='red'>Updation failed — no product with id " + id + ".</font></h3>");
}
📊

It comes from executeUpdate()

That method returns the number of rows affected. rows > 0 converts a count into the yes/no the UI actually needs.

🎯

It distinguishes two silent cases

"Ran fine but matched nothing" vs "found it and changed it." Without this check both look like success — and you'd lie to the user.

🧱

It keeps layers separate

The DAO reports a fact; the servlet decides the wording and the colour. Presentation stays out of the data layer.

Watch this happen in the lab — it's the clearest demonstration of the layers working Insert a duplicate id: the page says "failed" and the console logs SQLState 23505 — the DAO caught a real database error. Now insert a negative price: the page says "failed" but the console stays silent — because the service rejected it before any SQL ran. Same message, two completely different code paths.

Extracting the repeated display code

After every operation you want to show the updated table. Write that loop four times and you have four copies to fix when the table design changes. Extract it once.

✗ Before — duplicated four times

if (action.equals("view")) {
    // 15 lines of table loop
} else if (action.equals("insert")) {
    // ... insert ...
    // the SAME 15 lines again
} else if (action.equals("update")) {
    // ... update ...
    // the SAME 15 lines again
} else if (action.equals("delete")) {
    // ... delete ...
    // the SAME 15 lines AGAIN
}

60 lines. One design change = four edits — and you'll forget one.

→

✓ After — one method, called once

if (action.equals("view")) {
    // nothing
} else if (action.equals("insert")) {
    handleInsert(request, out);
} else if (action.equals("update")) {
    handleUpdate(request, out);
} else if (action.equals("delete")) {
    handleDelete(request, out);
}

// runs for EVERY action:
displayAllProducts(out);

15 lines, in one place. One design change = one edit.

DRY — Don't Repeat Yourself The trigger to watch for: the moment you'd copy-paste code for the second time, extract it into a method instead. Not before — premature abstraction is its own problem — but definitely then. In the lab we deliberately write the duplication first and then refactor, because feeling the pain is what makes the lesson stick.
Signature note — the thread-safety rule again private void displayAllProducts(PrintWriter out) — pass the writer in as a parameter rather than storing it in a field. An instance field would be shared across all users' threads (Part 1, slide 19). A parameter is per-call and therefore safe.

An honest look at what we're NOT building

The gap you'll notice: nothing is protected

At the end of the lab, try this: log in successfully, then go straight to /ServletBasics/product?action=view. It works. Now open a fresh browser, skip the login entirely, and go to the same URL. It still works.

Why? Because HTTP is stateless — and we did nothing about it The login response was sent and Tomcat immediately forgot you. Our ProductServlet has no idea whether the person calling it ever authenticated, and never asks. Every CRUD operation is wide open to anyone who knows the URL.

The fix is sessions — the machinery hinted at by that Set-Cookie: JSESSIONID=... header in Part 1:

// In LoginServlet, after credentials check out:
HttpSession session = request.getSession();
session.setAttribute("user", id);                 // remember them, server-side

// At the top of EVERY protected servlet:
HttpSession session = request.getSession(false);   // false = don't create a new one
if (session == null || session.getAttribute("user") == null) {
    response.sendRedirect("index.html");           // 302 — go log in
    return;                                        // and STOP processing
}
Why we're leaving it out today, deliberately Because adding it now would mean teaching cookies, session scope, timeouts, redirects and logout — on top of five new layers and a database. That's too much at once. Seeing the hole is the lesson for today; filling it is the natural first topic of whatever comes next. Recognising that your app is insecure is genuinely more valuable than being handed code that hides the problem.

Honest context — this is not how you'll write web apps in 2026

Building HTML with out.println() is genuinely unpleasant, and you should know that's not a limitation of your skill — it's why the industry moved on. Here's the honest lineage:

The eight mistakes you're most likely to make

Part 1's list still applies — these are the new ones that come with databases and layers:

  • derby.jar missing from WEB-INF/lib/ → No suitable driver found, even though the Data Source Explorer works perfectly.
  • Relative Derby path in DBHelper → "No products found" while the explorer clearly shows 4 rows. Two different databases. Use an absolute path.
  • Data Source Explorer still connected when Tomcat starts → XSDB6: Another instance may have already booted. Disconnect first.
  • Forgot the if (con == null) guard in a DAO method → NullPointerException and a 500 page instead of a clean failure message.
  • Wrong ? binding order — SET price = ? WHERE id = ? means setDouble(1, price) then setInt(2, id). Reversed, you'd update the wrong thing. Placeholders are 1-based, not 0.
  • executeQuery vs executeUpdate mixed up → SELECT with executeUpdate returns 0; INSERT with executeQuery throws.
  • Delete link parameter name mismatch — the link sends p=3, so read getParameter("p"), not "id". A silent null, then NumberFormatException.
  • Quote confusion in generated HTML — the Java string uses ", so the HTML attribute must use ': "<a href='product?action=delete&p=" + id + "'>".
The triage list — five symptoms, five answers 404? URL or url-pattern wrong; restart Tomcat.  500? Read the first line of the console stack trace.  "No suitable driver"? JAR not in WEB-INF/lib.  "No products found" but rows exist? Relative Derby path.  "Already booted"? Disconnect the explorer.
