⚠ Trap 1 — use an ABSOLUTE database path, or your servlet will see an empty table A relative URL like jdbc:derby:productdb creates the database in the JVM's current working directory — and Eclipse's working directory is not Tomcat's. The result is baffling: the Data Source Explorer shows your 4 rows, but the servlet reports "No products found," because it silently created a second, empty database somewhere else. 
// ✗ Relative — two different databases, depending on who connects
jdbc:derby:productdb;create=true

// ✓ Absolute — Eclipse and Tomcat both open the SAME database
jdbc:derby:C:/derbydb/productdb;create=true               // Windows
jdbc:derby:/home/yourname/derbydb/productdb;create=true   // macOS / Linux
Use forward slashes even on Windows — backslashes in a Java string need escaping and cause needless errors. Use this same absolute URL in the Data Source Explorer and in DBHelper.
⚠ Trap 2 — embedded Derby allows only ONE program at a time Embedded Derby loads inside whichever JVM opens it and takes an exclusive lock. So if Eclipse's Data Source Explorer is connected when Tomcat starts, your servlet fails with:
ERROR XSDB6: Another instance of Derby may have already booted the database C:\derbydb\productdb.
The fix: in Data Source Explorer, right-click the connection → Disconnect before running the app. Reconnect when you want to inspect rows, then disconnect again.

Tired of that dance? Two clean options: switch to H2 with AUTO_SERVER=TRUE (see prerequisites — simultaneous access just works), or run Derby Network Server and use the client URL jdbc:derby://localhost:1527/productdb;create=true. Both let Eclipse and Tomcat connect at once.

LAB 2bean▶ The Model — Product POJO
Concept — what a POJO is and why it's so plain A POJO (Plain Old Java Object) — also called a bean — is a class that does nothing but hold data. Private fields, public getters and setters, constructors. No SQL, no HTML, no logic. Its plainness is the point: it's the neutral currency the layers pass to each other, so no layer has to know anything about any other. One field per table column, with matching types.
Do this

Right-click com.tcs.bean → New → Class → name it Product → Finish. Paste the whole file.

📄Product.javasrc/com/tcs/bean/paste the WHOLE file
package com.tcs.bean;

/**
 * One row of the product table, as a Java object.
 * Field names and types mirror the columns exactly.
 */
public class Product {

    private int    id;         // id       INT PRIMARY KEY
    private String name;       // name     VARCHAR(50)
    private double price;      // price    DOUBLE
    private int    quantity;   // quantity INT

    // No-argument constructor: needed if you create an empty object
    // and fill it via setters. Frameworks require it too.
    public Product() {
    }

    // All-arguments constructor: build a complete object in one line.
    // This is the one the DAO and the servlet use.
    public Product(int id, String name, double price, int quantity) {
        this.id       = id;
        this.name     = name;
        this.price    = price;
        this.quantity = quantity;
    }

    // ===== getters and setters =====
    public int getId() {
        return id;
    }
    public void setId(int id) {
        this.id = id;
    }

    public String getName() {
        return name;
    }
    public void setName(String name) {
        this.name = name;
    }

    public double getPrice() {
        return price;
    }
    public void setPrice(double price) {
        this.price = price;
    }

    public int getQuantity() {
        return quantity;
    }
    public void setQuantity(int quantity) {
        this.quantity = quantity;
    }

    // Handy for System.out debugging — prints readable values instead
    // of something like com.tcs.bean.Product@1b6d3586
    @Override
    public String toString() {
        return "Product [id=" + id + ", name=" + name
             + ", price=" + price + ", quantity=" + quantity + "]";
    }
}
Time-saver worth learning now You don't have to type accessors by hand. Declare the four fields, then use Eclipse: Source → Generate Getters and Setters (Alt+Shift+S, then R) → Select All → Generate. The same menu has Generate Constructor using Fields and Generate toString(). Every Java developer uses these; typing forty lines of boilerplate is not a rite of passage.
Why private fields with public getters, rather than just public fields? Encapsulation. Right now the getter just returns the value — so it does look like extra typing. But the moment a rule appears ("price can never be negative", "name is always trimmed"), a setter gives you one place to enforce it, and no calling code needs to change. Public fields give you nowhere to put that rule.

The naming matters too: getPrice()/setPrice() is the JavaBeans convention, and tooling depends on it — it's how JSP tags, Spring form binding and JSON libraries discover that there's a property called price. Name them wrong and frameworks stop seeing your data.

📄DBHelper.javasrc/com/tcs/helper/paste the WHOLE file
package com.tcs.helper;

import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.SQLException;

/**
 * The ONLY class that knows how to reach the database.
 * Change the URL here and the whole application follows.
 */
public class DBHelper {

    // <<< PASTE YOUR OWN URL FROM LAB 0 HERE >>>
    // Must be an ABSOLUTE path, with forward slashes, and must be the
    // SAME path the Data Source Explorer uses — otherwise Tomcat quietly
    // creates a second, empty database and "view" shows nothing.
    private static final String URL  = "jdbc:derby:C:/derbydb/productdb;create=true";
    private static final String USER = "sa";
    private static final String PASS = "";

    /** Opens a connection. Returns null if it fails — callers MUST check. */
    public static Connection connect() {
        try {
            // No Class.forName() needed: JDBC 4.0+ auto-discovers the driver
            // from the JAR — which is why it must be in WEB-INF/lib.
            return DriverManager.getConnection(URL, USER, PASS);

        } catch (SQLException e) {
            // System.out -> Eclipse console. This is your debugging channel;
            // the user never sees it. Read it when a page says "failed".
            System.out.println("DB connect failed [" + e.getSQLState() + "]: " + e.getMessage());
            return null;
        }
    }

    /** Closes a connection. Null-tolerant, so callers can call it blindly. */
    public static void close(Connection con) {
        try {
            if (con != null) {
                con.close();
            }
        } catch (SQLException e) {
            System.out.println("DB close failed: " + e.getMessage());
        }
    }
}
Three design decisions worth understanding 1 · Why static methods? There's no state to keep, so there's nothing to instantiate — DBHelper.connect() reads cleanly from anywhere.
2 · Why return null on failure rather than throwing? It keeps the DAO simple for a first build. It is a compromise — null-returning methods are easy to misuse — which is exactly why every DAO method below starts with an if (con == null) guard. Production code would throw a custom DataAccessException.
3 · Why is close() null-tolerant? So a finally block can call it unconditionally without its own null check. Fewer branches, fewer bugs.
Optional 2-minute sanity check — highly recommended Before building three more layers on top, prove the connection works. Temporarily add a main method to DBHelper and run it as a plain Java Application: 
public static void main(String[] args) {
    Connection con = connect();
    System.out.println("Connected: " + (con != null));
    close(con);
}
Expected: Connected: true in the console. Get that working now and the rest of the lab is about logic instead of configuration.

Note: running this from Eclipse needs derby.jar on the project build path too (Properties → Java Build Path → Libraries → Add JARs → the one in WEB-INF/lib). If you'd rather not bother, skip this check — Lab 6 will tell you soon enough. Remember to disconnect the Data Source Explorer first (Trap 2 in Lab 0), and delete this main when you're done.

LAB 4daoINSERTSELECTUPDATEDELETE▶ All the SQL — ProductDao
Concept The Data Access Object is the only place in the entire application where SQL appears. Four methods, one per CRUD operation. Every one uses a PreparedStatement with ? placeholders — never string concatenation — and the three write methods return a boolean so the layers above can branch on success without knowing any SQL.

📄ProductDao.javasrc/com/tcs/dao/paste the WHOLE file
package com.tcs.dao;

import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.util.ArrayList;
import java.util.List;

import com.tcs.bean.Product;
import com.tcs.helper.DBHelper;

/**
 * Every SQL statement in the application lives in this class.
 * No HTML here, no validation here — just data access.
 */
public class ProductDao {

    // ==================== CREATE ====================
    public boolean insertProduct(Product p) {

        String sql = "INSERT INTO product VALUES (?, ?, ?, ?)";

        Connection con = DBHelper.connect();
        if (con == null) {
            return false;                // couldn't even connect
        }

        // try-with-resources: the PreparedStatement closes itself,
        // on success AND on exception.
        try (PreparedStatement ps = con.prepareStatement(sql)) {

            ps.setInt(1, p.getId());          // placeholders are 1-based, not 0
            ps.setString(2, p.getName());
            ps.setDouble(3, p.getPrice());
            ps.setInt(4, p.getQuantity());

            // executeUpdate returns the number of rows changed.
            return ps.executeUpdate() > 0;    // 1 row -> true, 0 rows -> false

        } catch (SQLException e) {
            // SQLState 23505 = duplicate primary key (that id already exists)
            System.out.println("Insert failed [" + e.getSQLState() + "]: " + e.getMessage());
            return false;

        } finally {
            DBHelper.close(con);              // always release the connection
        }
    }

    // ==================== READ ALL ====================
    public List<Product> getAllProducts() {

        String sql = "SELECT id, name, price, quantity FROM product ORDER BY id";

        // Return an EMPTY list rather than null on failure — then callers
        // can always safely write "for (Product p : list)".
        List<Product> list = new ArrayList<Product>();

        Connection con = DBHelper.connect();
        if (con == null) {
            return list;
        }

        try (PreparedStatement ps = con.prepareStatement(sql);
             ResultSet rs = ps.executeQuery()) {          // SELECT -> executeQuery

            // rs.next() starts BEFORE row 1; each call advances one row
            // and returns false when the rows run out.
            while (rs.next()) {
                Product p = new Product(
                        rs.getInt("id"),
                        rs.getString("name"),
                        rs.getDouble("price"),
                        rs.getInt("quantity"));
                list.add(p);
            }

        } catch (SQLException e) {
            System.out.println("Select failed [" + e.getSQLState() + "]: " + e.getMessage());

        } finally {
            DBHelper.close(con);
        }

        return list;
    }

    // ==================== UPDATE ====================
    public boolean updateProduct(int id, double price) {

        String sql = "UPDATE product SET price = ? WHERE id = ?";

        Connection con = DBHelper.connect();
        if (con == null) {
            return false;
        }

        try (PreparedStatement ps = con.prepareStatement(sql)) {

            ps.setDouble(1, price);      // order matches the ?s in the SQL:
            ps.setInt(2, id);            // first ? = price, second ? = id

            // 0 rows means "no product had that id" — NOT an error,
            // which is exactly the case the boolean lets us report.
            return ps.executeUpdate() > 0;

        } catch (SQLException e) {
            System.out.println("Update failed [" + e.getSQLState() + "]: " + e.getMessage());
            return false;

        } finally {
            DBHelper.close(con);
        }
    }

    // ==================== DELETE ====================
    public boolean deleteProduct(int id) {

        String sql = "DELETE FROM product WHERE id = ?";

        Connection con = DBHelper.connect();
        if (con == null) {
            return false;
        }

        try (PreparedStatement ps = con.prepareStatement(sql)) {

            ps.setInt(1, id);
            return ps.executeUpdate() > 0;    // false = nothing matched that id

        } catch (SQLException e) {
            System.out.println("Delete failed [" + e.getSQLState() + "]: " + e.getMessage());
            return false;

        } finally {
            DBHelper.close(con);
        }
    }
}
The five patterns repeating in every method — learn the shape, not the lines
  1. Connect, then guard. DBHelper.connect() can return null, so every method checks before using it. Skipping the guard gives you a NullPointerException and a 500 page instead of a clean failure.
  2. PreparedStatement with ?, always. Parameters are bound as data and can never become SQL, so SQL injection is impossible. It's also faster, since the database compiles the template once.
  3. Bind in the ? order, 1-based. SET price = ? WHERE id = ? means setDouble(1, price) then setInt(2, id). Reverse them and you'd update the wrong thing.
  4. Match the execute method to the SQL verb. executeQuery() for SELECT (returns a ResultSet); executeUpdate() for INSERT/UPDATE/DELETE (returns a row count). Swap them and you get 0 rows or an exception.
  5. Close in finally. The statement and result set are auto-closed by try-with-resources; the Connection is closed in finally so it's released even when an exception fires. Leaked connections eventually exhaust the database.
Why getAllProducts() returns a list instead of printing It would be shorter to print the table right here — and completely wrong. The DAO must not know that its caller is a web page. Returning List<Product> keeps it reusable by a servlet, a REST endpoint, a scheduled report, or a unit test. Data layers return data; presentation layers decide how it looks.
Try it yourself — after the app works end to end Add two more methods, following the same shape: Product getProductById(int id) — use if (rs.next()) rather than while, since a primary key matches at most one row, and return null when nothing is found. Then List<Product> searchByName(String keyword) using WHERE name LIKE ? with ps.setString(1, "%" + keyword + "%"). Note the wildcards go in the value, not the SQL.
LAB 5service▶ Business Logic — ProductService
Concept — and an honest answer to "isn't this layer pointless?" A service that only forwarded calls to the DAO would be pointless. So ours does real work: validation. Business rules like "a price can't be negative" and "a name can't be blank" belong here — not in the servlet (where every new UI would duplicate them) and not in the DAO (whose job is data access, not policy). Put the rule in one place and every caller inherits it.
Do this

Right-click com.tcs.service → New → Class → name it ProductService → Finish. Paste the whole file.

📄ProductService.javasrc/com/tcs/service/paste the WHOLE file
package com.tcs.service;

import java.util.List;

import com.tcs.bean.Product;
import com.tcs.dao.ProductDao;

/**
 * Business rules live here. Knows nothing about HTTP (no request/response)
 * and nothing about SQL (no statements) — it sits cleanly between the two.
 */
public class ProductService {

    private ProductDao dao = new ProductDao();

    // ===== CREATE — validate before touching the database =====
    public boolean addProduct(Product p) {

        if (p == null) {
            return false;
        }
        if (p.getId() <= 0) {
            return false;                                  // ids must be positive
        }
        if (p.getName() == null || p.getName().trim().isEmpty()) {
            return false;                                  // name is required
        }
        if (p.getPrice() < 0 || p.getQuantity() < 0) {
            return false;                                  // no negative money or stock
        }

        // Only now do we hit the database.
        return dao.insertProduct(p);
    }

    // ===== READ — nothing to validate, so just pass it through =====
    public List<Product> getAllProducts() {
        return dao.getAllProducts();
    }

    // ===== UPDATE =====
    public boolean updateProduct(int id, double price) {

        if (id <= 0 || price < 0) {
            return false;
        }
        return dao.updateProduct(id, price);
    }

    // ===== DELETE =====
    public boolean deleteProduct(int id) {

        if (id <= 0) {
            return false;
        }
        return dao.deleteProduct(id);
    }
}
Notice what this layer does not do No HttpServletRequest, no PrintWriter, no SQL, no HTML. That's what makes it testable as a plain Java class — no server required — and reusable by any front end. When you write Spring Boot, this exact class becomes @Service with the repository injected. Same layer, same job, less wiring.
The limitation of returning boolean — worth naming honestly false tells the servlet that something failed, never why. "Blank name", "duplicate id", and "database unreachable" all look identical from above. That's an acceptable simplification while learning, and the reason the DAO logs the real SQLException to the console — the detail isn't lost, just not surfaced. You'll watch both paths in Lab 7.

Read that link line carefully — it's the fiddliest string in the lab "<td><a href='product?action=delete&p=" + p.getId() + "'>Delete</a></td>"
  • Single quotes inside double quotes. The Java string uses ", so the HTML attribute uses ' — no escaping needed. Mixing these up is the usual cause of a broken link.
  • Two parameters joined by &: the fixed action=delete, and p= plus this row's id.
  • Each row gets a different URL — row 3 renders product?action=delete&p=3. That's the whole trick: the link already knows which record it refers to, so the user types nothing.
  • The parameter is p, not id — which is why handleDelete reads getParameter("p"). Mismatch these and you get a silent null, then a NumberFormatException.

Two things to notice about that delete URL 1 · It's a GET, and it changes data — which technically breaks the "GET is idempotent" rule from Part 1. It's the pragmatic classic approach and fine for learning, but be aware: a search-engine crawler or a browser pre-fetcher following that link would silently delete your data. package com.tcs.web;

import java.io.IOException;
import java.io.PrintWriter;
import java.util.List;

// On Tomcat 10+ change these four to jakarta.servlet.*
import javax.servlet.ServletException;
import javax.servlet.http.HttpServlet;
import javax.servlet.http.HttpServletRequest;
import javax.servlet.http.HttpServletResponse;

import com.tcs.bean.Product;
import com.tcs.service.ProductService;

/**
 * One servlet, four actions — a hand-written "front controller".
 * Spring MVC's DispatcherServlet is an industrial version of this.
 */
public class ProductServlet extends HttpServlet {

    private static final long serialVersionUID = 1L;

    // Stateless helper: safe to share across all request threads.
    private ProductService service = new ProductService();

    protected void doGet(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {

        response.setContentType("text/html");
        PrintWriter out = response.getWriter();

        String action = request.getParameter("action");
        if (action == null) {
            action = "view";                     // sensible default
        }

        out.println("<html><body>");
        out.println("<h2>Product Manager</h2>");

        // ===== ROUTING: pick the operation, print only its MESSAGE =====
        if (action.equals("view")) {
            // nothing to do — the table below is the whole point of "view"

        } else if (action.equals("insert")) {
            handleInsert(request, out);

        } else if (action.equals("update")) {
            handleUpdate(request, out);

        } else if (action.equals("delete")) {
            handleDelete(request, out);

        } else {
            out.println("<h3><font color='red'>Unknown action: " + action + "</font></h3>");
        }

        // ===== THE REFACTOR: written once, runs for EVERY action, so the
        // user always sees the up-to-date table right below the message. =====
        displayAllProducts(out);

        out.println("<p><a href='product.html'>&laquo; Back to the form</a></p>");
        out.println("</body></html>");
    }

    protected void doPost(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {
        doGet(request, response);
    }

    // ---------- CREATE ----------
    private void handleInsert(HttpServletRequest request, PrintWriter out) {
        try {
            int    id       = Integer.parseInt(request.getParameter("id"));
            String name     = request.getParameter("name");
            double price    = Double.parseDouble(request.getParameter("price"));
            int    quantity = Integer.parseInt(request.getParameter("quantity"));

            Product p = new Product(id, name, price, quantity);

            if (service.addProduct(p)) {
                out.println("<h3><font color='green'>Product added successfully.</font></h3>");
            } else {
                out.println("<h3><font color='red'>Insertion failed — is the id already used, "
                          + "or a value invalid?</font></h3>");
            }
        } catch (NumberFormatException e) {
            out.println("<h3><font color='red'>ID, price and quantity must be numbers.</font></h3>");
        }
    }

    // ---------- UPDATE ----------
    private void handleUpdate(HttpServletRequest request, PrintWriter out) {
        try {
            int    id    = Integer.parseInt(request.getParameter("id"));
            double price = Double.parseDouble(request.getParameter("price"));

            if (service.updateProduct(id, price)) {
                out.println("<h3><font color='green'>Product updated successfully.</font></h3>");
            } else {
                out.println("<h3><font color='red'>Updation failed — no product with id "
                          + id + ".</font></h3>");
            }
        } catch (NumberFormatException e) {
            out.println("<h3><font color='red'>ID and price must be numbers.</font></h3>");
        }
    }

    // ---------- DELETE ----------
    private void handleDelete(HttpServletRequest request, PrintWriter out) {
        try {
            // the delete link sends ?action=delete&p=<id>
            int id = Integer.parseInt(request.getParameter("p"));

            if (service.deleteProduct(id)) {
                out.println("<h3><font color='green'>Product " + id + " deleted.</font></h3>");
            } else {
                out.println("<h3><font color='red'>Deletion failed — no product with id "
                          + id + ".</font></h3>");
            }
        } catch (NumberFormatException e) {
            out.println("<h3><font color='red'>Invalid product id in the delete link.</font></h3>");
        }
    }

    // ---------- THE EXTRACTED METHOD: written ONCE, used by all four ----------
    // 'out' is a PARAMETER, not a field — one servlet instance, many threads.
    // A field would be shared between simultaneous users.
    private void displayAllProducts(PrintWriter out) {

        List<Product> list = service.getAllProducts();

        if (list.isEmpty()) {
            out.println("<h3>No products found.</h3>");
            return;                              // nothing to tabulate
        }

        out.println("<table border='1' cellpadding='6'>");
        out.println("<tr><th>ID</th><th>Name</th><th>Price</th>"
                  + "<th>Quantity</th><th>Action</th></tr>");

        for (Product p : list) {
            out.println("<tr>");
            out.println("<td>" + p.getId()       + "</td>");
            out.println("<td>" + p.getName()     + "</td>");
            out.println("<td>" + p.getPrice()    + "</td>");
            out.println("<td>" + p.getQuantity() + "</td>");
            out.println("<td><a href='product?action=delete&p="
                      + p.getId() + "'>Delete</a></td>");
            out.println("</tr>");
        }

        out.println("</table>");
    }
}

The five-minute triage list 404? URL wrong — check the project name, then <url-pattern>, then restart Tomcat.  500? Read the first line of the stack trace in the Eclipse console.  "No suitable driver"? derby.jar isn't in WEB-INF/lib.  "No products found" but rows exist? Relative Derby path — use an absolute one.  "Already booted"? Disconnect the Data Source Explorer.  NullPointerException? Missing if (con == null) guard in a DAO method.

Habits to keep

  1. Absolute database path, forward slashes, same URL as the explorer
  2. Driver JAR in WEB-INF/lib, not just the driver definition
  3. PreparedStatement with ? — never string concatenation
  4. if (con == null) guard at the top of every DAO method
  5. Close the connection in finally
  6. Return an empty list, never null, from a read
  7. Validation in the service, SQL in the DAO, HTML in the servlet

What you just built Across both sessions you went from "Java prints to a console" to a running, layered web application: a servlet answering HTTP requests, five MVC packages with clean responsibilities, full database CRUD with validation and error handling, and a refactor that removed every line of duplicated display code.

Every Java web framework is built on exactly this. When you write @GetMapping in Spring Boot, it's a URL mapping; @RequestParam is getParameter() with automatic conversion; @Service and @Repository are the layers you just created by hand; and DispatcherServlet is the action router you wrote yourself. You now know what the annotations are doing.
