Concept 1 — the problem

Why routing?

Look at your app right now. Header, login form, two registration forms, a table, cards, stats — all stacked on one endless page. That is not how applications work.

A real app has screens: a home page, a customer list, an add-customer form, an about page. The user moves between them, and — critically — the URL changes to match.

🔗

Shareable URLs

/customers/1002 can be bookmarked, emailed, or pasted into a chat — and it opens the right screen.

⬅️

The Back button works

Users expect it. Without routing, Back leaves your application entirely — which feels broken.

🧠

Only one screen in memory

Angular builds the current screen and discards the rest, instead of holding everything at once.

⚡

Still no page reload

The URL changes and the content swaps, but the browser never re-downloads the page. It stays a single-page application.

Analogy Without routing your app is one very long scroll of paper. With routing it is a ring binder with tabbed dividers — same binder, and you flip straight to the section you want.
The trick that makes this possible The Angular router changes the URL without asking the server for anything. It updates the address bar, records an entry in the browser's history so Back works, and swaps which component is displayed. No reload, no flicker, no lost state.

Concept 1 continued

What a route actually is

A route is just a pairing: this URL path → show that component. Nothing more.

{ path: 'customers', component: CustomerListComponent }

Read it as: "when the URL is /customers, display CustomerListComponent." A routing configuration is simply an array of these pairings.

URL the user is atComponent Angular displays
localhost:4200/redirected to /home
localhost:4200/homeHomeComponent
localhost:4200/customersCustomerListComponent
localhost:4200/customers/addCustomerFormComponent
localhost:4200/customers/1002CustomerDetailComponent — for customer 1002
localhost:4200/anything-elseNotFoundComponent — your 404 page
Notice the paths have no leading slash You write path: 'customers', not path: '/customers'. Angular adds the slash. Writing it yourself is a common early mistake and produces a route that never matches.
The Spring Boot parallel { path: 'customers', component: CustomerListComponent } is Angular's @GetMapping("/customers"). One maps a URL to a component; the other maps a URL to a method. Same idea, different side of the wire.

Concept 2 — setting it up · step 1

Defining your routes

Routes live in their own file, by convention called app-routing.module.ts. Create it with the CLI:

ng generate module app-routing --flat --module=app

--flat means "don't put it in its own folder"; --module=app means "register it in AppModule for me".

src/app/app-routing.module.ts
import { NgModule } from '@angular/core';
import { RouterModule, Routes } from '@angular/router';

import { HomeComponent } from './home/home.component';
import { CustomerListComponent } from './customer-list/customer-list.component';
import { CustomerFormComponent } from './customer-form/customer-form.component';
import { AboutComponent } from './about/about.component';
import { NotFoundComponent } from './not-found/not-found.component';

const routes: Routes = [
  { path: '',              redirectTo: '/home', pathMatch: 'full' },
  { path: 'home',          component: HomeComponent },
  { path: 'customers',     component: CustomerListComponent },
  { path: 'customers/add', component: CustomerFormComponent },
  { path: 'about',         component: AboutComponent },
  { path: '**',            component: NotFoundComponent }
];

@NgModule({
  imports: [RouterModule.forRoot(routes)],   // forRoot — only in the root module
  exports: [RouterModule]                    // so other components can use routerLink
})
export class AppRoutingModule { }
const routes: Routes = [ ]
An array of route objects. Routes is just Angular's type for it.
RouterModule.forRoot(routes)
"Set up the router for the whole application with these routes." forRoot is used once, in the root routing module.
exports: [RouterModule]
Re-exports the router's directives so your components can use routerLink and <router-outlet>. Forget this and nothing works.

<router-outlet> — where the screen appears

You have told Angular which component to show. Now you must tell it where to put it. That is <router-outlet> — a placeholder that the router fills in.

Notice what stays put The header, the nav bar and the footer are outside the outlet, so they never move, never flicker and never reload. Only the region inside the outlet changes. That is how every real application is laid out — a persistent shell around a swappable content area.
Two rules 1. It needs a closing tag: <router-outlet></router-outlet>.
2. If you forget it entirely, your URL will change correctly and nothing will appear on screen — with no error. Angular has a component to show and nowhere to put it.

Concept 2 — setting it up · step 3

routerLink — and why never href

This is a small detail with a large consequence, and it is worth thirty seconds.

❌ <a href="/customers">

  • The browser handles it
  • A full page reload — the whole app restarts
  • Visible white flash
  • All your in-memory state is lost
  • Slow, and it defeats the point of an SPA
→

✅ <a routerLink="/customers">

  • The Angular router handles it
  • Only the outlet's contents change
  • Instant, no flash
  • Services keep their data
  • Back and Forward still work

Two forms of routerLink

<!-- Static path — a plain string, no brackets -->
<a routerLink="/customers">Customers</a>

<!-- Dynamic path — an ARRAY of segments, with brackets -->
<a [routerLink]="['/customers', customer.id]">View</a>
<!-- produces /customers/1002 -->

<!-- also valid, and slightly harder to read -->
<a [routerLink]="'/customers/' + customer.id">View</a>
The bracket rule, one more time No brackets = a plain string. Brackets = an expression Angular evaluates. Exactly the same rule as src versus [src] from Session 2 — nothing new to learn.
The array form is the one to prefer ['/customers', id] lets Angular handle the slashes and URL-encode each segment properly. String concatenation breaks the moment a segment contains a space or a special character.

Concept 2 — a small touch that makes it feel finished

routerLinkActive — highlight the current page

Users need to see where they are. routerLinkActive adds a CSS class to a link automatically whenever its route is the active one.

<nav>
  <a routerLink="/home"      routerLinkActive="active">Home</a>
  <a routerLink="/customers" routerLinkActive="active">Customers</a>
  <a routerLink="/about"     routerLinkActive="active">About</a>
</nav>
/* in your CSS — an ordinary class, nothing special about the name */
nav a.active {
  color: #dd0031;
  font-weight: 700;
  border-bottom: 3px solid #dd0031;
}
You write no logic for this at all No *ngIf, no "which page am I on" field, no click handler. The router already knows the active route, so it maintains the class for you. This is one attribute for a feature that would otherwise be twenty lines.
The one gotcha — an always-active Home link routerLinkActive matches by prefix by default, so a link to / counts as active on every page. Fix it with an exact-match option: 
<a routerLink="/home"
   routerLinkActive="active"
   [routerLinkActiveOptions]="{ exact: true }">Home</a>

Concept 3 — the two routes everyone forgets

A default page, and a 404

The default redirect — what shows at /

{ path: '', redirectTo: '/home', pathMatch: 'full' }
path: ''
The empty path — the bare localhost:4200 with nothing after it.
redirectTo: '/home'
Send them to the home route instead of showing nothing.
pathMatch: 'full'
Required here. "Only redirect when the whole URL is empty." Without it, the empty path matches the start of every URL and redirects everything to home — an infinite loop.

The 404 — what shows for an unknown URL

{ path: '**', component: NotFoundComponent }

** is the wildcard: it matches anything at all. So this route catches every URL that none of your other routes matched — a typo, a stale bookmark, a broken link.

not-found.component.html — keep it helpful
<div class="not-found">
  <h2>404 — Page not found</h2>
  <p>We couldn't find the page you asked for.</p>
  <a routerLink="/home">← Back to home</a>
</div>
Without a wildcard route, a bad URL shows a blank page and a console error "Cannot match any routes. URL Segment: 'customerz'" — visible only to you, in the console. Your user just sees nothing at all. Always add the wildcard.

Concept 3 continued — the rule that causes silent bugs

Route order matters — a lot

Angular checks routes top to bottom and uses the first one that matches. It does not look for the best match.

❌ Broken — wildcard first

const routes: Routes = [
  { path: '**',
    component: NotFoundComponent },
  { path: 'home',
    component: HomeComponent },
  { path: 'customers',
    component: CustomerListComponent }
];

Every URL matches ** first, so every page shows the 404. No error is reported anywhere.

✅ Correct — wildcard last

const routes: Routes = [
  { path: '', redirectTo: '/home',
    pathMatch: 'full' },
  { path: 'home',
    component: HomeComponent },
  { path: 'customers',
    component: CustomerListComponent },
  { path: '**',
    component: NotFoundComponent }
];

Specific routes are tried first; the wildcard only catches what is left over.

The ordering rule, in one line Most specific first, wildcard ** always last. Put static paths like customers/add above parameter paths like customers/:id — otherwise /customers/add is read as "customer with id add".
That last point is a real bug you will hit With customers/:id listed first, clicking "Add Customer" opens the detail screen looking for a customer whose id is the string "add". You get an empty form or a crash, and nothing tells you why. Static before dynamic.

Concept 3 — the recipe

Adding a route, end to end

Five steps, every time. Once you have done it twice it takes about ninety seconds.

1 · Generate ng g c reports — creates the component and registers it in declarations.
2 · Import In app-routing.module.ts: import { ReportsComponent } from './reports/reports.component';
3 · Add the route { path: 'reports', component: ReportsComponent } — above the wildcard.
4 · Add the link <a routerLink="/reports" routerLinkActive="active">Reports</a>
5 · Test both ways Click the link and type localhost:4200/reports straight into the address bar. Both must work.
Why step 5 matters Clicking a link and typing a URL take different paths through the router. If the link works but a typed URL does not, your route is fine and something else is wrong — usually a missing wildcard, or a deployment that hasn't been told to send unknown URLs to index.html.

Concept 4 — passing data in the URL

Route parameters

You cannot write one route per customer. Instead you declare a placeholder in the path with a colon:

{ path: 'customers/:id', component: CustomerDetailComponent }

Now /customers/1002, /customers/1003 and /customers/9999 all match this one route, and the router hands you the value that filled the placeholder.

URLMatchesid is
/customers/1002✔"1002" — a string
/customers/1003✔"1003"
/customers✖ — no id segment—
/customers/1002/edit✖ — one segment too many—

Linking to it

<tr *ngFor="let c of customers">
  <td>{{ c.name }}</td>
  <td>
    <a [routerLink]="['/customers', c.id]">View</a>
  </td>
</tr>
The trap that catches everybody: parameters are always strings /customers/1002 gives you the string "1002", never the number 1002. So c.id === id is false — 1002 === "1002" compares a number with a string. Always convert first: const id = Number(params.get('id')); Then use === as normal. This is the number one route-parameter bug.

Concept 4 continued — reading the parameter

Reading a route parameter with ActivatedRoute

To find out which id the user asked for, you inject ActivatedRoute — a service describing the currently active route. Dependency injection, once again.

customer-detail.component.ts
import { Component, OnInit } from '@angular/core';
import { ActivatedRoute, Router } from '@angular/router';
import { Customer } from '../models/customer';
import { CustomerService } from '../services/customer.service';

@Component({ /* ... */ })
export class CustomerDetailComponent implements OnInit {

  customer: Customer | undefined;
  notFound = false;

  constructor(private route: ActivatedRoute,           // reads the URL
              private router: Router,                  // navigates
              private customerService: CustomerService) { }

  ngOnInit(): void {
    // 1. read the raw parameter — it is a STRING
    const raw = this.route.snapshot.paramMap.get('id');

    // 2. convert it to a number
    const id = Number(raw);

    // 3. look it up
    this.customer = this.customerService.getById(id);

    // 4. handle "not found" — never assume the id is valid
    if (!this.customer) {
      this.notFound = true;
    }
  }

  goBack(): void {
    this.router.navigate(['/customers']);
  }
}
route.snapshot.paramMap.get('id')
Reads the parameter once, as it is right now. The name 'id' must match the :id in your route.
Number(raw)
The conversion from the previous slide. Skip this and your lookup silently finds nothing.
if (!this.customer)
Someone will type /customers/9999. Handle it, or the template crashes on undefined.
snapshot versus subscribing snapshot reads the value once, which is right the vast majority of the time. It is not enough if the user can go from /customers/1002 to /customers/1003 without leaving the component — Angular reuses the instance and ngOnInit does not run again. For that case, subscribe instead: this.route.paramMap.subscribe(p => { ... }); — another Observable, same subscribe as Session 3.

Concept 5 — navigating without a link

Navigating from code with Router

routerLink is for things the user clicks. But sometimes your code needs to navigate: after a successful save, after a login, after a delete. For that you inject the Router service.

import { Router } from '@angular/router';

constructor(private router: Router) { }

// simple navigation
goHome(): void {
  this.router.navigate(['/home']);
}

// with a parameter
viewCustomer(id: number): void {
  this.router.navigate(['/customers', id]);      // → /customers/1002
}

// the classic: navigate after a successful save
onSave(): void {
  this.customerService.add(this.form.value).subscribe({
    next: () => {
      this.router.navigate(['/customers']);      // ← inside next, on SUCCESS only
    },
    error: () => {
      this.message = 'Save failed — you are still on the form.';
    }
  });
}
Note where that navigate call sits Inside next. Navigating immediately after calling subscribe would take the user away before the server had replied — so a failed save would look like a successful one. Navigate on confirmed success, exactly as you updated the screen inside next in Session 3.

The three ways to navigate — a summary

WayUse it when
routerLink="/customers"The user clicks something. Preferred — it renders a real, right-clickable link.
[routerLink]="['/customers', id]"The same, with a dynamic segment.
this.router.navigate([...])Your code decides — after a save, a login, a delete, or a timeout.
Query parameters, briefly this.router.navigate(['/customers'], { queryParams: { search: 'anoop' } }) produces /customers?search=anoop, read back with this.route.snapshot.queryParamMap.get('search'). Use route parameters for "which record" and query parameters for optional extras like search terms, filters and page numbers.

Concept 6 — the case study · the plan

Customer Management — what we're building

One screen with a complete set of data operations. CRUD stands for the four things every business application does:

➕

C — Create

A form adds a new customer. push() locally, POST against an API.

📖

R — Read

A table lists them, with a search box that filters as you type. filter() locally, GET against an API.

✏️

U — Update

Click a row, the form fills in, edit, save. findIndex() locally, PUT against an API.

🗑️

D — Delete

A confirmation, then removal. splice() locally, DELETE against an API.

The plan — we build it three times, and that's deliberate Round 1: everything inside one component, against a plain array. Simple, all in one place, easy to follow.
Round 2: move the data operations into a service. The component gets smaller.
Round 3: swap the service's array for HttpClient. The component barely changes at all.

Seeing the same feature three ways is what makes the value of layering obvious rather than theoretical.
Everything today is something you already know The six array methods from Session 1. *ngFor, *ngIf and ngClass from Session 2. Reactive forms, services and HttpClient from Session 3. There is almost no new syntax in this case study — it is assembly, not new learning.

export class CustomerListComponent implements OnInit {

  // ── screen state ──────────────────────────────────────
  searchTerm = '';
  message = '';

  // ── edit mode ─────────────────────────────────────────

  custForm: FormGroup;

  constructor(private fb: FormBuilder) {
    this.custForm = this.fb.group({
      name:    ['', [Validators.required, Validators.minLength(3)]],
      city:    ['', [Validators.required]],
      email:   ['', [Validators.required, Validators.email]],
      balance: [0,  [Validators.required, Validators.min(0)]]
    });
  }

  ngOnInit(): void { /* load the data — next slide */ }
}
Two design decisions worth explaining 1. Two arrays. allCustomers is the master list; customers is what the table shows. If you filter the master list, clearing the search box cannot bring the rows back — you destroyed them. Same pattern as Session 2's employee search.
2. editingId: number | null. One field carries the whole insert-versus-update distinction: null means "adding a new one", a number means "editing that id". This single field is what lets one form do both jobs.

Concept 6 · R for Read, part two

Read: search and filter

The class

onSearch(): void {
  const t = this.searchTerm
                .trim().toLowerCase();

  if (t === '') {
    this.customers = this.allCustomers;
    return;
  }

  this.customers =
    this.allCustomers.filter(c =>
      c.name.toLowerCase().includes(t) ||
      c.city.toLowerCase().includes(t) ||
      c.email.toLowerCase().includes(t)
    );
}

clearSearch(): void {
  this.searchTerm = '';
  this.onSearch();
}

The template

<input [(ngModel)]="searchTerm"
       (input)="onSearch()"
       name="searchTerm"
       placeholder="Search name, city
                    or email…">

<button (click)="clearSearch()"
        [disabled]="!searchTerm">
  Clear
</button>

<p>
  Showing {{ customers.length }}
  of {{ allCustomers.length }}
</p>
Why searching in the browser is instant — and when it isn't right The data is already in memory, so filtering costs nothing and needs no server round-trip. That is why an Angular search box feels instant next to a JSP page that reloads.

The limit: this only works because we have three customers. With fifty thousand you would not download them all — you would send the search term to the server (GET /customers?search=anoop) and let the database do the work. Knowing which approach a situation needs is the actual skill.
Always filter the master list, never the displayed one this.customers = this.allCustomers.filter(...) — correct.
this.customers = this.customers.filter(...) — wrong. Each keystroke narrows the already-narrowed list, so deleting a character never brings rows back.

Concept 6 · C for Create

Create: inserting a new customer

onSubmit(): void {
  if (this.custForm.invalid) {
    this.custForm.markAllAsTouched();      // reveal every error at once
    return;
  }

  if (this.editingId === null) {
    // ── ADD MODE ──────────────────────────────────────
    const newCustomer: Customer = {
      id: this.getNextId(),                // generate an id locally
      name:    this.custForm.value.name,
      city:    this.custForm.value.city,
      email:   this.custForm.value.email,
      balance: this.custForm.value.balance
    };

    this.allCustomers.push(newCustomer);
    this.message = 'Added ' + newCustomer.name + '.';

  } else {
    // ── EDIT MODE — the next slide but one ────────────
  }

  this.resetForm();
  this.onSearch();          // re-apply the filter so the table matches
}

private getNextId(): number {
  if (this.allCustomers.length === 0) { return 1001; }
  return Math.max(...this.allCustomers.map(c => c.id)) + 1;
}

resetForm(): void {
  this.custForm.reset({ name: '', city: '', email: '', balance: 0 });
  this.editingId = null;
}
Three details worth copying 1. Validate first and markAllAsTouched(), so a user who clicks Save on an empty form is told why nothing happened.
2. getNextId() takes the highest existing id and adds one — never length + 1, which produces duplicates as soon as anything is deleted.
3. Call onSearch() afterwards. Without it, a new customer is added to allCustomers but the table — which shows customers — does not update, and the row appears to have vanished.
Generating ids locally is a temporary measure Once a real server is involved, the database assigns ids. You will send id: 0 and use the id that comes back in the response — exactly as in Session 3's POST stretch task.

Concept 6 · D for Delete

Delete: with a confirmation step

onDelete(customer: Customer): void {

  // Never delete on a single click. Always confirm.
  const ok = confirm('Delete ' + customer.name + '? This cannot be undone.');
  if (!ok) { return; }

  // find the position, then remove one item there
  const i = this.allCustomers.findIndex(c => c.id === customer.id);
  if (i !== -1) {
    this.allCustomers.splice(i, 1);
  }

  // if we were editing this very customer, get out of edit mode
  if (this.editingId === customer.id) {
    this.resetForm();
  }

  this.message = 'Deleted ' + customer.name + '.';
  this.onSearch();                       // refresh the displayed list
}
confirm(...)
The browser's built-in Yes/No dialog. Ugly but honest, and it takes one line. Real projects use a styled modal — the logic is identical.
findIndex + splice
Get the position, remove one item there. Straight out of Session 1's Drill H.
if (this.editingId === ...)
An edge case people miss: deleting the customer you are currently editing would leave the form pointing at something that no longer exists.
Alternative: filter instead of findIndex + splice this.allCustomers = this.allCustomers.filter(c => c.id !== customer.id); does the same job in one line, and is arguably clearer. The difference: splice modifies the existing array, filter creates a new one. Both are correct — filter is the more modern style.
Always confirm destructive actions A misplaced click that silently deletes a customer is the kind of thing that ends up in a support ticket. One confirm() prevents it. Session 3's rule also applies once a server is involved: when the delete is an HTTP call, remove the row inside next, so a failed delete does not leave your screen lying to the user.

Concept 6 · U for Update

Update: click a row, edit, save

Update is two halves: load the row into the form, then save the changes back over the original.

Half 1 — loading the row into the form
startEdit(customer: Customer): void {
  this.editingId = customer.id;            // remember WHICH one we're editing

  // ONE LINE fills the whole form. This is why we used a reactive form.
  this.custForm.patchValue({
    name:    customer.name,
    city:    customer.city,
    email:   customer.email,
    balance: customer.balance
  });

  this.message = 'Editing ' + customer.name + '. Change the fields and press Save.';
}

cancelEdit(): void {
  this.resetForm();                        // sets editingId back to null
  this.message = 'Edit cancelled.';
}
Half 2 — saving it back (the else branch from the Create slide)
  } else {
    // ── EDIT MODE ──────────────────────────────────────
    const i = this.allCustomers.findIndex(c => c.id === this.editingId);

    if (i !== -1) {
      this.allCustomers[i] = {
        id: this.editingId,                // KEEP the original id
        name:    this.custForm.value.name,
        city:    this.custForm.value.city,
        email:   this.custForm.value.email,
        balance: this.custForm.value.balance
      };
      this.message = 'Updated successfully.';
    }
  }
patchValue is the whole reason Session 3 taught reactive forms Filling an entire form from an object takes one call. In a template-driven form you would assign every property by hand, one line each — and remember to add a line every time someone adds a field. This slide is where that lesson pays off.
Keep the id — always The form has no id field, so you must reuse this.editingId. Build the replacement object with a fresh or missing id and you have silently created a duplicate rather than updated a record.

Concept 7 — round 2 · the same CRUD, through a service

Moving the operations into a service

Round 1 works, and it puts data logic inside a component — exactly what Session 3 taught you not to do. Round 2 fixes it.

src/app/services/customer.service.ts
import { Injectable } from '@angular/core';
import { Customer } from '../models/customer';

@Injectable({ providedIn: 'root' })
export class CustomerService {

  private customers: Customer[] = [
    { id: 1001, name: 'Anoop Kumar', city: 'Ahmedabad', email: 'anoop@example.com', balance: 15000 },
    { id: 1002, name: 'Ajay Sharma', city: 'Pune',      email: 'ajay@example.com',  balance: 0 },
    { id: 1003, name: 'Rekha Nair',  city: 'Kochi',     email: 'rekha@example.com', balance: 42500 }
  ];

  getAll(): Customer[] {
    return this.customers;
  }

  getById(id: number): Customer | undefined {
    return this.customers.find(c => c.id === id);
  }

  search(term: string): Customer[] {
    const t = term.trim().toLowerCase();
    if (t === '') { return this.customers; }
    return this.customers.filter(c =>
      c.name.toLowerCase().includes(t) ||
      c.city.toLowerCase().includes(t) ||
      c.email.toLowerCase().includes(t)
    );
  }

  add(customer: Customer): Customer {
    customer.id = this.getNextId();
    this.customers.push(customer);
    return customer;
  }

  update(customer: Customer): boolean {
    const i = this.customers.findIndex(c => c.id === customer.id);
    if (i === -1) { return false; }
    this.customers[i] = customer;
    return true;
  }

  delete(id: number): boolean {
    const i = this.customers.findIndex(c => c.id === id);
    if (i === -1) { return false; }
    this.customers.splice(i, 1);
    return true;
  }

  private getNextId(): number {
    if (this.customers.length === 0) { return 1001; }
    return Math.max(...this.customers.map(c => c.id)) + 1;
  }
}
Look at the method names getAll, getById, add, update, delete. That is deliberately the shape of a repository — and it is why round 3 can swap the array for HTTP calls without renaming anything.

Concept 8 — round 3 · the same CRUD over HTTP

The service, talking to a real API

Now replace the array with network calls. The method names stay identical — only the bodies and the return types change.

src/app/services/customer.service.ts
import { Injectable } from '@angular/core';
import { HttpClient } from '@angular/common/http';
import { Observable } from 'rxjs';
import { Customer } from '../models/customer';

@Injectable({ providedIn: 'root' })
export class CustomerService {

  // ONE line to change when you switch backends
  private baseUrl = 'http://localhost:8080/api/customers';

  constructor(private http: HttpClient) { }

  getAll(): Observable<Customer[]> {
    return this.http.get<Customer[]>(this.baseUrl);
  }

  getById(id: number): Observable<Customer> {
    return this.http.get<Customer>(this.baseUrl + '/' + id);
  }

  add(customer: Customer): Observable<Customer> {
    return this.http.post<Customer>(this.baseUrl, customer);
  }

  update(customer: Customer): Observable<Customer> {
    return this.http.put<Customer>(this.baseUrl + '/' + customer.id, customer);
  }

  delete(id: number): Observable<void> {
    return this.http.delete<void>(this.baseUrl + '/' + id);
  }
}
The one real difference Every method now returns an Observable instead of a value. So every caller must .subscribe(). That is the only structural change — and it is exactly why Session 3 spent time on Observables before we got here.
Note the search method is gone With a real backend, searching is the database's job: getAll() then filter locally for small lists, or add search(term): Observable<Customer[]> hitting ?search=term for large ones. Do not download fifty thousand rows to filter three.

Concept 8 continued

The component, with subscribe

ngOnInit(): void {
  this.loadCustomers();
}

loadCustomers(): void {
  this.isLoading = true;
  this.errorMessage = '';

  this.customerService.getAll().subscribe({
    next: (data) => {
      this.allCustomers = data;
      this.customers = data;
      this.isLoading = false;
    },
    error: (err) => {
      this.errorMessage = 'Could not load customers. Is the API running?';
      this.isLoading = false;
      console.error(err);
    }
  });
}

onDelete(c: Customer): void {
  if (!confirm('Delete ' + c.name + '?')) { return; }

  this.customerService.delete(c.id).subscribe({
    next: () => {
      this.loadCustomers();                 // reload so the screen matches the server
      this.message = 'Deleted.';
    },
    error: () => { this.message = 'Delete failed — the customer is still there.'; }
  });
}

onSubmit(): void {
  if (this.custForm.invalid) { this.custForm.markAllAsTouched(); return; }

  const customer: Customer = {
    id: this.editingId ?? 0,                // 0 for a new one; the server assigns it
    ...this.custForm.value
  };

  const call = this.editingId === null
    ? this.customerService.add(customer)
    : this.customerService.update(customer);

  call.subscribe({
    next: () => { this.resetForm(); this.loadCustomers(); },
    error: () => { this.message = 'Save failed.'; }
  });
}
Two patterns to take away from that code 1. Reload after a change. After a successful add, update or delete, call loadCustomers() again. It guarantees the screen matches the server — including anything a colleague changed a moment ago. Slower than patching locally; far more trustworthy.
2. Choose the call, then subscribe once. const call = condition ? a() : b(); then one .subscribe(). Remember Observables are lazy, so building it without subscribing sends nothing — which makes this pattern safe.

Concept 9 — the full-stack moment

Connecting to your Spring Boot API

This is the payoff for eight sessions of work. On the Angular side it is one line.

private baseUrl = 'http://localhost:8080/api/customers';
the Spring Boot side — everything here is Spring Boot Session 2 material
@CrossOrigin(origins = "http://localhost:4200")   // ← REQUIRED, or CORS blocks you
@RestController
@RequestMapping("/api/customers")
public class CustomerController {

    @Autowired
    private CustomerService service;

    @GetMapping
    public List<Customer> getAll() { return service.findAll(); }

    @GetMapping("/{id}")
    public Customer getById(@PathVariable Long id) { return service.findById(id); }

    @PostMapping
    public Customer create(@RequestBody Customer c) { return service.save(c); }

    @PutMapping("/{id}")
    public Customer update(@PathVariable Long id, @RequestBody Customer c) {
        c.setId(id);
        return service.save(c);
    }

    @DeleteMapping("/{id}")
    public void delete(@PathVariable Long id) { service.deleteById(id); }
}
Read those two code blocks side by side http.get(baseUrl) ↔ @GetMapping. http.post(baseUrl, c) ↔ @PostMapping with @RequestBody. http.delete(baseUrl + '/' + id) ↔ @DeleteMapping("/{id}") with @PathVariable.

You now know both ends of the wire. That is what the whole eight-session programme was for.
Three things to check when it doesn't work first time 1. CORS. Without @CrossOrigin the browser blocks the request and the message says CORS. Fix it on the server.
2. Field names must match exactly. Java's customerName arrives as customerName — if your TypeScript interface says name, you get undefined. Check with {{ data | json }}.
3. Is the API actually running? Open http://localhost:8080/api/customers directly in a browser tab first. If it fails there, the problem is not in Angular.

Before you go and build things

Do these, avoid those

✅ Do

  • Put HTTP calls and data logic in a service
  • Use ng generate for everything
  • Type everything — interfaces for all API data
  • Always provide an error handler in subscribe
  • Show loading, error and empty states
  • Confirm before anything destructive
  • Keep components small and single-purpose
  • trackBy on any list that changes
  • Reactive forms for anything with real rules
  • Wildcard ** route last, always
  • Read the error message before reacting to it

❌ Avoid

  • HttpClient directly inside a component
  • new EmployeeService() — always inject
  • any as a habit rather than a note
  • Forgetting .subscribe() — nothing happens
  • Updating the screen before the server confirms
  • document.getElementById — bind instead
  • Heavy work inside {{ method() }}
  • Secrets or passwords in front-end code
  • Fetching data in the constructor
  • href for internal links — use routerLink
  • Trying to fix a CORS error in Angular
If you remember only three things from this series 1. Data flows down, events flow up.
2. Components display; services fetch.
3. Change the data and let Angular update the screen — never touch the DOM yourself.

The errors you'll hit today

SymptomCause and fix

'router-outlet' is not a known elementAppRoutingModule isn't in AppModule's imports, or it doesn't export RouterModule.
Can't bind to 'routerLink'Same cause. Your routing module must have exports: [RouterModule].

Shipping it

Building for production

Everything so far has run under ng serve, which is a development server — unoptimised, on your machine only. To deploy, you build.

ng build
dist/hello-world/browser/ ├── index.html the one page ├── main-A1B2C3.js your whole app, compiled and minified ├── polyfills-D4E5F6.js browser compatibility shims └── styles-G7H8I9.css your global styles
What the build doesWhy it matters
Compiles TypeScript → JavaScriptBrowsers cannot run TypeScript. No .ts file reaches the user.
MinifiesStrips comments, whitespace and long names. Far smaller download.
Tree-shakesRemoves code nothing uses — including services you never injected.
Hashes filenamesmain-A1B2C3.js — when you redeploy, the name changes, so browsers cannot serve a stale cached copy.
Deploying it is genuinely simple The contents of that folder are plain static files. Copy them to any web server — Apache, Nginx, S3, GitHub Pages, or your Spring Boot app's src/main/resources/static folder, which then serves your Angular app and your API from the same origin and eliminates the CORS problem entirely.
One deployment gotcha to know about Your server must send unknown URLs to index.html. Otherwise a user who bookmarks /customers and revisits it gets a server 404 — the server looks for a file called "customers", which does not exist. Angular's router only runs once index.html has loaded. On Nginx that is try_files $uri /index.html;.

Recap

What you now know

  • A route pairs a URL path with a component, and Routes is just an array of those pairings.
  • RouterModule.forRoot(routes) sets the router up; exports: [RouterModule] is what lets your components use routerLink.
  • <router-outlet> marks where the routed component appears — everything outside it is a persistent shell.
  • routerLink navigates without a reload; href restarts your whole application.
  • routerLinkActive highlights the current page with no logic of your own.
  • A default redirectTo needs pathMatch: 'full', and a ** wildcard 404 route goes last.
  • Routes are matched top to bottom, first match wins — so static paths go above dynamic ones.
  • Route parameters (:id) are read with ActivatedRoute and are always strings — convert with Number().
  • this.router.navigate([...]) navigates from code, and belongs inside next so it only runs on genuine success.
  • CRUD is the six array methods you learned in Session 1: push, filter, find, findIndex, splice, map.
  • One form handles both insert and update, driven by a single editingId field and patchValue().
  • Two arrays — a master list and a displayed list — is what makes search reversible.
  • Moving CRUD onto a service and then onto HttpClient left the template unchanged, for the fourth time in this series.
  • Your Angular service's five methods map one-to-one onto your Spring Boot controller's five mappings.
  • ng build produces plain static files in dist/ — and serving them from Spring Boot removes the CORS problem entirely.
