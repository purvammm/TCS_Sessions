Orientation — read this before you Google anything today

The Angular 19 way, versus what you'll find online

Most Angular tutorials on the internet were written for Angular 8–15. They still work, but they are not how Angular 19 is written. Today's session uses the modern style throughout, so keep this table in your head — it is the translation key for every older article you will ever read.

Older tutorials sayAngular 19 saysWhy it changed

declarations: [ ... ]nothing — components are standaloneIn v19 standalone: true is the default; you no longer write it.
app-routing.module.ts + RouterModule.forRoot()app.routes.ts + provideRouter(routes)Routing is a provider, not a module.

Nothing you learned is wasted The concepts are unchanged — components, bindings, DI, services, Observables. Only the packaging changed: modules became providers, and directives became language keywords. If you inherit an older Angular codebase at work, everything in the left column will look familiar and you will know what it maps to.
The one thing that will confuse you when copying from the internet In Angular 19 a standalone component must import what its own template uses. Paste a snippet containing routerLink into a component that doesn't list RouterLink in its imports: [ ] array and it fails — even though the same snippet worked fine in an NgModule app, because there the module imported it once for everybody.

Concept 1 — the problem

Why routing?

Look at your app right now. Header, login form, two registration forms, a table, cards, stats — all stacked on one endless page. That is not how applications work.

A real app has screens: a home page, a customer list, an add-customer form, an about page. The user moves between them, and — critically — the URL changes to match.

🔗

Shareable URLs

/customers/1002 can be bookmarked, emailed, or pasted into a chat — and it opens the right screen.

⬅️

The Back button works

Users expect it. Without routing, Back leaves your application entirely — which feels broken.

🧠

Only one screen in memory

Angular builds the current screen and discards the rest, instead of holding everything at once.

⚡

Still no page reload

The URL changes and the content swaps, but the browser never re-downloads the page. It stays a single-page application.

Analogy Without routing your app is one very long scroll of paper. With routing it is a ring binder with tabbed dividers — same binder, and you flip straight to the section you want.
The trick that makes this possible The Angular router changes the URL without asking the server for anything. It updates the address bar, records an entry in the browser's history so Back works, and swaps which component is displayed. No reload, no flicker, no lost state.

Concept 1 continued

What a route actually is

A route is just a pairing: this URL path → show that component. Nothing more.

{ path: 'customers', component: CustomerListComponent }

Read it as: "when the URL is /customers, display CustomerListComponent." A routing configuration is simply an array of these pairings — and in Angular 19 that array lives in a plain .ts file, with no class or module around it.

URL the user is atComponent Angular displays
localhost:4200/redirected to /home
localhost:4200/homeHomeComponent
localhost:4200/customersCustomerListComponent
localhost:4200/customers/addCustomerFormComponent
localhost:4200/customers/1002CustomerDetailComponent — for customer 1002
localhost:4200/anything-elseNotFoundComponent — your 404 page
Notice the paths have no leading slash You write path: 'customers', not path: '/customers'. Angular adds the slash. Writing it yourself is a common early mistake and produces a route that never matches.
The Spring Boot parallel { path: 'customers', component: CustomerListComponent } is Angular's @GetMapping("/customers"). One maps a URL to a component; the other maps a URL to a method. Same idea, different side of the wire.

<router-outlet> — where the screen appears

You have told Angular which component to show. Now you must tell it where to put it. That is <router-outlet> — a placeholder that the router fills in.

Notice what stays put The header, the nav bar and the footer are outside the outlet, so they never move, never flicker and never reload. Only the region inside the outlet changes. That is how every real application is laid out — a persistent shell around a swappable content area.
The two Angular 19 failure modes 1. You forgot RouterOutlet in imports. The compiler tells you: "'router-outlet' is not a known element". This is the good case — you get a real error.
2. You forgot the tag itself. Your URL changes correctly and nothing appears on screen — with no error at all. Angular has a component to show and nowhere to put it.

Concept 2 — setting it up · step 3

routerLink — and why never href

This is a small detail with a large consequence, and it is worth thirty seconds.

❌ <a href="/customers">

  • The browser handles it
  • A full page reload — the whole app restarts
  • Visible white flash
  • All your in-memory state is lost
  • Slow, and it defeats the point of an SPA
→

✅ <a routerLink="/customers">

  • The Angular router handles it
  • Only the outlet's contents change
  • Instant, no flash
  • Services keep their data
  • Back and Forward still work

Two forms of routerLink

<!-- Static path — a plain string, no brackets -->
<a routerLink="/customers">Customers</a>

<!-- Dynamic path — an ARRAY of segments, with brackets -->
<a [routerLink]="['/customers', customer.id]">View</a>
<!-- produces /customers/1002 -->

<!-- also valid, and slightly harder to read -->
<a [routerLink]="'/customers/' + customer.id">View</a>
The bracket rule, one more time No brackets = a plain string. Brackets = an expression Angular evaluates. Exactly the same rule as src versus [src] from Session 2 — nothing new to learn.
Two things to remember 1. Prefer the array form: ['/customers', id] lets Angular handle the slashes and URL-encode each segment properly. String concatenation breaks the moment a segment contains a space or a special character.
2. RouterLink must be in the imports array of every standalone component whose template uses it — not just the root one. Miss it and you get "Can't bind to 'routerLink' since it isn't a known property of 'a'".

Concept 2 — a small touch that makes it feel finished

routerLinkActive — highlight the current page

Users need to see where they are. routerLinkActive adds a CSS class to a link automatically whenever its route is the active one.

<nav>
  <a routerLink="/home"      routerLinkActive="active">Home</a>
  <a routerLink="/customers" routerLinkActive="active">Customers</a>
  <a routerLink="/about"     routerLinkActive="active">About</a>
</nav>
/* in your CSS — an ordinary class, nothing special about the name */
nav a.active {
  color: #dd0031;
  font-weight: 700;
  border-bottom: 3px solid #dd0031;
}
You write no logic for this at all No @if, no "which page am I on" signal, no click handler. The router already knows the active route, so it maintains the class for you. This is one attribute for a feature that would otherwise be twenty lines.
The one gotcha — an always-active Home link routerLinkActive matches by prefix by default, so a link to / counts as active on every page. Fix it with an exact-match option: 
<a routerLink="/home"
   routerLinkActive="active"
   [routerLinkActiveOptions]="{ exact: true }">Home</a>
Don't forget the import RouterLinkActive is a separate directive from RouterLink, so it needs its own entry: imports: [RouterOutlet, RouterLink, RouterLinkActive]. If the highlight simply never appears and there is no error, check the import list first — Angular treats an unknown attribute as a plain HTML attribute and silently ignores it.

Concept 3 — the two routes everyone forgets

A default page, and a 404

The default redirect — what shows at /

{ path: '', redirectTo: 'home', pathMatch: 'full' }
path: ''
The empty path — the bare localhost:4200 with nothing after it.
redirectTo: 'home'
Send them to the home route instead of showing nothing.
pathMatch: 'full'
Required here. "Only redirect when the whole URL is empty." Without it, the empty path matches the start of every URL and redirects everything to home — an infinite loop.

The 404 — what shows for an unknown URL

{ path: '**', component: NotFoundComponent }

** is the wildcard: it matches anything at all. So this route catches every URL that none of your other routes matched — a typo, a stale bookmark, a broken link.

not-found.component.html — keep it helpful
<div class="not-found">
  <h2>404 — Page not found</h2>
  <p>We couldn't find the page you asked for.</p>
  <a routerLink="/home">← Back to home</a>
</div>
That template uses routerLink, so the component must import it 
@Component({
  selector: 'app-not-found',
  imports: [RouterLink],               // ← easy to forget in a small component
  templateUrl: './not-found.component.html'
})
export class NotFoundComponent { }
Without a wildcard route, a bad URL shows a blank page and a console error "NG04002: Cannot match any routes. URL Segment: 'customerz'" — visible only to you, in the console. Your user just sees nothing at all. Always add the wildcard.

Concept 3 continued — the rule that causes silent bugs

Route order matters — a lot

Angular checks routes top to bottom and uses the first one that matches. It does not look for the best match.

❌ Broken — wildcard first

export const routes: Routes = [
  { path: '**',
    component: NotFoundComponent },
  { path: 'home',
    component: HomeComponent },
  { path: 'customers',
    component: CustomerListComponent }
];

Every URL matches ** first, so every page shows the 404. No error is reported anywhere.

✅ Correct — wildcard last

export const routes: Routes = [
  { path: '', redirectTo: 'home',
    pathMatch: 'full' },
  { path: 'home',
    component: HomeComponent },
  { path: 'customers',
    component: CustomerListComponent },
  { path: '**',
    component: NotFoundComponent }
];

Specific routes are tried first; the wildcard only catches what is left over.

The ordering rule, in one line Most specific first, wildcard ** always last. Put static paths like customers/add above parameter paths like customers/:id — otherwise /customers/add is read as "customer with id add".
That last point is a real bug you will hit With customers/:id listed first, clicking "Add Customer" opens the detail screen looking for a customer whose id is the string "add". You get an empty form or a crash, and nothing tells you why. Static before dynamic.

Concept 3 — the recipe

Adding a route, end to end

Four steps, every time — one fewer than in older Angular, because there are no declarations to maintain. Once you have done it twice it takes about sixty seconds.

1 · Generate ng g c pages/reports — creates a standalone component. Nothing to register anywhere.
2 · Import + route In app.routes.ts: import the class, then add { path: 'reports', component: ReportsComponent } — above the wildcard.
3 · Add the link <a routerLink="/reports" routerLinkActive="active">Reports</a> in the shell, which already imports RouterLink.
4 · Test both ways Click the link and type localhost:4200/reports straight into the address bar. Both must work.
The lazy alternative, worth knowing from day one Swap component: for loadComponent: and that screen's code is downloaded only when someone first visits it: 
{
  path: 'reports',
  loadComponent: () =>
    import('./pages/reports/reports.component').then(m => m.ReportsComponent)
}
With standalone components this is a one-line change per route — in older Angular it meant creating a feature module. On a large app it is the single biggest startup-time win available.
Why step 4 matters Clicking a link and typing a URL take different paths through the router. If the link works but a typed URL does not, your route is fine and something else is wrong — usually a missing wildcard, or a deployment that hasn't been told to send unknown URLs to index.html.

Concept 4 — passing data in the URL

Route parameters

You cannot write one route per customer. Instead you declare a placeholder in the path with a colon:

{ path: 'customers/:id', component: CustomerDetailComponent }

Now /customers/1002, /customers/1003 and /customers/9999 all match this one route, and the router hands you the value that filled the placeholder.

URLMatchesid is
/customers/1002✔"1002" — a string
/customers/1003✔"1003"
/customers✖ — no id segment—
/customers/1002/edit✖ — one segment too many—

Linking to it

@for (c of customers(); track c.id) {
  <tr>
    <td>{{ c.name }}</td>
    <td><a [routerLink]="['/customers', c.id]">View</a></td>
  </tr>
}
The trap that catches everybody: parameters are always strings /customers/1002 gives you the string "1002", never the number 1002. So c.id === id is false — 1002 === "1002" compares a number with a string. Always convert first with Number(...), then use === as normal. This is the number one route-parameter bug, and Angular 19 has a tidy way to do the conversion for you — next slide.

Concept 4 continued — reading the parameter, the Angular 19 way

Route parameter → signal input()

Because we turned on withComponentInputBinding() back in app.config.ts, the router will hand the parameter to your component as an input, named after the placeholder. No service to inject, no string to parse by hand.

src/app/pages/customer-detail/customer-detail.component.ts
import { Component, computed, inject, input } from '@angular/core';
import { Router, RouterLink } from '@angular/router';
import { CurrencyPipe } from '@angular/common';
import { CustomerService } from '../../services/customer.service';

@Component({
  selector: 'app-customer-detail',
  imports: [RouterLink, CurrencyPipe],
  templateUrl: './customer-detail.component.html',
  styleUrl: './customer-detail.component.css'
})
export class CustomerDetailComponent {

  private customerService = inject(CustomerService);
  private router = inject(Router);

  // The name 'id' MUST match the :id in the route path.
  // <number, string> means: "the template sees a number; the router writes a string".
  // The transform does the conversion the old code had to remember to do.
  id = input.required<number, string>({ transform: (raw: string) => Number(raw) });

  // Derived state: recomputed automatically whenever id() changes.
  // It is `Customer | undefined`, and the template's @else handles the
  // undefined case — so there is no separate `notFound` flag to keep in step.
  customer = computed(() => this.customerService.getById(this.id()));

  goBack(): void {
    this.router.navigate(['/customers']);
  }
}
customer-detail.component.html
@if (customer(); as c) {
  <h2>{{ c.name }}</h2>
  <p>Customer #{{ c.id }} · {{ c.city }} · {{ c.balance | currency:'INR' }}</p>
  <button (click)="goBack()">← Back to the list</button>
} @else {
  <h2>Customer not found</h2>
  <p>There is no customer with id <strong>{{ id() }}</strong>.</p>
  <a routerLink="/customers">← Back to the list</a>
}
This version fixes a bug the old code had for free With the classic route.snapshot approach, navigating from /customers/1002 to /customers/1003 without leaving the component changed the URL and left the screen showing the old customer — because Angular reuses the instance and ngOnInit does not run again. A signal input has no such problem: id() changes, so every computed() that reads it recalculates, and the screen updates. There is no ngOnInit here at all.

The classic way, which you still need to recognise

export class CustomerDetailComponent implements OnInit {
  private route = inject(ActivatedRoute);
  customer?: Customer;

  ngOnInit(): void {
    const raw = this.route.snapshot.paramMap.get('id');   // a STRING, or null
    const id = Number(raw);                               // convert it — always
    this.customer = this.customerService.getById(id);
  }
}

// …or, to react to parameter changes while staying in the same component:
this.route.paramMap.subscribe(p => {
  this.customer = this.customerService.getById(Number(p.get('id')));
});
When you still reach for ActivatedRoute When you need more than a parameter value — the resolved data, the fragment, the parent route, or the full URL — or when you are working in a codebase that hasn't enabled withComponentInputBinding(). Both approaches are correct in Angular 19; the input version is shorter and reactive, so prefer it for plain parameters.

Concept 5 — navigating without a link

Navigating from code with Router

routerLink is for things the user clicks. But sometimes your code needs to navigate: after a successful save, after a login, after a delete. For that you inject the Router service — with inject(), as everywhere else in Angular 19.

import { inject } from '@angular/core';
import { Router } from '@angular/router';

private router = inject(Router);

// simple navigation
goHome(): void {
  this.router.navigate(['/home']);
}

// with a parameter
viewCustomer(id: number): void {
  this.router.navigate(['/customers', id]);      // → /customers/1002
}

// the classic: navigate after a successful save
onSave(): void {
  this.customerService.add(this.form.getRawValue()).subscribe({
    next: () => {
      this.router.navigate(['/customers']);      // ← inside next, on SUCCESS only
    },
    error: () => {
      this.message.set('Save failed — you are still on the form.');
    }
  });
}
Note where that navigate call sits Inside next. Navigating immediately after calling subscribe would take the user away before the server had replied — so a failed save would look like a successful one. Navigate on confirmed success, exactly as you updated the screen inside next in Session 3.

The three ways to navigate — a summary

WayUse it when
routerLink="/customers"The user clicks something. Preferred — it renders a real, right-clickable link.
[routerLink]="['/customers', id]"The same, with a dynamic segment.
this.router.navigate([...])Your code decides — after a save, a login, a delete, or a timeout.
Query parameters, briefly this.router.navigate(['/customers'], { queryParams: { search: 'anoop' } }) produces /customers?search=anoop. With withComponentInputBinding() enabled you read it back as an ordinary input — search = input('') — or the classic way with this.route.snapshot.queryParamMap.get('search'). Use route parameters for "which record" and query parameters for optional extras like search terms, filters and page numbers.

Concept 6 — the case study · the plan

Customer Management — what we're building

One screen with a complete set of data operations. CRUD stands for the four things every business application does:

➕

C — Create

A form adds a new customer. signal.update() locally, POST against an API.

📖

R — Read

A table lists them, with a search box that filters as you type — a computed() locally, GET against an API.

✏️

U — Update

Click a row, the form fills in, edit, save. map() locally, PUT against an API.

🗑️

D — Delete

A confirmation, then removal. filter() locally, DELETE against an API.

The plan — we build it three times, and that's deliberate Round 1: everything inside one component, against a signal holding an array. Simple, all in one place, easy to follow.
Round 2: move the data operations into a service that owns the signal. The component gets smaller.
Round 3: swap the service's array for HttpClient. The component barely changes at all.

Seeing the same feature three ways is what makes the value of layering obvious rather than theoretical.
Everything today is something you already know The array methods from Session 1. @for, @if and class bindings from Session 2. Reactive forms, services, inject() and HttpClient from Session 3. The only genuinely new pieces are the router and computed() — the rest is assembly.

Concept 6 · step 1

The model, and state as signals

src/app/models/customer.ts
export interface Customer {
  id: number;
  name: string;
  city: string;
  email: string;
  balance: number;
}
customer-list.component.ts — the state we need
import { Component, computed, inject, signal } from '@angular/core';
import { FormBuilder, ReactiveFormsModule, Validators } from '@angular/forms';
import { CurrencyPipe } from '@angular/common';
import { Customer } from '../../models/customer';

@Component({
  selector: 'app-customer-list',
  imports: [ReactiveFormsModule, CurrencyPipe],
  templateUrl: './customer-list.component.html',
  styleUrl: './customer-list.component.css'
})
export class CustomerListComponent {

  // ── the data: ONE source of truth ─────────────────────
  readonly allCustomers = signal<Customer[]>([]);

  // ── screen state ──────────────────────────────────────
  readonly searchTerm = signal('');
  readonly message    = signal('');

  // ── edit mode: null = adding, a number = editing that id
  readonly editingId = signal<number | null>(null);

  // ── DERIVED state: what the table actually displays ───
  readonly customers = computed(() => {
    const t = this.searchTerm().trim().toLowerCase();
    if (t === '') { return this.allCustomers(); }
    return this.allCustomers().filter(c =>
      c.name.toLowerCase().includes(t) ||
      c.city.toLowerCase().includes(t) ||
      c.email.toLowerCase().includes(t)
    );
  });

  readonly totalBalance = computed(() =>
    this.customers().reduce((sum, c) => sum + c.balance, 0)
  );

  // ── the form (reactive, from Session 3) ───────────────
  private fb = inject(FormBuilder);

  readonly custForm = this.fb.nonNullable.group({
    name:    ['', [Validators.required, Validators.minLength(3)]],
    city:    ['', [Validators.required]],
    email:   ['', [Validators.required, Validators.email]],
    balance: [0,  [Validators.required, Validators.min(0)]]
  });
}
Three design decisions worth explaining 1. One array, not two. Older Angular code keeps a master list and a filtered list, and must remember to re-filter after every change. Here customers is a computed() derived from allCustomers and searchTerm — so it can never drift out of step, and the classic "I filtered the wrong array" bug is structurally impossible.
2. editingId: signal<number | null>. One signal carries the whole insert-versus-update distinction: null means "adding a new one", a number means "editing that id". This single value is what lets one form do both jobs.
3. fb.nonNullable.group. Typed forms: custForm.getRawValue() comes back as { name: string; city: string; email: string; balance: number } rather than with everything possibly undefined. Fewer casts, real type safety.
Analogy for computed() A signal is a cell in a spreadsheet you type into. A computed is a cell containing =SUM(A1:A9) — you never update it by hand, and it is never stale. Changing a source cell recalculates it for you, and only then.

Concept 6 · R for Read

Read: listing the customers

Concept 6 · C for Create

Create: inserting a new customer

onSubmit(): void {
  if (this.custForm.invalid) {
    this.custForm.markAllAsTouched();      // reveal every error at once
    return;
  }

  const form = this.custForm.getRawValue();  // fully typed, thanks to nonNullable

  if (this.editingId() === null) {
    // ── ADD MODE ──────────────────────────────────────
    const newCustomer: Customer = { id: this.nextId(), ...form };

    // update() gets the current value and returns a NEW array.
    this.allCustomers.update(list => [...list, newCustomer]);
    this.message.set('Added ' + newCustomer.name + '.');

  } else {
    // ── EDIT MODE — slide 22 ─────────────────────────
  }

  this.resetForm();
  // No re-filter call needed: `customers` is computed, so the table
  // has already updated by the time this method returns.
}

private nextId(): number {
  const list = this.allCustomers();
  if (list.length === 0) { return 1001; }
  return Math.max(...list.map(c => c.id)) + 1;
}

resetForm(): void {
  this.custForm.reset({ name: '', city: '', email: '', balance: 0 });
  this.editingId.set(null);
}
Four details worth copying 1. Validate first and markAllAsTouched(), so a user who clicks Save on an empty form is told why nothing happened.
2. [...list, newCustomer] creates a new array rather than calling push(). Signals compare by reference, so mutating the existing array in place would leave the screen unchanged — this is the number one signals mistake.
3. nextId() takes the highest existing id and adds one — never length + 1, which produces duplicates as soon as anything is deleted.
4. { id: this.nextId(), ...form } — the spread copies the four validated form fields, so adding a field to the form does not mean editing this line.
The mutation trap, spelled out this.allCustomers().push(newCustomer); looks right and is the most common signals bug there is. It mutates the array the signal is holding, the reference never changes, so no computed() recalculates and nothing appears on screen. Always go through .set() or .update() with a fresh array.
Generating ids locally is a temporary measure Once a real server is involved, the database assigns ids. You will send id: 0 and use the id that comes back in the response — exactly as in Session 3's POST stretch task.

Concept 6 · D for Delete

Delete: with a confirmation step

onDelete(customer: Customer): void {

  // Never delete on a single click. Always confirm.
  const ok = confirm('Delete ' + customer.name + '? This cannot be undone.');
  if (!ok) { return; }

  // filter() returns a new array, which is exactly what a signal wants
  this.allCustomers.update(list => list.filter(c => c.id !== customer.id));

  // if we were editing this very customer, get out of edit mode
  if (this.editingId() === customer.id) {
    this.resetForm();
  }

  this.message.set('Deleted ' + customer.name + '.');
}
confirm(...)
The browser's built-in Yes/No dialog. Ugly but honest, and it takes one line. Real projects use a styled modal — the logic is identical.
update(list => list.filter(...))
"Give me every customer except this one." One line, immutable, and it triggers the update. The old findIndex + splice pair still works but mutates in place — wrong for signals.
if (this.editingId() === ...)
An edge case people miss: deleting the customer you are currently editing would leave the form pointing at something that no longer exists.
Notice what is not here No call to re-filter the table, and no trackBy method. The computed() handles the first and track c.id in the template handles the second. Four lines of real work.
Always confirm destructive actions A misplaced click that silently deletes a customer is the kind of thing that ends up in a support ticket. One confirm() prevents it. Session 3's rule also applies once a server is involved: when the delete is an HTTP call, remove the row inside next, so a failed delete does not leave your screen lying to the user.

Concept 6 · U for Update

Update: click a row, edit, save

Update is two halves: load the row into the form, then save the changes back over the original.

Half 1 — loading the row into the form
startEdit(customer: Customer): void {
  this.editingId.set(customer.id);         // remember WHICH one we're editing

  // ONE LINE fills the whole form. This is why we used a reactive form.
  this.custForm.patchValue({
    name:    customer.name,
    city:    customer.city,
    email:   customer.email,
    balance: customer.balance
  });

  this.message.set('Editing ' + customer.name + '. Change the fields and press Save.');
}

cancelEdit(): void {
  this.resetForm();                        // sets editingId back to null
  this.message.set('Edit cancelled.');
}
Half 2 — saving it back (the else branch from the Create slide)
  } else {
    // ── EDIT MODE ──────────────────────────────────────
    const id = this.editingId()!;          // not null inside this branch

    this.allCustomers.update(list =>
      list.map(c => c.id === id
        ? { id, ...form }                  // replace this one, KEEPING the id
        : c)                               // leave every other row alone
    );

    this.message.set('Updated successfully.');
  }
map() is the signal-friendly way to update one item Read it as: "rebuild the list; wherever the id matches, substitute the edited version." It returns a new array — so the signal notices — and it needs no index lookup. The older findIndex() then list[i] = {...} pair mutates the array in place and leaves the screen stale.
patchValue is the whole reason Session 3 taught reactive forms Filling an entire form from an object takes one call. In a template-driven form you would assign every property by hand, one line each — and remember to add a line every time someone adds a field. This slide is where that lesson pays off.
Keep the id — always The form has no id field, so you must reuse this.editingId(). Build the replacement object with a fresh or missing id and you have silently created a duplicate rather than updated a record.

Concept 7 — round 2 · the same CRUD, through a service

Moving the operations into a signal-based service

Round 1 works, and it puts data logic inside a component — exactly what Session 3 taught you not to do. Round 2 fixes it, and the service keeps the signal so that every screen sees the same data.

src/app/services/customer.service.ts
import { Injectable, signal } from '@angular/core';
import { Customer } from '../models/customer';

@Injectable({ providedIn: 'root' })      // ONE instance for the whole app
export class CustomerService {

  // Private and writable inside the service…
  private readonly _customers = signal<Customer[]>([
    { id: 1001, name: 'Anoop Kumar', city: 'Ahmedabad', email: 'anoop@example.com', balance: 15000 },
    { id: 1002, name: 'Ajay Sharma', city: 'Pune',      email: 'ajay@example.com',  balance: 0 },
    { id: 1003, name: 'Rekha Nair',  city: 'Kochi',     email: 'rekha@example.com', balance: 42500 }
  ]);

  // …read-only outside it. Components can READ but never SET.
  readonly customers = this._customers.asReadonly();

  getById(id: number): Customer | undefined {
    return this._customers().find(c => c.id === id);
  }

  add(customer: Customer): Customer {
    const created: Customer = { ...customer, id: this.nextId() };
    this._customers.update(list => [...list, created]);
    return created;
  }

  update(customer: Customer): boolean {
    if (!this.getById(customer.id)) { return false; }
    this._customers.update(list =>
      list.map(c => c.id === customer.id ? customer : c));
    return true;
  }

  delete(id: number): boolean {
    if (!this.getById(id)) { return false; }
    this._customers.update(list => list.filter(c => c.id !== id));
    return true;
  }

  private nextId(): number {
    const list = this._customers();
    if (list.length === 0) { return 1001; }
    return Math.max(...list.map(c => c.id)) + 1;
  }
}
Two things this service does that matter 1. asReadonly() — a real guarantee, not a convention. Components can read customers() but cannot call .set() on it; the compiler enforces it. Every change must go through a method the service owns, which is where you would later add validation, logging or an audit trail.
2. The method names are a repository. getById, add, update, delete — deliberately, so round 3 can swap the array for HTTP calls without renaming anything.
Why the detail screen from slide 14 now works automatically getById reads this._customers(), so when the detail component wraps it in computed(() => this.customerService.getById(this.id())), that computed is subscribed to the service's signal. Delete a customer on the list screen and any open detail view of it re-evaluates by itself. Nobody wrote a notification mechanism — this is what signals buy you.

Concept 8 — round 3 · the same CRUD over HTTP

The service, talking to a real API

Now replace the array with network calls. The method names stay identical — only the bodies and the return types change.

src/app/services/customer.service.ts
import { inject, Injectable } from '@angular/core';
import { HttpClient } from '@angular/common/http';
import { Observable } from 'rxjs';
import { Customer } from '../models/customer';

@Injectable({ providedIn: 'root' })
export class CustomerService {

  private http = inject(HttpClient);

  // ONE line to change when you switch backends
  private baseUrl = 'http://localhost:8080/api/customers';

  getAll(): Observable<Customer[]> {
    return this.http.get<Customer[]>(this.baseUrl);
  }

  getById(id: number): Observable<Customer> {
    return this.http.get<Customer>(`${this.baseUrl}/${id}`);
  }

  add(customer: Customer): Observable<Customer> {
    return this.http.post<Customer>(this.baseUrl, customer);
  }

  update(customer: Customer): Observable<Customer> {
    return this.http.put<Customer>(`${this.baseUrl}/${customer.id}`, customer);
  }

  delete(id: number): Observable<void> {
    return this.http.delete<void>(`${this.baseUrl}/${id}`);
  }
}
src/app/app.config.ts — the one registration this needs
providers: [
  provideRouter(routes, withComponentInputBinding()),
  provideHttpClient(withFetch())      // withFetch() is optional but recommended
]
The one real difference in the service Every method now returns an Observable instead of a value. So every caller must .subscribe(). That is the only structural change — and it is exactly why Session 3 spent time on Observables before we got here.
There is no HttpClientModule in Angular 19 It is deprecated. provideHttpClient() replaces it, interceptors are plain functions passed as provideHttpClient(withInterceptors([authInterceptor])), and withFetch() switches the underlying implementation from XMLHttpRequest to the browser's fetch API — which is what you want for server-side rendering later.

Concept 8 continued

The component, with subscribe

readonly allCustomers  = signal<Customer[]>([]);
readonly isLoading     = signal(false);
readonly errorMessage  = signal('');

// `customers` is still the same computed() — it filters whatever
// allCustomers currently holds, no matter where that came from.

ngOnInit(): void {
  this.loadCustomers();
}

loadCustomers(): void {
  this.isLoading.set(true);
  this.errorMessage.set('');

  this.customerService.getAll().subscribe({
    next: (data) => {
      this.allCustomers.set(data);          // one line updates the whole table
      this.isLoading.set(false);
    },
    error: (err) => {
      this.errorMessage.set('Could not load customers. Is the API running?');
      this.isLoading.set(false);            // set it in BOTH branches
      console.error(err);
    }
  });
}

onDelete(c: Customer): void {
  if (!confirm('Delete ' + c.name + '?')) { return; }

  this.customerService.delete(c.id).subscribe({
    next: () => {
      this.loadCustomers();                 // reload so the screen matches the server
      this.message.set('Deleted.');
    },
    error: () => this.message.set('Delete failed — the customer is still there.')
  });
}

onSubmit(): void {
  if (this.custForm.invalid) { this.custForm.markAllAsTouched(); return; }

  const customer: Customer = {
    id: this.editingId() ?? 0,              // 0 for a new one; the server assigns it
    ...this.custForm.getRawValue()
  };

  const call = this.editingId() === null
    ? this.customerService.add(customer)
    : this.customerService.update(customer);

  call.subscribe({
    next: () => { this.resetForm(); this.loadCustomers(); },
    error: () => this.message.set('Save failed.')
  });
}
Two patterns to take away from that code 1. Reload after a change. After a successful add, update or delete, call loadCustomers() again. It guarantees the screen matches the server — including anything a colleague changed a moment ago. Slower than patching locally; far more trustworthy.
2. Choose the call, then subscribe once. const call = condition ? a() : b(); then one .subscribe(). Remember Observables are lazy, so building it without subscribing sends nothing — which makes this pattern safe.
The signal-native alternative: toSignal() For a read-only list you can skip subscribe entirely: 
import { toSignal } from '@angular/core/rxjs-interop';

readonly allCustomers = toSignal(this.customerService.getAll(),
                                 { initialValue: [] as Customer[] });
It subscribes for you, exposes the latest value as a signal, and unsubscribes when the component is destroyed. It is less convenient when you need to re-fetch on demand, which is why the CRUD screen above uses explicit subscribe. Know both.
About unsubscribing HttpClient Observables complete after one response, so they clean themselves up — you do not need to unsubscribe from them. For anything long-lived (a paramMap, a timer, a WebSocket) use takeUntilDestroyed() from @angular/core/rxjs-interop, which is the modern replacement for keeping a Subscription and tearing it down in ngOnDestroy.

Connecting to your Spring Boot API

This is the payoff for eight sessions of work. On the Angular side it is one line.

@CrossOrigin(origins = "http://localhost:4200")   // ← REQUIRED, or CORS blocks you
@RestController
@RequestMapping("/api/customers")
public class CustomerController {

    @Autowired
    private CustomerService service;

    @GetMapping
    public List<Customer> getAll() { return service.findAll(); }

    @GetMapping("/{id}")
    public Customer getById(@PathVariable Long id) { return service.findById(id); }

    @PostMapping
    public Customer create(@RequestBody Customer c) { return service.save(c); }

    @PutMapping("/{id}")
    public Customer update(@PathVariable Long id, @RequestBody Customer c) {
        c.setId(id);
        return service.save(c);
    }

    @DeleteMapping("/{id}")
    public void delete(@PathVariable Long id) { service.deleteById(id); }
}
Read those two code blocks side by side http.get(baseUrl) ↔ @GetMapping. http.post(baseUrl, c) ↔ @PostMapping with @RequestBody. http.delete(`${baseUrl}/${id}`) ↔ @DeleteMapping("/{id}") with @PathVariable.

You now know both ends of the wire. That is what the whole eight-session programme was for.
Three things to check when it doesn't work first time 1. CORS. Without @CrossOrigin the browser blocks the request and the message says CORS. Fix it on the server.
2. Field names must match exactly. Java's customerName arrives as customerName — if your TypeScript interface says name, you get undefined. Check with {{ data | json }} (and import JsonPipe).
3. Is the API actually running? Open http://localhost:8080/api/customers directly in a browser tab first. If it fails there, the problem is not in Angular.

Before you go and build things

Do these, avoid those — the Angular 19 edition

✅ Do

  • Put HTTP calls and data logic in a service
  • Use signal for state and computed for anything derived
  • Always update signals immutably — update(l => [...l, x])
  • Expose service state with asReadonly()
  • Use inject() and @if / @for in new code
  • Type everything — interfaces for all API data
  • Always provide an error handler in subscribe
  • Show loading, error and empty states (@empty)
  • Confirm before anything destructive
  • loadComponent for routes you can defer
  • Wildcard ** route last, always

❌ Avoid

  • HttpClient directly inside a component
  • signal().push(x) — mutation, so nothing renders
  • Reading a signal without () in a template
  • New NgModules in a v19 app
  • any as a habit rather than a note
  • Forgetting .subscribe() — nothing happens
  • Updating the screen before the server confirms
  • document.getElementById — bind instead
  • Heavy work inside {{ method() }} — use computed
  • Secrets or passwords in front-end code
  • href for internal links — use routerLink
If you remember only three things from this series 1. Data flows down, events flow up.
2. Components display; services fetch.
3. Change the data and let Angular update the screen — never touch the DOM yourself.

The pattern in that list Three families. Missing imports — new in v19, and they give you clear compiler errors. Ordering and string-versus-number — old friends, and they fail silently. Mutation instead of replacement — the signals-era bug, and it also fails silently. When something "doesn't work", check the imports array, then the route order, then whether you mutated.

Shipping it

Building for production

Everything so far has run under ng serve, which is a development server — unoptimised, on your machine only. To deploy, you build. In Angular 19 ng build is already a production build; there is no --prod flag any more.

ng build
dist/hello-world/browser/ ├── index.html the one page ├── main-A1B2C3.js your whole app, compiled and minified ├── chunk-XYZ789.js one per lazily loaded route, if you used loadComponent ├── polyfills-D4E5F6.js browser compatibility shims └── styles-G7H8I9.css your global styles
What the build doesWhy it matters
Compiles TypeScript → JavaScriptBrowsers cannot run TypeScript. No .ts file reaches the user.
MinifiesStrips comments, whitespace and long names. Far smaller download.
Tree-shakesRemoves code nothing uses. This is where standalone components pay off: because each component lists exactly what it imports, the build can prove far more code is unreachable than it could with NgModules.
Hashes filenamesmain-A1B2C3.js — when you redeploy, the name changes, so browsers cannot serve a stale cached copy.
Checks budgetsangular.json sets a maximum bundle size and the build warns or fails when you exceed it. A cheap, permanent guard against bloat.
Deploying it is genuinely simple The contents of that folder are plain static files. Copy them to any web server — Apache, Nginx, S3, GitHub Pages, or your Spring Boot app's src/main/resources/static folder, which then serves your Angular app and your API from the same origin and eliminates the CORS problem entirely.
One deployment gotcha to know about Your server must send unknown URLs to index.html. Otherwise a user who bookmarks /customers and revisits it gets a server 404 — the server looks for a file called "customers", which does not exist. Angular's router only runs once index.html has loaded. On Nginx that is try_files $uri /index.html;.

Recap

What you now know

  • A route pairs a URL path with a component, and routes in app.routes.ts is just an exported array of those pairings.
  • provideRouter(routes) in app.config.ts switches the router on — replacing AppRoutingModule and RouterModule.forRoot() entirely.
  • Every standalone component imports what its own template uses: RouterOutlet, RouterLink, RouterLinkActive, pipes, ReactiveFormsModule.
  • <router-outlet /> marks where the routed component appears — everything outside it is a persistent shell.
  • routerLink navigates without a reload; href restarts your whole application.
  • routerLinkActive highlights the current page with no logic of your own, and needs { exact: true } for a root-path link.
  • A default redirectTo needs pathMatch: 'full', and a ** wildcard 404 route goes last.
  • Routes are matched top to bottom, first match wins — so static paths go above dynamic ones.
  • Route parameters (:id) arrive as a signal input() when withComponentInputBinding() is on, or via ActivatedRoute — and are always strings, so convert them.
  • this.router.navigate([...]) navigates from code, and belongs inside next so it only runs on genuine success.
  • CRUD is the array methods you learned in Session 1, used immutably: spread to add, map to update, filter to delete.
  • signal() holds state; computed() derives from it — which is what removed the two-array bug, the stale-filter bug and the trackBy method all at once.
  • One form handles both insert and update, driven by a single editingId signal and patchValue().
  • Moving CRUD onto a service and then onto HttpClient left the template unchanged, for the fourth time in this series.
  • Your Angular service's five methods map one-to-one onto your Spring Boot controller's five mappings.
  • ng build produces plain static files in dist/ — and serving them from Spring Boot removes the CORS problem entirely.

What to learn next

Beyond these four sessions

Also plain functions: provideHttpClient(withInterceptors([authInterceptor])). Attach a token to every request in one place.

📦

loadComponent per route, and loadChildren for whole feature areas. One line each with standalone components.

⏳

@defer

Defer a part of a template until it is visible, idle, or hovered. Great for charts and heavy widgets.

More signals

Angular Material

Google's component library — tables, dialogs, date pickers, all accessible out of the box and all standalone.
