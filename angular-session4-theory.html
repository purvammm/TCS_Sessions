Concept 1

Why routing?

Here's the apparent contradiction: a single-page application… with multiple pages? The trick is that the "pages" are never fetched from the server. Angular's router watches the URL and swaps which component is rendered — instantly, in the browser, with no reload.

Traditional multi-page navigation

  • Click a link → browser requests a whole new HTML page
  • Everything is torn down and rebuilt
  • Visible flash; scroll position lost
  • All in-memory state is gone
  • Every navigation is a network round trip
→

Angular router navigation

  • Click a link → the router swaps one component
  • The page never reloads
  • Instant, smooth, no flicker
  • Services keep their state (they're singletons)
  • Zero network traffic unless data is needed

And crucially, you keep everything users expect from real URLs:

  • Bookmarkable — /customers can be saved and shared.
  • Back and forward buttons work — the router integrates with browser history.
  • Deep-linkable — /customers/1003 opens straight to that record.
The one-line summary Routing gives you the navigation model of a multi-page site with the speed and smoothness of a desktop application. That combination is why single-page apps took over.

Concept 2 · step 1 — define

Defining routes

Routes live in a dedicated module: a simple array mapping URL paths to components.

src/app/app-routing.module.ts
import { NgModule } from '@angular/core';
import { RouterModule, Routes } from '@angular/router';

import { EmployeeListComponent } from './employee-list/employee-list.component';
import { RegistrationComponent } from './registration/registration.component';
import { CustomerManagementComponent } from './customer-management/customer-management.component';
import { NotFoundComponent } from './not-found/not-found.component';

const routes: Routes = [
  { path: '',          redirectTo: '/employees', pathMatch: 'full' },
  { path: 'employees', component: EmployeeListComponent },
  { path: 'register',  component: RegistrationComponent },
  { path: 'customers', component: CustomerManagementComponent },
  { path: '**',        component: NotFoundComponent }
];

@NgModule({
  imports: [RouterModule.forRoot(routes)],
  exports: [RouterModule]
})
export class AppRoutingModule { }
path: 'employees'
Matches /employees. No leading slash in the definition — a very common slip.
path: ''
The empty path is the default route. Here it redirects, so landing on / doesn't show a blank screen.
pathMatch: 'full'
Required with redirectTo on an empty path — without it the redirect matches everything and loops.
path: '**'
The wildcard. Matches anything unmatched — your 404 page. It must be last: routes are evaluated top to bottom, first match wins.
forRoot(routes)
Registers these as the application's root routes. Used once, in this module only.
If you answered "yes" to routing in ng new The CLI already created this file and imported it in app.module.ts. We deliberately answered no in Session 1 so that you'd build it yourself today and see every moving part.

Customer Management

Use routerLink, never href <a href="/customers"> triggers a full page reload — the browser throws your entire application away and downloads it again. It looks like it works, but it destroys the whole point of a single-page app. If a click causes a visible flash, you've used href somewhere.

Routing — going further

Route parameters & navigating from code

Real apps need URLs like /customers/1003 — "show me this record". A colon in the path declares a parameter.

// in the routes array
{ path: 'customers/:id', component: CustomerDetailComponent }

Reading the parameter

import { ActivatedRoute } from '@angular/router';

constructor(
  private route: ActivatedRoute,
  private customerService: CustomerService
) { }

ngOnInit(): void {
  // snapshot: fine when the component
  // is recreated for each id
  const id = Number(
    this.route.snapshot.paramMap.get('id')
  );
  this.customer =
    this.customerService.getById(id);
}

Navigating from TypeScript

import { Router } from '@angular/router';

constructor(private router: Router) { }

viewCustomer(id: number): void {
  this.router.navigate(['/customers', id]);
}

afterSave(): void {
  // e.g. return to the list after saving
  this.router.navigate(['/customers']);
}
Two navigation styles, two purposes routerLink in a template — for links the user clicks. Router.navigate() in TypeScript — for navigation your code decides: after a successful save, after login, after a delete. Both go through the same router; neither reloads the page.
snapshot vs subscribing route.snapshot.paramMap reads the parameter once. If the user can move from /customers/1 to /customers/2 without the component being destroyed, Angular reuses it and the snapshot never updates. In that case subscribe instead: this.route.paramMap.subscribe(p => ...). Snapshot is fine for these sessions — just know why the other form exists.

Concept 3 — CRUD

CRUD, two ways

CRUD — Create, Read, Update, Delete — is the backbone of almost every business application. Today you'll implement the same four operations twice, and the second time will feel almost identical. That's the point.

1️⃣

Strategy A — in-memory array

All four operations mutate a local array inside the component. No server needed.

Why start here: you see the UI logic clearly with nothing async to confuse it. Everything is instant and synchronous.

Downside: refresh the page and it's all gone.

2️⃣

Strategy B — service + HttpClient

The same four operations, routed through a service that calls GET / POST / PUT / DELETE.

Why finish here: this is how real applications work. Data persists, and multiple users see the same thing.

Cost: everything becomes asynchronous.

OperationArray-basedService + HTTP
Readthis.customershttp.get<Customer[]>(url)
Createthis.customers.push(c)http.post(url, c)
Updatethis.customers[i] = chttp.put(`${url}/${id}`, c)
Deletethis.customers.splice(i, 1)http.delete(`${url}/${id}`)
The insight this ordering is designed to give you When you do the refactor in the lab, notice how little of the template changes — often nothing at all. Good structure means swapping the data source touches the service and a few subscribe blocks, not the UI.

Array-based CRUD · Read & Search

List and search

The class

export interface Customer {
  id: number;
  name: string;
  age: number;
  mobile: string;
}

// the master list
customers: Customer[] = [
  { id: 1, name: 'Anoop',  age: 40, mobile: '9876543210' },
  { id: 2, name: 'Ajay',   age: 32, mobile: '9123456780' },
  { id: 3, name: 'Rekha',  age: 28, mobile: '9988776655' }
];

// what the table actually renders
filtered: Customer[] = [];
searchTerm: string = '';

ngOnInit(): void {
  this.filtered = this.customers;
}

onSearch(): void {
  const t = this.searchTerm.toLowerCase().trim();
  this.filtered = !t
    ? this.customers
    : this.customers.filter(c =>
        c.name.toLowerCase().includes(t) ||
        c.mobile.includes(t));
}

The template

<input [(ngModel)]="searchTerm"
       (input)="onSearch()"
       placeholder="Search name or mobile">

<table *ngIf="filtered.length > 0; else empty">
  <tr>
    <th>ID</th><th>Name</th>
    <th>Age</th><th>Mobile</th>
  </tr>
  <tr *ngFor="let c of filtered">
    <td>{{ c.id }}</td>
    <td>{{ c.name }}</td>
    <td>{{ c.age }}</td>
    <td>{{ c.mobile }}</td>
  </tr>
</table>

<ng-template #empty>
  <p>No customers match.</p>
</ng-template>
Why keep two arrays? customers is the truth; filtered is the view. If you filtered customers in place, the records you filtered out would be permanently deleted — clearing the search box couldn't bring them back. Keeping the master list intact is the single most important design decision in a searchable list.

Array-based CRUD · Create

Insert a new record

The class

newCustomer: Customer =
  { id: 0, name: '', age: 0, mobile: '' };

message: string = '';

insertCustomer(): void {
  // basic guard
  if (!this.newCustomer.name ||
      !this.newCustomer.mobile) {
    this.message = 'Name and mobile are required.';
    return;
  }

  // generate the next id
  const nextId = this.customers.length === 0
    ? 1
    : Math.max(...this.customers.map(c => c.id)) + 1;

  this.customers.push({
    ...this.newCustomer,      // spread = copy the values
    id: nextId
  });

  this.onSearch();            // refresh the filtered view
  this.resetForm();
  this.message = 'Customer added.';
}

resetForm(): void {
  this.newCustomer =
    { id: 0, name: '', age: 0, mobile: '' };
}

The template

<h3>Add a customer</h3>

<input [(ngModel)]="newCustomer.name"
       placeholder="Name">

<input type="number"
       [(ngModel)]="newCustomer.age"
       placeholder="Age">

<input [(ngModel)]="newCustomer.mobile"
       placeholder="Mobile">

<button (click)="insertCustomer()">Add</button>

<p *ngIf="message">{{ message }}</p>
Why { ...this.newCustomer } and not just this.newCustomer? Objects are held by reference. Pushing the object itself means the array holds the same object the form is still bound to — so typing in the form would silently edit the row you just added. The spread operator ... makes a copy. This is a genuinely common bug, and it looks like magic when it happens.
Notice the id generation Math.max(...ids) + 1 avoids reusing an id after a delete — length + 1 would collide. In the API-based version you delete this logic entirely: the server assigns the id, which is the only safe place to do it.

Array-based CRUD · Delete

Delete, with a confirmation step

deleteCustomer(c: Customer): void {
  const ok = confirm(
    'Delete customer ' + c.id + ' — ' + c.name + '?'
  );
  if (!ok) { return; }                          // user cancelled

  const index = this.customers.findIndex(x => x.id === c.id);
  if (index !== -1) {
    this.customers.splice(index, 1);            // remove 1 item at that position
  }

  this.onSearch();                              // refresh the filtered view
  this.message = 'Customer ' + c.id + ' deleted.';
}
<td>
  <button (click)="deleteCustomer(c)">Delete</button>
</td>
Never delete without asking Deletion is irreversible and always one mis-click away. confirm() is the browser's built-in dialogue — ugly, but it works everywhere with no setup, which makes it perfect for a lab. In production you'd use a styled modal, but the principle never changes: destructive actions require explicit confirmation.
Delete by id, not by index splice(i, 1) needs the position in the master array. If you passed the index from the filtered table, it would point at the wrong record as soon as a search was active — and you'd delete the wrong customer. Passing the whole object and looking up its id with findIndex is immune to that. It's a small detail that prevents a serious bug.

Array-based CRUD · Update

Update — click a row, edit, save

The flow: clicking a row copies it into an edit form; ID and Name become read-only once populated (business rule from the case study); Age and Mobile stay editable; Save writes the change back.

The class

editCustomer: Customer | null = null;

// clicking a row starts editing
selectForEdit(c: Customer): void {
  this.editCustomer = { ...c };   // edit a COPY
}

saveEdit(): void {
  if (!this.editCustomer) { return; }

  const i = this.customers.findIndex(
    x => x.id === this.editCustomer!.id
  );
  if (i !== -1) {
    this.customers[i] = { ...this.editCustomer };
  }

  this.editCustomer = null;       // close the form
  this.onSearch();
  this.message = 'Customer updated.';
}

cancelEdit(): void {
  this.editCustomer = null;
}

The template

<!-- the edit panel appears only while editing -->
<div *ngIf="editCustomer">
  <h3>Edit customer</h3>

  <label>ID (read-only)</label>
  <input [value]="editCustomer.id" readonly>

  <label>Name (read-only)</label>
  <input [value]="editCustomer.name" readonly>

  <label>Age</label>
  <input type="number"
         [(ngModel)]="editCustomer.age">

  <label>Mobile</label>
  <input [(ngModel)]="editCustomer.mobile">

  <button (click)="saveEdit()">Save</button>
  <button (click)="cancelEdit()">Cancel</button>
</div>

<!-- on each row -->
<td><button (click)="selectForEdit(c)">Edit</button></td>
Two design decisions worth understanding 1 · Edit a copy. { ...c } means Cancel actually cancels. Bind straight to the row object and every keystroke edits the live table — there'd be nothing to cancel.
2 · [value] + readonly for locked fields. One-way binding displays the value with no path back, and readonly stops the user typing. Using [(ngModel)] on a "read-only" field is a contradiction waiting to bite you.

Concept 3 · Strategy B

The same CRUD, through a service

src/app/customer.service.ts
import { Injectable } from '@angular/core';
import { HttpClient } from '@angular/common/http';
import { Observable } from 'rxjs';
import { Customer } from './models/customer';

@Injectable({ providedIn: 'root' })
export class CustomerService {

  private baseUrl = 'https://jsonplaceholder.typicode.com/users';
  // with your own backend: 'http://localhost:8080/api/customers'

  constructor(private http: HttpClient) { }

  getAll(): Observable<Customer[]> {
    return this.http.get<Customer[]>(this.baseUrl);
  }

  add(c: Customer): Observable<Customer> {
    return this.http.post<Customer>(this.baseUrl, c);
  }

  update(c: Customer): Observable<Customer> {
    return this.http.put<Customer>(`${this.baseUrl}/${c.id}`, c);
  }

  remove(id: number): Observable<any> {
    return this.http.delete(`${this.baseUrl}/${id}`);
  }
}
One file knows the URL. That's the whole design. Point baseUrl at your Spring Boot API and every operation follows. Components never change — they don't know an HTTP call is happening at all.

Concept 3 · Strategy B continued

What changes in the component

Before — synchronous array

insertCustomer(): void {
  this.customers.push({
    ...this.newCustomer, id: nextId
  });
  this.resetForm();
  this.message = 'Added.';
}

After — asynchronous HTTP

insertCustomer(): void {
  this.customerService.add(this.newCustomer)
    .subscribe({
      next: (created) => {
        this.customers.push(created);
        this.onSearch();
        this.resetForm();
        this.message = 'Added (id ' + created.id + ').';
      },
      error: (err) => {
        this.message = 'Save failed.';
        console.error(err);
      }
    });
}

Three things to internalise about the change:

  • The work moves inside next. Anything that must happen "after the save" has to be in the callback — code after subscribe() runs too early.
  • The server owns the id. You no longer compute it. Use created.id from the response.
  • Failure is now possible. An array push can't fail; a network call can. Every operation needs an error handler and a message the user can understand.
Two update strategies after a successful call Optimistic-ish (used above): update the local array from the response. Fast, no extra request. Re-fetch: call getAll() again in next. Slower but guaranteed to match the server, which matters when several users edit the same data. Both are legitimate — choose deliberately.

Habits worth carrying forward

Do these, avoid those

✅ Do

  • Generate everything with the CLI — it never forgets the module registration
  • Keep API URLs in services, never in components
  • Type everything with interfaces — no any[] for API responses
  • Fetch data in ngOnInit, inject in the constructor
  • Handle both next and error on every subscribe
  • Show loading and empty states — users need to know what's happening
  • Copy objects with { ...obj } before editing them
  • Guard optional data with *ngIf before reading its properties
  • Confirm before anything destructive

❌ Avoid

  • href for internal links — it reloads the whole app
  • Putting the '**' wildcard route anywhere but last
  • Business logic in templates — keep them declarative
  • Heavy method calls inside {{ }} — they re-run constantly
  • Filtering your master array in place — the data is then gone
  • Trusting client-side validation as security
  • Reading this.data on the line after subscribe()
  • private properties used in templates — the build fails
  • any everywhere — you lose the whole point of TypeScript
If you remember only one thing from this slide Components display; services fetch. Almost every Angular architecture problem is a violation of that one sentence.

Where to go next

Beyond these four sessions

You now have the foundation the rest of the ecosystem builds on. In roughly the order that makes sense to learn them:

🧩

Standalone components

Modern Angular can skip NgModule entirely — components declare their own imports. The recommended default in Angular 15+. Same concepts, less ceremony.

🔐

Route guards & interceptors

CanActivate to protect routes behind login; HTTP interceptors to attach auth tokens to every request automatically.

🎨

Angular Material

A complete, accessible component library — data tables with sorting and paging, dialogs, date pickers. Stop hand-rolling UI.

🌊

More RxJS

map, filter, debounceTime, switchMap — the operators that turn a search box into a proper typeahead.

📶

Signals

Angular's newer reactivity model. Simpler than Observables for component state, and increasingly the idiomatic choice.

📱

Ionic / Cordova

Build native mobile apps with the Angular you already know. Angular + reactive forms + TypeScript are the prerequisites — which you now have. (Not covered in these four sessions.)

The most valuable next step, though, isn't a library Point your Angular app at your own Spring Boot API. Change one baseUrl, add @CrossOrigin on the controller, and you have a genuine full-stack application built entirely by you. That's the exercise that makes all eight of these sessions click into place.
