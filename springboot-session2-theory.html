Foundations · 1 of 4

Why do APIs exist at all?

In Session 1 your endpoint returned text to a browser. But a browser is only one possible caller. Consider a company with a single database of students and four different things that need it:

📱 A mobile app

Written in Kotlin or Swift. Can't talk to your database directly, and shouldn't.

💻 A web dashboard

Written in React. Runs in the user's browser — nowhere near your server.

🏢 A partner company

Different language, different servers, and definitely no access to your database.

🤖 A nightly report script

Written in Python by someone in the analytics team.

Four callers, four languages, none of them able to reach into your database. So you put one program in the middle that owns the data and exposes a set of agreed URLs. Everyone talks to that. It's the only thing that has to know about the database.

Definition An API (Application Programming Interface) is a contract that lets one program use another program's functionality. A web service is an API you reach over the network using HTTP. That's the whole distinction: all web services are APIs; not all APIs are web services.

Foundations · 2 of 4

Web application vs web service

Both live on a server and answer HTTP requests. The difference is who the answer is for — and it changes everything about what you return.

Web application → for humans

Returns HTML — a page with layout, colours and buttons, meant to be looked at.

<h1>Student List</h1>
<table>
  <tr><td>Amit</td><td>A</td></tr>
</table>

Spring annotation: @Controller (returns a view name).

Web service → for programs

Returns data — usually JSON. No layout, no styling; the caller decides how to display it.

[
  { "name": "Amit", "grade": "A" }
]

Spring annotation: @RestController (returns the body itself).

Why "data, not layout" is the smarter choice Return JSON and the same endpoint serves the mobile app, the React dashboard, the partner company and the Python script — each rendering it however suits them. Return HTML and you've baked in one presentation that only a browser can use. This separation is why virtually all modern backends are built as web services. Everything in this course uses @RestController.

Idempotent — worth a second look, it comes up in interviews Delete student 5, and student 5 is gone. Delete student 5 again — still gone, nothing extra happened. That's idempotent. JSON · 1 of 3

JSON — the language APIs speak

JSON (JavaScript Object Notation) is just text in an agreed shape. Every language can read and write it, which is exactly why it won. There are only two structures to learn:

An object — curly braces

{
  "id": 1,
  "name": "Amit Shah",
  "active": true
}

A set of key: value pairs. Maps to a Java object.

An array — square brackets

[
  { "id": 1, "name": "Amit" },
  { "id": 2, "name": "Neha" }
]

An ordered list. Maps to a Java List.

The rules are strict, and breaking them causes a 400 Bad Request:

  • Keys must be in double quotes. {"name": "Amit"} ✅   {name: "Amit"} ❌
  • Strings use double quotes only — never single. 'Amit' ❌
  • No trailing comma after the last pair. {"a":1,} ❌
  • No comments. JSON has no // or /* */.

Objects and arrays can nest freely, and Java classes mirror that nesting exactly:

{
  "id": 1,
  "name": "Amit Shah",
  "address": {                       ← a nested OBJECT  → an Address field
    "city": "Ahmedabad",
    "pincode": "380015"
  },

Dates are the one awkward case JSON has no date type, so dates travel as strings. The convention is ISO-8601: "2026-09-05" or "2026-09-05T10:32:14". Spring handles LocalDate and LocalDateTime in that format by default — stick to it and everything just works.

You never write JSON by hand

This is the part beginners find surprising. You do not build JSON strings in your code. You return a Java object, and a library called Jackson — already included with spring-boot-starter-web — converts it. The conversion runs automatically in both directions.

Two rules make it work, and forgetting them causes most JSON bugs:

The practical takeaway for the lab Your data classes need a no-arg constructor, getters and setters. Every IDE generates these for you — IntelliJ: Alt+Insert → Getter and Setter. Don't type them by hand.

REST · 1 of 4

REST, defined properly

REST — Representational State Transfer — is an architectural style described by Roy Fielding in 2000. It is not a library, a protocol or a Spring feature. It's a set of design agreements that, if you follow them, make your API predictable to anyone who has used any other REST API.

The core idea in one sentence:

The REST idea Expose your data as resources at URLs, and use HTTP's existing verbs to act on them.

Look at what that buys you. One URL, four completely different operations — and no reader has to guess what any of them do:

RequestWhat it means
GET /api/students/5Give me student 5
PUT /api/students/5Update student 5 with the data in my body
DELETE /api/students/5Remove student 5
POST /api/studentsCreate a new student from the data in my body

The path never changes meaning — it always identifies which data. The verb carries the intent. That's REST.

REST · 2 of 4

The six REST constraints

Fielding listed six rules. An API that follows them is called "RESTful". Spring Boot gives you most of them for free — but you should know what they are and why they matter.

1 · Client–Server

The client (UI) and server (data) are separate and can be developed, deployed and scaled independently.

2 · Stateless

Every request carries everything needed to understand it. The server stores no session between calls.

3 · Cacheable

Responses say whether they may be cached, so repeated reads needn't hit the server at all.

4 · Uniform Interface

The same small set of verbs and conventions everywhere, so an unfamiliar API still feels familiar.

5 · Layered System

Gateways, load balancers and caches may sit in between; the client can't tell and doesn't care.

6 · Code on Demand (optional)

The server may send executable code (e.g. JavaScript). Rarely used in practice.

Number 2 is the one that matters most — and here's why Because the server keeps no memory of you, any copy of the server can handle any request. That means you can run ten identical copies behind a load balancer and requests can land on any of them. Statelessness is what makes horizontal scaling possible — and it's precisely what Session 4 exploits when we run three instances of one service. Stateless design today is what lets you scale tomorrow.

REST · 3 of 4

REST vs SOAP

Before REST won, the standard was SOAP — a heavyweight, XML-based protocol. You'll still meet it in banking, telecom and older enterprise systems, so it's worth knowing the contrast.

RESTSOAP
What it isAn architectural style — a set of conventionsA strict protocol with a formal specification
Data formatJSON (usually), or anything you likeXML only
Message sizeSmall and lightLarge — envelope, header and body wrappers
ReadabilityEasy to read by eyeVerbose and hard to scan
ContractOptional (OpenAPI / Swagger)Mandatory and machine-readable (WSDL)
TransportHTTP onlyHTTP, SMTP, JMS, TCP…
Built-in transactionsNoYes (WS-* standards)
Best suited toWeb & mobile apps, microservices, public APIsBanking, telecom, formal enterprise integration
The honest summary REST won because it is simpler and lighter, and because mobile apps and browsers handle JSON effortlessly. SOAP is not "bad" — its rigidity is a genuine advantage when you need guaranteed contracts and built-in transaction support. But for new projects, REST is the default, and it's what we build all four sessions on.

REST · 4 of 4

HTTP verbs → CRUD → Spring

CRUD stands for Create, Read, Update, Delete — the four things you do to almost any data. Each maps to one HTTP verb and one Spring annotation. Learn this table; today's lab is literally this table.

CRUDVerbSpring annotationPathBody?Success code
CreatePOST@PostMapping/api/studentsYes201 Created
Read allGET@GetMapping/api/studentsNo200 OK
Read oneGET@GetMapping("/{id}")/api/students/5No200 OK
UpdatePUT@PutMapping("/{id}")/api/students/5Yes200 OK
DeleteDELETE@DeleteMapping("/{id}")/api/students/5No204 No Content

Note the pattern in the paths: operations on the collection use /api/students, and operations on one item add its id — /api/students/5.

PUT vs PATCH PUT means replace the whole thing — send every field, and anything you omit gets wiped. PATCH means change only these fields — send just what's different. PUT is simpler and far more common; we use PUT today and you should default to it until you have a reason not to.

Getting the verbs right

Safe, idempotent, and why it matters

Two properties of each verb decide whether a browser may pre-fetch it, whether a proxy may cache it, and whether a mobile app may safely retry it after a dropped connection.

VerbSafe? (changes nothing)Idempotent? (repeat = same result)Consequence
GET✅ Yes✅ YesCacheable; safe to retry or pre-fetch freely.
POST❌ No❌ NoRetrying creates a duplicate. This is why browsers warn "confirm form resubmission".
PUT❌ No✅ YesSafe to retry — you'd just set the same values again.
DELETE❌ No✅ YesSafe to retry — already-deleted stays deleted.
PATCH❌ No⚠️ DependsIdempotent if you set absolute values; not if you say "add 1".
The rule this gives you — and it's a real-world rule Never use GET for anything that changes data. A URL like GET /deleteStudent/5 looks harmless but is genuinely dangerous: browsers pre-fetch links, crawlers follow them, and proxies cache them. People have wiped production data this way. If it changes something, use POST, PUT, PATCH or DELETE.

Status codes · 1 of 2

Status codes: the five families

Every response carries a three-digit code. You don't need to memorise all of them — you need to know what the first digit means, because that alone tells you who has the problem.

1xx
Informational — "still working on it." You'll rarely see these.
2xx
Success — it worked. 200 OK, 201 Created, 204 No Content.
3xx
Redirection — "it lives somewhere else now."
4xx
Client error — the caller did something wrong. Bad JSON, wrong id, no permission. Fix the request.
5xx
Server error — your code broke. An unhandled exception, a database that's down. Fix the server.
4xx vs 5xx — the most useful distinction in debugging 4xx means it's the caller's fault; 5xx means it's yours. When a client reports "your API returned 400", the answer is usually "check what you sent me." When it returns 500, that's your bug and it belongs in your logs. Getting this right saves enormous amounts of finger-pointing — and returning 500 for a bad user input is a genuine API design fault, not a cosmetic one.

401 vs 403, since everyone mixes them up 401 = "I don't know who you are" → log in.    403 = "I know exactly who you are, and you're not allowed" → no amount of logging in will help.

Designing URLs properly

Your URLs are your API's public face. They're read by other developers, hard to change once published, and a good set makes an API feel obvious. The rules are simple:

Rule❌ Avoid✅ Prefer
Nouns, not verbs — HTTP already has the verb/getStudent/5
/createStudent		GET /students/5
POST /students
Plural for collections — consistent and reads naturally/student/students
Lower-case with hyphens/StudentRecords
/student_records		/student-records
Nest to show ownership/getCoursesForStudent?id=5GET /students/5/courses
Query params for filtering, paths for identity/students/gradeA/students?grade=A
No file extensions — headers handle format/students.json/students
Version your API/students (then break it later)/api/v1/students
Path or query parameter? The test Ask: "is this value required to identify the thing?" If yes → path (/students/5 — without the 5 there's no request to make). If it merely narrows or sorts a list → query (/students?grade=A&sort=name — still meaningful without it). This maps exactly onto @PathVariable and @RequestParam.

The code

@RestController, unpacked

Like @SpringBootApplication, this is shorthand. It is exactly two annotations combined:

@Controller
Makes it a bean that handles web requests — so component scanning picks it up and the DispatcherServlet can route to it.
@ResponseBody
Says "my return value IS the response body" — convert it to JSON and send it — rather than "my return value is the name of an HTML page to render".

That second one explains a classic beginner error. Watch what happens with the wrong annotation:

❌ @Controller alone

@Controller
public class StudentController {

    @GetMapping("/hello")
    public String hello() {
        return "Hello!";
    }
}

Spring reads "Hello!" as the name of a page, hunts for a template called Hello!, fails, and you get a 500 error or a Whitelabel page.

✅ @RestController

@RestController
public class StudentController {

    @GetMapping("/hello")
    public String hello() {
        return "Hello!";
    }
}

Spring sends Hello! as the response body. Correct — and the same reasoning applies to objects, which become JSON.

Rule of thumb Building an API? @RestController, always. Rendering HTML pages server-side (with Thymeleaf or JSP)? @Controller. We use @RestController exclusively in this course.

The code

@RequestMapping at class level

Every endpoint for one resource shares a path prefix. Rather than repeating it on every method, declare it once on the class — the method paths are then appended to it.

❌ Repetitive

@RestController
public class StudentController {

    @GetMapping("/api/students")
    @GetMapping("/api/students/{id}")
    @PostMapping("/api/students")
    @PutMapping("/api/students/{id}")
    @DeleteMapping("/api/students/{id}")
    // /api/students typed 5 times.
    // Change the prefix → edit 5 lines.
}

✅ Prefix declared once

@RestController
@RequestMapping("/api/students")
public class StudentController {

    @GetMapping             → /api/students
    @GetMapping("/{id}")    → /api/students/5
    @PostMapping            → /api/students
    @PutMapping("/{id}")    → /api/students/5
    @DeleteMapping("/{id}") → /api/students/5
    // One place to change the prefix.
}
Two things that catch people out One: the full path is always class prefix + method path. If your class says /api/students and your method says /api/students/{id}, the real URL becomes /api/students/api/students/5 — and you'll get a confusing 404. Two: a bare @GetMapping with no value maps to the class path exactly, which is precisely what you want for "get all".

The code · new today

@RequestBody — data coming in

Until now every input arrived through the URL, which is fine for an id but hopeless for a whole student record. To create something, the client sends JSON in the request body, and @RequestBody is what turns that JSON into a Java object.

@PostMapping
public Student create(@RequestBody Student student) {
    // 'student' is a fully-populated Java object.
    // Jackson parsed the JSON body and filled it in — you wrote no parsing code.
    return service.save(student);
}
Client sends JSON in the request body
→
Jackson parses it using your setters
→
Your method gets a Student ready to use

The JSON keys are matched to your class's fields by name:

The JSON sent

{
  "name": "Amit Shah",
  "email": "amit@tcs.com",
  "grade": "A"
}

The object you receive

student.getName()   → "Amit Shah"
student.getEmail()  → "amit@tcs.com"
student.getGrade()  → "A"
student.getId()     → null (not sent)
Two failure modes you will definitely hit in the lab 415 Unsupported Media Type → the Content-Type: application/json header is missing. Swagger UI sets it automatically, so you'll only meet this with other tools. 400 Bad Request → your JSON is malformed (a trailing comma, single quotes, a missing brace). Both are client errors, which is why they're 4xx.

The code · new today

ResponseEntity — control what goes out

Returning a plain object always produces 200 OK. But we established that a POST should return 201, a DELETE should return 204, and a missing id should return 404. ResponseEntity<T> is the wrapper that lets you set status code, headers and body yourself.

Plain return — always 200

@PostMapping
public Student create(
        @RequestBody Student s) {
    return service.save(s);
}
// Works, but returns 200 OK.
// A creation should say 201 Created.

With ResponseEntity

@PostMapping
public ResponseEntity<Student> create(
        @RequestBody Student s) {
    Student saved = service.save(s);
    return ResponseEntity
            .status(HttpStatus.CREATED)
            .body(saved);
}
// 201 Created + the new object.

There are convenient shortcuts for the common cases:

CodeProducesTypical use
ResponseEntity.ok(obj)200 + bodyA successful GET or PUT
ResponseEntity.status(HttpStatus.CREATED).body(obj)201 + bodyA successful POST
ResponseEntity.noContent().build()204, no bodyA successful DELETE
ResponseEntity.notFound().build()404, no bodyThat id doesn't exist
ResponseEntity.badRequest().body(msg)400 + messageInvalid input
The classic pattern: found or not found 
@GetMapping("/{id}")
public ResponseEntity<Student> getById(@PathVariable int id) {
    Student found = service.findById(id);
    if (found == null) {
        return ResponseEntity.notFound().build();   // 404
    }
    return ResponseEntity.ok(found);                // 200 + the student
}
You'll write exactly this in the lab. In Session 3 we replace the if with a cleaner approach — a custom exception and a global handler.

Putting it together

A complete CRUD controller

Everything from the last several slides, in one class. This is the shape of the file you'll build across today's labs — read it as a map of where you're going.

@RestController
@RequestMapping("/api/students")          // shared prefix
public class StudentController {

    private final StudentService service;

    public StudentController(StudentService service) {   // constructor injection
        this.service = service;
    }

    // READ ALL   ·  GET /api/students
    @GetMapping
    public List<Student> getAll() {
        return service.findAll();
    }

    // READ ONE   ·  GET /api/students/5
    @GetMapping("/{id}")
    public ResponseEntity<Student> getById(@PathVariable int id) {
        Student s = service.findById(id);
        return (s == null) ? ResponseEntity.notFound().build()
                           : ResponseEntity.ok(s);
    }

    // SEARCH     ·  GET /api/students/search?grade=A
    @GetMapping("/search")
    public List<Student> search(@RequestParam String grade) {
        return service.findByGrade(grade);
    }

    // CREATE     ·  POST /api/students  + JSON body
    @PostMapping
    public ResponseEntity<Student> create(@RequestBody Student student) {
        return ResponseEntity.status(HttpStatus.CREATED).body(service.save(student));
    }

    // UPDATE     ·  PUT /api/students/5  + JSON body
    @PutMapping("/{id}")
    public ResponseEntity<Student> update(@PathVariable int id,
                                          @RequestBody Student student) {
        Student updated = service.update(id, student);
        return (updated == null) ? ResponseEntity.notFound().build()
                                 : ResponseEntity.ok(updated);
    }

    // DELETE     ·  DELETE /api/students/5
    @DeleteMapping("/{id}")
    public ResponseEntity<Void> delete(@PathVariable int id) {
        return service.delete(id) ? ResponseEntity.noContent().build()
                                  : ResponseEntity.notFound().build();
    }
}

An honest limitation

Where does today's data live?

We have no database yet — that's Session 3. So today the students live in an ordinary ArrayList held in memory, inside a @Service bean.

@Service
public class StudentService {

    // Just a list in memory. Remember: the @Service bean is a SINGLETON,
    // so there is ONE list shared by every request — which is what makes
    // it behave like a tiny database for the duration of the run.
    private final List<Student> students = new ArrayList<>();
    private int nextId = 1;
    ...
}
The consequence — and it's the whole motivation for Session 3 Restart the app and every student you created is gone. The list lived in memory, and memory is wiped when the process ends. That's not a bug in the lab; it's the honest limit of what we've built. Session 3 fixes it with a real database, and you'll appreciate why we need one far more having felt this.
The good news: the controller won't change Because the controller only talks to StudentService and never to the list, swapping the list for a real database means rewriting the service and leaving the controller untouched. That is the layered architecture from Session 1 paying off — and you'll see it happen for real next session.

Testing · 1 of 2

Why a browser isn't enough any more

Here's a problem: typing a URL into a browser can only ever send a GET. There's no way to choose a verb or attach a body, so you cannot test POST, PUT or DELETE from the address bar. From today you need a proper API client.

There are two common choices, and we use the second:

The other direction

Calling someone else's API

So far your app has answered requests. Often it also needs to make them — fetching an exchange rate, or in Session 4, calling another microservice. Spring gives you a client for that.

@Service
public class ExchangeRateService {

    private final RestTemplate restTemplate = new RestTemplate();

    public Student fetchStudent(int id) {
        String url = "http://localhost:8081/api/students/" + id;

        // Sends a GET, receives JSON, and converts it straight into a
        // Student object — the same Jackson conversion, in reverse.
        return restTemplate.getForObject(url, Student.class);
    }
}

A note on what's current RestTemplate is in maintenance mode — still fully supported and everywhere in existing code, which is why you must recognise it. For new code, Spring recommends RestClient (modern, same synchronous style) or WebClient (for reactive/async work). In Session 4 you'll see RestTemplate gain a superpower: add @LoadBalanced and it can call a service by name instead of by URL, letting Eureka find the address for it.

Common mistakes in REST APIs

MistakeSymptomFix
Missing Content-Type: application/json415 Unsupported Media TypeSwagger UI sets it for you. With curl: add -H "Content-Type: application/json".
Malformed JSON — trailing comma, single quotes400 Bad RequestDouble quotes on keys and strings; no comma after the last pair.
Sending POST to a @GetMapping405 Method Not AllowedMatch the annotation to the verb.
Class prefix repeated in the method path404 on a URL that looks rightThe real path is class + method. Use @GetMapping("/{id}"), not the full path again.
Data class has no gettersResponse is {} or fields go missingGenerate getters — Jackson reads values through them.
Data class has no no-arg constructor400, or every field nullAdd a public no-argument constructor for Jackson to use.
Returning 200 for everythingWorks, but misleads callersUse ResponseEntity: 201 create, 204 delete, 404 missing.
Returning 500 for bad user inputCallers think your server is broken4xx is their mistake; 5xx is yours. Choose deliberately.

Check yourself

Quick recap — tap each card to reveal

Q · What's the difference between a web application and a web service? tap to reveal ▾
A web application returns HTML for humans to look at (@Controller). A web service returns data, usually JSON, for other programs to consume (@RestController).
Q · Which HTTP verbs are idempotent, and why does it matter? tap to reveal ▾
GET, PUT and DELETE — repeating them has the same effect as doing them once. POST is not, which is why calling it twice creates two records and why retries after a dropped connection are risky.
Q · What do 4xx and 5xx tell you? tap to reveal ▾
4xx = the caller's fault (bad JSON, wrong id, no permission) — fix the request. 5xx = your server's fault (an unhandled exception) — fix the code. Never return 5xx for bad user input.
Q · What two things does @RestController combine? tap to reveal ▾
@Controller (makes it a request-handling bean) + @ResponseBody (my return value is the response body, converted to JSON — not the name of a page).
Q · You send valid JSON and get 415. What did you forget? tap to reveal ▾
The Content-Type: application/json header. Swagger UI sets it for you automatically — so if you hit 415, you're using a tool that doesn't, and you must add the header yourself.
Q · What must a class have for Jackson to convert it both ways? tap to reveal ▾
Getters for going out (Java → JSON), and a no-argument constructor plus setters for coming in (JSON → Java).
Q · Path variable or query parameter? tap to reveal ▾
If the value is needed to identify the resource → path (/students/5). If it merely filters or sorts a list → query (/students?grade=A).
Q · Why does today's data vanish on restart? tap to reveal ▾
It lives in an ArrayList in memory inside a singleton bean, and memory is wiped when the process ends. Session 3 replaces it with a real database.
