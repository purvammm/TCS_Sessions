Concept 1 — forms

Angular has two form systems. Why?

A form isn't just some inputs. A real form needs to collect values, validate them, report its state (is it valid? has the user touched it yet?), and package the data for an API. Angular gives you two ways to do all that, and they suit different situations.

📄

Template-driven

The template is the source of truth. You add ngModel to inputs and Angular builds the form model behind the scenes for you.

Feels like: ordinary HTML with a little Angular sprinkled on.

Needs: FormsModule

🧮

Reactive (model-driven)

The TypeScript class is the source of truth. You build the form explicitly in code from FormGroup and FormControl objects, then bind the template to it.

Feels like: writing a data structure, then wiring HTML to it.

Needs: ReactiveFormsModule

Today you'll build the same form twice Same four fields, once each way, side by side. That's the fastest way to feel the difference rather than memorise a comparison table — and it's exactly what Tasks 1 and 2 of the lab ask for.
Ask the batch Before we look at the code — why might it be useful to represent a form as an object in your class rather than as markup in the template? (Look for: you can validate it, test it, pre-fill it, reset it and serialise it without touching or even rendering the HTML.)

Template-driven forms · 1 of 3

Setup — FormsModule and ngForm

src/app/app.module.ts
import { FormsModule } from '@angular/forms';

@NgModule({
  imports: [ BrowserModule, FormsModule ],
  ...
})
export class AppModule { }

Once FormsModule is imported, Angular automatically attaches an ngForm directive to every <form> tag in your templates. You don't add it — it's already there. To use it, you just need a name for it:

<form #userForm="ngForm" (ngSubmit)="registerEmployee(userForm.value)">
  ...
</form>
#userForm
A template reference variable. The # creates a name you can use elsewhere in this template.
="ngForm"
Points that name at the auto-attached ngForm directive — not at the raw DOM element.
userForm.value
An object containing every field's current value, keyed by its name attribute.
userForm.valid
true only when every field passes its validation rules.
(ngSubmit)
Fires on form submit. Prefer this over (click) on the button — it also handles the Enter key, which users expect.
What you get for free Without writing a single line of TypeScript, userForm already knows every field's value, whether the form is valid, and whether the user has interacted with it. That's the appeal of the template-driven approach.

Template-driven forms · 2 of 3

The fields — name + ngModel

Every field needs two things to join the form: a name attribute (which becomes the key in userForm.value) and the ngModel directive (which registers it).

registration.component.html
<form #userForm="ngForm" (ngSubmit)="registerEmployee(userForm.value)">

  <input type="text"   name="name"       ngModel placeholder="Name">
  <input type="number" name="age"        ngModel placeholder="Age">
  <input type="text"   name="city"       ngModel placeholder="City">
  <input type="text"   name="postalCode" ngModel placeholder="Postal code">

  <button type="submit">Register</button>
</form>

Note: bare ngModel with no brackets. You only need [(ngModel)]="something" when you also want a class property kept in sync. To simply collect the value on submit, plain ngModel is enough.

Grouping related fields with ngModelGroup

<div ngModelGroup="address">
  <input type="text" name="city"       ngModel>
  <input type="text" name="postalCode" ngModel>
</div>

The handler

registerEmployee(value: any): void {
  console.log(value);
  console.log(value.name);
  console.log(value.address.city);
}

{

}
Why grouping matters ngModelGroup produces nested JSON — which usually matches exactly what your Spring Boot DTO expects. Shape the form to match the API and you never write mapping code.

Template-driven forms · 3 of 3

Validation the template-driven way

Validation rules are ordinary HTML attributes. Angular reads them and tracks the result.

<form #userForm="ngForm" (ngSubmit)="registerEmployee(userForm.value)">

  <input type="text" name="name" ngModel required minlength="3" #nameField="ngModel">

  <!-- show the error only once the user has actually interacted -->
  <small *ngIf="nameField.invalid && nameField.touched">
    <span *ngIf="nameField.errors?.['required']">Name is required.</span>
    <span *ngIf="nameField.errors?.['minlength']">At least 3 characters.</span>
  </small>

  <!-- block submission until the whole form is valid -->
  <button type="submit" [disabled]="userForm.invalid">Register</button>
</form>
StateMeansUse it for
valid / invalidPasses / fails its rulesEnabling the submit button
touched / untouchedHas / hasn't been focused and leftNot shouting "required!" at an empty form on load
dirty / pristineValue has / hasn't been changed"You have unsaved changes" warnings
The UX detail that separates good forms from annoying ones Always pair a validation message with && touched (or dirty). Without it, every error message screams at the user the instant the page loads, before they've typed anything. That single condition is the difference between a form that feels helpful and one that feels hostile.

Reactive forms · 1 of 4

Reactive forms — the model comes first

In a reactive form you build the form in TypeScript, then point the template at it. The form exists as a real object you can inspect, test, pre-fill and reset — whether or not any HTML is rendered.

1️⃣

FormControl

Represents one field. Tracks its value, its validators and its state (valid, touched, dirty).

name = new FormControl('');
🧩

FormGroup

A collection of controls treated as one unit. Its value is an object; it's valid only when all its children are.

userForm = new FormGroup({
  name: new FormControl(''),
  age:  new FormControl('')
});
Rule of thumb for choosing between them FormControl on its own for one or two independent fields — a search box, a single filter dropdown. FormGroup for any multi-field form you'll serialise and send to an API, because userForm.value hands you the whole object ready to POST.

There's also FormArray for a dynamic, growable list of controls — "add another phone number". Worth knowing it exists; not needed for these four sessions.

Reactive forms · 2 of 4

Building a reactive form

src/app/app.module.ts
import { ReactiveFormsModule } from '@angular/forms';   // ← a DIFFERENT module

@NgModule({
  imports: [ BrowserModule, FormsModule, ReactiveFormsModule ],
  ...
})

reactive-registration.component.ts

import { Component } from '@angular/core';
import { FormGroup, FormControl } from '@angular/forms';

@Component({ /* ... */ })
export class ReactiveRegistrationComponent {

  userForm = new FormGroup({
    name:       new FormControl(''),
    age:        new FormControl(''),
    city:       new FormControl(''),
    postalCode: new FormControl('')
  });

  onSubmit(): void {
    console.log(this.userForm.value);
  }
}

reactive-registration.component.html

<form [formGroup]="userForm"
      (ngSubmit)="onSubmit()">

  <input formControlName="name">
  <input formControlName="age" type="number">
  <input formControlName="city">
  <input formControlName="postalCode">

  <button type="submit">Register</button>
</form>
Spot the difference from template-driven No ngModel. No name attributes. No #userForm="ngForm". The template simply refers to a form that already exists in the class — [formGroup] names the group, formControlName names each control. The class defines the form; the template renders it.
Two very common errors here ReactiveFormsModule is not the same as FormsModule — importing the wrong one gives you "Can't bind to 'formGroup'". And the string in formControlName="name" must match the key in your FormGroup exactly, or you get "Cannot find control with name: 'name'".

Reactive forms · 3 of 4

Validation with the Validators class

In a reactive form, validators are passed as the second argument to each FormControl — so the rules live in your TypeScript, next to the data they guard.

import { FormGroup, FormControl, Validators } from '@angular/forms';

userForm = new FormGroup({
  name: new FormControl('', [
    Validators.required,
    Validators.minLength(3)
  ]),
  age: new FormControl('', [
    Validators.required,
    Validators.min(18),
    Validators.max(60)
  ]),
  email: new FormControl('', [
    Validators.required,
    Validators.email
  ]),
  postalCode: new FormControl('', [
    Validators.required,
    Validators.pattern('^[0-9]{6}$')      // exactly 6 digits
  ])
});
ValidatorRejects when
Validators.requiredThe field is empty
Validators.minLength(3)Fewer than 3 characters
Validators.maxLength(20)More than 20 characters
Validators.min(18) / max(60)Numeric value out of range
Validators.emailNot a valid email format
Validators.pattern('…')Doesn't match your regular expression
Client-side validation is UX, not security It gives instant feedback and saves round trips — but anyone can bypass it with browser tools. Always validate again on the server (Bean Validation / @Valid in Spring Boot). Client-side for friendliness; server-side for correctness.

Reactive forms · 4 of 4

Showing the errors

<form [formGroup]="userForm" (ngSubmit)="onSubmit()">

  <input formControlName="name" placeholder="Name">

  <div *ngIf="userForm.controls['name'].touched">
    <small *ngIf="userForm.controls['name'].hasError('required')">
      Name is required.
    </small>
    <small *ngIf="userForm.controls['name'].hasError('minlength')">
      Name must be at least 3 characters.
    </small>
  </div>

  <button type="submit" [disabled]="userForm.invalid">Register</button>
</form>

<!-- brilliant while learning: watch the whole model live -->
<pre>Valid? {{ userForm.valid }}</pre>
<pre>{{ userForm.value | json }}</pre>
.controls['name']
Reaches into the group to get that one FormControl.
.hasError('required')
Was this specific rule broken? Lets you show a different message per rule.
.touched
Only complain after the user has visited the field.
[disabled]="userForm.invalid"
The whole group is invalid if any control is — so one binding guards the button.
Put those last two lines in every form you build while learning {{ userForm.value | json }} shows you the live model as you type, and {{ userForm.valid }} shows why the button won't enable. It turns "why isn't this working?" into something you can simply read off the screen. Delete them before you ship.

Concept 2 — services

What is a service, and why?

A service is an ordinary TypeScript class that holds reusable business logic and data access — no template, no UI. Its job is to keep components focused on one thing: presentation.

❌ Without a service

  • The employee array lives inside EmployeeListComponent
  • Need the same data in a dropdown? Copy the array
  • Search/filter logic sits next to display logic
  • Switching to a real API means rewriting the component
  • Testing the data logic requires rendering a template
→

✅ With a service

  • The data lives in EmployeeService
  • Any component injects it and gets the same data
  • Component = display only; service = data only
  • Swap the array for an HTTP call — components don't change
  • Test the service as a plain class
Three steps to use a service — that's the whole pattern 1 · Create it (ng generate service employee)  →  2 · Register it (@Injectable({ providedIn: 'root' }) — the CLI adds this for you)  →  3 · Inject it (constructor(private employeeService: EmployeeService) { }).

If you've written a Spring @Service injected into a @RestController, you already know this pattern. It is the same idea, in the same shape, on the front end.

Services · step 1 — create

Creating a service

ng generate service employee

# short form
ng g s employee
CREATE src/app/employee.service.spec.ts (367 bytes) CREATE src/app/employee.service.ts (137 bytes)
src/app/employee.service.ts
import { Injectable } from '@angular/core';
import { Employee } from './models/employee';

@Injectable({
  providedIn: 'root'          // ← step 2 (registration) — the CLI added this
})
export class EmployeeService {

  private employees: Employee[] = [
    { id: 1001, name: 'Anoop',  designation: 'Software Engineer', salary: 25000, status: 'Active' },
    { id: 1002, name: 'Ajay',   designation: 'Team Lead',         salary: 45000, status: 'Inactive' },
    { id: 1003, name: 'Rekha',  designation: 'Tester',            salary: 22000, status: 'Active' },
    { id: 1004, name: 'Suresh', designation: 'Architect',         salary: 65000, status: 'Inactive' }
  ];

  getEmployees(): Employee[] {
    return this.employees;
  }

  searchByName(term: string): Employee[] {
    if (!term) { return this.employees; }
    return this.employees.filter(e =>
      e.name.toLowerCase().includes(term.toLowerCase())
    );
  }

  getById(id: number): Employee | undefined {
    return this.employees.find(e => e.id === id);
  }
}
Two details worth calling out @Injectable marks the class as available for injection — it's the front-end twin of Spring's @Service. And notice the array is private: the outside world can only reach the data through your methods, so you keep control of how it's read and changed.

Services · step 3 — inject

Using a service in a component

src/app/employee-list/employee-list.component.ts
import { Component, OnInit } from '@angular/core';
import { Employee } from '../models/employee';
import { EmployeeService } from '../employee.service';

@Component({
  selector: 'app-employee-list',
  templateUrl: './employee-list.component.html'
})
export class EmployeeListComponent implements OnInit {

  employees: Employee[] = [];

  // ← the constructor shorthand from Session 1, slide 18
  constructor(private employeeService: EmployeeService) { }

  ngOnInit(): void {
    this.employees = this.employeeService.getEmployees();
  }

  search(term: string): void {
    this.employees = this.employeeService.searchByName(term);
  }
}
constructor(private x: X)
Declares a private field and assigns Angular's injected instance to it — in one line. You never write new EmployeeService().
implements OnInit
A lifecycle interface. Angular calls ngOnInit() once, after the component is constructed and its inputs are set.
ngOnInit()
The right place for setup work — fetching data, initialising forms. Keep the constructor for injection only.
Why not just fetch data in the constructor? It technically works for a synchronous array, but it's the wrong habit. The constructor runs before Angular has finished setting the component up, and mixing "wiring" with "work" makes components harder to test. Constructor for dependencies, ngOnInit for initialisation. Follow it always.
Notice what did NOT change The template is identical. It still says *ngFor="let emp of employees". The data now arrives from a completely different place and the view neither knows nor cares. That's the whole point of the refactor — and it's Task 5 of today's lab.

Deep dive — how injection actually works

Dependency injection & the injector

You asked for an EmployeeService in a constructor and one appeared. Who created it? Angular's injector — a registry that knows how to build every registered service and hands out instances on request.

1 · Angular creates EmployeeListComponent and reads its constructor's parameter types
▼
2 · It asks the injector for an EmployeeService
▼
3 · Injector: "Do I already have one?" Yes → reuse it. No → create it, cache it, return it.
▼
4 · The instance is passed in, and your private employeeService field is set

Two consequences worth understanding:

  • It's a singleton by default. With providedIn: 'root' there is exactly one instance for the whole application. Ten components injecting EmployeeService all share the same object — so data cached in it is genuinely shared.
  • Your component is decoupled. It declares what it needs, never how to build it. Swap the real service for a mock in a test and the component doesn't change a line.
Two ways to register a service @Injectable({ providedIn: 'root' }) — the modern default, and what the CLI generates. One shared instance, and unused services are dropped from the build automatically.
providers: [EmployeeService] in a module or component — older style, still valid. Listing it in a component's providers gives that component its own private instance, which is occasionally what you want.
How many services should an app have? As many as it has feature areas — there's no "one service per app" rule. A banking app would naturally have a CustomerService and a TransactionService and an AuthService. One service, one responsibility.

Concept 3 — talking to a backend

HttpClient — the bridge to your API

Everything so far has been in-memory. HttpClient is Angular's built-in way to send HTTP requests and receive JSON — the piece that connects your Angular app to the Spring Boot API you already know how to build.

Architectural rule: components never call HttpClient directly Always put the call in a service. The component asks the service for data; the service knows the URL. That way the endpoint is defined in one place, and swapping mock data for a live API touches one file.

HttpClient · GET

Reading data — .get()

src/app/user.service.ts
import { Injectable } from '@angular/core';
import { HttpClient } from '@angular/common/http';
import { Observable } from 'rxjs';

@Injectable({ providedIn: 'root' })
export class UserService {

  private baseUrl = 'https://jsonplaceholder.typicode.com/users';

  constructor(private http: HttpClient) { }      // inject HttpClient

  getUsers(): Observable<any[]> {
    return this.http.get<any[]>(this.baseUrl);   // returns an Observable
  }
}
the component
users: any[] = [];
errorMsg: string = '';
loading: boolean = false;

constructor(private userService: UserService) { }

ngOnInit(): void {
  this.loading = true;
  this.userService.getUsers().subscribe({
    next: (data) => {                 // ✅ the response arrived
      this.users = data;
      this.loading = false;
    },
    error: (err) => {                 // ❌ something went wrong
      this.errorMsg = 'Could not load users.';
      this.loading = false;
      console.error(err);
    }
  });
}
The one thing that trips up everyone this.http.get(...) does not send the request. Nothing happens until you call .subscribe(). An Observable is a recipe, not a result — forget to subscribe and your network tab stays empty with no error at all. Also: the code after subscribe() runs before the data arrives, so never read this.users on the next line.

HttpClient · POST

Sending data — .post()

import { HttpClient, HttpHeaders } from '@angular/common/http';

addPerson(person: any): Observable<any> {
  const headers = new HttpHeaders({
    'Content-Type': 'application/json'
  });

  return this.http.post<any>(this.baseUrl, person, { headers });

the component
onSubmit(): void {
  this.userService.addPerson(this.userForm.value).subscribe({
    next: (created) => {
      console.log('Server created:', created);
      this.message = 'Saved successfully. New id: ' + created.id;
      this.userForm.reset();                 // clear the form
    },
    error: (err) => {
      this.message = 'Save failed — please try again.';
      console.error(err);
    }
  });
}

1st — the URLWhere to send it
2nd — the bodyThe object to send. You don't stringify it — HttpClient serialises to JSON for you.

Two conveniences you get automatically HttpClient parses the response as JSON by default — no JSON.parse() anywhere. And it sets Content-Type: application/json for object bodies, so the explicit headers above are usually unnecessary. Shown here because you'll see them in older code.

HttpClient · PUT & DELETE

The full set of four

// READ all
getUsers(): Observable<any[]> {
  return this.http.get<any[]>(this.baseUrl);
}

// READ one
getUser(id: number): Observable<any> {
  return this.http.get<any>(`${this.baseUrl}/${id}`);
}

// CREATE
addUser(user: any): Observable<any> {
  return this.http.post<any>(this.baseUrl, user);
}

// UPDATE
updateUser(id: number, user: any): Observable<any> {
  return this.http.put<any>(`${this.baseUrl}/${id}`, user);
}

// DELETE
deleteUser(id: number): Observable<any> {
  return this.http.delete<any>(`${this.baseUrl}/${id}`);
}
VerbPurposeSpring Boot counterpart
GETRead — never changes data@GetMapping
POSTCreate a new record@PostMapping
PUTUpdate an existing record@PutMapping
DELETERemove a record@DeleteMapping
Note the backtick syntax `${this.baseUrl}/${id}` is a TypeScript template literal — backticks, with ${ } for embedded expressions. It's much cleaner than this.baseUrl + '/' + id and it's what you'll see in every modern codebase.
CORS — the error you'll meet with your own Spring Boot API Calling your API from localhost:4200 when it runs on localhost:8080 is a cross-origin request, and the browser blocks it by default. Fix it on the server: add @CrossOrigin(origins = "http://localhost:4200") to your controller. No amount of Angular code can fix a CORS error — it's a browser security rule the server has to permit.

Concept 4 — Observables

What is an Observable, and why does Angular use them?

An Observable represents a stream of values that arrive over time. It comes from RxJS, and Angular leans on it for anything asynchronous — HTTP responses, router events, form value changes.

You subscribe "tell me when it arrives"
→
Request is sent your code keeps running
→
Value arrives your next() handler runs

The key idea: an HTTP call takes time. Angular can't freeze the browser while it waits, so instead of returning a value it returns an object that promises to call you back. Meanwhile the UI stays responsive.

this.userService.getUsers().subscribe({
  next:     (data) => { this.users = data; },       // may fire one or many times
  error:    (err)  => { console.error(err); },      // fires at most once
  complete: ()     => { console.log('done'); }      // the stream has finished
});
 PromiseObservable
EmitsExactly one valueZero, one, or many values over time
StartsImmediately when createdOnly when you subscribe() — "lazy"
CancellableNoYes — unsubscribe()
OperatorsVery fewDozens — map, filter, debounceTime, switchMap
Where Observables show up beyond HTTP Router: "the URL parameters changed" (Session 4). Forms: userForm.valueChanges.subscribe(...) fires on every keystroke — perfect for live search. HTTP: the response. One mental model, three places. Learning it once pays off everywhere.

Bonus — the neater way

The async pipe

There's a way to skip subscribe() entirely: let the template subscribe for you. This is worth showing because you'll see it constantly in real codebases.

Manual subscribe

users: any[] = [];

ngOnInit() {
  this.userService.getUsers()
    .subscribe(d => this.users = d);
}
<li *ngFor="let u of users">
  {{ u.name }}
</li>

With the async pipe

users$ = this.userService.getUsers();

// no ngOnInit, no subscribe needed
<li *ngFor="let u of users$ | async">
  {{ u.name }}
</li>
Why it's preferred The async pipe subscribes when the component appears and unsubscribes automatically when it's destroyed — which removes a whole class of memory leak. The $ suffix on users$ is just a naming convention meaning "this is an Observable".
Which should you use today? Use explicit .subscribe() in the lab — it makes the asynchronous flow visible, which is what you're here to learn. Recognise the async pipe so you're not confused when you meet it in a real project, and reach for it once the mechanics feel obvious.

The full picture

How today's pieces fit together

TemplateA reactive form collects input; *ngFor renders the results; *ngIf shows loading and error states.
Component classOwns the FormGroup, injects the service, subscribes in ngOnInit, and holds the data for the template. No URLs, no business rules.
ServiceOwns the endpoint URLs and returns Observables. The only place that knows the API exists.

Compare this with the layering you already know from Spring Boot — it's the same discipline, applied on the client:

AngularSpring Boot equivalentShared responsibility
Component@RestControllerHandles the interaction, delegates the work
Service@ServiceBusiness logic, reusable across callers
HttpClientRepository / JdbcTemplateTalks to the data source
Interface / modelDTO / EntityDefines the shape of the data
Why this matters Good Angular architecture isn't a new set of rules — it's the same separation of concerns you already practise on the server. If you'd be uncomfortable putting SQL in a controller, be equally uncomfortable putting a URL in a component.

Recap

What you now know

  • Template-driven forms: FormsModule, #f="ngForm", plus name + ngModel on each field; ngModelGroup for nested JSON.
  • Reactive forms: ReactiveFormsModule, a FormGroup of FormControls in the class, bound with [formGroup] and formControlName.
  • Validation: the Validators class, checked with hasError(), and always paired with touched so you don't nag the user.
  • Reactive forms are the default choice for anything real — testable, dynamic, and honest about where the truth lives.
  • Services hold reusable data and logic. Three steps: create → register (@Injectable) → inject (constructor).
  • Dependency injection gives you one shared instance with providedIn: 'root', and decouples your component from construction details.
  • HttpClient (needs HttpClientModule) does GET, POST, PUT and DELETE, and parses JSON automatically.
  • Observables are lazy: nothing happens until subscribe(). Handle next and error.
  • Components display, services fetch. A URL never belongs in a component.
