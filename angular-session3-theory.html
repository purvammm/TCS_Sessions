Concept 1 — the problem

Why ngModel alone isn't enough

In Session 2 you built a login form with [(ngModel)], and it worked. So why is there a whole topic called "forms"? Because a real form has to answer questions your login form cannot:

❓

Is this field valid?

Is the email actually an email? Is the salary a number? Is the name long enough?

🙈

When do I show the error?

Not immediately — nobody wants "name is required" before they've had a chance to type. Only after they've touched it and left it empty.

🚦

Can I submit yet?

The Submit button should be disabled until every field is valid — not just non-empty.

🔄

Has anything changed?

"You have unsaved changes" needs to know whether the user actually edited anything.

You could answer all of those with your own fields and if statements. It would be a hundred lines of fiddly code per form, and you would get the edge cases wrong. Angular tracks all of it for you — that is what a form system is.

Analogy ngModel on its own is a plain notepad — it holds whatever you write. A form system is a proper application form that knows which boxes are compulsory, checks your entries, marks the problems in red, and refuses to be submitted until it's right.

Concept 1 continued

Angular has two form systems. Why?

This surprises people and feels like a design flaw. It isn't — they solve the same problem from opposite ends, and each is genuinely better for different work.

Template-driven

  • The HTML is in charge
  • You add required, minlength etc. as HTML attributes
  • Angular builds the form model from your template, behind the scenes
  • Very little TypeScript
  • Needs FormsModule
vs

Reactive

  • The TypeScript is in charge
  • You build the form as an object in your class
  • The template just connects to that object
  • More TypeScript, and far more control
  • Needs ReactiveFormsModule
The one-line difference Template-driven: "write the HTML, and Angular will work out the form."
Reactive: "define the form in code, then point the HTML at it."
Which will you use at work? Reactive, most likely — it is what the Angular team recommends for anything non-trivial, and what you will find in serious codebases. But template-driven is quicker to read and quicker to write, so we teach it first: you will build the same form both ways today and see the trade-off yourself rather than taking anyone's word for it.

Concept 2 — template-driven forms · step 1

Setup: FormsModule and ngForm

You already added FormsModule in Session 2 for ngModel. It also brings the rest of the template-driven machinery — the key piece being an invisible directive that attaches itself to every <form> tag.

the important line
<form #empForm="ngForm" (ngSubmit)="onSubmit()">
#empForm
Creates a template reference variable — a name you can use elsewhere in this template. Call it whatever you like.
="ngForm"
Says "set that variable to the form object Angular built", not to the HTML element. This is the part that gives you empForm.valid.
(ngSubmit)
Angular's submit event. Use this rather than (submit) — it stops the browser's default behaviour of reloading the page, which would otherwise wipe your app.

Once you have that reference, the whole form's state is available in the template:

<button type="submit" [disabled]="empForm.invalid">Save</button>

<p>Form valid? {{ empForm.valid }}</p>
<pre>{{ empForm.value | json }}</pre>   <!-- everything the user has typed -->
That last line is worth using immediately {{ empForm.value | json }} shows you the entire form as an object, live, updating as you type. When a form "isn't working", put that on the page and you will usually see the problem in five seconds. It is the same | json debugging trick from Session 2.

Concept 2 — template-driven forms · step 2

The fields: name + ngModel

For Angular to include a field in the form, that field needs two things. Miss either one and the field is invisible to the form.

<input type="text"
       name="empName"           <!-- 1. a name attribute -->
       [(ngModel)]="employee.name">  <!-- 2. ngModel -->
🏷️

Why name?

It becomes the key in the form's value object. Without it Angular throws "If ngModel is used within a form tag, either the name attribute must be set…"

🔗

Why ngModel?

It registers the field with the parent form and binds it to your data. Both jobs, one directive.

Given three fields named empName, empEmail and empSalary, empForm.value is exactly this:

{
  "empName": "Anoop Kumar",
  "empEmail": "anoop@example.com",
  "empSalary": 25000
}
A useful variation you'll see You can register a field without two-way binding it, by writing bare ngModel with no brackets: <input name="city" ngModel>. Angular still tracks it and it still appears in empForm.value — you just read it from the form object instead of from your own field. Handy when you don't need a class property for every input.

Concept 2 — template-driven forms · step 3

The state flags Angular tracks for you

This is the part that makes a form system worth having. For every single field, and for the form as a whole, Angular maintains these flags — continuously, for free.

FlagTrue whenYou use it to…
validEvery validation rule passesEnable the Submit button
invalidAt least one rule failsDisable Submit; the opposite of valid
touchedThe user has focused the field and then left itDecide when to show an error
untouchedThe user has never visited the fieldStay quiet — don't nag yet
dirtyThe value has been changed"You have unsaved changes"
pristineNothing has been changedDisable a "Reset" button
errors—An object naming which rules failed
touched is the flag that makes forms feel polite Showing "Name is required" the instant an empty form loads is aggressive and confusing. The professional pattern is "invalid and touched" — complain only once the user has actually visited the field and left it in a bad state. That single condition is the difference between a form that feels considerate and one that feels like it's shouting at you.
Remember the pairs valid/invalid · touched/untouched · dirty/pristine. Three questions: is it correct?, have they visited it?, have they changed it?

Concept 2 — template-driven forms · step 4

Validation, the template-driven way

You declare the rules as ordinary HTML attributes. Angular notices them and starts enforcing them.

<input type="text"
       name="empName"
       [(ngModel)]="employee.name"
       #nameField="ngModel"        <!-- a reference to THIS FIELD's state -->
       required
       minlength="3"
       maxlength="30">

<!-- Show errors only once the user has been here and left -->
<div *ngIf="nameField.invalid && nameField.touched" class="error">
  <small *ngIf="nameField.errors?.['required']">
    Name is required.
  </small>
  <small *ngIf="nameField.errors?.['minlength']">
    Name must be at least 3 characters.
  </small>
</div>
#nameField="ngModel"
Same trick as the form, one level down: gives you this field's flags. Note it's ="ngModel", not ="ngForm".
required minlength="3"
Plain HTML attributes. Angular reads them and builds the validation rules from them.
invalid && touched
The politeness condition from the previous slide.
errors?.['required']
Which rule failed, so you can write a specific message. The ?. is needed because errors is null when the field is valid.

The validators you get out of the box

AttributeChecks
requiredNot empty
minlength="3" / maxlength="30"Text length
min="0" / max="100"Numeric range
emailLooks like an email address
pattern="[0-9]{10}"Matches a regular expression

Concept 2 — template-driven forms · the whole thing

A complete template-driven form

The class — barely anything

export class RegisterComponent {

  // one object holding the whole form
  employee = {
    name: '',
    email: '',
    salary: 0,
    designation: ''
  };

  submitted = false;

  onSubmit(): void {
    this.submitted = true;
    console.log(this.employee);
    // later: send it to the server
  }

  onReset(): void {
    this.employee = {
      name: '', email: '',
      salary: 0, designation: ''
    };
    this.submitted = false;
  }
}

The template — where the work is

<form #f="ngForm" (ngSubmit)="onSubmit()">

  <label>Name</label>
  <input name="name"
         [(ngModel)]="employee.name"
         #n="ngModel"
         required minlength="3">
  <small *ngIf="n.invalid && n.touched">
    Name must be 3+ characters.
  </small>

  <label>Email</label>
  <input name="email" type="email"
         [(ngModel)]="employee.email"
         #e="ngModel"
         required email>
  <small *ngIf="e.invalid && e.touched">
    Enter a valid email.
  </small>

  <label>Salary</label>
  <input name="salary" type="number"
         [(ngModel)]="employee.salary"
         required min="1000">

  <button type="submit"
          [disabled]="f.invalid">Save</button>
  <button type="button"
          (click)="onReset()"
          [disabled]="f.pristine">Reset</button>
</form>

<p *ngIf="submitted">Saved ✅</p>
Notice the balance — this is the defining characteristic The class is almost empty; the template does everything. That is exactly the appeal of template-driven forms, and exactly their limitation: all your validation logic lives in HTML, where it cannot be unit-tested, reused, or changed at runtime.

Concept 3 — reactive forms · the idea

Reactive forms: the model comes first

Now the same problem, inverted. In a reactive form you build the form as a real object in your TypeScript, and the template merely connects to it.

1 · You create a FormGroup in the classnaming every field and every rule, in code
▼
2 · The template binds to it[formGroup]="empForm" and formControlName="name"
▼
3 · The form object is now yours to inspect and controlread values, set values, add rules, react to changes — all from code

The first step is registering a different module. This is the third time today's error pattern appears, and you should recognise it now:

src/app/app.module.ts
import { ReactiveFormsModule } from '@angular/forms';

@NgModule({
  imports: [
    BrowserModule,
    FormsModule,            // template-driven
    ReactiveFormsModule     // reactive  ← add this
  ]
})
You may keep both FormsModule and ReactiveFormsModule coexist happily — you need both today because your Session 2 login form and search box still use ngModel. What you must not do is mix the two styles on the same form: never put [(ngModel)] and formControlName on the same input.

Concept 3 — reactive forms · building the model

FormGroup and FormControl

Two classes, and the relationship is simple: a FormControl is one field, a FormGroup is a collection of them.

register.component.ts
import { Component } from '@angular/core';
import { FormGroup, FormControl } from '@angular/forms';

@Component({ /* ... */ })
export class RegisterComponent {

  empForm = new FormGroup({
    name:        new FormControl(''),          // '' is the starting value
    email:       new FormControl(''),
    salary:      new FormControl(0),
    designation: new FormControl('Software Engineer')
  });

  onSubmit(): void {
    console.log(this.empForm.value);
    // { name: '...', email: '...', salary: 0, designation: '...' }
  }
}
Analogy A FormControl is one box on a paper form — it knows its own contents and whether they're acceptable. A FormGroup is the whole sheet of paper — it is valid only when every box on it is valid.
What you gain immediately empForm is a genuine object in your class. You can console.log it, inspect it in a debugger, write a unit test against it without rendering any HTML, and read or change any field from code. None of that is possible with a template-driven form, where the form only exists once the HTML has rendered.

Concept 3 — reactive forms · wiring the template

Connecting the template to the model

Two new attributes, and that is the entire template side.

<form [formGroup]="empForm" (ngSubmit)="onSubmit()">

  <label>Name</label>
  <input formControlName="name">

  <label>Email</label>
  <input formControlName="email" type="email">

  <label>Salary</label>
  <input formControlName="salary" type="number">

  <button type="submit" [disabled]="empForm.invalid">Save</button>
</form>
[formGroup]="empForm"
Property binding, on the <form>: "this form is that object in my class". Square brackets, because empForm is an expression.
formControlName="name"
No brackets — it's a plain string naming a key inside the group. The string must match the property name in your FormGroup exactly.

Template-driven needed

  • name="empName"
  • [(ngModel)]="employee.name"
  • #n="ngModel"
  • required minlength="3"
→

Reactive needs

  • formControlName="name"
  • …and that's it
  • the rules live in the class
The mistake that produces a very confusing error Writing [formControlName]="name" with brackets makes Angular look for a class field called name to use as the control's name. It isn't there, and the error talks about a null value. formControlName takes a plain string, so no brackets.

Concept 3 — reactive forms · validation

Validation with the Validators class

In a reactive form the rules are the second argument to each FormControl — an array of validator functions.

import { FormGroup, FormControl, Validators } from '@angular/forms';

empForm = new FormGroup({
  name: new FormControl('', [
    Validators.required,
    Validators.minLength(3),
    Validators.maxLength(30)
  ]),
  email: new FormControl('', [
    Validators.required,
    Validators.email
  ]),
  salary: new FormControl(0, [
    Validators.required,
    Validators.min(1000),
    Validators.max(500000)
  ]),
  phone: new FormControl('', [
    Validators.pattern('[0-9]{10}')       // exactly ten digits
  ])
});
ValidatorEquivalent HTML attribute
Validators.requiredrequired
Validators.minLength(3)minlength="3"
Validators.maxLength(30)maxlength="30"
Validators.min(1000)min="1000"
Validators.emailemail
Validators.pattern('...')pattern="..."
Watch the capitalisation — it differs from the HTML It is Validators.minLength with a capital L, but the HTML attribute is minlength all lower case. Also note Validators.required has no brackets (you're passing the function itself), while Validators.minLength(3) does (you're calling it to build a function). Getting that wrong is a common early error.

Concept 3 — reactive forms · error messages

Showing the errors

Same politeness rule as before — invalid and touched — but you reach the field through the form object rather than a template reference.

<label>Name</label>
<input formControlName="name">

<div *ngIf="empForm.get('name')?.invalid && empForm.get('name')?.touched">
  <small *ngIf="empForm.get('name')?.errors?.['required']">
    Name is required.
  </small>
  <small *ngIf="empForm.get('name')?.errors?.['minlength']">
    At least 3 characters, please.
  </small>
</div>

That is correct but repetitive. Two ways to tidy it, and you should know both:

Tidy option 1 — a getter on the class

// in the class
get name() { return this.empForm.get('name'); }

// in the template — much easier to read
<div *ngIf="name?.invalid && name?.touched">
  <small *ngIf="name?.errors?.['required']">Name is required.</small>
</div>

Tidy option 2 — ng-container to hold the lookup

<ng-container *ngIf="empForm.get('name') as nameCtrl">
  <div *ngIf="nameCtrl.invalid && nameCtrl.touched">
    <small *ngIf="nameCtrl.errors?.['required']">Name is required.</small>
  </div>
</ng-container>
Why all the ?. marks? empForm.get('name') returns AbstractControl | null — it has to allow for you passing a name that doesn't exist. Strict mode then insists you handle the null case, and ?. is the concise way. It is the same operator from Session 1, doing the same job.

Concept 3 — reactive forms · the shorthand you'll actually see

FormBuilder — less typing, same result

Writing new FormControl(...) for every field gets noisy. FormBuilder is a service that builds the same structure with far less ceremony — and it is what you will find in most real code, so you need to recognise it.

The long way

import { FormGroup, FormControl,
         Validators }
  from '@angular/forms';

export class RegisterComponent {
  empForm = new FormGroup({
    name: new FormControl('', [
      Validators.required,
      Validators.minLength(3)
    ]),
    email: new FormControl('', [
      Validators.required,
      Validators.email
    ]),
    salary: new FormControl(0, [
      Validators.min(1000)
    ])
  });
}

Identical, with FormBuilder

import { FormBuilder,
         Validators }
  from '@angular/forms';

export class RegisterComponent {
  empForm;

  constructor(private fb: FormBuilder) {
    this.empForm = this.fb.group({
      name:   ['', [Validators.required,
                    Validators.minLength(3)]],
      email:  ['', [Validators.required,
                    Validators.email]],
      salary: [0,  [Validators.min(1000)]]
    });
  }
}
How to read the shorthand Each field becomes an array of two things: fieldName: [ startingValue, [validators] ]. That's all there is to it.
Look at that constructor — you have seen it before constructor(private fb: FormBuilder) { } is the exact shorthand from Session 1's slide 29, and it is dependency injection — the topic we reach in six slides. You asked for a FormBuilder and Angular handed you one. Note also that with FormBuilder the form must be built in the constructor, because this.fb doesn't exist until then.

Concept 3 — reactive forms · the real payoff

Reading and setting values from code

Here is where reactive forms earn their keep. Because the form is an object, you can drive it programmatically — and in Session 4 you will need exactly this to build an edit screen.

// ── READ ────────────────────────────────────────────────
console.log(this.empForm.value);            // the whole form as an object
console.log(this.empForm.get('name')?.value);  // one field
console.log(this.empForm.valid);            // true / false

// ── WRITE all fields (every field must be supplied) ─────
this.empForm.setValue({
  name: 'Anoop Kumar',
  email: 'anoop@example.com',
  salary: 25000,
  designation: 'Software Engineer'
});

// ── WRITE some fields (this is the one you'll use) ──────
this.empForm.patchValue({ name: 'Ajay Sharma' });

// ── CLEAR the form and reset every flag ─────────────────
this.empForm.reset();

// ── DISABLE / ENABLE a field ────────────────────────────
this.empForm.get('salary')?.disable();
this.empForm.get('salary')?.enable();

// ── REACT to every change as it happens ─────────────────
this.empForm.get('name')?.valueChanges.subscribe(value => {
  console.log('name is now:', value);
});
Remember patchValue — Session 4 depends on it In Session 4 you build an "edit customer" screen: the user clicks a row and the form fills in with that row's data. That is one line — this.form.patchValue(selectedCustomer). Doing the same thing in a template-driven form means manually assigning every property.
And note that last one valueChanges.subscribe(...) gives you a live stream of every keystroke. That word subscribe is about to become very important — it is how Observables work, and it is the same mechanism HttpClient uses.

Concept 4 — services · the problem first

What is a service, and why do you need one?

A service is an ordinary TypeScript class that holds reusable logic and data access. It has no template and no UI — its job is to let components focus on one thing: presentation.

Right now your employees array lives inside EmployeeListComponent. Here is what that costs you:

❌ Without a service

  • The array lives inside EmployeeListComponent
  • Need the same data in a dropdown? Copy the array.
  • Search logic sits next to display logic
  • Switching to a real API means rewriting the component
  • Testing the data logic requires rendering a template
  • Two components with two copies drift apart
→

✅ With a service

  • The data lives in EmployeeService
  • Any component injects it and gets the same data
  • Component = display. Service = data.
  • Swap the array for an HTTP call — components don't change
  • Test the service as a plain class
  • One source of truth, always
Analogy A component is a shop window — its job is to display things attractively. A service is the warehouse — it owns the stock. You would not store your entire inventory in the window, and you would not want ten windows each keeping their own separate stock.
You have already done this on the backend Your Spring Boot @RestController does not contain SQL — it delegates to a @Service, which delegates to a @Repository. An Angular service is that same separation, on the front end. Same reasoning, same benefits, same shape.

Concept 4 — services · the whole pattern in three steps

Three steps to use a service — that's all there is

1 · Create itng generate service employee
▼
2 · Register it@Injectable({ providedIn: 'root' }) — the CLI writes this for you
▼
3 · Inject itconstructor(private employeeService: EmployeeService) { }

Step 2 is done automatically. Step 1 is one command. So in practice using a service is one command and one constructor line.

The Spring Boot comparison, line for line @Injectable is Angular's @Service. providedIn: 'root' is "make it a singleton bean in the application context". constructor(private employeeService: EmployeeService) is constructor injection — exactly what you write in a Spring @RestController. If that pattern is familiar, you already understand this topic and today is just new syntax.
The one rule that surprises people You never write new EmployeeService(). Angular creates it and hands it to you. If you find yourself typing new in front of a service, stop — you are about to create a second, separate copy, and your two components will silently stop sharing data.

Concept 4 — services · filling it in

Inside the service

src/app/employee.service.ts
import { Injectable } from '@angular/core';
import { Employee } from './models/employee';

@Injectable({
  providedIn: 'root'
})
export class EmployeeService {

  // PRIVATE — the outside world can only reach this through my methods
  private employees: Employee[] = [
    { id: 1001, name: 'anoop kumar',  designation: 'Software Engineer', salary: 25000, status: 'Active', email: 'anoop@example.com' },
    { id: 1002, name: 'ajay sharma',  designation: 'Team Lead',         salary: 45000, status: 'Inactive' },
    { id: 1003, name: 'rekha nair',   designation: 'Tester',            salary: 22000, status: 'Active', email: 'rekha@example.com' },
    { id: 1004, name: 'suresh patel', designation: 'Architect',         salary: 65000, status: 'Inactive' }
  ];

  getEmployees(): Employee[] {
    return this.employees;
  }

  getById(id: number): Employee | undefined {
    return this.employees.find(e => e.id === id);
  }

  searchByName(term: string): Employee[] {
    const t = term.trim().toLowerCase();
    if (t === '') { return this.employees; }
    return this.employees.filter(e => e.name.toLowerCase().includes(t));
  }

  addEmployee(emp: Employee): void {
    this.employees.push(emp);
  }

  deleteEmployee(id: number): void {
    const i = this.employees.findIndex(e => e.id === id);
    if (i !== -1) { this.employees.splice(i, 1); }
  }
}
Two decisions in there worth copying 1. The array is private. Nothing outside can reassign or corrupt it — every access goes through a method you control. That is the same discipline as a private field with getters in Java.
2. Those are the six array methods from Session 1's Drill H — find, filter, push, findIndex, splice. This service is a complete in-memory CRUD layer, and Session 4 will swap its innards for HTTP calls without touching a single component.

Concept 4 — services · step 3

Injecting the service into a component

src/app/employee-list/employee-list.component.ts
import { Component, OnInit } from '@angular/core';
import { Employee } from '../models/employee';
import { EmployeeService } from '../employee.service';

@Component({
  selector: 'app-employee-list',
  templateUrl: './employee-list.component.html',
  styleUrls: ['./employee-list.component.css']
})
export class EmployeeListComponent implements OnInit {

  employees: Employee[] = [];

  // ← the constructor shorthand from Session 1, slide 29
  constructor(private employeeService: EmployeeService) { }

  ngOnInit(): void {
    this.employees = this.employeeService.getEmployees();
  }

  onSearch(term: string): void {
    this.employees = this.employeeService.searchByName(term);
  }
}
LineWhat it does
import { EmployeeService }Tells this file where the class is.
constructor(private employeeService: EmployeeService)Declares a private field and assigns Angular's injected instance to it, in one line. You never write new.
implements OnInitDeclares that this class has an ngOnInit, so TypeScript catches a misspelling.
ngOnInit()Where the data is actually fetched. Not the constructor.
"Why not fetch the data in the constructor?" For a synchronous array it would technically work — and it is still the wrong habit. The constructor runs before Angular has finished setting the component up, and mixing wiring with work makes components harder to test and harder to reason about. The rule from Session 2 stands: constructor for dependencies, ngOnInit for work.

Concept 5 — dependency injection · how it actually works

Who created that service?

You asked for an EmployeeService in a constructor parameter and one appeared. No new anywhere. That is dependency injection, and here is the mechanism — worth understanding rather than treating as magic.

1 · Angular needs to create EmployeeListComponentso it reads the constructor's parameter TYPES
▼
2 · It sees the parameter is an EmployeeServiceand asks the injector for one
▼
3 · The injector: "do I already have one?"Yes → hand back the existing instance. No → create it, cache it, hand it back.
▼
4 · The instance is passed in, and your private field is setyour component never knew how it was built

The injector is a registry that knows how to build every registered service and hands out instances on request.

Why this is worth having, in two points 1. Your component is decoupled. It declares what it needs, never how to build it. If EmployeeService later needs an HttpClient and a logger, the component doesn't change one character.
2. It's testable. In a test, hand the component a fake service that returns two known employees. Because the component never called new, it cannot tell the difference.

With providedIn: 'root' there is exactly one instance of your service for the entire application. Ten components injecting EmployeeService all receive the same object.

Why the singleton behaviour is the point, not a side effect In Session 4, a form component will add a customer and the list component will immediately show it — with no code connecting them. That works only because both are talking to the same service instance. Genuinely shared state, for free.

Two ways to register a service

HowEffect
@Injectable({ providedIn: 'root' })The modern default, and what the CLI generates. One shared instance; unused services are dropped from the build automatically.

How many services should an app have? As many as it has feature areas — there is no "one service per app" rule. A banking app would naturally have a CustomerService, a TransactionService and an AuthService. One service, one responsibility — the same instinct that stops your Spring services becoming a dumping ground.

Concept 6 — setup · third time you'll see this pattern

Setting up HttpClient

Two steps, and if you remember the FormsModule lesson from Session 2 you can predict both.

Step 1 — src/app/app.module.ts
import { HttpClientModule } from '@angular/common/http';   // ← note the package

@NgModule({
  declarations: [ /* ...your components... */ ],
  imports: [
    BrowserModule,
    FormsModule,
    ReactiveFormsModule,
    HttpClientModule            // ← add this
  ],
  providers: [],
  bootstrap: [AppComponent]
})
export class AppModule { }
Step 2 — inject it into your service
import { Injectable } from '@angular/core';
import { HttpClient } from '@angular/common/http';

@Injectable({ providedIn: 'root' })
export class EmployeeService {

  private baseUrl = 'https://jsonplaceholder.typicode.com/users';

  constructor(private http: HttpClient) { }   // ← the shorthand again
}
The error if you forget step 1 — you know its shape by now NullInjectorError: No provider for HttpClient!
That is the same family as "Can't bind to 'ngModel'": a module is missing from imports. Third time today. Also note the package is @angular/common/http, not @angular/core — a genuinely easy import to get wrong.
On newer Angular versions Angular 15+ also offers provideHttpClient() in main.ts for standalone applications. HttpClientModule still works and is what module-based projects — including yours, and most corporate codebases — use.

Concept 6 — reading data

GET — reading from the server

in the service
getEmployees(): Observable<Employee[]> {
  return this.http.get<Employee[]>(this.baseUrl);
}
this.http.get(...)
Sends an HTTP GET to the URL.
<Employee[]>
A generic type argument: "the JSON that comes back is an array of Employee". This is what gives you autocomplete on server data.
Observable<Employee[]>
The return type. Not the data itself — a promise of future data. Next slide explains why this matters enormously.
in the component
employees: Employee[] = [];

constructor(private employeeService: EmployeeService) { }

ngOnInit(): void {
  this.employeeService.getEmployees().subscribe(data => {
    this.employees = data;              // runs LATER, when the reply arrives
  });
}
The mistake absolutely everyone makes once 
// ✖ THIS DOES NOT WORK
this.employees = this.employeeService.getEmployees();
// Type 'Observable<Employee[]>' is not assignable to type 'Employee[]'

A get() does not return data — it returns an Observable, which is a description of data that will arrive later. You must .subscribe() to receive it. If you take one thing from this slide, take that.

Concept 7 — the idea behind subscribe

What is an Observable, and why does Angular use them?

An HTTP request takes time — 50 milliseconds on a good day, several seconds on a bad one. Your app cannot freeze while it waits, so the reply must be handled asynchronously: "carry on, and run this code when the answer turns up."

An Observable is Angular's way of representing "a value that will arrive later, possibly more than once".

Analogy — this one is worth remembering You order a coffee. The barista gives you a numbered ticket, not a coffee.
The ticket is the Observable. It is not the drink — it is a promise that a drink is coming.
subscribe() is you saying "call my number when it's ready, and here's what I'll do when you do."
And crucially: no subscribe, no coffee. An Observable nobody subscribes to never even sends the request.
PromiseObservable
ValuesExactly oneOne, many, or a continuous stream
StartsImmediately, whether you want it or notOnly when subscribed ("lazy")
Cancellable?NoYes — unsubscribe()
OperatorsFewMany — map, filter, debounceTime…
Used forOne-off async workHTTP, form changes, route changes, events
Where else you've already met them today this.empForm.get('name')?.valueChanges.subscribe(...) from the reactive-forms slide is an Observable too — a stream of every keystroke. Observables are everywhere in Angular: HTTP, form changes, route parameters. Learning subscribe once buys you all of them.

Concept 7 continued

subscribe — and always handle the error

subscribe takes an object with up to three handlers. Most tutorials show only the first, and that is why so many apps break silently when the network fails.

this.employeeService.getEmployees().subscribe({

  next: (data) => {
    // ✅ the reply arrived
    this.employees = data;
    console.log('Received ' + data.length + ' employees');
  },

  error: (err) => {
    // ❌ something went wrong — DON'T SKIP THIS
    console.error('Request failed:', err);
    this.errorMessage = 'Could not load employees. Please try again.';
  },

  complete: () => {
    // 🏁 the Observable has finished. For HTTP, right after next.
    console.log('Done');
  }
});
HandlerRuns whenOptional?
nextA value arrives. For HTTP this happens exactly once.You'll always want it
errorThe request fails — network down, 404, 500, CORS blocked.Technically yes. Never omit it.
completeThe stream has ended.Usually omitted for HTTP
What "no error handler" looks like to a user The screen stays permanently blank. No message, no spinner, nothing — the failure was reported only to the browser console, which the user will never open. Handling errors is not a polish task; it is the difference between an app and a demo.
You will also see the older style .subscribe(data => { ... }, err => { ... }) — two positional arguments instead of an object. It still works and it is deprecated. Prefer the object form, but recognise the old one in existing code.

Concept 6 — creating data

POST — sending data to the server

in the service
addEmployee(emp: Employee): Observable<Employee> {
  return this.http.post<Employee>(this.baseUrl, emp);
}

The difference from GET: a second argument — the object to send. Angular converts it to JSON and sets the Content-Type header for you.

in the component
onSave(): void {
  const newEmp: Employee = {
    id: 0,                                   // the server assigns the real id
    name: this.empForm.value.name,
    designation: this.empForm.value.designation,
    salary: this.empForm.value.salary,
    status: 'Active'
  };

  this.employeeService.addEmployee(newEmp).subscribe({
    next: (saved) => {
      this.message = 'Saved with id ' + saved.id;
      this.employees.push(saved);      // use what the SERVER returned
      this.empForm.reset();
    },
    error: (err) => {
      this.message = 'Save failed. Please try again.';
      console.error(err);
    }
  });
}
Push the server's object, not your own — this matters The reply usually differs from what you sent: the real database id, a server-generated timestamp, defaults you left out. Always use the object from next. Pushing your local copy leaves you with an employee whose id is 0, and the delete button will then fail mysteriously.
And remember: nothing is sent until you subscribe Calling addEmployee(emp) without .subscribe() sends no request at all. No error, no warning, no network traffic — Observables are lazy. When "my POST isn't firing", this is almost always why.

Concept 6 — updating and deleting

PUT and DELETE

in the service
// PUT — replace an existing record. The id goes in the URL.
updateEmployee(emp: Employee): Observable<Employee> {
  return this.http.put<Employee>(this.baseUrl + '/' + emp.id, emp);
}

// DELETE — no body, just the URL
deleteEmployee(id: number): Observable<void> {
  return this.http.delete<void>(this.baseUrl + '/' + id);
}

// GET one — same idea
getById(id: number): Observable<Employee> {
  return this.http.get<Employee>(this.baseUrl + '/' + id);
}
in the component — note what happens after a successful delete
onDelete(id: number): void {
  if (!confirm('Delete this employee?')) { return; }

  this.employeeService.deleteEmployee(id).subscribe({
    next: () => {
      // The SERVER has deleted it. Now update the local copy so the
      // screen matches — otherwise the row stays visible until a reload.
      this.employees = this.employees.filter(e => e.id !== id);
      this.message = 'Deleted.';
    },
    error: (err) => {
      this.message = 'Delete failed — the employee is still there.';
      console.error(err);
    }
  });
}
The habit to build: update the screen inside next, never before Removing the row before the server confirms means that when the delete fails, your screen is lying to the user — the row is gone locally but still in the database. Do the local change inside next, so it only happens on genuine success.
PUT vs PATCH, briefly put() replaces the whole record; patch() sends only the changed fields. Angular supports both with identical syntax. Which one to use is decided by your API, not by Angular — check what your Spring Boot controller expects.

Concept 6 — the complete set on one slide

All four verbs, and the Spring Boot side

ActionAngularSpring Boot
Read all http.get<Employee[]>(url) @GetMapping("/employees")
Read one http.get<Employee>(url + '/' + id) @GetMapping("/employees/{id}")
Create http.post<Employee>(url, emp) @PostMapping("/employees")
Update http.put<Employee>(url + '/' + id, emp) @PutMapping("/employees/{id}")
Delete http.delete<void>(url + '/' + id) @DeleteMapping("/employees/{id}")
The whole pattern, in one sentence Every method returns an Observable, so every call needs a .subscribe(). The only differences between the four are the HTTP verb, whether there is a body, and whether the id is in the URL.

Concept 8 — what separates a demo from an application

Loading and error states

A real request is not instant, and sometimes it fails. Your screen needs three states, not one: loading, loaded, and failed. This is a small amount of code that makes an enormous difference to how finished an app feels.

the class — three fields
employees: Employee[] = [];
isLoading = false;
errorMessage = '';

ngOnInit(): void {
  this.loadEmployees();
}

loadEmployees(): void {
  this.isLoading = true;         // 1. before the call
  this.errorMessage = '';

  this.employeeService.getEmployees().subscribe({
    next: (data) => {
      this.employees = data;
      this.isLoading = false;    // 2. on success
    },
    error: (err) => {
      this.errorMessage = 'Could not load employees. Is the server running?';
      this.isLoading = false;    // 3. on failure — easy to forget!
      console.error(err);
    }
  });
}
the template — three mutually exclusive blocks
<p *ngIf="isLoading">⏳ Loading employees…</p>

<div *ngIf="errorMessage" class="error">
  ⚠️ {{ errorMessage }}
  <button (click)="loadEmployees()">Retry</button>
</div>

<table *ngIf="!isLoading && !errorMessage">
  <tr *ngFor="let emp of employees">
    <td>{{ emp.name }}</td>
  </tr>
</table>

<p *ngIf="!isLoading && !errorMessage && employees.length === 0">
  No employees found.
</p>
The bug in every beginner's first version Forgetting isLoading = false in the error handler. The request fails, and the user is left staring at "Loading…" forever. Set it in both branches, every time.
Notice the Retry button Because the whole call lives in a method, offering a retry costs one line: (click)="loadEmployees()". That is why you extract it into loadEmployees() rather than writing it inline in ngOnInit.

Concept 8 continued — a tidier alternative

The async pipe

There is a way to skip subscribe entirely. Hand the Observable itself to the template and let the async pipe do the subscribing.

With subscribe

// class
employees: Employee[] = [];

ngOnInit(): void {
  this.service.getEmployees()
    .subscribe(d => this.employees = d);
}
<!-- template -->
<tr *ngFor="let e of employees">
  <td>{{ e.name }}</td>
</tr>

With the async pipe

// class
employees$!: Observable<Employee[]>;

ngOnInit(): void {
  this.employees$ =
    this.service.getEmployees();
}
<!-- template -->
<tr *ngFor="let e of employees$ | async">
  <td>{{ e.name }}</td>
</tr>
employees$
A naming convention: a trailing $ means "this variable holds an Observable". Not required by Angular, universally used by Angular developers.
| async
The pipe subscribes, hands the value to the template, and unsubscribes automatically when the component is destroyed.
Why professionals prefer it Automatic cleanup. A manual subscribe can leak — the subscription outlives the component unless you tidy up in ngOnDestroy. The async pipe cannot leak, because it manages its own lifecycle. Less code, and one entire class of bug removed.
Which should you use today? Learn subscribe first — it makes the "data arrives later" idea concrete, and you need it whenever you must do something with the reply (show a message, navigate away, reset a form). Reach for async when you are only displaying the data. Both are entirely correct.

Concept 9 — the error that will confuse you the most

CORS — and why it isn't your Angular code

You will point Angular at your own Spring Boot API and see this. Your code is fine. The request never even reached your server.

the browser console
Access to XMLHttpRequest at 'http://localhost:8080/api/employees'
from origin 'http://localhost:4200' has been blocked by CORS policy:
No 'Access-Control-Allow-Origin' header is present on the requested resource.

Your Angular app is served from port 4200. Your API is on port 8080. Different port means a different origin, and browsers block cross-origin requests by default. This is a browser security rule, not an Angular bug — and the server has to grant permission.

Analogy The browser is a security guard at your office. A visitor from another building arrives, and the guard says "I'm not letting you in unless someone inside vouches for you." The server must vouch. Nothing the visitor says will change the guard's mind.

The fix — on the Spring Boot side

// Option 1 — quick, per controller
@CrossOrigin(origins = "http://localhost:4200")
@RestController
@RequestMapping("/api/employees")
public class EmployeeController { }
// Option 2 — application-wide, and the better habit
@Configuration
public class CorsConfig implements WebMvcConfigurer {
  @Override
  public void addCorsMappings(CorsRegistry registry) {
    registry.addMapping("/**")
            .allowedOrigins("http://localhost:4200")
            .allowedMethods("GET", "POST", "PUT", "DELETE");
  }
}
How to recognise it instantly, and what not to do The tell is the word CORS in the message, plus a request that shows as failed in the Network tab with no response body. Do not start rewriting your Angular service — nothing in Angular can fix it. Fix the server, or use the CLI's proxy configuration for local development.

Recap

What you now know

  • Angular has two form systems: template-driven (HTML in charge, FormsModule) and reactive (TypeScript in charge, ReactiveFormsModule).
  • Angular tracks valid, touched and dirty for every field — and "invalid and touched" is the polite condition for showing an error.
  • Reactive forms use FormGroup + FormControl + Validators, or the FormBuilder shorthand, and let you patchValue from code.
  • A service is a plain class holding data and logic, created with ng g s and registered by @Injectable({ providedIn: 'root' }).
  • Dependency injection means you declare what you need in a constructor and Angular supplies it — you never write new for a service.
  • providedIn: 'root' gives one shared instance app-wide, which is how two components see the same data.
  • Refactoring data into a service left the template completely unchanged — that is the whole point of layering.
  • HttpClient (needs HttpClientModule) does get, post, put and delete, and belongs in a service, never a component.
  • Every HTTP method returns an Observable — a ticket, not the coffee. No subscribe, no request.
  • subscribe({ next, error }) — and never skip error, or failures are invisible to your user.
  • Real screens need loading, loaded and failed states; the async pipe subscribes and cleans up for you.
  • CORS errors are a browser security rule fixed on the server — no amount of Angular changes will help.
