Uniqueness, for free

Why Set

A Set is a collection that cannot contain duplicates. Add something twice and the second attempt is silently ignored — and add() returns false to tell you.

✗ Enforcing uniqueness with a List

List<String> ids = new ArrayList<>();

void addId(String id) {
    if (!ids.contains(id)) {   // O(n) scan
        ids.add(id);
    }
}
// 10,000 adds = up to 50 million
// comparisons. And you must
// remember the check EVERY time.
→

✓ A Set does it structurally

Set<String> ids = new HashSet<>();

ids.add(id);       // that's it
// Duplicate? Ignored automatically.
// contains() is O(1), not O(n).
// Impossible to forget the rule,
// because it isn't your job.
Set<String> accountNumbers = new HashSet<>();

System.out.println(accountNumbers.add("AC1001"));   // true  - added
System.out.println(accountNumbers.add("AC1002"));   // true  - added
System.out.println(accountNumbers.add("AC1001"));   // false - already present!
System.out.println(accountNumbers.size());          // 2

// The return value of add() is how you DETECT a duplicate:
if (!accountNumbers.add(newNumber)) {
    throw new DuplicateAccountException("Account " + newNumber + " already exists");
}
Three things a Set gives you 1. Guaranteed uniqueness, enforced by the data structure rather than by your discipline. 2. contains() in O(1) instead of O(n). 3. A meaningful return from add() so you can react to duplicates.

The most important slide in this deck

The equals / hashCode contract

A Set has to answer "have I seen this before?". For String and Integer that's already handled. For your own classes, you must tell it how — and if you get it wrong, nothing warns you.

The contract 1. If a.equals(b) then a.hashCode() == b.hashCode(). (Mandatory.)
2. If a.hashCode() == b.hashCode(), a.equals(b) may be false — that's a collision, and it's perfectly legal.
3. hashCode() must return the same value every time, as long as the object doesn't change. 
public class Account {
    private final String accountNumber;      // the identity

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (o == null || getClass() != o.getClass()) return false;
        return accountNumber.equals(((Account) o).accountNumber);
    }

    @Override
    public int hashCode() {
        return Objects.hash(accountNumber);   // SAME field as equals()
    }
}
What you wroteWhat happens in a HashSet
Both, on the same fieldsWorks correctly
equals onlyDuplicates get stored. contains() returns false for objects that are in there
hashCode onlyEvery object is treated as distinct — duplicates again
Different fields in eachUnpredictable, and very hard to debug
NeitherReference identity only — two "identical" objects are seen as different

How HashSet actually works

A HashSet is an array of buckets. To store an element it computes hashCode(), reduces that to a bucket index, and puts the element there. Lookup does exactly the same arithmetic — so it goes straight to the right bucket instead of searching.

Now the Session 2 bug makes sense Two equal customers with different hash codes land in different buckets. contains() computes the hash, goes to that one bucket, finds nothing, and returns false — equals() is never even called. That's why a broken hashCode fails silently: the lookup never reaches the comparison step.
Why O(1) Good hash distribution means most buckets hold 0 or 1 elements, so a lookup is: one hash calculation, one array index, at most a couple of equals calls. That's constant time regardless of whether the set holds 10 items or 10 million.

The mutable-key trap If you put an object in a HashSet and then change a field used by hashCode(), the object is now sitting in the wrong bucket. You will never find it again — contains() returns false even though it's right there. Only use immutable fields in hashCode.

Mathematical set operations

Union, intersection & difference

Set<String> javaDevs   = new HashSet<>(Set.of("Priya", "Rahul", "Anita"));
Set<String> pythonDevs = new HashSet<>(Set.of("Anita", "Deepa", "Vikram"));

// UNION - everyone
Set<String> all = new HashSet<>(javaDevs);
all.addAll(pythonDevs);              // [Priya, Rahul, Anita, Deepa, Vikram]

// INTERSECTION - knows both
Set<String> both = new HashSet<>(javaDevs);
both.retainAll(pythonDevs);          // [Anita]

// DIFFERENCE - Java only
Set<String> javaOnly = new HashSet<>(javaDevs);
javaOnly.removeAll(pythonDevs);      // [Priya, Rahul]

// SYMMETRIC DIFFERENCE - one but not both
Set<String> exclusive = new HashSet<>(all);
exclusive.removeAll(both);           // [Priya, Rahul, Deepa, Vikram]

// SUBSET test
javaDevs.containsAll(Set.of("Priya", "Rahul"));    // true
All three mutate the set you call them on addAll, retainAll and removeAll change the receiver in place. That's why every example above starts with new HashSet<>(original) — copy first, then operate, or you'll destroy your source data.
Practical uses Deduplicating a list in one line: new ArrayList<>(new LinkedHashSet<>(list)) — removes duplicates and keeps the original order. Also: finding which permissions a user is missing, which tags two articles share, which records exist in one file but not another.

The most useful data structure in programming

Why Map

A Map stores key → value pairs. Give it a key, get the value back — instantly, without searching.

✗ Finding an account in a List

Account find(String number) {
    for (Account a : accounts) {
        if (a.getAccountNumber()
             .equals(number)) {
            return a;
        }
    }
    return null;
}
// O(n). 100,000 accounts =
// up to 100,000 comparisons,
// every single lookup.
→

✓ With a Map

Map<String, Account> byNumber
    = new HashMap<>();

byNumber.put(a.getAccountNumber(), a);

Account found = byNumber.get("AC1001");
// O(1). Same speed with 100
// accounts or 100 million.
Map is NOT a Collection Look back at Session 3's hierarchy diagram: Map sits on its own branch. It does not extend Collection, so it has no add() and you cannot for-each over it directly. It holds pairs, not elements — a fundamentally different shape. You get collection views of it: keySet(), values(), entrySet().

HashMap internals

Same bucket mechanism as HashSet — in fact HashSet is literally a HashMap where every value is a dummy object. Here each bucket holds Entry objects containing both key and value.

bucket 0null
bucket 1"AC1001" → Account@a1
bucket 2"AC1004" → Account@b2→"AC1009" → Account@c3
bucket 3"AC1002" → Account@d4
DetailWhat it means
Default capacity16 buckets
Load factor 0.75When 75% full (12 of 16), the table doubles and everything is rehashed
Collision handlingA linked list in the bucket
TreeificationJava 8+: if one bucket exceeds 8 entries it becomes a balanced tree, so worst case is O(log n) instead of O(n)
Key requirementsCorrect equals + hashCode, and ideally immutable
nullOne null key allowed, many null values
Why String is the ideal key It's immutable (so its hash can never go stale), it caches its hash code after the first computation, and it has a well-distributed hashCode. That combination is why the overwhelming majority of real-world maps are keyed by String.
Ask the batch "What if I wrote hashCode() { return 1; }?" — Legal! The contract holds. But every entry lands in bucket 1, so lookups degrade to a linear scan. You've turned an O(1) structure into an O(n) one while remaining technically correct.

Beyond put and get

The Map API worth knowing

Map<String, Account> accounts = new HashMap<>();

// ===== Basics =====
accounts.put("AC1001", savings);          // insert or OVERWRITE
accounts.get("AC1001");                   // the value, or null if absent
accounts.get("NOPE");                     // null - not an exception
accounts.containsKey("AC1001");           // O(1)
accounts.containsValue(savings);          // O(n) - scans every value
accounts.remove("AC1001");                // removes and returns the old value
accounts.size();  accounts.isEmpty();

// ===== The methods that make code much cleaner =====
accounts.getOrDefault("NOPE", emptyAccount);   // a fallback instead of null
accounts.putIfAbsent("AC1001", other);         // only if not already there

// The classic counter, three ways:
Map<String, Integer> counts = new HashMap<>();

//  verbose
Integer c = counts.get(word);
counts.put(word, c == null ? 1 : c + 1);

//  better
counts.put(word, counts.getOrDefault(word, 0) + 1);

//  best
counts.merge(word, 1, Integer::sum);

// Grouping - computeIfAbsent creates the list only when needed
Map<String, List<Account>> byType = new HashMap<>();
byType.computeIfAbsent(account.accountType(), k -> new ArrayList<>())
      .add(account);

accounts.forEach((key, value) -> System.out.println(key + " -> " + value));
Two methods worth memorising today merge(key, 1, Integer::sum) — counting anything, in one line.
computeIfAbsent(key, k -> new ArrayList<>()).add(item) — grouping into a map of lists, in one line. These two patterns cover a large share of everyday Map work.

Three views

Iterating a Map

Map<String, Double> balances = new LinkedHashMap<>();
balances.put("AC1001", 52000.0);
balances.put("AC1002", 80000.0);

// 1. keySet() - keys only
for (String key : balances.keySet()) {
    System.out.println(key);
}

// 2. values() - values only
for (Double value : balances.values()) {
    System.out.println(value);
}

// 3. entrySet() - BOTH. The efficient choice when you need both.
for (Map.Entry<String, Double> entry : balances.entrySet()) {
    System.out.println(entry.getKey() + " = " + entry.getValue());
}

// 4. forEach + lambda - cleanest for a simple action
balances.forEach((key, value) -> System.out.println(key + " = " + value));
Don't do this for (String k : map.keySet()) { map.get(k); } — that's two lookups per iteration (one to walk, one to fetch). Use entrySet() and you get both halves in one pass. It's the single most common inefficiency in beginner Map code.
These are live views, not copies keySet(), values() and entrySet() are views backed by the map. map.keySet().remove(k) genuinely removes the entry from the map. And modifying the map while iterating a view throws ConcurrentModificationException — exactly as with List in Session 3. Use entrySet().removeIf(...) instead.

Session 1 becomes mandatory here Every file operation throws IOException — a checked exception. The compiler will not let you ignore it. And files must be closed, or you leak OS handles and your writes may never reach the disk. This is precisely what try-with-resources exists for.

The rule Text → Reader/Writer. Binary → InputStream/OutputStream. Using a byte stream for text will corrupt any non-ASCII character (Hindi, accented letters, emoji, the ₹ symbol), because a single character may be several bytes.
Always specify the encoding new FileWriter("f.txt") uses the platform default encoding, which differs between your laptop and the server. Write new FileWriter("f.txt", StandardCharsets.UTF_8) — this class of bug is miserable to diagnose.

The core operations

Writing and reading text

import java.io.*;
import java.nio.charset.StandardCharsets;

// ===== WRITE (overwrites the file) =====
try (BufferedWriter writer = new BufferedWriter(
        new FileWriter("accounts.txt", StandardCharsets.UTF_8))) {
    writer.write("AC1001,Priya Sharma,52000.00");
    writer.newLine();                        // platform-correct line ending
    writer.write("AC1002,Rahul Verma,80000.00");
    writer.newLine();
}                                            // closed automatically - and FLUSHED

// ===== APPEND (note the 'true') =====
try (BufferedWriter writer = new BufferedWriter(
        new FileWriter("accounts.txt", StandardCharsets.UTF_8, true))) {
    writer.write("AC1003,Anita Desai,214000.00");
    writer.newLine();
}

// ===== READ line by line =====
try (BufferedReader reader = new BufferedReader(
        new FileReader("accounts.txt", StandardCharsets.UTF_8))) {
    String line;
    while ((line = reader.readLine()) != null) {     // null means end of file
        String[] parts = line.split(",");
        System.out.println(parts[1] + " has " + parts[2]);
    }
} catch (FileNotFoundException e) {
    System.out.println("File not found - starting with an empty list");
} catch (IOException e) {
    System.out.println("Could not read the file: " + e.getMessage());
}
Three things to notice 1. readLine() returns null at end of file — that's the loop condition.
2. FileWriter's third argument true means append; without it you silently destroy the existing file.
3. FileNotFoundException is caught before IOException — subclass first, exactly the ordering rule from Session 1.

Why the extra wrapper

Why buffering matters

A plain FileWriter asks the operating system to write every single character — thousands of system calls, each one slow. A buffer collects characters in memory and writes them in large blocks.

✗ Unbuffered — one call per char

FileWriter w =
    new FileWriter("out.txt");
for (int i = 0; i < 100_000; i++) {
    w.write("line " + i + "\n");
}
// ~100,000 trips to the OS.
// Measurably, painfully slow.
→

✓ Buffered — batched

BufferedWriter w =
    new BufferedWriter(
        new FileWriter("out.txt"));
for (int i = 0; i < 100_000; i++) {
    w.write("line " + i);
    w.newLine();
}
// ~12 trips to the OS.
// Often 10-50x faster.

The bug this causes: "my file is empty!" If you forget to close() a BufferedWriter, whatever is still sitting in the buffer is never written. Your program runs without error and the file is empty or truncated. try-with-resources closes it — and closing flushes. This is the most common file-handling bug beginners hit, and Session 1's syntax prevents it entirely.

The modern API

NIO.2 — Path & Files

Java 7 added java.nio.file, which does in one line what java.io needs eight for. Prefer it for new code.

import java.util.List;

Path path = Path.of("data", "accounts.csv");     // OS-independent separators

The most useful file skill you'll learn

CSV round-trip: objects → file → objects

// ===== SAVE: objects -> CSV =====
public void save(Map<String, Account> accounts, Path file) throws IOException {
    List<String> lines = new ArrayList<>();
    lines.add("type,number,holder,balance");                 // header row
    for (Account a : accounts.values()) {
        lines.add(String.join(",",
            a.accountType(),
            a.getAccountNumber(),
            a.getHolder(),
            String.valueOf(a.getBalance())));
    }
    Files.createDirectories(file.getParent());
    Files.write(file, lines, StandardCharsets.UTF_8);
}

// ===== LOAD: CSV -> objects =====
public Map<String, Account> load(Path file) throws IOException {
    Map<String, Account> accounts = new LinkedHashMap<>();

    if (!Files.exists(file)) {
        return accounts;                    // first run - empty, not an error
    }

    List<String> lines = Files.readAllLines(file, StandardCharsets.UTF_8);

    for (int i = 1; i < lines.size(); i++) {        // skip the header
        String line = lines.get(i);
        if (line.isBlank()) continue;

        String[] p = line.split(",", -1);           // -1 keeps trailing empties
        if (p.length != 4) {
            System.err.println("Skipping malformed line " + (i + 1) + ": " + line);
            continue;                               // one bad row must not kill the load
        }
        try {
            Account a = switch (p[0]) {             // recreate the right SUBCLASS
                case "Savings"       -> new SavingsAccount(p[1], p[2], Double.parseDouble(p[3]));
                case "Current"       -> new CurrentAccount(p[1], p[2], Double.parseDouble(p[3]), 25000);
                case "Fixed Deposit" -> new FixedDepositAccount(p[1], p[2], Double.parseDouble(p[3]), 12);
                case "Salary"        -> new SalaryAccount(p[1], p[2], Double.parseDouble(p[3]));
                default -> throw new IllegalArgumentException("Unknown type: " + p[0]);
            };
            accounts.put(a.getAccountNumber(), a);
        } catch (NumberFormatException | IllegalArgumentException e) {
            System.err.println("Skipping bad line " + (i + 1) + ": " + e.getMessage());
        }
    }
    return accounts;
}
All four sessions in one method Exceptions (Session 1) handle the file and the bad rows · polymorphism (Session 2) recreates the right subclass · collections (Session 3) hold the parsed objects · Map + File I/O (today) give O(1) lookup and persistence. That's the whole course in 40 lines.
Real CSV is harder than split(",") What if a holder's name contains a comma? Proper CSV quotes such fields — "Sharma, Priya" — and split(",") breaks on it. For real projects use a library like OpenCSV or Apache Commons CSV. For this lab, we just avoid commas in the data.

Best practices

Set & Map

  • Always override equals AND hashCode before using a class as a Set element or Map key
  • Use immutable keys. Never mutate a field involved in hashCode after insertion
  • entrySet() when you need both key and value — not keySet() plus get()
  • getOrDefault, merge, computeIfAbsent instead of manual null checks
  • Declare the interface: Map<K,V> m = new HashMap<>()

File I/O

  • Always try-with-resources. Never hand-roll close()
  • Always specify the charset — StandardCharsets.UTF_8
  • Prefer java.nio.file (Path, Files) over java.io.File
  • Handle a missing file as a normal case — first run isn't an error
  • Don't let one malformed row kill the whole load — log it and continue
  • Use Files.lines() for very large files, not readAllLines
  • Write to a temp file then rename for critical saves, so a crash mid-write can't corrupt the original
