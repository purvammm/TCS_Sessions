The problem inheritance solves

Copy-paste is not a design

Suppose we need three kinds of employee. Without inheritance, here's what happens:

✗ Three classes, one shared mess

class Developer {
    String name; int id;
    double salary;
    void printDetails() { ... }
    double annualPay() { ... }
    // + writeCode()
}
class Manager {
    String name; int id;      // same
    double salary;            // same
    void printDetails() { ... }  // same
    double annualPay() { ... }   // same
    // + approveLeave()
}
class Intern {
    String name; int id;      // AGAIN
    ...
}

✓ Say it once

class Employee {
    String name; int id;
    double salary;
    void printDetails() { ... }
    double annualPay() { ... }
}

class Developer extends Employee {
    void writeCode() { ... }
}
class Manager extends Employee {
    void approveLeave() { ... }
}
class Intern extends Employee { }
The real cost of duplication It isn't the typing. It's that when the pay calculation changes, you must remember to change it in three places — and one day you'll change two. That bug is subtle, silent, and expensive.

The mechanism

IS-A: extends

extends creates an IS-A relationship. A Developer is a Employee. Everything an Employee can do, a Developer can do — plus more.

class Employee {                 // SUPERCLASS  (parent / base)
    protected String name;
    protected double salary;

    public void printDetails() {
        System.out.println(name + " earns " + salary);
    }
}

class Developer extends Employee {    // SUBCLASS  (child / derived)
    private String language;

    public void writeCode() {
        System.out.println(name + " writes " + language);   // inherited 'name'
    }
}

The IS-A test — apply it before you type extends Say it out loud: "A Developer is an Employee." True → inheritance is appropriate.
Now try: "A Car is an Engine." False! A car HAS an engine. That's composition, which we cover in Session 3. Getting this test wrong is the most common OOP design error.

Precision matters here

What gets inherited — and what doesn't

MemberInherited?
public fields & methodsYes — fully accessible
protected fields & methodsYes — accessible in subclasses
Package-private (no modifier)Only if the subclass is in the same package
private fields & methodsNo — not accessible. They still exist in the object, but only the superclass's own methods can touch them

class Parent {
    private   int secret = 42;      // exists in every Child object, but invisible to Child
    protected int shared = 7;
    public    int open   = 1;

    public int revealSecret() { return secret; }   // the approved way in
}

class Child extends Parent {
    void test() {
        System.out.println(open);            // OK
        System.out.println(shared);          // OK
        // System.out.println(secret);       // COMPILE ERROR - private
        System.out.println(revealSecret());  // OK - 42, via the public method
    }
}
The subtle point students miss A private field is not absent from the child object — memory is still allocated for it. It's simply not accessible by name. That's encapsulation doing its job: the parent keeps control of its own internals, even from its own children.

You've been inheriting all along

Object — the root of everything

Every class in Java extends java.lang.Object, whether you write it or not. class Employee { } is silently class Employee extends Object { }.

Inherited from ObjectDefault behaviour — and why you usually override it
toString()Returns Employee@1b6d3586 — the class name and a hash. Useless in logs. Always override.
equals(Object)Compares references — true only for the same object. Override for value equality.
hashCode()An identity-based number. Must be overridden together with equals — critical for Session 4's HashMap/HashSet.
getClass()The runtime type. final — can't be overridden.
clone(), finalize()Legacy and problematic. Avoid both in new code.
wait(), notify()Thread coordination — beyond today's scope.
 
Employee e = new Employee("Priya", 90000);

System.out.println(e);              // Employee@1b6d3586   ← default, unhelpful
// after overriding toString():
System.out.println(e);              // Employee{name='Priya', salary=90000.0}
Why this matters today System.out.println(anyObject) calls toString() on it — and which version runs is decided at runtime by the object's actual type. You have been using polymorphism since your very first Java program without realising it.

Reaching upwards

The super keyword — three uses

class Employee {
    protected String name;
    protected double salary;

    public Employee(String name, double salary) {          // parent constructor
        this.name = name;
        this.salary = salary;
    }
    public double annualPay() { return salary * 12; }
}

class Manager extends Employee {
    private double bonus;

    public Manager(String name, double salary, double bonus) {
        super(name, salary);          // 1. call the PARENT CONSTRUCTOR - must be first line
        this.bonus = bonus;
    }

    @Override
    public double annualPay() {
        return super.annualPay() + bonus;   // 2. call the PARENT'S VERSION of a method
    }                                       //    (reuse, then extend - no duplication)

    void show() {
        System.out.println(super.name);     // 3. access a parent FIELD (rarely needed)
    }
}
UseMeaning
super(args)Invoke a parent constructor. Must be the very first statement in the child constructor.
super.method()Call the parent's implementation — essential when overriding to extend rather than replace.
super.fieldReach a parent field that a child field is shadowing.
The pattern to internalise return super.annualPay() + bonus; — reuse the parent's logic, then add your own. If the parent's pay formula ever changes, Manager automatically gets the fix. Copy-pasting the formula instead would break that.

Order of operations

Constructor chaining — parents build first

Creating a subclass object runs a chain of constructors, from the top of the hierarchy downwards. The logic is simple: a child cannot initialise itself before the parent part of the object exists.

class A            { A() { System.out.println("A constructor"); } }
class B extends A  { B() { System.out.println("B constructor"); } }
class C extends B  { C() { System.out.println("C constructor"); } }

new C();
A constructor ← Object's constructor ran before this, invisibly B constructor C constructor ← the one you actually called finishes LAST
You call new C()
↓ implicit super()
B's constructor entered
↓ implicit super()
A's constructor entered
↓ then bodies run, bottom-up
A body → B body → C body
The error you will definitely hit If the parent has no no-argument constructor, Java's implicit super() fails and you get constructor Employee in class Employee cannot be applied to given types. The fix: call super(...) explicitly with the right arguments as the first line of your child constructor.

Controlling the boundary

Access modifiers

What protected really means It's often described as "package + subclasses", and that's accurate — but there's a catch that trips people up. A subclass in a different package can access protected members only through a reference of its own type (or a subtype), not through an arbitrary parent reference. It's narrower than most people assume.
Practical guidance Default to private. Make fields private and expose behaviour through methods. Use protected deliberately, when you are designing for extension — because every protected member becomes part of the contract you owe your subclasses forever.

Shapes of hierarchies

Types of inheritance in Java

1. Single

B extends A. One parent, one child. The common case.

2. Multilevel

C extends B extends A. A chain. FixedDepositAccount → SavingsAccount → Account.

3. Hierarchical

One parent, several children. Developer, Manager, Intern all extend Employee.

4. Multiple ✗

Not allowed for classes. class C extends A, B won't compile. Achieved with interfaces instead.

Why multiple inheritance of classes is banned — the diamond problem

A
greet()
╱        ╲
B extends A
overrides greet()
C extends A
overrides greet()
╲        ╱
D extends B, C
whose greet() does D inherit?!
Ambiguous — so Java simply forbids it for classes
Java's answer Single inheritance of implementation, multiple inheritance of type. One extends, but as many implements as you like. Interfaces carry no state, so there's nothing to conflict — and when two interfaces provide clashing default methods, the compiler forces you to resolve it explicitly.

The heart of polymorphism

Method overriding

Overriding means a subclass provides its own version of a method it inherited. Same signature, different body.

class Account {
    protected double balance = 10000;
    public double interestRate() { return 0.0; }
    public void applyInterest() {
        double interest = balance * interestRate();
        balance += interest;
        System.out.printf("%s: +%.2f%n", getClass().getSimpleName(), interest);
    }
}

class SavingsAccount extends Account {
    @Override
    public double interestRate() { return 0.04; }     // 4%
}

class FixedDepositAccount extends Account {
    @Override
    public double interestRate() { return 0.07; }     // 7%
}

The rules of overriding

RuleDetail
Same method nameExactly — Java is case-sensitive
Same parameter listTypes and order. Change it and you've overloaded, not overridden
Return type: same or covariantA subclass of the original return type is allowed
Access: same or widerprotected → public ✓. public → private ✗
Checked exceptions: same or narrowerCannot add new or broader checked exceptions — ties directly back to Session 1
Cannot overridefinal, static or private methods
Ask the batch — connecting to Session 1 "Why can't an overriding method throw broader checked exceptions?" Because a caller holding an Account reference compiled against Account's throws clause. If the subclass could throw something extra, the caller's catch blocks would be incomplete — and the compiler could no longer guarantee checked exceptions are handled.

Four characters that save hours

Always write @Override

It's optional. Use it anyway, every single time. It asks the compiler to verify you really are overriding something — and it catches the single most frustrating bug in Java OOP.

✗ Silent failure — no annotation

class Account {
    public void applyInterest() { }
}
class Savings extends Account {
    public void applyinterest() { }
    //            ^ lowercase 'i'
}
// Compiles fine!
// You've created a NEW method.
// applyInterest() does nothing.
// Hours of confused debugging.

✓ Caught instantly

class Savings extends Account {
    @Override
    public void applyinterest() { }
}
// error: method does not override
// or implement a method from a
// supertype

// Found in 1 second, at compile
// time, with the exact line.
Rule If you intend to override, write @Override. It costs nothing at runtime — it's purely a compile-time assertion — and it turns a class of silent, expensive bugs into instant compiler errors. It also documents your intent for the next reader.
It works for interfaces too Since Java 6, @Override is valid on methods implementing an interface method as well, not just overriding a class method. Use it there too.

The payoff

Polymorphism — one reference, many forms

From Greek: poly = many, morph = form. In practice: a parent-type reference can point to any subclass object, and calling a method runs the subclass's version.

// The reference type is Account. The OBJECT type is different each time.
Account[] accounts = {
    new SavingsAccount(),
    new CurrentAccount(),
    new FixedDepositAccount()
};

for (Account acc : accounts) {
    acc.applyInterest();      // SAME line of code, THREE different behaviours
}
SavingsAccount: +400.00 ← 4% CurrentAccount: +0.00 ← 0% FixedDepositAccount: +700.00 ← 7%

✗ Without polymorphism

for (Account a : accounts) {
  if (a instanceof SavingsAccount)
      rate = 0.04;
  else if (a instanceof CurrentAccount)
      rate = 0.0;
  else if (a instanceof FixedDeposit...)
      rate = 0.07;
  // add a new type?
  // EDIT THIS METHOD. Again.
}
→

✓ With polymorphism

for (Account a : accounts) {
    a.applyInterest();
}
// Add RecurringDepositAccount
// tomorrow? This loop needs
// NO changes at all.
Why this is the most important idea in OOP You can add new types without modifying existing code. That's the Open/Closed Principle — open for extension, closed for modification. A long if-else chain checking types is almost always a missed polymorphism opportunity.

Moving between types

Upcasting, downcasting & instanceof

⬆ Upcasting — always safe

Account a = new SavingsAccount();

Implicit, no cast needed. A Savings is an Account, so it can never fail.

⬇ Downcasting — risky

SavingsAccount s =
    (SavingsAccount) a;

Explicit cast required. Compiles fine, but throws ClassCastException at runtime if the object isn't really that type.

Account acc = new CurrentAccount();

// The compiler allows this. The JVM does not.
SavingsAccount s = (SavingsAccount) acc;
// Exception in thread "main" java.lang.ClassCastException:
//   class CurrentAccount cannot be cast to class SavingsAccount

// ALWAYS guard a downcast:
if (acc instanceof SavingsAccount) {
    SavingsAccount safe = (SavingsAccount) acc;
    safe.addBonusInterest();
}

// Java 16+ — pattern matching for instanceof: test and bind in one step
if (acc instanceof SavingsAccount safe) {      // 'safe' only exists if true
    safe.addBonusInterest();
}
Design smell alert If your code is full of instanceof checks followed by downcasts, that's usually a sign the behaviour belongs in the classes themselves as an overridden method. Reach for polymorphism first; downcast only when you genuinely need a capability that exists on just one subtype.

Incomplete on purpose

Abstract classes

Sometimes a parent should never be instantiated. What is a plain "Account", with no type? abstract says: this class exists to be extended, and children must fill in the blanks.

abstract class Account {                 // cannot do: new Account()

    protected double balance;
    protected String accountNumber;

    public Account(String accountNumber, double balance) {   // abstract classes
        this.accountNumber = accountNumber;                  // CAN have constructors
        this.balance = balance;
    }

    // ABSTRACT: no body. Every concrete subclass MUST implement this.
    public abstract double interestRate();
    public abstract String accountType();

    // CONCRETE: shared logic, written once, inherited by all
    public final void applyInterest() {         // final: subclasses can't break the flow
        double interest = balance * interestRate();
        balance += interest;
        System.out.printf("%-14s %8.2f interest -> balance %10.2f%n",
                          accountType(), interest, balance);
    }

    public double getBalance() { return balance; }
}
error: Account is abstract; cannot be instantiated Account a = new Account("AC1", 5000); ^
The Template Method pattern — you just wrote one applyInterest() defines the algorithm (get rate → add → report) while leaving one step (interestRate()) for subclasses to supply. The skeleton is fixed and reliable; the varying detail is delegated. This is one of the most widely used patterns in real Java frameworks.

Pure contract

Interfaces

An interface says what a type can do, with no opinion about how. It's a promise, and a class can promise many things at once.

public interface Taxable {
    double TAX_RATE = 0.30;              // implicitly public static final

    double taxableIncome();              // implicitly public abstract

    default double taxDue() {            // Java 8+: a DEFAULT method with a body
        return taxableIncome() * TAX_RATE;
    }

    static boolean isExempt(double income) {   // Java 8+: a STATIC helper
        return income < 250000;
    }
}

// Multiple inheritance of TYPE — one extends, many implements
class SavingsAccount extends Account implements Taxable, Comparable<SavingsAccount> {

    @Override public double interestRate()   { return 0.04; }
    @Override public String accountType()    { return "Savings"; }
    @Override public double taxableIncome()  { return balance * interestRate(); }
    @Override public int compareTo(SavingsAccount other) {
        return Double.compare(this.balance, other.balance);
    }
}
Why default methods were added in Java 8 Before them, adding a method to a published interface broke every existing implementation. default methods let interfaces evolve: existing classes inherit the new method for free. This is exactly how forEach was added to Iterable — you'll use it in Session 3.
Ask the batch "So do interfaces bring back the diamond problem?" — If two interfaces give clashing default methods, the compiler refuses to guess and makes you write InterfaceName.super.method() to state which one you mean. The ambiguity is resolved by you, explicitly.

Shutting the door

The final keyword — three meanings

Applied toEffectWhy
final variableCan be assigned once onlyConstants; safety in lambdas
final methodCannot be overriddenProtect logic subclasses must not change

public final class String { ... }        // that's why you can't extend String

class Account {
    private final String accountNumber;   // set in the constructor, never changes

    public final void applyInterest() {   // the ALGORITHM is fixed...
        balance += balance * interestRate();
    }
    public abstract double interestRate();  // ...but the RATE is open
}
A final reference is not an immutable object final List<String> list = new ArrayList<>(); — you cannot point list at a different list, but list.add("x") works perfectly. final freezes the reference, not the contents. Guaranteed exam question, and a real source of bugs.
Immutable class recipe final class + all fields private final + no setters + defensive copies of any mutable field in the constructor and getters. Immutable objects are automatically thread-safe and make excellent HashMap keys — which matters a great deal in Session 4.

Overriding done properly

equals, hashCode & toString

These three are the overrides you'll write most often. Getting equals/hashCode right is essential for Session 4 — a broken pair silently corrupts every HashSet and HashMap you put the object into.

public class Employee {
    private final int id;
    private final String name;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;                       // same object - fast path
        if (o == null || getClass() != o.getClass()) return false;
        Employee other = (Employee) o;
        return id == other.id && Objects.equals(name, other.name);
    }

    @Override
    public int hashCode() {
        return Objects.hash(id, name);        // MUST use the same fields as equals
    }

    @Override
    public String toString() {
        return "Employee{id=" + id + ", name='" + name + "'}";
    }
}
The contract — memorise this If a.equals(b) is true, then a.hashCode() == b.hashCode() must also be true. The reverse need not hold (different objects may share a hash — that's a collision, and it's fine). Break this contract and a HashSet will happily store two "equal" objects, or fail to find one you just added.
Override equals, always override hashCode Never one without the other. Your IDE generates both together for exactly this reason — and both must use the same fields.

A word of caution

Favour composition over inheritance

Inheritance is powerful and over-used. It is the tightest coupling in object-oriented programming: a subclass depends on its parent's internal behaviour, so a change upstream can silently break it. Session 3 covers HAS-A in depth; here's the essential warning.

✗ Inheriting for reuse

class CountingList
        extends ArrayList<String> {
    int added = 0;

    @Override
    public boolean add(String s) {
        added++;
        return super.add(s);
    }
    @Override
    public boolean addAll(
            Collection<? extends String> c) {
        added += c.size();
        return super.addAll(c);
    }
}
// addAll() internally calls add()
// so every item is COUNTED TWICE.
// Adding 3 items reports 6.

✓ Composition — wrap it

class CountingList {
    private final List<String> inner
        = new ArrayList<>();
    private int added = 0;

    public boolean add(String s) {
        added++;
        return inner.add(s);
    }
    public int getAdded() { return added; }
}
// You control the whole surface.
// ArrayList's internals cannot
// surprise you.
The rule of thumb Use inheritance when the child genuinely is a kind of the parent and you want polymorphic substitution. Use composition when you merely want to reuse functionality. If you find yourself inheriting just to avoid retyping code, that's the wrong reason.

The design principle behind it all

Substitutability — don't surprise the caller

Polymorphism only works if a subclass can be used anywhere the parent is expected without breaking the caller's assumptions. This is the Liskov Substitution Principle, and it's less abstract than it sounds.

✗ The classic violation

class Rectangle {
    void setWidth(int w)  { ... }
    void setHeight(int h) { ... }
    int area() { return w * h; }
}
class Square extends Rectangle {
    // a square must stay square,
    // so setWidth ALSO sets height
}

// Caller's reasonable assumption:
r.setWidth(5);
r.setHeight(4);
assert r.area() == 20;   // FAILS
                         // for Square: 16

✓ Honest modelling

interface Shape {
    double area();
}
class Rectangle implements Shape {
    Rectangle(int w, int h) { ... }
    public double area() { ... }
}
class Square implements Shape {
    Square(int side) { ... }
    public double area() { ... }
}
// Both ARE shapes. Neither
// pretends to be the other.
Practical warning signs you're violating it An override that throws where the parent didn't · an override that does nothing ("not supported for this type") · an override that tightens what inputs it accepts · callers needing instanceof to use your class safely. Any of these means the IS-A claim was wrong.

The whole picture

Everything in one example

abstract class Account {                                   // ABSTRACTION
    private final String number;                          // ENCAPSULATION
    protected double balance;

    protected Account(String number, double balance) {    // CONSTRUCTOR CHAINING
        this.number = number;
        this.balance = balance;
    }
    public abstract double interestRate();                // must be implemented
    public abstract String type();

    public final void applyInterest() {                   // TEMPLATE METHOD
        double interest = balance * interestRate();
        balance += interest;
    }
    @Override public String toString() {                  // OVERRIDES Object
        return String.format("%-8s %-10s %10.2f", number, type(), balance);
    }
    public double getBalance() { return balance; }
}

class SavingsAccount extends Account {                    // INHERITANCE
    SavingsAccount(String n, double b) { super(n, b); }
    @Override public double interestRate() { return 0.04; }   // OVERRIDING
    @Override public String type()         { return "Savings"; }
}

class CurrentAccount extends Account {
    CurrentAccount(String n, double b) { super(n, b); }
    @Override public double interestRate() { return 0.0; }
    @Override public String type()         { return "Current"; }
}

class FixedDepositAccount extends Account implements Taxable {   // + CAPABILITY
    FixedDepositAccount(String n, double b) { super(n, b); }
    @Override public double interestRate()  { return 0.07; }
    @Override public String type()          { return "FD"; }
    @Override public double taxableIncome() { return getBalance() * interestRate(); }
}

// --- and the payoff: ONE loop, no type checks anywhere ---
Account[] portfolio = {
    new SavingsAccount("AC1001", 50000),
    new CurrentAccount("AC1002", 80000),
    new FixedDepositAccount("AC1003", 200000)
};
for (Account a : portfolio) {         // POLYMORPHISM
    a.applyInterest();
    System.out.println(a);
    if (a instanceof Taxable t) {     // pattern matching, only where needed
        System.out.printf("   tax due: %.2f%n", t.taxDue());
    }
}

Every @Service behind an interface, every JpaRepository — the whole framework is dynamic dispatch and programming to interfaces.

One idea, everywhere List<String> names = new ArrayList<>(); — after today you can explain every part of that line: List is the reference type (an interface, so you're programming to the contract), ArrayList is the object type, and every method call on names is dispatched dynamically to ArrayList's implementation.

Best practices

  • Apply the IS-A test out loud before typing extends
  • Always write @Override — it costs nothing and catches typos instantly
  • Program to the interface: List<X> l = new ArrayList<>(), not ArrayList<X> l = …
  • Keep fields private and never shadow a parent field
  • Override equals and hashCode together, using the same fields
  • Always override toString() — your future self debugging at 2am will thank you
  • Prefer super.method() + additions over copy-pasting the parent's logic
  • Replace instanceof chains with an overridden method wherever you can
  • Favour composition when you only want to reuse code, not to be substitutable
  • Keep hierarchies shallow — two or three levels. Deep trees are hard to reason about
