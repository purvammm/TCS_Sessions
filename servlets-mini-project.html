The project
Library Management System A small web application a librarian would actually use. A librarian logs in, manages the book catalogue, registers members, and issues and returns books — with the system refusing anything that doesn't make sense, like issuing a book that has no copies left.

Why this project and not another product CRUD? Because issuing a book is not a CRUD operation. It reads one table, checks several rules, then writes to two tables. That forces genuine business logic into your service layer — which is the thing plain CRUD never teaches you.

🔐 Librarian login

A login screen. Every other page must be unreachable without it — this is the session work Part 2 deliberately left undone.

📗 Book catalogue

Add, view, update and remove books. Each book tracks how many copies exist and how many are currently available.

👤 Member registry

Register members and list them. A member can hold only a limited number of books at once.

🔄 Issue & return

The heart of the project. Issue a book to a member, and take it back later. Several rules must hold before either is allowed.

🔎 Search

Find books by title or author using a partial match, not an exact one.

📋 Currently-issued report

A screen showing every book currently out, who has it, and when it was taken.

The one-sentence summary A five-layer servlet application, backed by three database tables, with a protected login, full CRUD on books, and an issue/return feature whose rules live in the service layer.

Before you open Eclipse — answer these on paper
  1. How does the system know a book has copies left? Do you store that number, or calculate it every time? What are the trade-offs?
  2. When a book is issued, how many tables change?
  3. When a book is returned, how do you know which issue record to close?

Phase 0 — Plan it before you build it
PHASE 0Thinking30–45 min▶ Design on paper
Goal Decide your data model and your list of actions before writing a line of Java. Every hour spent here saves three later — and rewriting a table halfway through means touching all five layers.

Step 1 — Sketch your three tables

You need three. Two are obvious; the third is the interesting one.

TableWhat one row representsThink about
bookOne title in the catalogueHow do you know how many copies are free right now?
memberOne person who can borrowWhat's the minimum you need to identify and contact them?
issueOne act of borrowing — not a book, not a memberHow do you tell an open loan from a closed one?
💡 Hint — the issue table is where people go wrong A row in issue is an event: "member 4 took book 2 on this date." It needs its own primary key, a reference to the book, a reference to the member, and enough information to answer "has this been returned yet?"

There are two common ways to answer that last question. One adds a flag column; one uses the return date itself. Both work. Pick one, write down why, and stay consistent — because your "currently issued" query depends entirely on this choice.

Step 2 — List every action your app performs

Write them out as a table. This becomes your servlet routing plan, so be exhaustive.

ActionTriggered byGET or POST?What it needs from the user
view all booksa link?nothing
add a booka form?title, author, number of copies…
delete a book??which book
issue a book???
return a book???
…keep going. Aim for 10–12 rows. Fill in every question mark yourself.
💡 Hint — deciding GET vs POST Ask the Part 1 question: am I reading or writing? And: does the user have to type anything? Nothing to type → a link. Something to type → a form. Changing data → POST. You already know this; just apply it consistently and note your reasoning next to each row.

Step 3 — Decide how many servlets

Part 2 used one servlet with an action parameter. This project is bigger. You have a real choice:

ApproachConsider
One servlet for everythingOne mapping — but a very long if-ladder covering books, members and loans.
One servlet per area — books, members, loans, authEach has its own short action ladder. More mappings, much clearer files. This is what most people find easier here.
One servlet per actionMany tiny classes and many mappings. Usually more overhead than it's worth at this size.

There is no single right answer — but there is a requirement: you must be able to justify your choice. Write one sentence explaining it and keep it with your plan.

Before moving on, you should have Three table sketches with column names and types · a list of 10–12 actions with GET/POST decided · a decision on how many servlets, with a reason · answers to the four questions from the Ground rules section.

Design decision — store "available", or calculate it?
  1. Store it as a column. Issuing decrements it; returning increments it. Fast to read — but now two places hold the truth, and they can drift apart if a bug slips in.
  2. Calculate it. Available = total copies minus the number of open loans for that book. Always correct by construction — but every book listing needs a count query.

Either is acceptable. Option 1 is simpler to write and is what the wireframe implies. Option 2 is more robust. Choose, write down why, and be ready to explain the trade-off — that explanation matters more than which one you picked.

💡 Hint — dates, the pragmatic version Proper date handling is a topic of its own. For this project, storing the date as text in YYYY-MM-DD form is a perfectly reasonable simplification: it sorts correctly as a string and it's easy to generate and display.

If you'd rather use a real date type, go ahead — but know that you're taking on JDBC date conversion as well. Don't let it block the rest of the project.
💡 Hint — foreign keys You can declare the book and member columns as foreign keys, and it's good practice: the database will then refuse to record a loan against a book that doesn't exist.

But be aware of the consequence — you will no longer be able to delete a book that has loan history, and you'll have to decide what your delete feature should do about that. That's a genuine design question, and either answer is defensible as long as your app handles it with a message rather than a stack trace.

Seed data — make it useful for testing

Don't seed the minimum. Seed data that lets you test the interesting cases immediately:

Seed thisSo you can test

Save your setup script — you will need it repeatedly Keep every statement in one saved .sql file, including the seed rows. You'll re-run it every time your testing leaves the data in a mess — which will be often, because you're about to build a delete feature.

End it with a SELECT on each table and actually look at the output. Building four layers on top of an empty table is a miserable way to spend an afternoon.

This is the biggest phase. Below is what each method must achieve. The SQL, the signatures and the bodies are yours to write.

Book DAO

💡 Hint — the search method A partial match needs the SQL LIKE comparison, and the wildcard characters belong in the bound value, not in the SQL text. If you find yourself concatenating a keyword into the statement, stop — that's the injectable pattern you were taught to avoid.

To match title or author in one query, you'll need the same keyword bound twice. Remember placeholders are numbered in the order they appear.
💡 Hint — the available-copies method You need to move that number up and down by one. You could pass the new absolute value — but it's cleaner and safer to let the database do the arithmetic on the current value, which avoids reading it and writing it back as two separate steps.

Also consider: should the SQL itself refuse to take the count below zero? Adding that condition to your WHERE clause is a neat safety net — and it means "no copies left" shows up naturally as zero rows affected.

If you chose to calculate availability in Phase 2 instead of storing it, this method doesn't exist — you'll need a counting query instead.

The report query — think before you code
  1. The report needs the book title and member name, but issue stores only ids.
  2. Option A: one SQL query that pulls from all three tables at once. Efficient, one round trip — you'll need to look up how to combine tables in a query if you haven't met it.
  3. Option B: fetch the loans, then look up each book and member separately in Java. Simpler SQL, but many more queries.

Option A is the better engineering answer and worth the learning. Option B is acceptable and honest. Pick one, and know why the other exists.

Every method in this layer follows the same shape You learned it in Part 2 and it does not change: get a connection, guard against failure, use a prepared statement with placeholders, bind values in order, match the execute call to the SQL verb, catch and log the database error, and release the connection in a way that always runs.

Write one method completely and get it working. Then the other fifteen are mechanical. Don't write all sixteen and then start debugging.
💡 Hint — test the DAO before building on it You don't need the web layer to test this. A temporary main method that calls your fetch-all and prints the results will tell you in seconds whether your SQL and your row-to-object mapping are right.

Debugging a DAO through a browser is far harder than debugging it directly.

PHASE 6serviceHard60–90 min▶ The service layer — the heart of the project
Goal All the rules. This is where this project stops being another CRUD exercise — and it's the phase that will teach you the most.
Why this layer matters here more than in Part 2 In Part 2 the service checked a few obvious things — no negative prices, no blank names. Useful, but not exciting.

Here, "issue a book" is a genuine business operation. It has to check several conditions across two tables, and only then perform two separate writes. That logic belongs in exactly one place, and this is it. Put it in the servlet and you'll duplicate it the first time you add another way to issue a book.

Rules for issuing a book

Before a loan may be recorded, all of these must hold. Your job is to check them in a sensible order and report which one failed.

#RuleWhy it matters
1The book id must existOtherwise you'd record a loan against nothing
2The member id must existSame reason
3At least one copy must be availableThe core rule. This is what the wireframe's red message is about
4The member must be under their borrowing limitPick a limit — 3 is sensible. Define it as a named constant, not a number buried in an if
5The member must not already hold this same titleA library lends one copy of a title per person

If every rule passes, two things must happen: record the loan, and reduce the available count by one. Both, or the data no longer makes sense.

Rules for returning a book

#RuleWhy it matters
1The loan must existYou can't close something that isn't there
2It must still be openReturning the same loan twice would inflate the available count above the number of copies you own

If both pass: close the loan and increase the available count by one.

⚠ The trap in both operations — two writes, one operation Issuing writes to two tables. So does returning. If the first write succeeds and the second fails, your data is now wrong: a loan recorded but the count not reduced, or vice versa.

The real fix is a database transaction — both writes commit together, or neither does. You have not been taught transactions yet, so you are not required to implement them.

What you are required to do: notice the problem, and write a comment where it occurs saying what should happen there. Recognising a correctness gap you can't yet fix is a real engineering skill — and it's exactly the kind of thing a reviewer looks for.

The big question: how do you report which rule failed?

In Part 2 every write method returned a plain true/false. That was honest about its own limitation: false says that it failed, never why.

Here that isn't good enough. Look at the wireframe again — the screen says "no copies of Clean Code are available", not "issue failed". Five different rules can block an issue, and the user needs to know which.

ApproachTrade-off
Return a message string — empty or null meaning successVery easy. But now your service layer is deciding user-facing wording, which is really the web layer's job.
Return a small result object carrying a success flag and a reasonClean separation, and easy to extend. A little more code. Often the sweet spot here.
Throw a custom exception per failure reasonThe most "professional" answer, and what Spring does. More classes, and you must catch them properly in the servlet.
Return an enum of outcomesNeat and type-safe; the servlet maps each outcome to a message. Nicely keeps wording in the web layer.
Choose deliberately
  1. All four are acceptable. The plain true/false is the only option that is not, because it cannot express five different reasons.
  2. Ask yourself: which layer should decide the exact wording the user sees? Your answer should push you towards one of the last three.
  3. Write down your choice and one sentence of reasoning. Being able to justify a design decision is the actual skill being practised here.

Don't forget the ordinary validation too

Alongside the interesting rules, this layer still does the unglamorous work: ids must be positive, titles and names must not be blank, copy counts must not be negative, and an email must look like an email. You wrote all of this in Part 2 — the same patterns apply.

Deliverable Service classes containing every rule above, no SQL, no HTML — plus a written note of how you chose to report failure reasons and why, and a comment marking the two-writes problem.
Phases 7–10 — The web layer & features
PHASE 7webMedium40 min▶ Login & session protection — the one new technique
Goal A librarian logs in once and can then use the app. Anyone who hasn't logged in is sent back to the login screen, no matter which URL they type.
This is the gap Part 2 deliberately left open Remember the experiment at the end of Part 2: open a private browser window, skip the login, paste the CRUD URL — and it worked. Because HTTP is stateless and the servlet never asked who you were.

Closing that gap is this phase. It is the only genuinely new technique in the whole project, so expect to look it up — that's intended, not a failure.

What you need to build

PieceWhat it must do
Login pageA form asking for staff id and password. Think about which HTTP method a login form should use, and why.
Login servletCheck the credentials. On success, record in the session that this person is authenticated. On failure, show a message and let them retry.
A protection checkAt the top of every protected servlet: is there a session, and does it say this person logged in? If not, send them to the login page and stop processing.
LogoutDiscard the session and return to the login page. Then confirm the protected pages really are locked again.
Menu pageA simple hub linking to books, members, issue, return and the report. Only reachable when logged in.
💡 Hint — the two things to look up
  • Storing something in a session: the request object can give you a session, and a session can hold named values. That's all you need — put a marker in on successful login, read it back later.
  • Checking without creating: there's a version of "get me the session" that creates one if none exists, and a version that doesn't. For a login check you want the second — otherwise you'd always get a session and your check would never fail. Session 2 notes, chapter 21, shows the shape of this in outline.
⚠ The mistake almost everyone makes here After redirecting an unauthenticated visitor, you must stop the method. If you redirect and then carry on building the page, you'll get an error about the response already being committed — and the protection won't actually protect anything.

Redirect, then return immediately.
Worth thinking about
  1. You'll repeat the same protection check at the top of four or five servlets. That's duplication. How could you write it once? There are at least three answers: a shared helper method, a common parent class, or a servlet filter. A filter is the proper tool — look it up if you're curious, but don't let it block you.
  2. Where do the librarian's credentials come from? Hardcoded is fine for this project. What would production do instead? Two things change — where they're stored, and what form the password is stored in.
Deliverable Login, logout, a menu page, and protection on every other page — verified by pasting a protected URL into a fresh private window and being bounced to the login screen.

  • ❌ "Issue failed." — the user has no idea what to do next.
  • ✅ "Cannot issue — no copies of 'Clean Code' are available." — actionable.

💡 Hint — where each of these gets caught
  • Text that should be a number → the web layer, when converting.
  • Blank or nonsensical values → the service layer, as validation.
  • Missing rows / rule violations → the service layer, using what the DAO reports back.
  • Database unreachable → caught in the DAO, logged there, surfaced upward as a failure.
If you're catching number-conversion problems in your DAO, or database problems in your servlet, something is in the wrong layer.
Also worth tidying while you're here Consistent page titles and headings · a "back to menu" link on every page so nobody gets stranded · your success messages in one colour and failures in another · and remove any debugging output that would confuse someone reading the console. Keeping a few deliberate trace lines is fine and sensible — just make them intentional.

When you get stuck
▶ 🧭 Common pitfalls — symptom first

You've met most of these before. This is a lookup table, ordered by what you see — because that's how problems arrive.

SymptomWhere to look
404 on a page you just addedThe URL, then your mapping, then — did you restart the server after changing the descriptor?
500 error pageThe console. First line of the trace, not the last. It names the exception and your line number.
Tags showing as literal textContent type — missing, or set after you took the writer.
Blank pageYou printed to the console instead of the response.
405Your form's method doesn't match the methods your servlet implements.
"No suitable driver"The driver JAR isn't in the folder your running app loads from.
Table is empty but your explorer shows rowsTwo different databases — a relative path. Make it absolute and identical everywhere.
"Already booted" / locked databaseYour database browser is still connected. Disconnect it.
Null pointer in a DAO methodYou used a connection without checking it was actually opened.
A parameter is always nullThe name in your HTML doesn't match the string you're reading. It's case-sensitive.
Update or delete silently does nothingCheck what your statement reports as rows affected — zero means it matched nothing. Also check your placeholder order.
Availability count drifts from realityOne of your two writes is failing, or running twice. Phase 6, and the consistency check in Phase 12.
Protection redirects but then errorsYou redirected and kept going. Return immediately after.
Login "works" but every page bounces you backYou're storing one thing in the session and checking for a different one. Or you're creating a fresh session in your check instead of reading the existing one.
💡 The debugging habit that beats all of these When something doesn't behave, print what actually arrived — the parameter values at the top of the servlet, and the values being bound in the DAO.

Most of the time the bug isn't in your logic at all; it's that the data reaching your logic isn't what you assumed. Assume nothing, print everything, narrow it down.
And when you're properly stuck for more than 20 minutes Go back to the lab sheet or notes for the technique — how a DAO method is shaped, how a session is read — then return and apply it to your own problem.

Resist copying a whole file across. It usually creates two new problems (names that don't fit, layers that don't match your design) and skips the learning this project exists for.
What finishing this actually proves Not that you can write servlets — the labs already showed you that. It proves you can take a described problem, design a data model for it, place logic in the right layer, and build something that stands up to a user trying to break it.

It also means you've built, by hand, the exact architecture Spring Boot generates: a controller reading requests, a service holding the rules, a repository owning the SQL, entities carrying the data, and configuration holding the connection. When you meet those annotations, you'll recognise your own design in them.
💡 One last piece of advice Keep a short notes file as you go: your table design, the two design decisions you were asked to justify, anything that doesn't work, and anything you'd do differently.

An honest list of known issues is worth more than a silent bug — and when you come back to this in six months, that file is what will make sense of it.
