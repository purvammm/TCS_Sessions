Motivation

The problem with Session 2

Our Student API worked beautifully. Then someone restarted it, and every student ever created was gone. Here's why:

@Service
public class StudentService {
    // This list lives in RAM — inside the running process.
    private final List<Student> students = new ArrayList<>();
}

RAM is volatile: when the process ends, the operating system reclaims that memory and the contents are simply gone. There is nothing to recover.

Three separate problems, not one
  1. No persistence. Restart, deploy, or crash → all data lost.
  2. No sharing. Run two copies of the app (as Session 4 does) and each has its own list. Create a student on copy A and copy B doesn't know about it.
  3. No capacity. A million students would exhaust your memory. A database keeps data on disk and loads only what's asked for.
The fix Move the data out of the application and into a database — a separate program built for storing data permanently, safely, and shared between many callers. Today we make that happen with remarkably little code.

Groundwork · 2 of 4

Why we don't write JDBC by hand

JDBC is Java's built-in, low-level way to talk to a database. It works — and it is exhausting. Here is what fetching one post costs you:

public Post findById(int id) {
    String sql = "SELECT * FROM posts WHERE id = ?";

    try (Connection conn = dataSource.getConnection();                // 1. open a connection
         PreparedStatement ps = conn.prepareStatement(sql)) {         // 2. prepare the SQL

        ps.setInt(1, id);                                            // 3. bind the parameter
        try (ResultSet rs = ps.executeQuery()) {                      // 4. execute
            if (rs.next()) {
                Post post = new Post();                               // 5. build the object
                post.setId(rs.getInt("id"));                          //    field...
                post.setTitle(rs.getString("title"));                 //    by field...
                post.setContent(rs.getString("content"));             //    by hand
                post.setAuthor(rs.getString("author"));
                return post;
            }
            return null;
        }
    } catch (SQLException e) {                                        // 6. handle checked exceptions
        throw new RuntimeException(e);
    }
}
Twenty lines for one read — and that's the easy case Now write the other three operations. Then add a fifth column and update every method. Then notice the SQL is a plain String, so a typo compiles fine and fails at runtime. Multiply by twenty tables. This is genuine, repetitive, error-prone work — and it's why ORM was invented.

Groundwork · 3 of 4

What is ORM?

ORM stands for Object-Relational Mapping. The name describes the gap it bridges: Java thinks in objects, databases think in relations (tables). ORM automates the translation.

Java world objects, fields, references
⇄
ORM translates both ways
⇄
Database world tables, columns, keys

You declare the mapping once, and the ORM generates the SQL and fills in your objects for you:

Without ORM (JDBC)

  • Write every SQL statement by hand
  • Copy each column into each field, manually
  • Manage connections and resources yourself
  • Handle SQLException everywhere
  • SQL is a String → typos fail at runtime
  • ~20 lines per operation
→

With ORM (JPA/Hibernate)

  • Annotate the class once with @Entity
  • Mapping is automatic, by field name
  • Connections managed for you
  • Runtime exceptions, no boilerplate catches
  • Methods are type-checked by the compiler
  • repository.findById(1) — one line
Analogy ORM is a translator in a meeting between two people who don't share a language. You speak Java; the database speaks SQL. You could learn to say every sentence yourself — or you could state your intent once and let the translator handle the grammar, every time, without mistakes.

Three names that get used interchangeably and confuse every beginner. They are three different layers stacked on each other — and once you see the stack, the confusion disappears.

Spring Data JPA Spring's convenience layer — gives you repositories with zero implementation
▼ uses
Hibernate The implementation — actually generates and runs the SQL
▼ implements
JPA The specification — just interfaces and annotations, no working code
▼ talks to
The database H2, MySQL, PostgreSQL, Oracle…
NameWhat it actually isAnalogy
JPAA specification — a standard set of interfaces and annotations (@Entity, @Id). Contains no working code.The rules of the road
HibernateAn implementation of JPA. Real code that generates SQL and runs it. The default in Spring Boot.The car that obeys them

Our database today

H2 — a database with zero setup

Installing MySQL or PostgreSQL in a two-hour session would eat the whole session. So we use H2: a complete SQL database written in Java that runs inside your application, storing everything in memory.

✅ Nothing to install

It's just a JAR. Add the dependency and it exists.

✅ Real SQL

Genuine tables, real SQL, actual constraints. Not a fake.

✅ Web console built in

Browse your tables and run queries at /h2-console.

⚠️ In-memory by default

Data is still lost on restart — but it's a genuine database while running, and switching to MySQL is a config change, not a code change.

"So we haven't fixed persistence?" Fair challenge. With in-memory H2, data still resets on restart — but for a completely different and much better reason. Everything you write today (entities, repositories, SQL, transactions) is exactly what you'd write against MySQL in production. Moving there means changing four lines in application.properties and zero lines of Java. H2 also supports file-based storage (jdbc:h2:file:./data/demo) if you want the data to survive — try it as a stretch goal.

Entities · 1 of 3

@Entity — a class becomes a table

An entity is a Java class that represents a database table. Each object of that class is one row. You mark it with annotations and Hibernate builds the table for you.

package com.tcs.training.posts.entity;

import jakarta.persistence.*;

@Entity                              // "this class maps to a table"
@Table(name = "posts")               // optional: name the table explicitly
public class Post {

    @Id                              // this field is the PRIMARY KEY
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;                 // the DB assigns the value

    @Column(nullable = false, length = 200)
    private String title;            // NOT NULL, VARCHAR(200)

    @Column(columnDefinition = "TEXT")
    private String content;

    private String author;           // no annotation needed — sensible defaults apply

    // A no-arg constructor is REQUIRED by JPA. Plus getters and setters.
    public Post() { }
}
⚠️ jakarta, not javax In Spring Boot 3.x the imports are jakarta.persistence.*. Older tutorials say javax.persistence.*, which was correct for Boot 2.x and will not compile today. If your IDE offers both, always pick jakarta. This is the single most common copy-paste error when following older material.

The four @GeneratedValue strategies, since the choice matters:

StrategyHow the id is producedUse when
IDENTITYAn auto-increment column in the databaseMySQL, H2, SQL Server — our choice today
SEQUENCEA database sequence objectPostgreSQL, Oracle — best performance for batches
AUTOLet the provider decideConvenient, but less predictable
TABLEA separate table holding countersPortable, but slow. Avoid.
Why Long rather than long for the id? Because a new Post that hasn't been saved yet has no id, and only the object type Long can hold null to represent that. A primitive long would default to 0, which JPA can't distinguish from a real id of zero. Always use the wrapper type for entity ids.

Entities · 3 of 3

Who creates the table? ddl-auto

You never wrote a CREATE TABLE statement — yet the table exists. That's Hibernate reading your entity classes at startup and building the schema. The spring.jpa.hibernate.ddl-auto setting controls how aggressively:

ValueWhat it does at startupUse in
noneNothing. You manage the schema yourself.Production
validateChecks the schema matches your entities; fails fast if not.Production
updateAdds missing tables and columns. Never deletes anything.Development — our choice today
createDrops and recreates all tables on every start.Testing
create-dropSame, plus drops everything on shutdown.Automated tests
⚠️ Never use create or update in production create would delete your entire production database on every deployment. This has genuinely happened to people. Even update is risky: it makes silent schema changes nobody reviewed. Real teams use validate plus a migration tool (Flyway or Liquibase) where every schema change is a reviewed, version-controlled file.
Watch it work Set spring.jpa.show-sql=true and Hibernate prints every statement it runs — including the CREATE TABLE it generates from your entity. Watching that appear in the console is the fastest way to believe that ORM is not magic.

Repositories · 1 of 3

Repositories — the best trick in Spring

Remember those twenty lines of JDBC for a single read? Here is the entire data-access layer for our Post entity — full CRUD, and it is an interface with no methods in it:

package com.tcs.training.posts.repository;

import com.tcs.training.posts.entity.Post;
import org.springframework.data.jpa.repository.JpaRepository;

//                                      <entity type, primary key type>
public interface PostRepository extends JpaRepository<Post, Long> {
}

That's the whole file. You write no implementation. At startup Spring Data notices the interface, generates a class implementing it, and registers that as a bean you can inject.

1

You declare

An interface extending JpaRepository<Post, Long>.

2

Spring generates

A full implementation at runtime, using Hibernate underneath.

3

You inject & use

postRepository.findAll() — and it just works.

You don't even need @Repository Spring Data detects any interface extending JpaRepository automatically. Adding @Repository is harmless and some teams do it for clarity, but it is genuinely optional here.

save() does double duty — and that's deliberate One method for both create and update. If post.getId() is null, Hibernate issues an INSERT; if it holds a value, an UPDATE. This is why our update logic will be "load the existing row, change its fields, save it" — the same save() call handles it.

Repositories · 3 of 3

Custom queries from method names alone

This is where Spring Data becomes genuinely surprising. Declare a method whose name describes the query, and Spring Data parses the name and writes the SQL:

public interface PostRepository extends JpaRepository<Post, Long> {

    // SELECT * FROM posts WHERE author = ?
    List<Post> findByAuthor(String author);

    // SELECT * FROM posts WHERE title LIKE %?%
    List<Post> findByTitleContaining(String keyword);

    // SELECT * FROM posts WHERE author = ? ORDER BY title ASC
    List<Post> findByAuthorOrderByTitleAsc(String author);

    // SELECT COUNT(*) FROM posts WHERE author = ?
    long countByAuthor(String author);

    // SELECT * FROM posts WHERE title = ? AND author = ?
    List<Post> findByTitleAndAuthor(String title, String author);
}

Still no implementation. Spring Data reads the method name at startup, splits it into keywords, and generates the query.

KeywordBecomes
findBy… / readBy…SELECT … WHERE …
And / OrAND / OR
Containing / LikeLIKE %value%
GreaterThan / LessThan / Between> / < / BETWEEN
OrderBy…Asc / DescORDER BY … ASC/DESC
IgnoreCasecase-insensitive comparison
Top3 / FirstLIMIT
The field names must match your entity exactly findByAuthor works because the entity has a field called author. Write findByWriter and the app fails at startup with "No property 'writer' found for type 'Post'". That's a good failure — it's caught immediately, not in production. For anything too complex to express in a name, use @Query with real JPQL.

A Java detail that matters

Optional and orElseThrow()

Notice that findById() doesn't return a Post — it returns Optional<Post>. An Optional is a small box that either contains a value or is explicitly empty. Its purpose is to make "there might be nothing here" impossible to ignore.

❌ The old way — returning null

Post post = repo.findByIdOldStyle(5);

// Nothing forces you to check.
// Forget, and you get a
// NullPointerException later —
// far from the real cause.
post.getTitle();

✅ With Optional

Optional<Post> maybe = repo.findById(5L);

// You CANNOT call getTitle() directly.
// The compiler forces you to deal
// with the empty case first.
Post post = maybe.orElseThrow(
    () -> new PostNotFoundException(5L));
MethodBehaviour when empty
orElseThrow(() -> new X())Throws your exception. The pattern we use today.
orElse(defaultValue)Returns the fallback you supply
isPresent() / isEmpty()Returns true/false so you can branch
get()Throws NoSuchElementException — avoid; it defeats the point
The one line to remember 
Post post = postRepository.findById(id)
        .orElseThrow(() -> new PostNotFoundException(id));
Read it as: "get the post with this id — and if there isn't one, throw my exception." After this line, post is guaranteed to be non-null, so the rest of the method needs no defensive checks. This single line replaces every if (x == null) you wrote in Session 2.

Structure · 1 of 6

The full layered architecture

In Session 1 we introduced layers as a diagram. Today you'll actually build all of them. Each layer talks only to its neighbour — never skipping.

ControllerHandles HTTP. Reads the request, calls the service, sets the status code. Knows nothing about the database.
ServiceHolds business logic. Rules, validation, DTO↔entity conversion, transactions. Knows nothing about HTTP.
RepositoryTalks to the database. Nothing but data access.
Entity / DTOCarries the data. The entity mirrors the table; the DTO is what crosses the API boundary.

Today's project has one package per responsibility, all under the base package:

com.tcs.training.posts ← base package (main class here) ├── controller PostController — HTTP ├── service PostService (interface) │ PostServiceImpl — business logic ├── repository PostRepository — data access ├── entity Post — the table ├── dto PostDTO — the API shape └── exception PostNotFoundException GlobalExceptionHandler — error handling
Why the strict one-way flow? Because it makes change local. Swap H2 for MySQL → only the repository layer's configuration is affected. Add a rule like "titles must be unique" → only the service changes. Move from REST to a message queue → only the controller is replaced. A layer you can change without touching the others is a layer that doesn't cost you anything to maintain.

Structure · 2 of 6

Why not just return the entity?

It would be simpler. In Session 2 we returned Student objects directly and everything worked. So why add another class? Consider a realistic User entity:

@Entity
public class User {
    @Id private Long id;
    private String username;
    private String email;
    private String passwordHash;     // 🚨 a password hash!
    private String panNumber;        // 🚨 sensitive personal data
    private boolean isAdmin;         // 🚨 internal privilege flag
    private LocalDateTime lastLogin;
    private int failedLoginAttempts; // 🚨 internal security detail
}

Return that from a @GetMapping and Jackson serialises every field it can reach. Your public API has just published password hashes and PAN numbers to anyone who calls it.

ProblemWhat goes wrong
1 · Security leakEvery field is exposed, including ones you'd never intend to publish. The most serious of the five.
2 · Tight couplingYour API's shape becomes your table's shape. Rename a column and every client breaks.
3 · Over-fetchingA list page needs a title and an author; you send twenty fields per row.
4 · Wrong shapeClients often want combined or computed values (fullName, commentCount) that no single table holds.
5 · Lazy-loading errorsEntities with relationships can throw LazyInitializationException during serialisation, or recurse infinitely.
The principle Your database schema is an internal implementation detail. Your API is a public contract. Tying them together means you can never change one without breaking the other. Keeping them separate is what a DTO is for.

Structure · 3 of 6

What is a DTO?

A DTO — Data Transfer Object — is a simple class whose only job is to carry data across a boundary. It has fields, getters and setters, and no logic. It defines exactly the shape your API exposes: no more, no less.

Database posts table
→
Entity Post · all columns
→
Service converts picks what to expose
→
DTO PostDTO · public shape
→
Client receives JSON

Applied to that dangerous User:

❌ The entity — internal

class User {
    Long id;
    String username;
    String email;
    String passwordHash;      🚨
    String panNumber;         🚨
    boolean isAdmin;          🚨
    int failedLoginAttempts;  🚨
}

✅ The DTO — public

class UserDTO {
    Long id;
    String username;
    String email;

    // The sensitive fields simply
    // don't exist here, so they
    // cannot leak. Safe by
    // construction.
}
The safety property that makes this worth the extra class The DTO is safe by construction, not by discipline. Someone adds a creditCardNumber field to the entity next year — it does not appear in the API, because the DTO doesn't mention it. Compare the alternative (@JsonIgnore on each sensitive field), which relies on every future developer remembering. Allow-lists beat block-lists.

The boundary rule — commit this to memory Entities never leave the service layer. DTOs never enter the repository layer. The service is the only place that knows about both, and its job is to convert between them. If you find yourself importing an entity class into a controller, something has gone wrong.
Is this overkill for a small project? Honest answer: for a two-table hobby project, arguably yes — and plenty of small apps skip DTOs. But the habit costs little and the failure mode is severe (leaked credentials, or an API you can't evolve). Every professional codebase you join will use them, so learn the pattern here where the stakes are zero.

Structure · 5 of 6

Converting between entity and DTO

Something has to copy the fields across, and that something is the service layer — the only layer that legitimately knows about both types. Two small private methods do all the work:

// ---- Entity → DTO : going OUT to the client ----
private PostDTO toDTO(Post post) {
    PostDTO dto = new PostDTO();
    dto.setId(post.getId());
    dto.setTitle(post.getTitle());
    dto.setContent(post.getContent());
    dto.setAuthor(post.getAuthor());
    return dto;
}

// ---- DTO → Entity : coming IN from the client ----
private Post toEntity(PostDTO dto) {
    Post post = new Post();
    // Note: we deliberately do NOT copy the id.
    // The DATABASE assigns ids — never the client.
    post.setTitle(dto.getTitle());
    post.setContent(dto.getContent());
    post.setAuthor(dto.getAuthor());
    return post;
}

Every service method then follows the same three-step shape:

1

Receive a DTO

The controller hands you the public shape.

2

Convert & work with the entity

Save, load or modify through the repository.

3

Return a DTO

Convert the result back before it leaves the service.

Yes, this is repetitive — and there are tools for that Hand-written mapping is honest and completely transparent, which is why we do it today: you can see exactly what's happening. Real projects often use MapStruct (generates the mapping code at compile time — fast and type-safe) or ModelMapper (reflection-based, less code but slower). Learn the manual version first; then the tools are obviously just shortcuts for it.

Structure · 6 of 6

Why a service interface plus an implementation?

Today you'll write two files where Session 2 had one: PostService (an interface) and PostServiceImpl (the class that implements it). This is standard practice in Spring projects, and here's the reasoning:

The interface — the contract

public interface PostService {
    List<PostDTO> getAllPosts();
    PostDTO getPostById(Long id);
    PostDTO createPost(PostDTO dto);
    PostDTO updatePost(Long id, PostDTO dto);
    void deletePost(Long id);
}
// WHAT the service can do.
// No hint of HOW.

The implementation — the how

@Service
public class PostServiceImpl
        implements PostService {

    private final PostRepository repo;
    // ... the actual logic, using JPA
}
// @Service goes on the IMPL,
// because that's the real bean.

The controller then depends on the interface, never the implementation:

public PostController(PostService postService) {   // the interface
    this.postService = postService;                // Spring injects the Impl
}
BenefitWhy it matters
Swap implementationsWrite CachedPostServiceImpl later; the controller doesn't change a line.
TestablePass a fake implementation into the controller in a test — no database needed.
Readable contractThe interface is a one-screen summary of everything the service does.
Enables AOPSpring can wrap the bean in a proxy to add transactions, security or logging.
A fair counter-argument Some experienced developers argue that an interface with exactly one implementation is unnecessary ceremony, and they have a point. But because it's near-universal in the Spring codebases you'll join — and because it's what makes the "depend on abstractions" idea from Session 1 concrete — we use it here.

Errors · 2 of 4

Step 1 — a custom exception

First, an exception that means one specific thing. It's a tiny class:

package com.tcs.training.posts.exception;

// extends RuntimeException (unchecked), so we don't have to
// declare "throws" on every method in the call chain.
public class PostNotFoundException extends RuntimeException {

    public PostNotFoundException(Long id) {
        super("Post not found with id: " + id);   // the message clients will see
    }
}

Now the service can be blunt about failure, and it reads like a sentence:

@Override
public PostDTO getPostById(Long id) {
    Post post = postRepository.findById(id)
            .orElseThrow(() -> new PostNotFoundException(id));
    return toDTO(post);
}
Look at what disappeared No if. No null check. No ResponseEntity.notFound() in the controller. The method states the happy path, and the failure case is one clause. Compare Session 2, where every controller method carried an if (x == null) branch.
Why RuntimeException rather than Exception? A checked exception (extending Exception) must be declared with throws on every method that might propagate it, and caught or re-declared all the way up. That noise would spread through your whole codebase. An unchecked exception (extending RuntimeException) travels up silently until something handles it — which is exactly what we want, because the handler is a single global class.

Errors · 3 of 4

Step 2 — one global handler

Throwing the exception isn't enough by itself — something must turn it into a proper HTTP response. That's @RestControllerAdvice: one class that catches exceptions from every controller in the application.

package com.tcs.training.posts.exception;

import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

import java.time.LocalDateTime;
import java.util.HashMap;
import java.util.Map;

@RestControllerAdvice     // "watch EVERY controller"
public class GlobalExceptionHandler {

    @ExceptionHandler(PostNotFoundException.class)      // catch this type…
    public ResponseEntity<Map<String, Object>> handleNotFound(
            PostNotFoundException ex) {

        Map<String, Object> body = new HashMap<>();
        body.put("timestamp", LocalDateTime.now());
        body.put("status", 404);
        body.put("error", "Not Found");
        body.put("message", ex.getMessage());          // our friendly text

        return new ResponseEntity<>(body, HttpStatus.NOT_FOUND);   // → 404
    }

    @ExceptionHandler(Exception.class)                 // safety net for anything else
    public ResponseEntity<Map<String, Object>> handleEverythingElse(Exception ex) {
        Map<String, Object> body = new HashMap<>();
        body.put("timestamp", LocalDateTime.now());
        body.put("status", 500);
        body.put("message", "An unexpected error occurred");   // no stack trace leaked
        return new ResponseEntity<>(body, HttpStatus.INTERNAL_SERVER_ERROR);
    }
}
The flow, end to end Controller calls service → service throws PostNotFoundException → it travels up past the controller → Spring finds the matching @ExceptionHandler → that method builds a 404 with a clean message → the client receives it. The controller contains no error-handling code at all.

Errors · 4 of 4

Three ways to map exceptions to statuses

You'll see all three in real code. Know when each is appropriate:

ApproachHowScopeVerdict
1 · @ResponseStatus on the exception @ResponseStatus(HttpStatus.NOT_FOUND) above the exception class Wherever it's thrown Simplest. But you can't customise the response body.
2 · @ExceptionHandler in a controller A handler method inside the controller itself That one controller only Leads to duplication across controllers.
3 · @RestControllerAdvice A separate class holding all handlers Every controller ✅ Recommended. One place, full control of the body. What we use.

A realistic handler class maps several exception types:

ExceptionMaps toMeaning
PostNotFoundException404No such resource
MethodArgumentNotValidException400@Valid checks failed
DuplicateResourceException409Clashes with existing data
AccessDeniedException403Authenticated, but not permitted
Exception (catch-all)500Something unexpected — log it fully, expose nothing
Log the detail, return the summary In the catch-all handler, log the full stack trace on the server (so you can debug it) but return only a generic message to the client. Detailed errors are for your logs; opaque errors are for the outside world.

Guarding the input

Bean Validation — rejecting bad data early

Right now a client can POST a post with an empty title and we'd store it happily. Rather than writing if checks, declare the rules as annotations on the DTO and let Spring enforce them.

public class PostDTO {

    private Long id;

    @NotBlank(message = "Title is required")
    @Size(min = 3, max = 200, message = "Title must be 3–200 characters")
    private String title;

    @NotBlank(message = "Content is required")
    private String content;

    @NotBlank(message = "Author is required")
    private String author;
}

Then add @Valid in the controller, and Spring checks the rules before your method even runs:

@PostMapping
public ResponseEntity<PostDTO> create(@Valid @RequestBody PostDTO dto) {
    // If validation fails, this method is NEVER entered.
    // Spring throws MethodArgumentNotValidException instead.
    return ResponseEntity.status(HttpStatus.CREATED).body(postService.createPost(dto));
}
AnnotationRule
@NotNullMust not be null (but "" is allowed)
@NotBlankMust not be null, empty, or only whitespace — usually what you want for text
@Size(min=, max=)Length of a String or size of a collection
@EmailMust look like an email address
@Min / @MaxNumeric bounds
@Pattern(regexp=)Must match a regular expression
Two things to remember One: you need the spring-boot-starter-validation dependency, and the imports are jakarta.validation.constraints.*. Two: @Valid in the controller is what triggers the check — the annotations on the DTO do nothing on their own. Add a handler for MethodArgumentNotValidException in your global advice and you get clean 400 responses listing exactly which fields failed.

Data integrity

@Transactional — all or nothing

A transaction is a group of database operations that must all succeed or all be undone. The classic example is a bank transfer:

@Transactional
public void transfer(Long fromId, Long toId, BigDecimal amount) {
    Account from = accountRepo.findById(fromId).orElseThrow();
    Account to   = accountRepo.findById(toId).orElseThrow();

    from.setBalance(from.getBalance().subtract(amount));   // step 1
    to.setBalance(to.getBalance().add(amount));            // step 2

    accountRepo.save(from);
    accountRepo.save(to);
}
What happens if the app crashes between step 1 and step 2? Without @Transactional: the money has left the first account and never arrived in the second. It has simply vanished. With @Transactional: Spring rolls the whole thing back, and both balances return to how they were. Nobody loses money.
UsageEffect
@TransactionalCommit at the end; roll back automatically if a RuntimeException escapes.
@Transactional(readOnly = true)A hint for read-only methods. Lets the database and Hibernate optimise.
On the classApplies to every method in it.
Where to put it, and one gotcha Put it on service methods, not on controllers or repositories — the service is where a complete business operation lives. Spring Data already wraps each individual repository call in its own transaction, so single-call methods are fine without it. The gotcha: it works via a proxy, so calling one @Transactional method from another method in the same class bypasses it entirely. That surprises everyone once.

The monolith, and where it starts hurting

Everything we've built is a monolith: one application, one deployable unit, one database. And that is genuinely the right choice for most projects. The problems only appear at scale.

✅ Where a monolith wins

  • Simple to build, run and debug
  • One deployment, one thing to monitor
  • No network calls between components
  • Transactions across the whole app are easy
  • The right default for a small team

⚠️ Where it starts hurting

  • One bug can bring down everything
  • A one-line fix means redeploying the whole app
  • Can't scale one busy part independently
  • The whole codebase is locked to one language and framework version
  • 50 developers editing one codebase → constant conflicts
A concrete example of the scaling problem Imagine an e-commerce monolith where Search handles a thousand requests a second while Invoicing handles ten a day. They're in the same application, so to give Search more capacity you must run more copies of everything — including nine idle Invoicing modules per copy. You're paying for capacity you can't direct where it's needed.

Microservices — the alternative

A microservices architecture splits the application into several small, independent services, each owning one business capability and its own data, and each deployable on its own.

Monolith — one unit

  • One JAR containing everything
  • Users + Products + Orders + Payments
  • One shared database
  • Deploy all of it, or none of it
  • Scale all of it, or none of it
→

Microservices — many units

  • User Service  ·  own DB  ·  own deploy
  • Product Service  ·  own DB
  • Order Service  ·  own DB
  • Payment Service  ·  own DB
  • Scale and release each one separately
BenefitWhat it gives you
Independent deploymentFix Payments without touching, testing or redeploying Search.
Targeted scalingRun five copies of Search and one of Invoicing. Pay only for what's busy.
Fault isolationPayments failing shouldn't stop people browsing products.
Technology freedomEach service can use the language and database that suits it.
Team autonomySmall teams own a service end to end and release on their own schedule.
The honest trade-off — please remember this one Microservices don't remove complexity; they move it out of your code and into the spaces between your services. You inherit a new set of problems: network failures, service discovery, distributed transactions, tracing a request across five hops, and far more deployment machinery. Session 4 is entirely about the tools that manage those new problems. Start with a monolith; split it when the pain is real — not because microservices sound modern.

Looking ahead to Session 4 · 3 of 4

Horizontal vs vertical scaling

"Scaling" means handling more load. There are exactly two ways to do it, and the difference explains why statelessness kept coming up in Session 2.

⬆️ Vertical — a bigger machine

Add more CPU and RAM to the one server. 4 cores → 32 cores.

  • ✅ Simple — no code changes at all
  • ❌ There's always a physical ceiling
  • ❌ Cost rises steeply, not linearly
  • ❌ Usually needs downtime to resize
  • ❌ Still a single point of failure

➡️ Horizontal — more machines

Run more copies of the app behind a load balancer. 1 instance → 10 instances.

  • ✅ Effectively unlimited
  • ✅ Cost scales linearly
  • ✅ Add or remove copies with no downtime
  • ✅ No single point of failure
  • ⚠️ Requires the app to be stateless
Why that last point ties back to Session 2 Horizontal scaling only works if any copy can serve any request. That requires the app to hold no per-user state in memory — which is exactly the REST stateless constraint. It also explains today's session: with the data in a shared database rather than an in-memory list, ten copies of your app all see the same posts. You could not scale Session 2's app horizontally; you can scale today's.
In practice Teams do both: vertical scaling to a sensible machine size, then horizontal scaling from there. Cloud platforms make horizontal scaling nearly automatic — which is why "is my app stateless?" is such an important question.

Load balancing & high availability

If you're running ten copies of a service, something must decide which copy gets each request. That's a load balancer.

It does two jobs at once:

JobHow it works
Distribute loadSpread requests across instances so none is overwhelmed. The simplest strategy is round robin — take each in turn, then start again.
Provide high availabilityHealth checks: the balancer periodically asks each instance "are you alive?" (this is what /actuator/health is for). If one stops answering, it's removed from rotation and users never notice.
High availability, defined High availability means no single failure takes the system down. With one instance, one crash equals total outage. With three plus health checks, one crash means the other two absorb the traffic — degraded capacity, but the service stays up. Check yourself

Quick recap — tap each card to reveal

Q · JPA, Hibernate, Spring Data JPA — what's the difference? tap to reveal ▾
JPA is the specification (interfaces and annotations, no code). Hibernate is the implementation that actually generates SQL. Spring Data JPA sits on top and gives you repositories with no implementation of your own. One starter brings all three.
Q · What does extending JpaRepository<Post, Long> give you? tap to reveal ▾
Full CRUD for free — save, findAll, findById, deleteById, existsById, count, plus paging and sorting. Spring generates the implementation at startup; you write an empty interface.
Q · Why not return entities directly from a controller? tap to reveal ▾
It leaks every field (including password hashes), ties your API contract to your database schema, over-fetches, and can trigger lazy-loading errors. A DTO exposes only what's safe — and stays safe when someone adds a sensitive field later.
Q · What single line replaces every if (x == null) check? tap to reveal ▾
repository.findById(id).orElseThrow(() -> new PostNotFoundException(id)); — after it, the variable is guaranteed non-null, and the global handler turns the exception into a clean 404.
Q · What does @RestControllerAdvice do? tap to reveal ▾
Declares one class that catches exceptions from every controller in the app, and converts each into a proper HTTP response with the right status code and a clean body. Controllers end up with no error-handling code at all.
Q · Why is ddl-auto=create dangerous in production? tap to reveal ▾
It drops and recreates every table on each startup — deleting all production data. Use validate or none with Flyway or Liquibase migrations instead.
Q · Why must an app be stateless to scale horizontally? tap to reveal ▾
Because any of the ten copies must be able to serve any request. If a copy holds user data in its own memory, requests routed elsewhere would find it missing. Sharing a database instead of an in-memory list is exactly what fixed this today.
Q · What does @Transactional guarantee? tap to reveal ▾
That a group of database operations either all commit or all roll back. If a RuntimeException escapes the method, Spring undoes everything — so a half-finished bank transfer can't leave money in limbo.
