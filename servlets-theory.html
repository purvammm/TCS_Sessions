Part A · Web & HTTP foundations

What is a web application?

A web application is a program you use through a browser instead of installing it. Gmail, Amazon, your bank's site, the college portal — all web applications. They all follow one arrangement, the client–server model:

Client the browser — Chrome, Firefox, Edge
↔
Network the internet / your LAN
↔
Server the machine running your Java code

The client's job

  • Asks for something — "give me the product list"
  • Renders whatever HTML comes back
  • Knows nothing about your database or your Java classes

The server's job

  • Listens for requests, all day, forever
  • Runs logic — validate, calculate, query the DB
  • Replies with HTML (or JSON) the client can display
The mental shift to make today A console program is in charge: it decides when to read input and when to print. A web application is reactive — it sits still and waits, then wakes up when a request arrives, answers it, and goes back to sleep. You no longer write main(). You write methods that the server calls for you.

Why we need Java on the server at all

Static vs dynamic web pages

Before servlets make sense, you need to see the problem they solve. There are two kinds of thing a server can send back:

 Static pageDynamic page
What it isA .html file sitting on diskHTML generated at request time by a program
Who builds itA developer, once, by handYour Java code, freshly, on every request
ContentIdentical for every visitor, every timeDifferent per user, per query, per moment
ExampleAn "About Us" page"Your cart (3 items)", a search result, a bank balance
Needs a database?NoUsually yes
This is precisely why servlets exist A static file can't say "Welcome back, Priya — you have 3 items in your cart." It has no idea who Priya is. To produce that sentence you need code that runs on the server, at the moment of the request, that can look things up and build the HTML on the spot. In the Java world, that code is a servlet.
A useful analogy A static page is a printed poster — everyone who walks past sees the same thing. A dynamic page is a waiter — they ask who you are, go to the kitchen, and come back with your order. Today you're building the waiter.

The software that receives the request

What is a web server?

A web server is software that listens on a network port, accepts incoming HTTP requests, and sends back HTTP responses. It's the permanent receptionist of your application: always on, always listening.

ServerMade by / ecosystemTypically used for
Apache TomcatApache, JavaRunning Java servlets & JSP — this is ours today our server
NginxOpen source, CVery fast static files, reverse proxy, load balancing
IISMicrosoftASP.NET applications on Windows Server
LighttpdOpen source, CLightweight, low-memory environments
Apache HTTP ServerApache, CThe classic general-purpose web server ("httpd")
Why Tomcat, specifically? Nginx and IIS can serve files and forward requests, but they cannot run a Java class. Tomcat can — it contains a servlet container, the piece that knows how to load your compiled servlet, call its methods, and hand it the request. Tomcat is a web server that speaks Java. That's why every lab today runs on it.
Don't confuse the two "Apaches" Apache HTTP Server and Apache Tomcat are different products that happen to share a foundation's name. Tomcat is the Java one. When a job description says "experience with Tomcat," it means the Java servlet container.

A distinction interviewers love

Web server vs application server

These two terms get used loosely, and the boundary genuinely has blurred over the years. Here's the honest version:

 Web serverApplication server
Core jobServe content over HTTPHost and run full business applications
HandlesHTML, CSS, images, and (with a container) servletsServlets plus EJB, transactions, messaging, connection pooling
WeightLightHeavy — many more moving parts
ExamplesNginx, Apache HTTP Server, TomcatWildFly (JBoss), WebLogic, WebSphere, GlassFish
Where Tomcat sits — the nuance worth knowing Tomcat is usually called a web server with a servlet container (sometimes "web container"). It does servlets and JSP beautifully, but it doesn't implement the full Java EE stack — no EJB container, for instance. In practice that's fine: the overwhelming majority of modern Java web apps only ever need what Tomcat provides. Spring Boot ships an embedded Tomcat inside your JAR for exactly this reason.
Answer this crisply if asked "A web server handles HTTP and serves content. An application server adds enterprise services — transactions, EJB, messaging — on top. Tomcat is a web server plus a servlet container, which is all most applications need."

Reading an address properly

Anatomy of a URL

Every request starts with a URL. It looks like one blob of text, but it's really six labelled parts — and you'll be constructing these by hand all through the lab, so learn to see the seams:

1 · Protocolhttp://
2 · Server locationlocalhost
3 · Port (optional):8080
4 · Resource path/ServletBasics/product
5 · Query parameters?action=delete&p=3
6 · Fragment (optional)#results
PartWhat it meansThe detail that matters
ProtocolThe language to speak — http or httpshttps is the same protocol wrapped in encryption. Always https in production.
Server locationA domain name or an IP addresslocalhost means this machine — it resolves to 127.0.0.1. That's what you'll use all lab.
PortWhich program on that machineOptional because there are defaults: 80 for http, 443 for https. Tomcat defaults to 8080, so we must write it.
Resource pathWhat you're asking forFor us: /<project-name>/<url-pattern>. The first segment is the app, the second picks the servlet.

If a page 404s in the lab, re-read this line part by part; the mistake is almost always in the path.

The whole journey, end to end

What happens when you press Enter

This is the single most important diagram of the session. Every lab you build today is one lap around this loop:

1 · Browser you type a URL / click a link / submit a form
↓
2 · Web server (Tomcat) receives the HTTP request on port 8080
↓
3 · Servlet container matches the URL to your servlet, calls doGet / doPost
↓
4 · Your Java code servlet → service → DAO
↓
5 · JDBC driver translates your Java calls into database protocol
↓
6 · Database runs the SQL, returns a record set
↑
7 · Servlet builds HTML loops the rows, writes tags with PrintWriter
↑
8 · Browser renders it HTML text becomes a visible table
The insight that makes servlets click Notice step 7. Your servlet never sends a table — it sends a string of text that happens to be HTML. The browser is what turns <table><tr><td> into lines and boxes on screen. Your job is only to produce the right characters in the right order.

The rules of the conversation

HTTP — request in, response out

HTTP (HyperText Transfer Protocol) is the agreed format for those messages. Two properties define how it feels to program against:

🔁

1 · Strictly request–response

The client asks; the server answers; the exchange is over. The server cannot spontaneously push something to a browser — it can only reply to a request that arrived.

🧠

2 · Stateless

Each request is independent. The server remembers nothing from the previous one. Two requests from the same person look, by default, like two strangers.

Why "stateless" is a problem worth naming now You log in on one request. On the very next request — clicking a link — HTTP has already forgotten who you are. So how does any site keep you logged in? With extra machinery layered on top: cookies and sessions, where the server hands the browser an ID and the browser sends it back with every subsequent request. You'll see Set-Cookie: JSESSIONID=... two slides from now — that's Tomcat doing exactly this.
Scope note for today Our login servlet checks a hardcoded id and password and prints the result. It does not keep you logged in afterwards, because we haven't added sessions yet — and that's deliberate. Today: one request, one answer. Sessions come next.

Anatomy, part 1

Structure of an HTTP request

A request is just plain text in a fixed shape — four parts, always in this order. This is literally what travels down the wire when you submit the lab's login form:

GET /ServletBasics/login?action=login&id=123&pwd=Christi HTTP/1.1   <- 1. REQUEST LINE
Host: localhost:8080                            <- 2. HEADERS start
Accept: text/html,application/xhtml+xml,*/*
Accept-Encoding: gzip, deflate
Accept-Language: en-US,en;q=0.9
User-Agent: Mozilla/5.0 (Windows NT 10.0) Chrome/120.0
Content-Length: 0
                                                <- 3. ONE BLANK LINE (mandatory)
(body — empty for this GET request)            <- 4. BODY
PartWhat it carries
1 · Request lineThree things: the method (GET), the path + query string, and the HTTP version. Notice the parameters are sitting right here in the URL — that fact drives the whole GET-vs-POST discussion.
2 · Headerskey: value metadata. Host — which site (required in HTTP/1.1). Accept — formats I can read. Accept-Encoding — compressions I understand. Content-Length — how many bytes of body follow. User-Agent — which browser.
3 · Blank lineA single empty line marking "headers are finished, body begins." Not decoration — it's how the server knows where to stop parsing headers.
4 · BodyThe payload. Empty for GET. For POST, this is where the form data lives.
The takeaway There's nothing magical in a request — it's text you could type by hand. When you call request.getParameter("id") in the lab, you're asking Tomcat to pull id=123 out of the request line above and hand you the "123".

Anatomy, part 2

Structure of an HTTP response

The reply has the same four-part shape, with a status line instead of a request line. This is what your servlet produces:

HTTP/1.1 200 OK                                <- 1. STATUS LINE (version + code)
Content-Type: text/html;charset=UTF-8          <- 2. HEADERS start
Set-Cookie: JSESSIONID=8A1F3C9D; Path=/ServletBasics
Pragma: no-cache
Cache-Control: no-store, must-revalidate
Expires: Thu, 01 Jan 1970 00:00:00 GMT
Content-Length: 64
                                                <- 3. ONE BLANK LINE
<h3><font color="green">Login successful</font></h3>  <- 4. BODY
HeaderIts role
Content-TypeThe most important one for us. It tells the browser how to interpret the body. text/html → parse the tags and render. text/plain → show the characters literally. This is exactly what response.setContentType("text/html") sets — and forgetting it is the bug on slide 25.
Set-CookieAsks the browser to store a small value and send it back on later requests. JSESSIONID is how Tomcat recognises a returning visitor.
Pragma / Cache-ControlCaching instructions. no-cache / no-store mean "don't keep a copy" — important for pages showing live data or private information.
ExpiresContent expiry. A date in the past (like the 1970 one above) is the classic trick for "this is already stale, always re-fetch."
Content-LengthBody size in bytes, so the browser knows when it has received everything.
Where the body comes from in your code Everything you write with out.println(...) lands in part 4. Tomcat writes parts 1–3 for you automatically — which is a mercy, but also why a missing setContentType is invisible until the browser renders the wrong thing.

Reading the server's mood

HTTP status codes

The number in the status line is the server's one-word verdict. They're grouped by first digit, and knowing the groups means you can diagnose a problem before reading a single log line:

RangeMeaningOnes you will actually meet
1xxInformationalRare in day-to-day work. 100 Continue.
2xxSuccess200 OK — it worked. 201 Created — a new resource was made (you'll use this in REST).
3xxRedirection301 moved permanently · 302 Found — "look over there instead," what sendRedirect() sends.
4xxYou (the client) erred400 bad request · 401 not authenticated · 403 forbidden · 404 Not Found — wrong URL · 405 method not allowed.
5xxThe server erred500 Internal Server Error — your code threw an exception · 503 service unavailable.
The two you'll debug all lab — and how to tell them apart instantly 404 means Tomcat looked for your URL and found nothing — your address is wrong. Check the project name and the <url-pattern>. 500 means Tomcat found your servlet, ran it, and your code threw an exception — scroll the Eclipse console for the stack trace; the real error is there.
Remember the two groups by who's at fault 4xx = your fault (the client's). You asked for something wrong. 5xx = my fault (the server's). You asked correctly and I broke. Also worth knowing: 405 Method Not Allowed is what you get when a form POSTs to a servlet that only implements doGet — a very common beginner surprise, and slide 23 shows the fix.

The comparison that gets asked in every interview

GET vs POST — the full comparison

Both send data to the server. The difference is where the data rides, and everything else follows from that one fact:

AspectGETPOST
Data goes inThe URL — the query string of the request lineThe body of the request
Visible?Yes — in the address bar, browser history, server logs, and over anyone's shoulderNo — not shown in the address bar
Data volumeLimited — URLs are capped in practice (~2000 chars in older browsers)Effectively unlimited — fine for large forms and file uploads
Idempotent?Yes — repeating it changes nothingNo — repeating it may create a duplicate
Bookmarkable / shareable?Yes — the whole request is one URL you can save or sendNo — the body isn't part of the URL
Cached by browsers?Yes — which makes repeat views fastNo — every submit hits the server
Safe for passwords?NeverYes — with HTTPS; see the warning below
Servlet method calleddoGet(...)doPost(...)
Be precise about "POST is secure" — it's the most-repeated half-truth in web development POST only hides data from the address bar. The body still travels as plain text and anyone watching the network can read it. Only HTTPS makes data secure, by encrypting the whole exchange. Correct phrasing: "POST keeps data out of the URL; HTTPS keeps it out of an attacker's hands."

The tradeoff, in real terms

Idempotency, efficiency & when to use which

Idempotent is a fancy word for a simple test: if I do this twice, is the result the same as doing it once? Reading a product page twice = same result, so GET is idempotent. Submitting a payment twice = two charges, so POST is not.

Refresh a POST result

  • Browser asks: "Confirm form resubmission?"
  • Say yes → the registration/payment runs again
  • Duplicate rows, double charges
  • This is why that dialog exists — the browser knows POST isn't safe to repeat
vs

Refresh a GET result

  • Silently re-fetches — no prompt
  • Same page, no side effects
  • Can be cached, bookmarked, shared, pre-fetched
  • Safe to repeat any number of times
🔍

Use GET when you're reading

Browsing a catalogue, viewing a product, searching, filtering, paginating, our view-all-products link. You want these bookmarkable and cacheable — ?q=laptop&page=2 in the URL is a feature, not a leak.

✍️

Use POST when you're changing

Registration, login, placing an order, uploading a file, our insert-product form. Data is sensitive or large, and re-running it must not happen by accident.

The one-line rule to carry forward GET to read, POST to write. Efficiency-wise GET wins on repeat reads (cacheable, one tidy URL); POST wins on size and privacy. In today's lab we deliberately use both — links carry a GET for view and delete, forms POST for insert and update — so you feel the difference rather than just memorising the table.

Part B · Servlets

What is a servlet?

A servlet is an ordinary Java class that extends the capability of a web server — it lets the server answer a request with content your code generated, rather than a file from disk.

☕

It's just a Java class

No new language, no magic. You extends HttpServlet and override a method. Everything you know about Java still applies.

🚫

But it has no main()

You never run a servlet yourself. The server runs it, calling your methods when a matching request arrives.

📤

Its output is a response

Instead of System.out, you write to the response. The characters you write become the page the user sees.

// The smallest useful servlet — this is the whole shape of it
public class HelloServlet extends HttpServlet {

    protected void doGet(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {

        response.setContentType("text/html");
        PrintWriter out = response.getWriter();
        out.println("<h1>Hello from a servlet!</h1>");
    }
}
Read those two parameters carefully — they're the whole API HttpServletRequest request is everything the browser sent you — parameters, headers, the method used. HttpServletResponse response is the reply you're filling in — its content type, and the writer you print the body to. Request = incoming, response = outgoing. Master those two objects and you've mastered servlets.

The invisible partner doing half your work

The servlet container

The servlet container (also called the web container — inside Tomcat, it's the component named Catalina) is the part of the server that manages your servlets. Understanding what it does for you is what turns servlets from "magic" into "obvious":

The container handles……so you never write code for
Socket & port managementOpening port 8080, accepting TCP connections, reading bytes off the wire
Parsing HTTPSplitting that raw text into a request line, headers, and body
URL mappingDeciding which of your servlets should handle /product
Object creation (lifecycle)Loading your class, instantiating it, calling init(), and eventually destroy()
ThreadingServing 500 simultaneous users without you touching Thread
Building the responseWriting the status line, headers, and Content-Length around your body
This is a genuinely huge deal Without a container, "serve a web page in Java" means writing socket code, parsing HTTP by hand, and managing a thread pool — hundreds of lines before you display anything. The container does all of it. You write only the part that's unique to your application: the business logic.
Inversion of control — you've now met it twice You don't call the container; the container calls you. This "don't call us, we'll call you" arrangement is the same principle behind Spring's dependency injection. Servlets are where most Java developers meet it for the first time.

Where HttpServlet comes from

The Servlet API family tree

You'll write extends HttpServlet without thinking. Here's what's above it, because it explains why service() exists and where doGet gets called from:

interface Servlet the contract: init, service, destroy — protocol-neutral
↑
abstract class GenericServlet implements the boring parts; still protocol-neutral
↑
abstract class HttpServlet adds HTTP: service() inspects the method and dispatches to doGet/doPost/…
↑
class LoginServlet extends HttpServlet your class — override just the methods you need
So why do we override doGet and not service? Because HttpServlet.service() already contains the if-ladder: "was the request method GET? then call doGet. POST? call doPost." By overriding doGet you plug into that ladder at exactly the right rung. Override service() yourself and you'd break the dispatching. Rule: override doGet/doPost, leave service alone.
⚠ Read this before you write a single import — javax vs jakarta The package name changed when Java EE became Jakarta EE, and mismatching it is the #1 reason a servlet won't compile or 404s for people following older tutorials:
  • Tomcat 9 and earlier → import javax.servlet.*; — this is what our lab code uses.
  • Tomcat 10 and later → import jakarta.servlet.*; — identical class names, different package.
Check your Tomcat version first. If you're on 10+, change every javax.servlet to jakarta.servlet — nothing else in the code changes.

Keep this slide in mind for the whole lab

The servlet lifecycle

A servlet passes through three phases, and the container drives every one. The middle phase is the one that repeats:

1
init() — once, on the first request ever

The container loads the class, creates one single instance, and calls init(). Used for one-time setup — reading config, opening a connection pool. You usually don't override it. Called once in the servlet's entire life, not once per request.

2
service() → doGet() / doPost() — once per request

For every request, the container calls service(), which checks the HTTP method and dispatches to your doGet or doPost. This is where all your code lives. A thousand requests = a thousand doGet calls — on the same object.

3
destroy() — once, at shutdown

Called when Tomcat stops or the app is undeployed/redeployed. Your chance to release resources. Then the object is garbage collected.

Loaded class found
→
init() once
→
service() → doGet/doPost ↻ every request
→
destroy() once
The count that matters: 1 – many – 1 init() once. doGet() many times. destroy() once. If you remember one thing about lifecycle, remember those three numbers — the next slide shows why they have real consequences for your code.

The consequence beginners get bitten by

One instance, many threads

Here's the part that surprises people: the container creates exactly one object of your servlet class, no matter how many users arrive. Concurrency is handled by giving each request its own thread — all running through the same object.

User A thread 1
User B thread 2
User C thread 3
→
ONE ProductServlet object shared by all three

✗ Dangerous — shared mutable field

public class BadServlet extends HttpServlet {

    // ONE copy shared by every user!
    private String userName;

    protected void doGet(...) {
        userName = request.getParameter("name");
        // User B can overwrite this
        // between these two lines...
        out.println("Hello " + userName);
        // ...so A may greet B's name.
    }
}

✓ Safe — local variable

public class GoodServlet extends HttpServlet {

    // no request state as a field

    protected void doGet(...) {
        // local = one per thread,
        // living on that thread's stack
        String userName =
            request.getParameter("name");

        out.println("Hello " + userName);
        // always the right name
    }
}
The rule that keeps you safe Never store per-request data in an instance field. Keep it in local variables inside doGet/doPost — locals are per-thread and therefore automatically safe. Fields are acceptable only for things that are the same for everybody and never change, like our private ProductService service = new ProductService(); — that's a stateless helper, shared safely.

How the browser reaches your class

Browser-to-servlet: the contact model

The browser knows nothing about Java class names. It only sends a URL. Something must connect /login to com.tcs.web.LoginServlet — that connection is called a URL mapping, and there are two ways to declare it:

Option 1 · web.xml (what we use today)

<servlet>
  <servlet-name>LoginServlet</servlet-name>
  <servlet-class>
      com.tcs.web.LoginServlet
  </servlet-class>
</servlet>

<servlet-mapping>
  <servlet-name>LoginServlet</servlet-name>
  <url-pattern>/login</url-pattern>
</servlet-mapping>

Two blocks joined by the same <servlet-name>: the first names the class, the second names the URL. All mappings visible in one file — which is exactly why we start here.

Option 2 · Annotation (the modern way)

@WebServlet("/login")
public class LoginServlet
        extends HttpServlet {

    protected void doGet(...) {
        ...
    }
}

One line, right above the class — no XML at all. Servlet 3.0+ (Tomcat 7+). Shorter and harder to get out of sync, but the mapping is scattered across your source files instead of listed in one place.

Putting the URL together http://localhost:8080/ServletBasics/login = server  +  context path (your project name)  +  url-pattern. Get either of the last two wrong and you get a 404. The url-pattern must start with a /.
Why we teach web.xml first Because it makes the wiring visible. You can see, in one file, that a URL is deliberately bound to a class — nothing is hidden. Once that clicks, @WebServlet stops looking like magic and starts looking like a shortcut. It's the same reason we taught JDBC before Spring Data.

Your first real method

doGet, line by line

Let's dissect the method you'll write in Lab 2. Every line has a job:

protected void doGet(HttpServletRequest request,
                     HttpServletResponse response)
        throws ServletException, IOException {          <- 1

    response.setContentType("text/html");               <- 2  BEFORE getWriter()
    PrintWriter out = response.getWriter();             <- 3

    String action = request.getParameter("action");     <- 4

    if ("login".equals(action)) {                       <- 5  null-safe order
        out.println("<h3>Logging you in...</h3>");     <- 6
    }
}
#What it does & why
1protected because we're overriding HttpServlet.doGet. The two exceptions are declared by the parent — you must keep them (or narrow them), so just leave the signature as the IDE generates it.
2Tells the browser the body is HTML. Must come before getWriter() — slide 25 explains what happens if you get this wrong or forget it.
3Gets the pipe to the browser. PrintWriter is from java.io — Eclipse's Ctrl+Shift+O will add the import.
4Reads one parameter out of the request. Returns a String, or null if that parameter wasn't sent at all.
5Note the order: "login".equals(action), not action.equals("login"). If action is null the second form throws NullPointerException → a 500 page. Constant-first is a habit worth building today.
6Writes the response body. This text becomes part 4 of the HTTP response from slide 11.
GET vs POST must match your form, or you get a 405 doGet only answers GET requests. If your form says method="post", Tomcat looks for doPost, doesn't find it, and returns 405 Method Not Allowed. Fix it either way: change the form to method="get", or add a doPost that simply forwards — protected void doPost(req, res) { doGet(req, res); }. That one-liner is a very common, very practical pattern, and we use it in the lab.

Two outputs, two audiences

PrintWriter vs System.out

Both print. They print to completely different places, and mixing them up is the most common "my page is blank" moment for beginners:

✗ System.out.println() — goes to the console

System.out.println("<h3>Welcome</h3>");

// Appears in: the Eclipse console
// (Tomcat's log)
// The user sees: NOTHING.
// The browser page is blank.

Not useless — this is your debugging channel. Print here to check whether a method was reached or what a parsed value was.

✓ out.println() — goes to the browser

PrintWriter out = response.getWriter();
out.println("<h3>Welcome</h3>");

// Appears in: the HTTP response body
// The user sees: Welcome
// rendered as a heading.

This is your user-facing channel — the actual page. Everything the visitor should see goes through here.

One sentence to keep them straight System.out is for you. out (the PrintWriter) is for the user. If a page renders empty, your first check is whether you printed to the wrong one.
Where does the console even live in a web app? Tomcat runs inside Eclipse during development, so System.out lands in Eclipse's Console view. On a real server it goes to a log file such as catalina.out. Same stream, different destination — which is exactly why production code logs through a logging framework instead of System.out.

The bug every single person hits once

setContentType("text/html")

You wrote perfect HTML. The page shows the tags as literal text. Nothing is broken in your Java — you just forgot to tell the browser what kind of content it's receiving.

✗ Without setContentType

PrintWriter out = response.getWriter();
out.println("<h3>Hi</h3>");

Browser shows, literally:

<h3>Hi</h3>

Treated as plain text. Tags are characters, not instructions.

→

✓ With setContentType

response.setContentType("text/html");
PrintWriter out = response.getWriter();
out.println("<h3>Hi</h3>");

Browser shows:

Hi

Parsed as HTML. A real heading.

Order matters — and this one fails silently setContentType() must be called before getWriter(). Call it after and it is ignored — no exception, no warning, just the wrong rendering. Headers are committed when the writer is obtained; you cannot change them retroactively. 
response.setContentType("text/html");        // 1. FIRST — always
PrintWriter out = response.getWriter();     // 2. THEN get the writer
Other content types you'll meet text/html — a web page (today)  ·  text/plain — raw text  ·  application/json — JSON, what a REST API returns  ·  application/pdf, image/png — binary downloads. When you write @RestController in Spring Boot, it sets application/json for you — same header, chosen automatically.

Getting the user's input into Java

Reading form data — request.getParameter()

The bridge from an HTML form to your Java variables is one method, and it works off the name attribute — not the label, not the id:

The HTML you write

<form action="login" method="get">

  <input type="text"
         name="id" />

  <input type="password"
         name="pwd" />

  <input type="submit"
         name="action"
         value="login" />
</form>

The Java that reads it

String id =
    request.getParameter("id");

String pwd =
    request.getParameter("pwd");

String action =
    request.getParameter("action");

// The String you pass MUST match
// the name="" attribute exactly —
// including capitalisation.
It returns null, and null is not an error If the parameter wasn't sent, getParameter returns null — no exception. If the field was submitted but left empty, you get an empty string "", not null. Two different cases, and both will crash you if you call a method on the result blindly. Guard with if (x != null && !x.trim().isEmpty()).
The submit-button trick — worth understanding, since we use it in Lab 2 A submit button with name="action" value="login" sends action=login along with the form. That's how one servlet can tell which button was pressed. It works, and it's what many tutorials show — but a hidden field (<input type="hidden" name="action" value="insert">) is clearer, because the value the server reads is then independent of the button's visible label. We use the button trick in Part 1 and hidden fields in Part 3, deliberately, so you've seen both.
Two relatives of getParameter request.getParameterValues("hobbies") returns a String[] — use it for checkbox groups and multi-selects, where one name has several values. request.getParameterNames() returns every parameter name that arrived, which is a handy debugging tool when a value is mysteriously null.

A small fact with big consequences

Form data always arrives as a String

HTTP is a text protocol. There are no ints, doubles, or booleans on the wire — only characters. So getParameter() always returns a String, even for a field you think of as a number. Converting is your job.

// The request said:  id=123&price=55000.50&quantity=10

String idText = request.getParameter("id");          // "123"    — a String!

int    id       = Integer.parseInt(idText);                            // 123
double price    = Double.parseDouble(request.getParameter("price"));    // 55000.50
int    quantity = Integer.parseInt(request.getParameter("quantity"));   // 10
Both failure modes produce a 500 page — handle them
  • User typed "abc" in a number box → NumberFormatException
  • Field left blank → parseInt("") → NumberFormatException
  • Parameter missing entirely → parseInt(null) → NumberFormatException
Unhandled, each one shows the user a raw 500 Internal Server Error with a stack trace. Never acceptable in real software.
// The defensive version — this is what we write in the lab
try {
    int id = Integer.parseInt(request.getParameter("id"));
    double price = Double.parseDouble(request.getParameter("price"));
    // ... use them ...
} catch (NumberFormatException e) {
    out.println("<h3><font color='red'>Please enter valid numbers.</font></h3>");
}
The habit to build Every single value from a browser is untrusted text. Parse it, validate it, and be ready for it to be garbage — because sooner or later someone will type letters into your price box. (Later, Spring Boot will do this conversion and validation for you with @RequestParam int id and @Valid — but it's doing exactly what you're about to write by hand.)

Part C · MVC architecture

Model–View–Controller

Everything so far has been one servlet doing everything. That's fine for a login check and disastrous for a real application. MVC is the standard answer: split the code by responsibility, so each class has exactly one reason to change.

🗃️

Model — the data

What the application is about: a Product, an Employee. Plus the code that stores and fetches it. Knows nothing about the web.

🖥️

View — what the user sees

The presentation. Today it's HTML built by PrintWriter; later it'll be JSP or a template. Contains no business rules.

🎛️

Controller — the traffic cop

Receives the request, decides what should happen, calls the model, picks the view. Coordinates; doesn't do the work itself.

Browser
→
Controller servlet
→
Model service + DAO + bean
→
Database
Why bother, in one concrete sentence When the boss says "change the price column to show two decimals," you want to touch one place — not hunt through SQL, validation, and HTML tangled in a single 400-line method. Separation of concerns isn't neatness; it's the ability to change one thing safely.

The exact structure we build in the lab — keep this slide handy

The five packages

MVC in the abstract becomes five concrete packages. Every file you create today belongs to exactly one of these, and each layer talks only to the next one down:

PackageRoleWhat goes in it — and what must never
webView / Web layer The servlets — where client requests land. Reads parameters, calls the service, writes HTML. No SQL here, ever.
serviceController / Service layer Business logic and validation. "Is the price negative? Then refuse." Calls the DAO. Knows nothing about HTTP or SQL.
daoData Access Object All SQL lives here — and only here. INSERT, SELECT, UPDATE, DELETE via PreparedStatement. No HTML, no validation.
beanThe Model objects POJOs — private fields, getters/setters, constructors. Our Product. Pure data carriers; no logic at all.
helperInfrastructure Database connection management — one place that opens and closes connections. The only class that knows the JDBC URL.
web ProductServlet
→
service ProductService
→
dao ProductDao
→
helper DBHelper
→
Database
Where does bean sit in that chain? Everywhere — it's the currency, not a step. A Product object is what the layers hand to each other: the servlet builds one from form data, the service validates it, the DAO writes it to the database, and a DAO SELECT returns a List<Product> back up the chain. That's why it's in its own package that everyone imports.

The payoff, made concrete

Why the layers are worth the extra files

Five packages for a four-column table feels like overkill — a fair objection. Here's what you actually buy, in situations you will genuinely face:

The change requestAll-in-one servletLayered (MVC)
"Switch from Derby to MySQL"Hunt through every servlet for connection codeEdit DBHelper. One file.
"Reject negative prices"Add the same if in every place a price is written — and miss oneAdd it once in ProductService; every path is covered
"Also expose this as a JSON API"Copy-paste the logic and edit the copy — now two versions to maintainNew servlet, same service. Zero logic duplicated
"Write unit tests"Nearly impossible — logic needs a running server to executeTest ProductService as a plain Java class
"Redesign the page"Risk breaking SQL while editing HTML — they're in the same methodTouch only the web layer. Data code untouched
The honest caveat For a genuinely tiny app, layering is extra ceremony — and you should know that rather than treat it as gospel. But applications don't stay tiny, and retrofitting structure into tangled code is far more expensive than starting with it. The habit is what you're learning today, not the file count.
You've seen this shape before — and you'll see it again JDBC's DAO pattern (Tester → DAO → DBConnector) was the same idea with three layers. Spring Boot's @Controller → @Service → @Repository is the same idea with annotations. Learn the shape once and every Java framework afterwards looks familiar.

The one table behind the whole CRUD app

Creating the product table

Open a SQL Scrapbook (right-click the connection → Open SQL Scrapbook), pick your connection in the toolbar dropdown, and run these. Execute statements one at a time with Ctrl + Alt + X:

CREATE TABLE product (
    id       INT PRIMARY KEY,      -- unique identifier, never duplicated
    name     VARCHAR(50),          -- text, max 50 characters
    price    DOUBLE,               -- decimal number
    quantity INT                   -- whole number in stock
);

INSERT INTO product VALUES (1, 'Laptop',   55000.00, 10);
INSERT INTO product VALUES (2, 'Mouse',      750.50, 100);
INSERT INTO product VALUES (3, 'Keyboard',  1200.00, 45);
INSERT INTO product VALUES (4, 'Monitor',   9500.00, 20);

SELECT * FROM product;    -- always verify: you should see 4 rows
🔑

Why id is the primary key

It guarantees uniqueness, so WHERE id = 3 can only ever match one row. That's what makes update and delete precise instead of accidentally hitting many rows.

💾

Why we seed sample rows

So view has something to show and update/delete have something to work on. Otherwise your first test tells you nothing.

📄

Save the scrapbook

Save it as product-setup.sql. When you break your data — and you will while testing delete — you can re-seed in seconds.

Two Derby quirks worth knowing now 1. Derby folds unquoted identifiers to UPPERCASE, so the table appears as PRODUCT in the explorer. Your SQL can still say product — it's the same table. 2. Strings use single quotes ('Laptop'). Double quotes mean identifier in SQL, so "Laptop" would be read as a column name and error out.

The setup mistake that costs people an hour

The Derby JAR goes in two places

You already added derby.jar to the driver definition and the connection worked. So why does your servlet still fail? Because those were two different programs.

1 · The JAR in the driver definition

  • Used by Eclipse itself — the Data Source Explorer and SQL Scrapbook
  • Lets you browse tables and run queries by hand
  • An IDE tool convenience, nothing more
  • Your application cannot see it

2 · The JAR in WEB-INF/lib/

  • Used by your web app running on Tomcat
  • What makes DriverManager.getConnection() work at runtime
  • Gets packaged into the .war and deployed with your code
  • Mandatory for actual JDBC calls
The symptom, so you recognise it instantly The Data Source Explorer works perfectly — you can see your rows — but the servlet throws java.sql.SQLException: No suitable driver found for jdbc:derby:... and the page shows a 500. Every time you see "No suitable driver," the answer is: the JAR isn't in WEB-INF/lib/.
Why WEB-INF/lib/ specifically? The servlet spec says a web app's classloader automatically picks up every JAR in WEB-INF/lib/. Drop the file in that folder and it's on your classpath — no build-path configuration needed. This is also why WEB-INF is unreachable from the browser: nobody should be able to download your dependencies.

Part E · The CRUD design pattern

One servlet, four actions

CRUD is four operations. You could write four servlets with four mappings — or one servlet that reads an action parameter and branches. We do the latter, because it keeps all product-related handling in one readable place:

String action = request.getParameter("action");
// treat "no action given" as a sensible default instead of crashing
if (action == null) {
    action = "view";
}

if (action.equals("view")) {
    displayAllProducts(out);                  // READ

} else if (action.equals("insert")) {
    // read id, name, price, quantity -> service.addProduct(p)   // CREATE

} else if (action.equals("update")) {
    // read id, price -> service.updateProduct(id, price)          // UPDATE

} else if (action.equals("delete")) {
    // read p -> service.deleteProduct(id)                        // DELETE

} else {
    out.println("<h3><font color='red'>Unknown action</font></h3>");
}
ApproachTrade-off
One servlet + action+ One mapping, one file, shared helper methods, easy to see all behaviour at once.  − Grows long; the if-ladder can sprawl as features are added.
Four servlets+ Each class is tiny and single-purpose.  − Four mappings to maintain, and shared code needs a common parent or utility class.
Where this pattern leads That if-ladder is a hand-written front controller — and it's exactly what Spring MVC's DispatcherServlet does industrially. When you later write @GetMapping("/products") and @PostMapping("/products"), Spring is running a far more sophisticated version of the ladder you're about to write. Write it by hand once and annotations stop being mysterious.

Two ways to send that action

Passing parameters: links vs forms

Both put parameters in a request. Which one you reach for depends on whether the user needs to type anything:

🔗 A link — no input needed

<a href="product?action=view">
    View all products
</a>

<!-- delete row 3: two params,
     joined with &amp; -->
<a href="product?action=delete&amp;p=3">
    Delete
</a>

Always a GET; parameters sit in the query string. Perfect when the values are already known — the row's own id. This is how we build the per-row Delete link.

📝 A form — the user types

<form action="product" method="post">
  <input type="hidden"
         name="action" value="insert" />

  <input type="text" name="id" />
  <input type="text" name="name" />
  <input type="text" name="price" />
  <input type="text" name="quantity" />

  <input type="submit" value="Add" />
</form>

GET or POST, your choice. Necessary when values come from the user. The hidden field carries the action invisibly. This is our insert and update path.

In HTML, write &amp; to separate parameters Inside an href the correct separator is the entity &amp;, not a bare &. Browsers forgive the bare version, so it usually works — but &amp; is valid HTML and won't surprise you when a parameter name collides with an entity name (a real bug when a parameter is called something like p followed by amp). Note that Java string-concatenating a URL is where beginners lose the & entirely — check your quotes carefully.
The choice, summarised Nothing to type → link (GET). Something to type → form (POST for writes). Which lines up exactly with the GET-to-read / POST-to-write rule from slide 14 — the design isn't arbitrary, it follows from HTTP's own semantics.

How the layers report success

The boolean-return pattern

Your DAO ran an UPDATE. Did it change anything? Maybe the id didn't exist. The servlet needs to know so it can show the right message — so every write method returns a boolean:

// ===== DAO: turn "rows affected" into a plain yes/no =====
public boolean updateProduct(int id, double price) {
    String sql = "UPDATE product SET price = ? WHERE id = ?";
    // ... prepare and bind ...
    int rows = ps.executeUpdate();
    return rows > 0;        // 0 rows matched -> false. 1+ -> true.
}

// ===== SERVLET: branch on it and tell the user the truth =====
if (service.updateProduct(id, price)) {
    out.println("<h3><font color='green'>Product updated successfully.</font></h3>");
} else {
    out.println("<h3><font color='red'>Updation failed — no product with id " + id + ".</font></h3>");
}
📊

It comes from executeUpdate()

That method returns the number of rows affected. rows > 0 converts a count into the yes/no the UI actually needs.

🎯

It distinguishes two silent cases

"Ran fine but matched nothing" vs "found it and changed it." Without this check both look like success — and you'd lie to the user.

🧱

It keeps layers separate

The DAO reports a fact; the servlet decides the wording and the colour. Presentation stays out of the data layer.

Honest limitation — worth naming A boolean says that it failed, not why. "Id not found," "duplicate key," and "database down" all come back as false. That's an acceptable simplification while learning, and the right next step is custom exceptions carrying a reason — exactly what you'll do with @ControllerAdvice in Spring Boot. For today, log the real SQLException in the DAO's catch block so the detail isn't lost.

A small refactor with a big lesson

Extracting the repeated display code

After every operation you want to show the updated table. Write that loop four times and you have four copies to fix when the table design changes. Extract it once.

✗ Before — duplicated four times

if (action.equals("view")) {
    // 15 lines of table loop
} else if (action.equals("insert")) {
    // ... insert ...
    // the SAME 15 lines again
} else if (action.equals("update")) {
    // ... update ...
    // the SAME 15 lines again
} else if (action.equals("delete")) {
    // ... delete ...
    // the SAME 15 lines AGAIN
}

60 lines. One design change = four edits — and you'll forget one.

→

✓ After — one method, called four times

if (action.equals("view")) {
    displayAllProducts(out);
} else if (action.equals("insert")) {
    // ... insert ...
    displayAllProducts(out);
} else if (action.equals("update")) {
    // ... update ...
    displayAllProducts(out);
} else if (action.equals("delete")) {
    // ... delete ...
    displayAllProducts(out);
}

15 lines, in one place. One design change = one edit.

DRY — Don't Repeat Yourself The trigger to watch for: the moment you copy-paste code for the second time, extract it into a method instead. Not before (premature abstraction is its own problem) — but definitely then. In the lab we deliberately write the duplication first and then refactor, because feeling the pain is what makes the lesson stick.
Signature note private void displayAllProducts(PrintWriter out) — pass the writer in as a parameter rather than storing it in a field. Remember slide 19: an instance field would be shared across all users' threads. A parameter is per-call and therefore safe.

Honest context — this is not how you'll write web apps in 2026

Servlets → JSP → Spring MVC

Building HTML with out.println() is genuinely unpleasant, and you should know that's not a limitation of your skill — it's why the industry moved on. Here's the honest lineage:

TechnologyThe ideaWhy the next thing replaced it
Servlet
today		Java code that writes HTML stringsHTML inside Java is painful to write, impossible for a designer to edit, and you can't see the page shape.
JSPInverts it: an HTML page with Java sprinkled inMuch better for layout — but tempting to bury business logic in the page, which recreates the tangle.

So why learn servlets at all? Because every one of those layers is still a servlet underneath. Spring's DispatcherServlet is a servlet. @GetMapping is a URL mapping. @RequestParam is getParameter() with automatic type conversion. ResponseEntity is HttpServletResponse with a nicer API. Today you learn the machine; later you get the power tools — and you'll know what they're doing.
The direct translation table, for when you get to Spring Boot extends HttpServlet → @Controller  ·  doGet → @GetMapping  ·  doPost → @PostMapping  ·  getParameter("id") → @RequestParam int id  ·  web.xml mapping → the annotation's path  ·  our ProductService → @Service  ·  our ProductDao → @Repository / JpaRepository.

The ten mistakes you're most likely to make

Every one of these has cost a student an afternoon. Read them now and you'll recognise the symptom instead of guessing:

  • Plain Java Project instead of Dynamic Web Project → HttpServlet won't resolve, no "Run on Server". Recreate the project.
  • Wrong servlet package — javax.servlet on Tomcat 10+, or jakarta.servlet on Tomcat 9. Match your Tomcat version.
  • Forgot setContentType("text/html"), or called it after getWriter() → tags render as literal text.
  • Printed with System.out instead of out → blank page, output hiding in the console.
  • Form method="post" but only doGet exists → 405 Method Not Allowed. Add doPost delegating to doGet.
  • name attribute doesn't match getParameter("...") → silent null, then a confusing NumberFormatException.
  • action.equals("login") with a null action → NullPointerException → 500. Write "login".equals(action).
  • derby.jar missing from WEB-INF/lib/ → "No suitable driver found," even though the Data Source Explorer works fine.
  • Derby database still open in Eclipse while Tomcat starts → "another instance may have already booted." Embedded Derby allows one JVM at a time — disconnect in the explorer first.
  • Edited web.xml without restarting Tomcat → still a 404. The descriptor is read at startup; restart the server.
The two-question debugging routine Got a 404? Your URL is wrong — check project name, then <url-pattern>, then restart Tomcat. Got a 500? Your code threw — go to the Eclipse console and read the first line of the stack trace, not the last. Those two questions cover the large majority of what goes wrong.

Your closing checklist

Session recap

Nine things you should now be able to explain to someone else — the real test of understanding:

  • The client–server model and why dynamic pages need code running on the server.
  • URL anatomy — protocol, host, port, path, query parameters, fragment — and that the fragment never reaches the server.
  • HTTP request & response structure — request/status line, headers, blank line, body — plus the status-code families and that 4xx is the client's fault, 5xx the server's.
  • GET vs POST — URL vs body, visibility, size, idempotency, bookmarkability — and that only HTTPS provides real security.
  • What a servlet is, what the container does for you, and the lifecycle: init once, doGet many times, destroy once.
  • One instance, many threads — so per-request data belongs in local variables, never instance fields.
  • The mechanics — web.xml mapping, setContentType before getWriter, PrintWriter vs System.out, getParameter returning Strings you must parse.
  • MVC and the five packages — web, service, dao, bean, helper — and what must never appear in each.
  • The CRUD patterns — routing on action, links vs forms, boolean returns, and extracting repeated display code.
One sentence to carry forward A servlet is just a Java class whose methods are called by a server instead of by main() — and every Java web framework you will ever use is built on top of exactly that.
